1. サービス概要

AWS Secrets Managerは、アプリケーションで使う機密情報(DBのパスワードやAPIキーなど)を安全に保管・取得・ローテーションするサービスです。

2. 主な機能・特徴

  • 自動暗号化:保存時はKMS、転送時はHTTPSで暗号化される。
  • レプリケーション:設定したリージョンに暗号化されたシークレットを複製し、別リージョンのアプリからも使える。ローテーションは元のシークレットで行えば、複製先にも反映される。
  • ローテーション:パスワードを定期的に自動変更できる。

ローテーションの仕組み

  • マネージドローテーション:Amazon AuroraやRDSのマスターユーザーなど、サービスが管理する認証情報で使う。Lambda関数は不要で、最短4時間おきに実行できる。
  • Lambda関数によるローテーション:それ以外のシークレットで使う。AWSが用意したローテーション関数テンプレートを使うか、独自のLambda関数を作成する。

Lambda関数によるローテーションは、createSecret・setSecret・testSecret・finishSecret の4つのステップで進みます。

アクセス制御と共有

シークレットにはリソースポリシーを付けて、複数のユーザーやロールに許可を与えられます。別のAWSアカウントから使わせる場合は、リソースポリシーに加えて、呼び出し側のIAMポリシーでも許可が必要です。

暗号化に使うKMSキーも共有が必要です。AWS管理キー(aws/secretsmanager)は別アカウントからは使えないため、カスタマー管理キーを作成し、キーポリシーで相手アカウントに使用を許可します。許可の判断の仕組みは用語ページ「IAMポリシーと評価ロジック」を参照してください。

暗号化の仕組み

Secrets Managerはエンベロープ暗号化で値を保護します。KMSキーで256ビットのAESデータキーを生成・暗号化し、そのデータキーでシークレットの値を暗号化します。暗号化されたデータキーはシークレットのメタデータとして保存されます。暗号化の基本は用語ページ「保存時の暗号化と転送時の暗号化」を参照してください。

3. ユースケース

アプリのDB接続情報の管理

  1. 事前準備:アプリがDBに接続するための認証情報を、1つのシークレットとしてSecrets Managerに保存する(KMSで暗号化される)
    {"username": "app_user", "password": "xxxxx", "host": "db.example.com"}
  2. アプリのコードには、パスワードではなくシークレットの名前(またはARN)だけを設定しておく
  3. アプリが起動時などに GetSecretValue APIでシークレットを取得する(IAMロールに secretsmanager:GetSecretValue とKMSの復号権限が必要)
  4. 取得したユーザー名・パスワードでDBに接続する
  5. ローテーションでパスワードが変わっても、アプリは次に取得したときに新しい値を使うため、コードの変更や再デプロイは不要

「アプリの会員(エンドユーザー)のID/パスワードもSecrets Managerに保存すればよいのでは?」→ 非推奨。Secrets Managerは、DBのパスワードやAPIキーのようなシステムが使う少数の機密情報を管理するためのサービスで、シークレット1件ごとに料金がかかります。会員のパスワードは、DBにハッシュ化して保存するか、Amazon Cognitoなどの認証サービスで管理します。

4. 料金の考え方

シークレット1件ごとの月額料金と、APIの呼び出し回数で課金されます。公式料金ページの例では、1シークレットあたり月額 $0.40、API呼び出し1万回あたり $0.05です(最新の料金は料金ページで確認してください)。別リージョンに複製したシークレットは、別のシークレットとして課金されます。

Parameter Storeは標準パラメータであれば追加料金がかからないため、ローテーションが不要な設定値はParameter Storeが向いています。

5. 関連サービス

  • AWS KMS:シークレットの暗号化
  • Amazon RDS/Amazon Aurora:認証情報の自動ローテーション
  • AWS Systems Manager:Parameter Store
  • AWS Lambda:ローテーション処理の実行
  • Secrets Manager・Parameter Store・AppConfig・KMSの使い分け → 機密情報・設定値の保存先の選び方。

6. 試験・実務でのポイント

  • DBパスワードの自動ローテーション → Secrets Manager(Parameter Storeは自動ローテーションを提供しない)。
  • Aurora・RDSのマスターユーザー → マネージドローテーション(Lambda関数は不要)。それ以外のシークレットはLambda関数でローテーションする。
  • ダウンタイムをほぼなくしたい → 交代ユーザー方式。クローンのユーザーは元と同じ権限で作られるため、後から権限を変えたら両方に反映する必要がある。
  • ローテーションが不要な設定値 → Parameter Store(標準パラメータは追加料金なし)。
  • 料金はシークレット数とAPI呼び出し数で決まる。レプリカも別のシークレットとして課金される。
  • 別のアカウントに使わせる → リソースポリシーと呼び出し側のIAMポリシーの両方が必要。KMSキーはカスタマー管理キーにする(AWS管理キーは使えない)。
  • DRで別リージョンでも使いたい → レプリケーション。DR戦略の考え方は用語ページ「DR戦略」を参照してください。
  • アプリのコードにはパスワードを書かず、シークレット名(ARN)だけを設定して GetSecretValue で取得する。

7. まとめ

  • Secrets Managerは機密情報の保管・取得・ローテーションのサービス。
  • ローテーションはシングルユーザーと交代ユーザーの2方式。
  • ローテーション不要の設定値はParameter Storeで十分。
