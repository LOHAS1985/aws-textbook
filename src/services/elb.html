1. サービス概要

Elastic Load Balancing(ELB)は、受け取った通信を複数のサーバーへ分散するロードバランサーのサービス群です。リージョンサービスで、通信を複数のAZへ分散します(リージョンをまたいだ分散はしません)。

2. 主な機能・特徴

種類

種類レイヤー用途
ALB(Application Load Balancer)L7HTTP/HTTPS用
NLB(Network Load Balancer)L4TCP/UDP用。通信の高速転送
GWLB(Gateway Load Balancer)L3/L4ネットワークセキュリティ機器用。通信をファイアウォールなどのセキュリティ機器群へ分散
CLB(Classic Load Balancer)L4/L7旧世代。新規ではALB・NLBを使う

機能

  • ヘルスチェック:ALBはHTTP/HTTPSで行う。NLBはTCP・HTTP・HTTPSで行う(UDPのターゲットグループでも、ヘルスチェック自体はTCP・HTTP・HTTPSのいずれかで行う)。
  • パスルーティング:URLによって転送先を変える(例:https://api.example.com/users/list の api.example.com がホスト、/users/list がパス)。
    • ホストベース:異なるホストへの分散
    • パスベース:同じドメイン内での分散
  • HTTPS終端:HTTPSの復号をALBで行い、EC2の負担を軽減する。

NLBはAZごとに静的IP(Elastic IP)を割り当てられるのが特徴です。

リスナールール

受け取ったリクエストの処理ルールです。

  1. IF(条件):リクエストを判定する条件。例:パスベース、ホストベース、HTTPヘッダーなど
  2. THEN(アクション):条件に一致したときの動作。例:特定のターゲットグループへ転送、リダイレクト

ターゲットグループとターゲットタイプ

ターゲットグループは、通信の転送先(ターゲット)をまとめたものです。リスナーやリスナールールの転送先にはターゲットグループを指定し、ヘルスチェックの設定もターゲットグループごとに持ちます。ターゲットグループを作るときにターゲットタイプを選び、後から変更はできません。

ターゲットタイプ登録するもの使えるLB主な用途
インスタンスEC2インスタンスIDALB・NLB・GWLBEC2への分散。Auto Scalingグループと組み合わせる
IPプライベートIPアドレスALB・NLB・GWLBECS(Fargate、awsvpcモード)、ピアリング先VPCやオンプレミスのサーバー
LambdaLambda関数ALBのみHTTPリクエストをサーバーレスで処理
ALBApplication Load BalancerNLBのみNLBの静的IPとALBのL7ルーティングを組み合わせる

ヘルスチェックの設定項目

ロードバランサーは、ターゲットグループの設定に従って各ターゲットへ定期的にリクエストを送り、正常(healthy)なターゲットにだけ通信を転送します。

設定項目意味ALBの既定値
プロトコル・ポートヘルスチェックに使うプロトコルとポート(既定は通信と同じポート)HTTP・トラフィックポート
パスHTTP/HTTPSの場合にリクエストするパス(例:/health)/
間隔ヘルスチェックを送る間隔30秒
タイムアウト応答がないと失敗とみなすまでの時間5秒
正常のしきい値何回連続で成功したら正常に戻すか5回
非正常のしきい値何回連続で失敗したら非正常にするか2回
成功コード成功とみなすHTTPステータスコード(例:200、200-299)200

パスにアプリやDBの状態まで確認する専用のページを用意すると、「サーバーは動いているがアプリが壊れている」状態も検知できます。ログイン画面へのリダイレクト(302)が返るパスを指定すると、成功コードが200のままでは全ターゲットが非正常になる点に注意します。Auto ScalingグループでELBのヘルスチェックを有効にすると、非正常と判定されたインスタンスは自動で置き換えられます。

クロスゾーン負荷分散

ロードバランサーのノードはAZごとに置かれます。クロスゾーン負荷分散が無効だと、各ノードは自分のAZのターゲットにだけ転送し、有効だと全AZのターゲットに均等に転送します。

種類既定補足
ALB有効AZ間のデータ転送料金はかからない。ターゲットグループ単位で無効にもできる
NLB・GWLB無効有効にするとAZ間のデータ転送料金がかかる
CLBコンソールで作ると有効、API・CLIで作ると無効—

登録解除の遅延(Connection Draining)

スケールインやデプロイでターゲットをターゲットグループから外すとき、いきなり切り離すと処理中のリクエストが失敗します。登録解除の遅延を設定すると、ターゲットは「draining」状態になり、新しいリクエストは送られず、処理中のリクエストだけ指定時間まで完了を待ってから外されます。

  • 既定は300秒、0〜3600秒で設定できる
  • 短い処理しかないアプリでは短くすると、スケールインやデプロイが早く終わる
  • CLBでは「Connection Draining」という名前の設定

スティッキーセッション

スティッキーセッション(セッション維持)を有効にすると、同じクライアントからのリクエストを同じターゲットに送り続けます。セッション情報をサーバーのメモリに持つアプリで使います。

  • ALB:Cookieで実現する。ロードバランサーが発行するCookie(AWSALB、期間ベース)か、アプリが発行するCookie(アプリケーションベース)を使う。維持する期間は1秒〜7日
  • NLB:送信元IPアドレスで同じターゲットに送る
  • 負荷が偏りやすく、ターゲットが停止するとセッションが失われる。可能ならセッション情報をElastiCacheやDynamoDBに置いてサーバーをステートレスにする方がよい

内部向けとインターネット向け

ロードバランサーは作成時にスキームを選びます。作成後は変更できません。

スキームIPアドレス配置するサブネット用途
インターネット向け(internet-facing)パブリックIP(DNS名がパブリックIPに解決される)パブリックサブネットインターネットからの入り口
内部向け(internal)プライベートIPのみプライベートサブネットWeb層からアプリ層への分散など、VPC内(とVPN・Direct Connectの先)からの通信

インターネット向けのALBでも、ターゲットのEC2はプライベートサブネットに置けます(ALBからはプライベートIPで転送されるため)。

アクセスログ

アクセスログを有効にすると、リクエストごとの記録(受信時刻、クライアントIP、処理時間、リクエストの内容、ステータスコード、転送先のターゲットなど)がS3バケットに5分ごとに出力されます。

  • 既定では無効。有効にし、出力先のバケットのバケットポリシーでELBからの書き込みを許可する
  • 機能自体は無料で、S3の保存料金だけがかかる
  • 出力したログはAthenaでSQLを使って分析できる
  • NLBのアクセスログはTLSリスナーの通信だけが対象

集計値(リクエスト数、5xxの数、レイテンシーなど)を見るならCloudWatchメトリクス、リクエスト1件ずつの詳細を調べるならアクセスログ、と使い分けます。

SNI(1つのリスナーで複数の証明書)

SNI(Server Name Indication)は、TLSの接続開始時にクライアントが「どのホスト名に接続したいか」をサーバーへ伝える仕組みです。ALBとNLB(TLSリスナー)はSNIに対応していて、1つのHTTPS/TLSリスナーに複数の証明書を登録でき、クライアントが指定したホスト名に合う証明書を自動で選びます。

これにより、a.example.com と b.example.org のような別ドメインのサイトを、1つのALB・1つのリスナー(443)でまとめて提供できます。証明書はACMで発行・管理するのが一般的です。CLBはSNIに対応していません。

WAFとの連携

ALBにはAWS WAFのウェブACLを関連付けられます。ALBに届いたリクエストはWAFのルールで検査され、SQLインジェクションやクロスサイトスクリプティング、特定のIP・国からのアクセス、短時間の大量アクセス(レートベースのルール)などをターゲットに届く前にブロックできます。

WAFを関連付けられるのはALBで、NLB・GWLBには関連付けられません(WAFはHTTPの中身を検査するL7の機能のため)。CloudFrontやAPI Gatewayにも関連付けられます。

3. ユースケース

  • 複数AZのEC2/ECSへWebトラフィックを分散(ALB)
  • /api/* はAPIサーバー、/images/* は画像サーバーへ振り分け(パスベースルーティング)
  • ゲームやIoTなどTCP/UDPの大量・高速通信(NLB)
  • サードパーティ製ファイアウォールへの通信分散(GWLB)

4. 料金の考え方

ロードバランサーの稼働時間と、処理量の単位(ALBはLCU、NLBはNLCU)に応じて課金されます。

5. 関連サービス

  • Amazon EC2/Amazon ECS:代表的なターゲット
  • Amazon EC2 Auto Scaling:ターゲットの自動登録・ELBヘルスチェック
  • Amazon EKS:Ingress→ALB、Service→NLB
  • AWS Certificate Manager:HTTPS終端に使う証明書
  • AWS Global Accelerator:ALB/NLBの前段でグローバルに最適化
  • Amazon Route 53:エイリアスレコードでELBを指す

6. 試験・実務でのポイント

  • HTTP/HTTPSでパス・ホストによる振り分け → ALB。
  • TCP/UDP・超高速・静的IP → NLB。
  • セキュリティアプライアンスへの分散 → GWLB。
  • EC2のSSL処理負荷を減らす → ALBでHTTPS終端。
  • ELBはリージョン内の複数AZに分散する(リージョン間は Route 53 や Global Accelerator)。
  • Lambdaをターゲットにできる → ALB。NLBの後ろにALBを置く → ターゲットタイプ「ALB」。Fargateのタスク → ターゲットタイプ「IP」。
  • 全ターゲットが非正常になった → ヘルスチェックのパス・ポート・成功コードと、ターゲットのセキュリティグループでLBからの通信を許可しているかを確認する。
  • AZごとのターゲット数が違い負荷が偏る → クロスゾーン負荷分散を有効にする(NLBは既定で無効)。
  • スケールイン時に処理中のリクエストを失敗させない → 登録解除の遅延。
  • 同じユーザーを同じサーバーに送りたい → スティッキーセッション(ただしステートレス化の方が望ましい)。
  • リクエスト単位で記録を残したい → アクセスログ(S3に出力、既定は無効)。
  • 複数のドメインの証明書を1つのALBで扱う → SNI。
  • SQLインジェクションなどをブロック → ALBにAWS WAFを関連付ける。

7. まとめ

  • ELBはALB(L7)・NLB(L4)・GWLB(L3/4)・CLB(旧世代)の4種類。
  • ALBはリスナールール(IF/THEN)でホスト・パスごとに振り分ける。
