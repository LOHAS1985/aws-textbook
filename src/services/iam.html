1. サービス概要

AWS IAM(Identity and Access Management)は、AWSの認証・認可を管理するサービスです。

  • 認証:ユーザーが「誰か」を確認する
  • 認可:ユーザーが「何をしてよいか」を決める

2. 主な機能・特徴

用語

  • ルートユーザー:アカウント作成時に作られる、全権限を持つユーザー。日常の運用での使用は非推奨。
  • IAMユーザー・グループ:日常業務で必要な権限はポリシーで付与し、一時的に必要な権限はロールを使う権限を付与する。
  • IAMロール:ポリシーを持たせて特定の権限を一時的に付与する仕組み。信頼ポリシー(誰が引き受けられるか)と権限ポリシー(何ができるか)の両方の設定が必要。
  • IAMポリシー:アイデンティティベースの権限設定。IAMユーザー・グループ・ロールに設定してリソースへのアクセスを制御する。
    ※リソースベースのポリシー:リソース側から見てアクセスを制御する(S3バケットポリシーなど)。

Organizationsで複数のアカウントを使う場合は、各アカウントにIAMユーザーを作るのではなく、IAM Identity Centerでユーザーを一元管理し、パーミッションセットで各アカウントの権限を割り当てるのが推奨です。

ポリシーJSONの書き方

IAMポリシーはJSONで書き、1つ以上のステートメント(Statement)からなります。次の例は「my-bucket の読み書きを許可し、ただしMFAで認証していないときの削除は拒否する」ポリシーです。

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::my-bucket/*"
    },
    {
      "Effect": "Deny",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
      }
    }
  ]
}
要素意味
Versionポリシー言語のバージョン。常に "2012-10-17" を書く
EffectAllow(許可)か Deny(拒否)
Action対象の操作。サービス:アクション の形式で、s3:Get* のようにワイルドカードも使える
Resource対象のリソースをARNで指定する
Condition適用する条件(送信元IP、MFAの有無、タグ、リージョンなど)。省略すると常に適用
Principal誰に対するポリシーか。リソースベースのポリシー(バケットポリシーや信頼ポリシー)でだけ書く

要素の詳しい書き方と例は用語ページ「IAMポリシーと評価ロジック」を参照してください。

評価ロジック(明示的なDenyが最優先)

1つのリクエストに複数のポリシーが関係するとき、AWSは次の順番で判断します。

  1. どこかに明示的なDenyがあれば → 拒否(ほかにAllowがあっても覆らない)
  2. Denyがなく、明示的なAllowがあれば → 許可
  3. どちらもなければ → 暗黙的な拒否(既定はすべて拒否)

さらに、OrganizationsのSCPやアクセス許可の境界、ロールのセッションポリシーが設定されている場合は、そのすべてで許可されている範囲だけが実際に使えます。アイデンティティベースのポリシーでAllowしても、SCPで許可されていなければ使えません。

マネージドポリシーとインラインポリシー

種類作成・管理する人特徴
AWS管理ポリシーAWSAdministratorAccess、ReadOnlyAccess、AmazonS3ReadOnlyAccess など。AWSが更新する。手軽だが権限が広めになりやすい
カスタマー管理ポリシー利用者自分で作る独立したポリシー。複数のユーザー・グループ・ロールに付けて再利用でき、変更履歴(最大5バージョン)が残り、元のバージョンに戻せる
インラインポリシー利用者特定の1つのユーザー・グループ・ロールに直接埋め込むポリシー。付けた先を削除するとポリシーも消える。再利用やバージョン管理はできない

基本はマネージドポリシー(特にカスタマー管理ポリシー)を使い、「そのロールだけに厳密に1対1で付けたい権限」のときにインラインポリシーを使います。

アクセス許可の境界(Permissions Boundary)

アクセス許可の境界は、IAMユーザーやロールに設定する「付与できる権限の上限」です。マネージドポリシーで上限を定義して境界に設定すると、そのユーザー・ロールの実際の権限は「アイデンティティベースのポリシーと境界の両方で許可された範囲」になります。境界そのものは権限を与えません。

代表的な用途は権限の委任です。開発者にIAMロールを作る権限を与えつつ、「作るロールには必ずこの境界を付けること」を条件にすると、開発者が自分より強い権限のロールを作って権限昇格するのを防げます。SCPがアカウント全体の上限なのに対して、境界は個々のユーザー・ロールの上限です。

IAM Access Analyzer

IAM Access Analyzerは、ポリシーを分析して意図しないアクセスや不要な権限を見つける機能です。

機能内容
外部アクセスの分析S3バケット、IAMロール、KMSキー、Lambda関数、SQSキュー、Secrets Managerのシークレットなどのリソースベースのポリシーを調べ、アカウント(または組織)の外部からアクセスできるリソースを検出結果として表示する。無料
未使用のアクセスの分析使われていないロール、アクセスキー、パスワード、付与されているが使われていない権限を検出する(有料)
ポリシーの検証ポリシーを作るときに、文法エラーやセキュリティ上の問題(広すぎる権限など)を指摘する
ポリシーの生成CloudTrailのログから実際に使われたアクションを調べ、最小権限のポリシーのひな形を作る

「信頼ゾーン」(アナライザーを作ったアカウント、または組織全体)の外からのアクセスが検出の対象です。

認証情報レポート

認証情報レポートは、アカウント内のすべてのIAMユーザー(ルートユーザーを含む)の認証情報の状態をまとめたCSVファイルです。コンソールやCLIから生成・ダウンロードできます(生成は4時間に1回まで)。

  • パスワードの有無・最終使用日時・最終変更日時
  • MFAが有効かどうか
  • アクセスキーの有無・作成(ローテーション)日時・最終使用日時と使われたサービス

「90日以上ローテーションしていないアクセスキー」「MFAが無効なユーザー」「長期間使われていないユーザー」を洗い出す監査に使います。ユーザーやロールごとに「どのサービスを最後にいつ使ったか」を見る場合は、最終アクセス情報(アクセスアドバイザー)を使います。

OIDCとの連携

IAMにOIDC IdP(プロバイダーURL、クライアントID=IdPが発行するトークンの受信者)を登録します。

  1. アプリがOIDC IdPからIDトークンを取得
  2. アプリがトークンを持って、STSの AssumeRoleWithWebIdentity を呼び出す
  3. STSが、IAMに登録したIdP情報をもとにトークンの署名・発行者を検証
  4. 検証に通り、IAMロールの信頼ポリシーが許可していれば、一時的な認証情報を発行

認証情報の優先順位(AWS CLI/SDK)

優先順位認証情報

2環境変数(AWS_ACCESS_KEY_ID など)
3~/.aws/credentials
4~/.aws/config のプロファイル
5ECSタスクロール
6EC2インスタンスプロファイル(IAMロール)

3. ユースケース

  • 開発者ごとにIAMユーザーを作り、グループで権限を管理
  • EC2・Lambda・ECSにIAMロールを付けて、アクセスキーなしでAWSサービスを利用
  • 別アカウントのリソースへロールを引き受けてアクセス(クロスアカウント)
  • GitHub ActionsなどのOIDC連携で、アクセスキーを使わずにデプロイ

4. 料金の考え方

IAMは無料で利用できます。

6. 試験・実務でのポイント

基本

  • ルートユーザーは日常で使わない。
  • アクセスキーをコードやインスタンスに置かず、ロールを使う。
  • 環境変数のキーが、インスタンスプロファイルより優先される。意図しない権限で動くときは優先順位を確認。
  • ロールは信頼ポリシー+権限ポリシーの両方が必要。AssumeRoleできないときは信頼ポリシーを確認。

ポリシーの評価と種類

  • AllowとDenyが両方ある → 明示的なDenyが優先。どこにもAllowがなければ暗黙的に拒否。
  • 複数のロールで再利用・バージョン管理したい → カスタマー管理ポリシー。特定のロールだけに1対1 → インラインポリシー。
  • 開発者にロール作成を任せつつ権限昇格を防ぐ → アクセス許可の境界。
  • 他アカウントからのS3アクセスは、バケットポリシー(リソースベース)と相手側IAMポリシーの両方で許可。

監査

  • 外部アカウントに公開されているリソースを見つける → IAM Access Analyzer。CloudTrailから最小権限のポリシーを作るのもAccess Analyzer。
  • 全ユーザーのMFA・アクセスキーのローテーション状況を監査 → 認証情報レポート。

7. まとめ

  • IAMは「誰か(認証)」と「何ができるか(認可)」を管理する。
  • ユーザー・グループ・ロール・ポリシーの役割を区別する。
  • 認証情報は優先順位に従って選ばれる。
