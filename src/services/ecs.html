1. サービス概要

Amazon ECS(Elastic Container Service)は、AWS上でコンテナを実行・管理するためのコンテナオーケストレーションサービスです。どのサーバーでコンテナを動かすか、何個動かすか、壊れたら入れ替えるか、新しいバージョンにどう切り替えるかを、ECSが代わりに管理します。

Kubernetesの知識がなくても使え、IAM・ALB・CloudWatchなどのAWSのサービスと最初から連携できるのが特徴です。Kubernetesを使いたい場合はAmazon EKSを選びます。

2. 主な機能・特徴

構成要素

  • クラスター:実行環境のまとまり。複数のアプリや環境をまとめるときに使う。
  • タスク定義:コンテナを実行するときの設計書(Dockerfileはビルド時の設計書)。
    • 使用するイメージ(Docker Image)
    • CPU/メモリ
    • ポート(Port Mapping)
    • 環境変数(Environment Variables)とシークレット
    • IAMロール、ログの送り先、ヘルスチェック
  • タスク:タスク定義から起動された実体(コンテナ)。
  • サービス:タスクを常に指定数維持する仕組み。
    • 起動数の維持(Desired Count)
    • 自動増減(Auto Scaling)
    • ALB連携(Load Balancer)
    • 無停止更新(Rolling Update)
    • 異常タスクの交換(Health Check)

Webアプリのように動き続ける処理はサービスで、バッチのように終わる処理はタスクを単独で(EventBridgeのスケジュールなどから)実行します。

起動タイプ

起動タイプ内容特徴
EC2起動タイプユーザーがEC2(コンテナインスタンス)を用意し、その上でコンテナを実行GPUや特殊なインスタンスを使える。OSのパッチ当てや台数の管理が必要
Fargate起動タイプ(現在の主流)コンテナを指定するだけサーバー管理不要(ほぼサーバーレス)。タスクごとに分離される

EC2起動タイプでは、EC2にECSコンテナエージェントが入ったAMI(ECS最適化AMI)を使い、インスタンスにはECSへ登録するためのIAMロール(インスタンスロール)を付けます。

タスクロールとタスク実行ロール

ECSのタスクには、目的の違う2つのIAMロールを設定します。取り違えやすいので、試験でもよく問われます。

ロール使う人必要な権限の例
タスク実行ロールECS(コンテナを起動する側)ECRからイメージを取得する、CloudWatch Logsにログを書く、Secrets Manager・Parameter Storeからシークレットを読んでコンテナに渡す
タスクロールコンテナの中のアプリアプリがS3にファイルを置く、DynamoDBを読み書きする、など

アプリにアクセスキーを持たせる必要はありません。パスワードなどは、タスク定義の secrets でSecrets ManagerやParameter Storeを参照すると、起動時に環境変数として渡されます。

ネットワークモード

モード内容
awsvpcタスクごとにENI(プライベートIPアドレス)が付き、タスクごとにセキュリティグループを設定できる。Fargateではこのモードだけを使う
bridgeEC2起動タイプで、ホストの中の仮想ネットワークを使う。ホストのポートを動的に割り当て(動的ポートマッピング)、ALBが自動で振り分け先のポートを登録する
hostEC2のネットワークをそのまま使う。同じポートのタスクを1台に2つ置けない

プライベートサブネットのタスクがECRからイメージを取得するには、NATゲートウェイか、ECR(ecr.api・ecr.dkr)とS3のVPCエンドポイントが必要です。どちらもないと、タスクが起動できません。

キャパシティプロバイダー

ECSタスクをどの計算リソース上でどれだけ実行するかを管理します。

  • 計算リソース:FARGATE(通常)、FARGATE_SPOT(余剰リソースを安価に利用)、ASG Capacity Provider(ECSがEC2 Auto Scalingを管理)
  • 実行数:Base=最低保証タスク数、Weight=どれくらいの割合で配置するか

ASG Capacity Providerでは、マネージドスケーリングを有効にすると、タスクを置く場所が足りなくなったときに、ECSがEC2の台数を自動で増やします。

サービスのAuto Scaling

サービスのタスク数は、Application Auto Scalingで増減します。ターゲット追跡で、サービスの平均CPU使用率・平均メモリ使用率、ALBのターゲットあたりのリクエスト数(ALBRequestCountPerTarget)を目標値に保つのが基本です。SQSのキューの長さなど、独自のメトリクスでも増減できます。

デプロイ

方式動き
ローリング更新(既定)新しいタスクを起動してから古いタスクを止める。minimumHealthyPercent(更新中に最低限動かしておく割合)と maximumPercent(一時的に増やせる上限)で、入れ替えの速さを決める
Blue/Green新しいバージョンのタスクを並べて起動し、ALBの通信を切り替える。一度に切り替えるほか、少しずつ移す線形・カナリアも選べる。問題があればすぐ元に戻せる。ECSのサービス自体で実行でき、以前はCodeDeployと組み合わせていた
  • デプロイサーキットブレーカー:新しいタスクが起動に失敗し続ける(ヘルスチェックに通らない、すぐ止まる)と、デプロイを失敗とみなし、ロールバックを有効にしておけば前のバージョンに自動で戻す。
  • CloudWatchアラームによるロールバック:タスクは起動したが、エラー率などのアラームが鳴った場合にも、自動で前のバージョンに戻せる。
  • ALBのヘルスチェックに通る前にタスクが入れ替えられる場合は、サービスのヘルスチェックの猶予期間を延ばす。

ログと監視

  • ログ:タスク定義のログドライバーに awslogs を指定すると、コンテナの標準出力がCloudWatch Logsに送られる。S3やOpenSearch Serviceなどに送りたい場合はFireLens(Fluent Bit)を使う。
  • サービスのメトリクス:サービスのCPU使用率・メモリ使用率は、標準でCloudWatchに送られる。
  • CloudWatch Container Insights:クラスター・サービス・タスク・コンテナ単位のCPU・メモリ・ネットワーク・ストレージ、実行中のタスク数などを集め、ダッシュボードで表示する。クラスターごと、またはアカウントの既定で有効にする(オブザーバビリティを強化したモードでは、コンテナ単位まで詳しく見られる)。
  • イベント:タスクの状態の変化(停止など)やサービスのデプロイの状態は、EventBridgeのイベントになる。タスクが止まったら通知する、などに使う。

タスクが止まる・起動しないときの調べ方

止まったタスクの「停止理由」(コンソールのタスクの詳細、または DescribeTasks の stoppedReason)を見ると、原因の見当がつきます。

停止理由の例よくある原因と対処
CannotPullContainerErrorイメージを取得できない。NATゲートウェイやVPCエンドポイントがない、タスク実行ロールにECRの権限がない、イメージのタグが間違っている
ResourceInitializationErrorシークレットやログの準備に失敗した。タスク実行ロールにSecrets Manager・Parameter Store・KMSの権限がない、エンドポイントに届かない
OutOfMemoryErrorコンテナがタスク定義のメモリの上限を超えた。メモリを増やすか、アプリの使い方を見直す
ELBのヘルスチェックに失敗ヘルスチェックのパスやポートが違う、セキュリティグループでALBからの通信を許可していない、猶予期間が短い
Essential container in task exited必須のコンテナが終了した。CloudWatch Logsでアプリのエラーを確認する

動いているコンテナの中に入って調べたいときは、ECS Execを使います(Systems Manager Session Managerのしくみを使うため、タスクロールに権限が必要)。

3. ユースケース

  • Webアプリ・APIをコンテナで常時稼働させる(サービス+ALB)
  • FARGATE_SPOTを組み合わせたコスト重視のバッチ処理
  • Lambdaの15分制限を超える長時間処理
  • 新しいバージョンを止めずにリリースし、失敗したら自動で戻す
  • 関連する運用シナリオ:ECSのサービスを止めずに更新し、失敗したら自動で戻す、コンテナ(ECS・EKS)の性能を監視する

4. 料金の考え方

ECS自体の利用料はかかりません。EC2起動タイプではEC2インスタンスの料金、Fargate起動タイプではタスクに割り当てたvCPU・メモリと実行時間に応じた料金がかかります。

FARGATE_SPOTを使うと余剰リソースを安価に利用できます(中断される可能性あり)。Container Insightsを有効にすると、集めたメトリクスとログの分のCloudWatchの料金がかかります。

5. 関連サービス

  • Amazon ECR:コンテナイメージの保存先
  • Amazon EKS:Kubernetesベースのオーケストレーション
  • Elastic Load Balancing:サービスとALBの連携
  • Amazon EC2/Amazon EC2 Auto Scaling:EC2起動タイプの実行基盤
  • Amazon CloudWatch:ログ、Container Insights、ロールバックに使うアラーム
  • AWS Secrets Manager/AWS Systems Manager:シークレットの受け渡し、ECS Exec
  • Amazon EventBridge:タスクの状態の変化の通知、スケジュール実行
  • AWS CodeDeploy/AWS CodePipeline:デプロイの自動化
  • AWS Copilot:ECSアプリの構築・デプロイを簡単にするCLI
  • 関連する用語:デプロイ戦略、サーキットブレーカー、IAMロールと一時的な認証情報、マネージドとサーバーレス

6. 試験・実務でのポイント

設定

  • コンテナの環境変数・CPU/メモリ・イメージはタスク定義で指定する。
  • タスク数の維持・ALB連携・ローリング更新はサービスの役割。
  • サーバー管理をしたくない → Fargate。
  • Fargateと安価なFARGATE_SPOTの配分 → キャパシティプロバイダーのBase/Weight。
  • アプリがS3などを使う権限 → タスクロール。イメージの取得・ログ・シークレットの取得 → タスク実行ロール。
  • タスクごとにセキュリティグループを分けたい → awsvpcモード。

デプロイと監視

  • 新しいタスクの起動失敗で自動で戻したい → デプロイサーキットブレーカー(ロールバックを有効に)。
  • エラー率の上昇で自動で戻したい → デプロイにCloudWatchアラームを設定する。
  • コンテナ・タスク単位のCPU・メモリを見たい → Container Insights。
  • コンテナのログを集めたい → awslogs ログドライバーでCloudWatch Logsへ。
  • プライベートサブネットで CannotPullContainerError → NATゲートウェイかECR・S3のVPCエンドポイント、タスク実行ロールの権限を確認する。

7. まとめ

  • ECSは「クラスター/タスク定義/タスク/サービス」で構成される。
  • 起動タイプはEC2とFargate。主流はFargate。キャパシティプロバイダーでリソースの配分を制御する。
  • 権限はタスク実行ロール(起動)とタスクロール(アプリ)に分ける。
  • デプロイはサーキットブレーカーとアラームで自動で戻し、監視はContainer InsightsとCloudWatch Logsで行う。
