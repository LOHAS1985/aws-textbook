1. サービス概要

AWS STS(Security Token Service)は、一時的な認証情報を発行するサービスです。短時間だけ有効なアクセスキーを発行するため、長期のキーを配る必要がありません。

発行される認証情報:Access Key ID、Secret Access Key、Session Token

AssumeRole

別の権限(ロール)を一時的に使います。ユーザー/サービスがSTSにリクエスト → STSが一時クレデンシャルを発行 → それを使ってAWSリソースにアクセス、という流れです。

AssumeRoleWithSAML

SAML認証の結果を使ってロールを引き受けます。

  1. ユーザーがIdP(例:会社の認証基盤)にログイン。IdP=本人確認を行い証明を発行するシステム
  2. IdPがSAMLアサーション(「認証済み」を証明するデータ)を発行
  3. IdPがブラウザ経由でAWSに送信
  4. STSが検証し、一時クレデンシャルを発行

AssumeRoleWithWebIdentity

Web/モバイルアプリの利用者向けに、OIDC/OAuth 2.0のIDプロバイダーのトークンを使ってロールを引き受けます。

  1. ユーザーがWeb IdP(Google、Facebookなど)でログイン
  2. IdPがIDトークン(JWT)を発行
  3. クライアントが、使いたい権限とIDトークンを送ってSTSを呼び出す
  4. STSが検証し、一時クレデンシャルを発行

3. ユースケース

  1. ロール切り替え:普段は一般ユーザーだが、作業時だけ管理者権限を使いたい
  2. クロスアカウントアクセス:別のAWSアカウントのリソースに安全にアクセス
  3. IDフェデレーション:社内IdPやGoogleアカウントでAWSを利用

4. 料金の考え方

STSは追加料金なしで利用できます。

5. 関連サービス

  • AWS IAM:引き受けるロールの定義
  • Amazon Cognito:IDプールで内部的にSTSを利用
  • AWS Organizations:マルチアカウント環境でのロール運用
  • AWS Directory Service:Active Directoryとの連携

6. 試験・実務でのポイント

  • 別アカウントのリソースへアクセス → AssumeRole。
  • 社内AD/SAMLでSSO → AssumeRoleWithSAML。
  • Googleなどのソーシャルログイン/OIDC → AssumeRoleWithWebIdentity(実際はCognito経由が推奨)。
  • MFAを条件にした一時認証 → GetSessionToken。
  • 一時認証情報にはSession Tokenが含まれる。

7. まとめ

  • STSは一時的な認証情報(キーID・シークレット・セッショントークン)を発行する。
  • 認証元に応じてAssumeRole/WithSAML/WithWebIdentityを使い分ける。
