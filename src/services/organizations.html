1. サービス概要

AWS Organizationsは、複数のAWSアカウントをまとめて管理するサービスです。アカウントをグループに分け、組織全体に共通のルールを適用できます。

本番・開発・ログ保管などの用途ごとにアカウントを分けると、障害や権限の影響範囲を小さくでき、費用も分けて把握できます。Organizationsは、そうしたマルチアカウント環境の土台です。Control TowerやIdentity Centerも、Organizationsの上で動きます。

組織には「すべての機能」と「一括請求の機能だけ」の2つのモードがあります。SCPなどのポリシーや、ほかのAWSサービスとの連携を使うにはすべての機能を有効にします。

2. 主な機能・特徴

用語

  • ルート:組織の階層の最上位。ルートにポリシーを適用すると、組織内のすべてのアカウントが対象になる。
  • 管理アカウント:組織を作成したアカウント。メンバーアカウントの招待・作成や一括請求を行う。
  • メンバーアカウント:組織に所属する管理アカウント以外のアカウント。
  • OU(組織単位):アカウントのグループ。OUの中にOUを入れて階層にできる。
  • SCP(サービスコントロールポリシー):権限の制御(拒否が中心)。IAMで許可しても、SCPで拒否されていれば拒否される。

ポリシーの種類

Organizationsのポリシーは、権限を制限する「認可ポリシー」と、設定をそろえる「管理ポリシー」に分かれます。どれも、ルート・OU・アカウントに適用します。

ポリシー分類内容
SCP(サービスコントロールポリシー)認可アカウント内のIAMユーザー・ロール(プリンシパル)が使える権限の上限
RCP(リソースコントロールポリシー)認可アカウント内のリソース(S3バケット・KMSキー・SQSキューなど)に対して、許される権限の上限。組織外からのアクセスを一律に禁止する、などに使う
タグポリシー管理タグのキーと値の書き方をそろえる(例:CostCenter の大文字・小文字、使ってよい値)
バックアップポリシー管理AWS Backupのバックアッププランを全アカウントに配る
宣言型ポリシー管理EC2・VPCなどの設定の基準を強制する(例:IMDSv2を必須にする、AMIやスナップショットの公開を禁止する)。新しいAPIが増えても効き続ける
AIサービスのオプトアウトポリシー管理AWSのAIサービスが、組織のデータをサービスの改善に使わないようにする

SCPの利用イメージ

Organizationsの管理アカウント側の管理者が設定します。

  • 組織全体の権限の管理 → SCP
  • 個々の権限の管理 → IAM
AWS Organizations
├── SCP
│    ├── 使用可能リージョンを制限
│    ├── CloudTrail停止を禁止
│    └── Organizations操作を禁止
├── IAM Identity Center
│    ├── 開発者 → Developer権限
│    ├── 運用者 → Administrator権限
│    └── 監査者 → ReadOnly権限
└── 各AWSアカウント
     ├── Production
     ├── Development
     └── Test

SCPは権限を「与える」ものではなく、上限(ガードレール)を決めるものです。実際の操作には、SCPで禁止されていないことに加えて、IAMでの許可が必要です。

SCPの書き方と継承

次のSCPは、東京・大阪以外のリージョンでの操作を拒否する例です。IAMやCloudFrontなどのグローバルサービスは、米国東部(バージニア北部)リージョンのAPIを使うため、NotAction で対象から外しています。

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyOtherRegions",
    "Effect": "Deny",
    "NotAction": ["iam:*", "organizations:*", "sts:*", "cloudfront:*", "support:*"],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "aws:RequestedRegion": ["ap-northeast-1", "ap-northeast-3"]
      }
    }
  }]
}
  • 組織を作ると、すべての操作を許可するSCP(FullAWSAccess)が、ルート・OU・アカウントに付いている。これを残したまま、禁止したいことだけをDenyで書く(拒否リスト方式)のが一般的。
  • FullAWSAccess を外し、使ってよいサービスだけをAllowで書く方式(許可リスト方式)もある。この場合、ルートからアカウントまでのすべての階層で許可されていないと使えない。
  • Denyは、どの階層に書いても配下のすべてのアカウントに効く。下の階層のSCPで打ち消すことはできない。
  • 例外にしたいロール(管理者用のロールなど)は、Conditionで aws:PrincipalArn を使って除外する。

SCPが効かないもの

  • 管理アカウントには、SCPは適用されない。そのため、管理アカウントでは普段の作業やワークロードを動かさない。
  • サービスリンクロール(AWSのサービスが代わりに操作するためのロール)には効かない。
  • メンバーアカウントのルートユーザーには効く。ルートユーザーでもSCPで拒否された操作はできない。

SCPの要点と、よく使う書き方

SCP(サービスコントロールポリシー)は、アカウントの中で使える権限の「上限(ガードレール)」を決めるポリシーです。IAMポリシーの書き方(JSON)で書きますが、SCPだけでは何の権限も与えません。実際に操作できるのは「SCPで許されていて、かつIAMポリシーでも許可されている」範囲だけです。評価の流れは用語ページ「IAMポリシーと評価ロジック」を参照してください。

項目内容
適用先ルート・OU・アカウント。上の階層のSCPは配下のすべてのOU・アカウントに継承される
効く相手メンバーアカウントのIAMユーザー・IAMロール・ルートユーザー
効かない相手管理アカウント、サービスリンクロール、組織の外のアカウントのプリンシパル(リソースベースのポリシーで許可された外部アカウントからのアクセスは、SCPでは止められない → RCPを使う)
有効にする条件組織で「すべての機能」を有効にし、ルートでSCPのポリシータイプを有効にする(一括請求の機能だけの組織では使えない)
反映付けたり外したりすると、すぐに効く。既存のリソースが消えることはなく、これからの操作が制限される

試験によく出る、典型的なSCPの使い方です。どれもDenyで書くのが基本です。

やりたいことSCPで拒否するアクション・条件
許可したリージョン以外を使わせないすべてのアクションを、aws:RequestedRegion が許可リストにないときに拒否(グローバルサービスは NotAction で除外)
CloudTrailの証跡を止めさせないcloudtrail:StopLogging、cloudtrail:DeleteTrail
GuardDuty・Config・Security Hubを無効にさせないguardduty:DeleteDetector、config:StopConfigurationRecorder、securityhub:DisableSecurityHub など
組織から勝手に抜けさせないorganizations:LeaveOrganization
メンバーアカウントのルートユーザーを使わせないすべてのアクションを、aws:PrincipalArn が arn:aws:iam::*:root のときに拒否
使ってよいインスタンスタイプを限定するec2:RunInstances を、ec2:InstanceType が許可リストにないときに拒否
暗号化されていないボリューム・バケットを作らせないec2:CreateVolume を ec2:Encrypted が false のときに拒否、など
タグのないリソースを作らせない作成のアクションを、aws:RequestTag/CostCenter がない(Null 条件)ときに拒否
セキュリティ用のロールを変更させないiam:* の変更系アクションを、対象が管理用のロールのときに拒否(管理者は aws:PrincipalArn で除外)

SCPのサイズは1つあたり5,120文字まで、1つの対象(ルート・OU・アカウント)に付けられるSCPは5つまでです。複数のガードレールは1つのSCPにまとめるか、OUの階層を分けて付けます。SCPを本番のOUに付ける前に、テスト用のOUで動作を確かめると安全です。

RCPとデータ境界

SCPは「自分のアカウントの人が何をできるか」を制限しますが、バケットポリシーで外部のアカウントに公開してしまうと、外部の人のアクセスは止められません。RCPはリソースの側に上限をかけるため、「組織のプリンシパル以外は、このバケットにアクセスできない」を、各アカウントのリソースポリシーに関係なく強制できます。条件キー aws:PrincipalOrgID で組織のIDを指定するのが基本です。

委任管理者と信頼されたアクセス

  • 信頼されたアクセス:GuardDuty・Security Hub・Config・CloudTrail・Backup・IAM Identity Center・CloudFormation StackSetsなどのサービスに、組織全体での操作を許可する設定。
  • 委任管理者:そのサービスの組織全体の管理を、管理アカウントではなく特定のメンバーアカウント(例:セキュリティ用のアカウント)に任せる。管理アカウントに入る人を減らせる。

アカウントの作成・招待と管理

  • 組織から新しく作成したアカウントには、管理アカウントから引き受けられる管理者ロール OrganizationAccountAccessRole が自動で作られる。
  • 既存のアカウントを招待した場合、このロールは作られない。管理アカウントから操作したいときは、招待したアカウント側で同じ名前のロールを作る。
  • メンバーアカウントのルートユーザーの認証情報をなくし、ルートユーザーでしかできない操作(バケットポリシーのロックの解除など)を管理アカウントから行う、ルートアクセスの一元管理もできる。
  • 組織から外れるアカウントには、単独で使うための支払い情報などが必要になる。

3. ユースケース

  • 本番・開発・テストのアカウントを分けて管理
  • 全アカウントで使用できるリージョンを制限
  • CloudTrailの停止など、セキュリティ設定の変更を全アカウントで禁止
  • 組織外のアカウントから、組織のS3バケットやKMSキーにアクセスさせない(RCP)
  • セキュリティ用のアカウントを委任管理者にして、GuardDutyやSecurity Hubを全アカウントで有効にする
  • IAM Identity Centerで、複数アカウントへのログインを一元化

4. 料金の考え方

Organizations自体は無料です。複数アカウントの請求をまとめる一括請求(コンソリデーティッドビリング)により、使用量を合算したボリュームディスカウントや、リザーブドインスタンス・Savings Plansの割引の共有の恩恵も受けられます。割引の共有は、アカウントごとにオフにすることもできます。

5. 関連サービス

  • AWS IAM:個々の権限管理
  • AWS IAM Identity Center:組織内の複数アカウントへのシングルサインオン(パーミッションセット)
  • AWS Control Tower:ベストプラクティスに沿ったマルチアカウント環境の構築
  • AWS CloudTrail:組織全体の証跡
  • AWS Config:組織全体のルール評価、アグリゲーター
  • AWS CloudFormation:StackSetsで全アカウントに同じリソースを配る
  • AWS Resource Access Manager:組織内でのリソース共有
  • AWS Security Hub/Amazon GuardDuty:委任管理者による組織全体のセキュリティ管理
  • AWS Backup:組織全体のバックアップポリシー
  • Savings Plans:一括請求での割引の共有
  • 関連する用語:IAMポリシーの評価、タグ、ルートユーザーとアカウントの保護

6. 試験・実務でのポイント

SCPとRCP

  • IAMで許可してもSCPで拒否されたら拒否。SCPは権限を与えない(上限を決めるだけ)。
  • 全アカウントで特定の操作・リージョンを禁止 → SCPをOUやルートに適用。リージョン制限は aws:RequestedRegion。
  • SCPは管理アカウントとサービスリンクロールには効かない。メンバーアカウントのルートユーザーには効く。
  • 許可リスト方式で「許可したのに使えない」→ ルートからアカウントまでの途中の階層で許可されているか確認する。
  • CloudTrailの停止・GuardDutyの無効化・組織からの離脱を全アカウントで禁止 → SCPでDeny(cloudtrail:StopLogging、organizations:LeaveOrganization など)。
  • SCPを使うには組織のすべての機能が必要。1つの対象に付けられるのは5つまで。
  • 組織外からのリソースへのアクセスを一律に禁止したい → RCP(aws:PrincipalOrgID)。

管理ポリシーと組織の運用

  • タグの書き方をそろえたい → タグポリシー。全アカウントで同じバックアップを取りたい → バックアップポリシー。
  • 全アカウントのEC2でIMDSv2を必須にしたい・AMIの公開を禁止したい → 宣言型ポリシー。
  • 管理アカウントを使わずに、組織全体のGuardDutyなどを管理したい → 委任管理者。
  • 招待したアカウントを管理アカウントから操作できない → OrganizationAccountAccessRole を手動で作る。
  • アカウントのグループ化 → OU。SCPなどのポリシーを使うには組織のすべての機能を有効にする。

7. まとめ

  • Organizationsは複数アカウントの管理サービス。OUでアカウントをまとめ、ポリシーで統制する。
  • SCPはプリンシパル、RCPはリソースに対する権限の上限。管理アカウントにはSCPが効かない。
  • タグ・バックアップ・宣言型などの管理ポリシーで設定をそろえ、委任管理者で管理アカウントの利用を減らす。
