1. サービス概要

Amazon CloudFrontは、CDN(Content Delivery Network)サービスです。世界中のエッジサーバーにコンテンツをキャッシュし、ユーザーの近くから高速に配信します。

  • オリジン:コンテンツを取得する元のサーバー(S3、ALB、EC2など)
  • ディストリビューション:各種設定の集合
  • キャッシュ対象はGET・HEAD・OPTIONSのみ

2. 主な機能・特徴

仕組み

  • CloudFrontなし:日本のユーザーがアメリカのWebサーバーへ直接アクセスすると時間がかかる。
  • CloudFrontあり
    • 初回:日本のエッジロケーションにキャッシュがないため、エッジがアメリカのオリジンへ取りに行き(時間は直接アクセスと同程度)、エッジにキャッシュを残す。
    • 2回目以降:ユーザーは近くのエッジロケーションから応答を受け取るだけで済み、高速になる。

エッジロケーションとオリジンの間には、リージョナルエッジキャッシュという、より大きなキャッシュの層があります。エッジロケーションにキャッシュがないときはまずリージョナルエッジキャッシュを探し、そこにもなければオリジンへ取りに行きます。エッジロケーションは利用者の近くに多数ある小さなキャッシュ、リージョナルエッジキャッシュはその背後にある少数の大きなキャッシュ、と区別します。

ビヘイビア(パスごとのオリジン・設定)

ビヘイビア(キャッシュビヘイビア)は、リクエストのパスに応じて「どのオリジンに送るか」「どうキャッシュするか」を決める設定です。1つのディストリビューションに複数のビヘイビアを作り、パスパターンで振り分けます。

  • パスパターンの例:/api/*、/images/*、*.jpg。上から順(優先順位の順)に評価され、最初に一致したものが使われる。どれにも一致しなければ既定のビヘイビア(*)
  • ビヘイビアごとに設定するもの:オリジン(またはオリジングループ)、Viewer Protocol Policy、許可するHTTPメソッド、キャッシュポリシー・オリジンリクエストポリシー、関連付ける関数、署名付きURL/Cookieの要求
  • 静的ファイルはS3から長めのTTLで、APIはALBからキャッシュなしで、のように1つのドメインで静的・動的コンテンツをまとめて配信できる

キャッシュキーとキャッシュポリシー

キャッシュキーは、エッジがキャッシュを見分けるための値です。同じキャッシュキーのリクエストには同じキャッシュを返します。既定ではドメイン名とURLのパスだけがキャッシュキーで、クエリ文字列・ヘッダー・Cookieは含まれません。

ポリシー決めるもの例
キャッシュポリシーキャッシュキーに含めるクエリ文字列・ヘッダー・Cookieと、TTL(最小・既定・最大)?lang=ja の違いで別のキャッシュにする。マネージドポリシー「CachingOptimized」「CachingDisabled」
オリジンリクエストポリシーキャッシュキーには含めないが、オリジンには転送する値ログ用のヘッダーや、オリジンで使うCookieをオリジンに渡す
レスポンスヘッダーポリシーユーザーへの応答に付けるヘッダーセキュリティヘッダー、CORSヘッダーの追加

キャッシュキーに含める値が多いほどキャッシュが細かく分かれ、キャッシュヒット率が下がります。表示内容を変える値だけをキャッシュキーに含め、オリジンが必要なだけの値はオリジンリクエストポリシーで渡すのが基本です。キャッシュヒット率はCloudWatchのメトリクスやレポートで確認できます。

無効化(Invalidation)

オリジンのファイルを更新しても、エッジのキャッシュはTTLが切れるまで古いままです。すぐに反映したい場合は無効化(Invalidation)で、指定したパスのキャッシュを全エッジから削除します。

  • パスを指定する(例:/index.html、/images/*、全体なら /*)。ワイルドカードを含むパスも1パスと数える
  • 毎月最初の1,000パスまで無料、それ以降はパスごとに課金される
  • 反映には数分かかる

頻繁に更新するファイルは、無効化に頼るよりファイル名にバージョンを付ける(app.v2.js、style.3f9a.css など)方が確実で安くなります。新しい名前のファイルは新しいキャッシュとして扱われるためです。

署名付きURL/署名付きCookie

会員向けの動画や有料コンテンツなど、許可された人だけに配信したいときは、ビヘイビアで「署名付きリクエストを要求」し、署名付きURLか署名付きCookieでアクセスさせます。

方式向いている場面
署名付きURL1つのファイルへのアクセス(ダウンロードリンクなど)。Cookieに対応していないクライアント
署名付きCookie複数のファイルへのアクセス(動画配信の分割ファイル、会員エリア全体など)。URLを変えたくないとき
  • CloudFrontに公開鍵を登録して信頼されたキーグループを作り、アプリが対応する秘密鍵で署名する
  • ポリシーで有効期限を指定する。カスタムポリシーなら開始日時・アクセス元のIP範囲・ワイルドカードでの対象パスも指定できる
  • S3の署名付きURLとは別の仕組み。CloudFront経由で配信し、S3はOACで直接アクセスを防ぐ組み合わせにする

地理的制限

地理的制限を設定すると、国単位でコンテンツへのアクセスを制限できます。許可する国の一覧(許可リスト)か、拒否する国の一覧(ブロックリスト)のどちらかを指定し、制限された国からのアクセスには 403(Forbidden) を返します。配信権利が国ごとに決まっている動画などで使います。

国より細かい条件(特定のIP範囲、国+パスの組み合わせなど)で制御したい場合は、AWS WAFのルール(地理的一致の条件)を使います。

オリジンフェイルオーバー(オリジングループ)

オリジングループにプライマリとセカンダリの2つのオリジンを登録すると、プライマリが失敗したときに自動でセカンダリに切り替えて取得し直します。

  • 切り替える条件:指定したHTTPステータスコード(500・502・503・504・403・404など)や、接続の失敗・タイムアウト
  • 対象はGET・HEAD・OPTIONSのリクエスト
  • S3のクロスリージョンレプリケーションで別リージョンにコピーしたバケットをセカンダリにすると、リージョン障害にも備えられる

CloudFront FunctionsとLambda@Edge

どちらもエッジでコードを動かし、リクエストやレスポンスを加工する機能です。

項目CloudFront FunctionsLambda@Edge
言語JavaScriptNode.js・Python
実行場所エッジロケーションリージョナルエッジキャッシュ
実行できるタイミングビューワーリクエスト・ビューワーレスポンスのみビューワーリクエスト・レスポンス+オリジンリクエスト・レスポンス
実行時間1ミリ秒未満ビューワー側5秒、オリジン側30秒まで
ネットワーク・外部サービスへのアクセス不可可能

主な用途ヘッダーの追加・変更、URLのリダイレクト・書き換え、キャッシュキーの正規化、トークンの簡単な検証外部APIやDBを使う認証、画像の加工、リクエスト内容に応じたオリジンの切り替え

軽くて大量に呼ばれる処理はCloudFront Functions、ネットワークアクセスや長い処理が必要ならLambda@Edgeを選びます。Lambda@Edgeの関数はus-east-1で作成し、CloudFrontが各地に複製します。

オリジンシールド

複数のエッジロケーションからオリジンへのリクエストをまとめ、オリジンへのリクエスト数を減らす機能です。リージョナルエッジキャッシュを1つにまとめるイメージです。

Origin Access Control(OAC)

S3オリジンへアクセスする仕組みで、CloudFront経由でのみS3にアクセスできるようにします(S3への直接アクセスを防ぐ)。

フィールドレベル暗号化

HTTPリクエスト内の特定の項目(クレジットカード番号など)をCloudFrontで暗号化する機能です。

TTL(キャッシュ期限)

  • 静的コンテンツ:誰がアクセスしても同じ内容なので、長時間キャッシュする。
  • 動的コンテンツ:人や時刻によって内容が変わるので、短時間キャッシュする。

HTTPS制御

  • Viewer Protocol Policy:ユーザー ⇔ CloudFront 間
  • Origin Protocol Policy:CloudFront ⇔ オリジン 間

独自ドメインで配信する(代替ドメイン名と証明書)

CloudFrontのディストリビューションには d111111abcdef8.cloudfront.net のようなドメイン名が付きます。www.example.com などの独自ドメインで配信するには、次の手順で設定します。

  1. ACMで独自ドメインの証明書を発行する。CloudFrontで使うACM証明書は us-east-1(バージニア北部)で発行する必要がある。
  2. ディストリビューションの代替ドメイン名(CNAME)に独自ドメインを登録し、その証明書を選択する。
  3. DNSで独自ドメインをディストリビューションに向ける。Route 53ならエイリアスレコードを使う(example.com のようなゾーンの頂点にも設定でき、クエリ料金も無料)。他のDNSではCNAMEレコードを使う(ゾーンの頂点には設定できない)。

API Gatewayのエッジ最適化APIは内部でCloudFrontを使うため、カスタムドメインの証明書は同じくus-east-1で発行します。

3. ユースケース

  • S3の静的Webサイト・画像・動画の高速配信(OACでS3を非公開に)
  • グローバルユーザー向けWebアプリの高速化
  • エッジでのリクエスト加工(Lambda@Edge/CloudFront Functions)

4. 料金の考え方

エッジからユーザーへのデータ転送量と、HTTP/HTTPSリクエスト数で課金されます。オリジン(AWS内)からCloudFrontへの転送は無料です。キャッシュヒット率を上げるとオリジンの負荷とコストを下げられます。

5. 関連サービス

  • Amazon S3:代表的なオリジン(OAC)
  • Elastic Load Balancing:動的コンテンツのオリジン
  • AWS Lambda:Lambda@Edge
  • AWS Certificate Manager:証明書(us-east-1)
  • AWS Global Accelerator:TCP/UDPの経路最適化(キャッシュなし)
  • Amazon API Gateway:エッジ最適化APIで内部的にCloudFrontを利用
  • AWS WAF/AWS Shield:アプリケーション層の攻撃とDDoSへの対策

6. 試験・実務でのポイント

セキュリティ・配信制御

  • S3へのアクセスをCloudFront経由に限定 → OAC。
  • CloudFrontで使うACM証明書はus-east-1。
  • ユーザー側のHTTPS強制 → Viewer Protocol Policy、オリジン側 → Origin Protocol Policy。
  • 機密項目だけを暗号化 → フィールドレベル暗号化。
  • 有料コンテンツの配信 → 1ファイルなら署名付きURL、複数ファイル・URLを変えたくないなら署名付きCookie。
  • 特定の国からのアクセスを拒否 → 地理的制限(403を返す)。

キャッシュ

  • オリジンの負荷を減らしたい → オリジンシールド、TTLを長くする。
  • POST/PUTなどはキャッシュされない(キャッシュはGET/HEAD/OPTIONSのみ)。
  • パスごとにオリジンやキャッシュの設定を変える → ビヘイビア(どれにも一致しなければ既定の *)。
  • キャッシュヒット率が低い → キャッシュポリシーでキャッシュキーに含めるヘッダー・Cookie・クエリ文字列を減らす。オリジンに渡すだけならオリジンリクエストポリシー。
  • 更新したファイルをすぐ反映 → 無効化(月1,000パスまで無料)。頻繁な更新ならファイル名にバージョンを付ける。

可用性・エッジでの処理

  • オリジンの障害時に別のオリジンへ → オリジングループによるオリジンフェイルオーバー。
  • ヘッダー操作やリダイレクトなどの軽い処理 → CloudFront Functions。オリジン側のイベントや外部へのアクセスが必要 → Lambda@Edge。

7. まとめ

  • CloudFrontはエッジでキャッシュして配信を高速化するCDN。
  • OAC・フィールドレベル暗号化・プロトコルポリシーでセキュリティを確保する。
  • 証明書はus-east-1、キャッシュ対象はGET/HEAD/OPTIONS。
