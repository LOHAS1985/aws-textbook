1. 発表の内容

通常の TLS は、クライアントがサーバーの証明書を確かめる一方向の認証です。相互TLS(mTLS)は、サーバーもクライアントに証明書(X.509)の提示を求め、双方が身元を確かめ合います。IoT デバイスや API 間通信、規制の厳しい環境でよく使われます。

これまで NLB で mTLS を使うには、自前の仕組みやサードパーティのプロキシが必要でした。今回、NLB の TLS リスナーがクライアント証明書の検証を行えるようになり、重い認証処理を NLB に任せられます。手順は、信頼する認証局(CA)の証明書をまとめた「トラストストア」を作り、リスナーに付けるだけです。AWS Private CA の CA も使えます。

トラストストアには、信頼しなくなった証明書を止めるための失効リスト(CRL)を加えられます。また、証明書の Common Name、Organizational Unit、SAN の DNS 名や URI(SPIFFE ID など)で、通すクライアントを絞り込めます。

何がうれしいか
バックエンドのアプリに証明書の処理を書かずに、クライアントを認証できます。
試験・実務への影響
「クライアント側も証明書で認証したい」という要件では mTLS が候補です。ALB に続いて NLB でも使えるようになったので、プロトコルに合わせたロードバランサーの選び方と合わせて確認しましょう。
