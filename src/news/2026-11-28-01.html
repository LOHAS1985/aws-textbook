1. 発表の内容

AWS Network Firewall は、VPC を出入りする通信を検査して許可・拒否するマネージドサービスです。これまでルールの送信元・送信先は IP アドレスで書くのが基本でした。ところが、Lambda 関数や Auto Scaling のインスタンスのように増減や入れ替わりが激しいワークロードでは、IP アドレスの一覧を更新する前に新しいリソースが通信を始めてしまい、ルールが追いつかないことがありました。

今回加わったコンテキスト対応ルールでは、送信元・送信先を VPC、サブネット、セキュリティグループ、Transit Gateway アタッチメントといったリソースの単位で指定できます。例えば「本番用セキュリティグループが付いたリソースから外部への SSH(22番ポート)を拒否する」と書けば、あとからそのセキュリティグループを付けた新しいリソースにも自動で適用されます。

仕組みは、制御用の流れと通信の流れの2つで成り立っています。まず「コンテキストストア」(通信しうる AWS リソースの一覧表。AWS Network Manager で作ります)が、どんなリソースがあるかをファイアウォールに伝えます。次に Transit Gateway が、通過する各パケットに送信元の情報(VPC・サブネット・アタッチメント・セキュリティグループの ID)の目印を付けます。ファイアウォールはこの目印を読み取り、ルールで使う「コンテキストセット」(リソースをまとめた名前付きの変数)と照合します。

利用には、Transit Gateway にアタッチしたファイアウォールが必要です。Transit Gateway を AWS RAM で共有すれば、1つのポリシーで複数のアカウントのリソースを扱えます。送信元のコンテキストは全プロトコルで使え、送信先のコンテキストでの照合は TCP のルールで使えます。ファイアウォールのアラートログとフローログには、一致したリソースのコンテキストも記録されます。

何がうれしいか
スケールアウトや置き換えが頻繁なワークロードでも、IP アドレスの一覧を保守せずに、通信の許可・拒否を保てます。
試験・実務への影響
セキュリティグループはインスタンス単位の許可リスト、Network Firewall は VPC 境界での集中的な検査、という役割の違いを押さえましょう。複数アカウントの通信を Transit Gateway に集めて検査する構成では、リソース単位のルールが使えると覚えておくと選択肢の判断に役立ちます。
