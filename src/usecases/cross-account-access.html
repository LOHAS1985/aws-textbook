1. やりたいこと

  • アカウントAのロールから、アカウントBのS3バケットを操作したい。
  • アカウントBにIAMユーザーを作ってアクセスキーを渡すことはしたくない。

2. 構成を組み立てる

① 別アカウントのロールを引き受け、一時的な認証情報を発行するものは?

  • AWS STS(AssumeRole)有効期限付きのアクセスキー・シークレットキー・セッショントークンを発行します(IAMロールと一時的な認証情報)。
  • AWS KMS暗号化のキーを管理するサービスで、認証情報は発行しません。
  • AWS Secrets Manager保存した秘密情報を渡せますが、長期のアクセスキーを渡すのと同じになります。

② 「アカウントAがこのロールを引き受けてよい」と決めるのは?

  • アカウントBのロールの信頼ポリシー誰がロールを引き受けられるかを Principal で決めます。
  • アカウントBのロールの権限ポリシー引き受けたあとに何ができるかを決めるもので、誰が引き受けられるかではありません。
  • アカウントBのSCP権限の上限を決めるもので、引き受けを許可するものではありません。

③ AssumeRoleで AccessDenied になるとき、確認するものは?

  • アカウントA側の sts:AssumeRole の許可と、B側の信頼ポリシーの両方別アカウントへのアクセスは、両方の側で許可されている必要があります(IAMポリシーと評価ロジック)。
  • アカウントBのS3バケットのバージョニングロールの引き受けには関係ありません。
  • アカウントAのルートユーザーのMFAロールの引き受けの判定には関係ありません。

3. 構成図

アカウントAがSTSでアカウントBのロールを引き受け、ロールの信頼ポリシーで許可されていれば一時的な認証情報が返ります。その認証情報で、ロールの権限ポリシーの範囲でS3を操作します。CloudTrailには AssumedRole として記録されます。

4. 使うサービスと役割

  • AWS STS:有効期限付きの一時認証情報(アクセスキー、シークレットキー、セッショントークン)を発行する
  • AWS IAM:アカウントAのIDベースポリシー、アカウントBのロール(信頼ポリシー・権限ポリシー)を定義する
  • Amazon S3などのアクセス先リソース:必要に応じてリソース側のポリシー(バケットポリシーなど)も確認される
  • AWS CloudTrail:ロールを引き受けた操作が AssumedRole として記録される

5. 構築の流れ

手順誰が何をするか確認・使用されるポリシー結果
①アカウントAのIAMユーザー/ロールSTSに sts:AssumeRole を呼び出す(BのロールのARNを指定)AのIDベースポリシー(Bのロールへの sts:AssumeRole が許可されているか)引き受けのリクエストがSTSに届く
②AWS STSBのロールの信頼ポリシーを確認するBのロールの信頼ポリシー(Principal にAが含まれるか、ExternalIdなどの条件を満たすか)引き受けの可否が判定される
③AWS STSAのプリンシパルに一時認証情報を返す(有効期限はデフォルト1時間)―アクセスキー、シークレットキー、セッショントークンを取得
④アカウントAのIAMユーザー/ロール一時認証情報を使ってBのリソースを操作するBのロールの権限ポリシー(必要に応じてリソース側のポリシーも)ロールの権限の範囲で操作できる。CloudTrailには AssumedRole として記録される

6. ポイント・注意点

ポリシーひとことで答える問い
IDベースポリシー「自分が何をできるか」このユーザー/ロールは、どのリソースに何をしてよいか
権限ポリシー「ロールになった後に何ができるか」このロールを引き受けた人は、何をしてよいか
信頼ポリシー「誰がこのロールになれるか」このロールを引き受けてよいのは誰か
  • 信頼ポリシーは、ロールを引き受けてよい相手の一覧。例:アカウントAはOK、アカウントBのIAMユーザー tanaka はNG。
  • 権限ポリシーは、ロールで何ができるか。例:特定のS3バケットに読み書きできる。
  • AssumeRoleできないときは、Aの IDベースポリシーとBのロールの信頼ポリシーの両方を確認する。
  • アクセスキーを渡さずに済み、認証情報は自動で期限切れになるため安全。
