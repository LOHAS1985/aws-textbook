1. やりたいこと

EC2上のアプリやDBで、ディスクの読み書きが遅いという問い合わせがある。原因がEBSボリュームの性能不足なのか、インスタンス側の上限なのかを切り分け、サービスを止めずに性能を上げたい。逆に、性能を持て余しているリソースは小さくして費用を下げたい。

2. 構成図

3. 使うサービスと役割

  • Amazon CloudWatch:VolumeQueueLength・VolumeReadOps/VolumeWriteOps・インスタンスのEBS関連の指標の確認とアラーム
  • Amazon EBS:Elastic Volumesでボリュームのタイプ・IOPS・スループット・サイズをオンラインで変更
  • Amazon EC2:インスタンスタイプの変更(EBS最適化・EBS帯域の大きいタイプ)
  • AWS Compute Optimizer:EC2・EBSの過不足の推奨

4. 構築の流れ

  1. CloudWatchで、ボリュームの読み書き回数(IOPS)・スループット・VolumeQueueLength を確認する。IOPSやスループットがボリュームの上限に張り付き、キューが溜まっていればボリューム側が原因
  2. ボリュームに余裕があるのに遅い場合は、インスタンスの EBSIOBalance%・EBSByteBalance% などで、インスタンス側のEBS帯域の上限を確認する
  3. ボリューム側:Elastic Volumesで gp2 → gp3 に変える、gp3のIOPS・スループットを追加する、さらに高い性能が必要なら io2 にする
  4. インスタンス側:EBS帯域の大きいインスタンスタイプに変更する(停止・起動が必要)
  5. Compute Optimizerの推奨で、過剰なリソースは小さくし、変更後もアラームで監視を続ける

5. ポイント・注意点

  • I/Oが詰まっている → VolumeQueueLength。ボリュームの性能を止めずに上げる → Elastic Volumes。
  • gp3はサイズに関係なく3,000IOPS・125MiB/sが付き、IOPS・スループットを個別に追加できる。gp2はサイズに比例するので、性能のために容量を増やす必要があった。
  • 同じボリュームの再変更は6時間空ける。サイズを増やしたら、OS側でパーティションとファイルシステムを拡張する。
  • ボリュームを速くしても、インスタンスのEBS帯域の上限で頭打ちになることがある。
  • スナップショットから復元した直後のボリュームは、初回アクセスが遅い。すぐに最大性能が必要なら高速スナップショット復元(FSR)を使う。
