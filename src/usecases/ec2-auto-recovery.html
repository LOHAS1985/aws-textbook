1. やりたいこと

  • EC2が障害で応答しなくなったら、人手を介さず自動で復旧させたい。
  • 物理ホストの障害と、OSの中の問題とで、対処を分けたい。

2. 構成を組み立てる

① システムステータスチェックの失敗(ホストの障害)への対処は?

  • アラームの復旧アクションインスタンスを別の物理ホストに移して起動し直します。インスタンスID・プライベートIP・EBSのデータは引き継がれます。
  • アラームの再起動アクション再起動では同じホストのままなので、ホストの障害は解消しません。
  • アラームの終了アクションインスタンスが削除されるだけで、復旧になりません。

② インスタンスステータスチェックの失敗(OSの問題)に対処する手順を実行するものは?

  • Systems Manager AutomationAWS-RestartEC2Instance などのランブックで、再起動などの手順を自動で実行します(イベント駆動の自動修復)。
  • Systems Manager Patch Managerパッチを適用する機能で、障害の対処の手順を実行するものではありません。
  • AWS Backupバックアップの取得と保管のサービスです。

③ 復旧アクションで失われるものは?

  • インスタンスストアのデータインスタンスストアは物理ホストに付いたディスクなので、別のホストに移ると消えます。残したいデータはEBSに置きます。
  • EBSボリュームのデータEBSはホストとは別のストレージなので、そのまま引き継がれます。
  • プライベートIPアドレス復旧アクションでは、プライベートIPアドレスもインスタンスIDも変わりません。

3. 構成図

システムステータスチェックの失敗はAWS側(ホスト)の問題なので、アラームの復旧アクションで別のホストに移します。インスタンスステータスチェックの失敗はOS側の問題なので、EventBridgeからSSM Automationで再起動などの手順を実行します。

4. 使うサービスと役割

  • Amazon EC2:ステータスチェックのメトリクス(StatusCheckFailed)
  • Amazon CloudWatch:アラームで障害を検知し、EC2のアクション(復旧・再起動)を実行する
  • Amazon EventBridge:アラームの状態変化をきっかけに自動処理を起動する
  • AWS Systems Manager:Automationランブック(例:AWS-RestartEC2Instance)で復旧手順を実行する
  • Amazon SNS:復旧したことの通知

5. 構築の流れ

  1. StatusCheckFailed_System にアラームを作成し、アクションに「インスタンスの復旧」を設定する
  2. StatusCheckFailed_Instance にアラームを作成し、EventBridgeルールでアラームの状態変化を検知する
  3. EventBridgeのターゲットにSSM Automation(再起動のランブック)を指定する
  4. SNSで運用担当者に通知する

6. ポイント・注意点

  • システムステータスチェックの失敗はAWS側(ホスト)の問題 → 復旧アクション(停止・起動でも別ホストへ移る)。
  • インスタンスステータスチェックの失敗はOS・設定の問題 → 再起動や設定の修正が必要。
  • 復旧アクションではインスタンスID・プライベートIP・EBSのデータは引き継がれるが、インスタンスストアのデータは失われる。
  • 手順の多い復旧処理は、SSM Automationでランブック化しておく。
