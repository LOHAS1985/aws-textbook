1. やりたいこと

  • EC2が乗っ取られたら、すぐにネットワークから切り離したい。
  • 調査のため、インスタンスを削除せずにディスクの状態を保存したい。
  • 夜間でも自動で対応し、担当者にも知らせたい。

2. 構成を組み立てる

① 不審な通信やマイニングなどの脅威を検出するものは?

  • Amazon GuardDutyVPCフローログ・DNSのログ・CloudTrailなどを分析して、脅威を検出します。リージョンごとに有効にします。
  • Amazon Inspectorソフトウェアの脆弱性を見つけるもので、実際の攻撃の兆候は検出しません(セキュリティ検出のサービスの選び方)。
  • Amazon MacieS3の機密データを見つけるサービスです。

② 調査のためにディスクの状態を残すものは?

  • EBSのスナップショットその時点のボリュームの状態を保存し、あとで別の環境で調べられます。
  • インスタンスの終了証拠が消えてしまいます。終了保護をかけておきます。
  • インスタンスの再起動メモリの状態などの証拠が失われ、隔離にもなりません。

③ Auto Scalingグループのインスタンスを隔離するときの注意は?

  • 先にグループから切り離す(デタッチする)グループに入ったままだと、ヘルスチェックで置き換えられて証拠が消えます。
  • グループの希望容量を0にする全台が終了し、証拠も消えます。
  • 特に注意はいらない自動で置き換えられるおそれがあります。

3. 構成図

GuardDutyの検出結果をEventBridgeで受け、自動処理で隔離用のセキュリティグループに付け替え、スナップショットで証拠を残します。追跡中の通信はセキュリティグループを替えても切れないことがあるので、ネットワークACLでの遮断も併用します(ネットワークACLとセキュリティグループ)。

4. 使うサービスと役割

  • Amazon GuardDuty:不審な通信・マイニング・認証情報の悪用などの検出
  • Amazon EventBridge:検出結果(GuardDuty Finding)を種類・重要度で絞り込んで自動処理を起動
  • AWS Systems Manager/AWS Lambda:隔離・スナップショット・タグ付けの処理
  • Amazon EC2:隔離用セキュリティグループ、終了保護、EBSスナップショット
  • AWS Security Hub:検出結果の集約と対応状況の管理

5. 構築の流れ

  1. 組織の全アカウント・全リージョンでGuardDutyを有効にする(委任管理者を使う)
  2. インバウンド・アウトバウンドのルールが何もない隔離用セキュリティグループを用意する
  3. EventBridgeで、GuardDutyの検出結果のうち重要度が高く、EC2が対象のものに一致するルールを作る
  4. ターゲットの自動処理で、インスタンスの終了保護を有効にし、EBSのスナップショットを取り、セキュリティグループを隔離用に付け替える。Auto Scalingグループからは切り離す
  5. SNSで担当者に通知し、隔離したインスタンスを調査する。漏えいした可能性のある認証情報(IAMロールの一時認証情報など)は無効化する

6. ポイント・注意点

  • GuardDutyの検出結果への自動対応 → EventBridgeルール+Lambda/SSM Automation。
  • 調査のため、すぐに終了しない。終了保護をかけ、スナップショットで証拠を残す。
  • セキュリティグループを付け替えても、既に確立している通信は追跡されていると切れないことがある。ネットワークACLでの遮断も併用する。
  • Auto Scalingグループに入ったままだと、ヘルスチェックで置き換えられて証拠が消えるので、先にグループから切り離す。
  • GuardDutyはリージョンごとに有効化が必要。使っていないリージョンも有効にしておく。
