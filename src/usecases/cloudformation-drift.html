1. やりたいこと

  • CloudFormationで作った環境を、コンソールで手作業で変えた人がいる。
  • テンプレートと実際の設定のずれを、定期的に自動で見つけて知らせたい。

2. 構成を組み立てる

① スタックのドリフトを定期的に自動で確認するものは?

  • AWS Configのマネージドルールcloudformation-stack-drift-detection-check が定期的にドリフト検出を実行し、ずれがあれば非準拠にします。
  • AWS CloudTrail誰が変えたかは記録しますが、テンプレートとのずれは判定しません。
  • 変更セットこれからの更新の影響を見るもので、手作業の変更は見つけません。

② 非準拠になったことを受けて、通知につなぐものは?

  • Amazon EventBridgeConfigの準拠状況の変化のイベントをルールで拾い、SNSなどに送ります(イベント駆動の自動修復)。
  • Amazon SQSメッセージをためるだけで、人への通知にはなりません。
  • Amazon AthenaS3のデータをSQLで検索するもので、通知はしません。

③ ドリフトが見つかったあとの対応は?

  • テンプレートか実際のリソースのどちらかに合わせるドリフト検出は見つけるだけで、自動では直しません。
  • 何もしなくても次の更新で自動的に直るずれたままだと、次の更新が失敗したり、手作業の変更が消えたりします。
  • スタックを削除して作り直すしかないデータのあるリソースまで消えるおそれがあり、必要ありません。

3. 構成図

Configのマネージドルールでドリフトを定期的に確認し、EventBridgeからSNSで知らせます。そもそも本番でコンソールの変更ができないよう、IAMやSCPで権限を絞るのが根本的な対策です。CloudFormationの外で作ったリソースは、リソースのインポートでスタックに取り込めます。

4. 使うサービスと役割

  • AWS CloudFormation:ドリフト検出(スタック・StackSets)、リソースのインポート
  • AWS Config:マネージドルール cloudformation-stack-drift-detection-check による定期的な確認
  • Amazon EventBridge/Amazon SNS:非準拠の通知
  • AWS IAM/AWS Organizations:本番環境のコンソールでの変更そのものを制限する

5. 構築の流れ

  1. CloudFormationのコンソールまたはCLI(detect-stack-drift)でドリフト検出を実行し、DRIFTED のリソースと、期待値・実際の値の差分を確認する
  2. Configのルール cloudformation-stack-drift-detection-check を有効にし、ドリフト検出を定期的に実行させる
  3. 非準拠になったらEventBridge経由でSNSに通知する
  4. ずれを解消する:手作業の変更を残すべきならテンプレートを修正して更新する。不要な変更なら、リソースの設定をテンプレートどおりに戻す
  5. 再発を防ぐため、本番環境ではIAMやSCPで手作業の変更を制限し、変更はテンプレート経由で行う運用にする

6. ポイント・注意点

  • テンプレートと実際の設定のずれを見つける → ドリフト検出。定期的に自動で → Configルール。
  • ドリフト検出は見つけるだけで、自動では直さない。テンプレートか実際のリソースのどちらかに合わせる。
  • テンプレートで明示的に指定したプロパティだけが比較の対象。ドリフト検出に対応していないリソースタイプもある。
  • CloudFormationの外で作ったリソースをスタックの管理下に入れる → リソースのインポート。
  • 複数アカウント・リージョンに展開したスタックは、StackSetsのドリフト検出でまとめて確認できる。
