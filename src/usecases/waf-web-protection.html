1. やりたいこと

公開しているWebアプリに、SQLインジェクションを狙ったリクエストや、ログイン画面への大量の試行が来ている。アプリを改修せずに前段で攻撃を止め、DDoSにも備えたい。どのリクエストをブロックしたかの記録も残したい。

2. 構成図

3. 使うサービスと役割

  • AWS WAF:マネージドルール(SQLインジェクション・既知の悪い入力・IP評価リスト)、レートベースルール、ジオマッチ、ログ
  • AWS Shield:Standard(自動)によるL3/L4のDDoS対策、必要ならAdvanced
  • Amazon CloudFront:エッジでの受付とキャッシュ
  • Elastic Load Balancing:オリジンのALB
  • Amazon CloudWatch:ルールごとのブロック件数の監視

4. 構築の流れ

  1. CloudFront用のWeb ACLを作る(CloudFront用はus-east-1で作成)
  2. AWSマネージドルール(コアルールセット・SQLデータベース・既知の悪い入力・Amazon IP評価リスト)を追加する
  3. ログインのパスに、IPごとのレートベースルールを追加する。必要に応じて国のジオマッチやBot Controlを加える
  4. まずは新しいルールを Count で動かし、正常な通信を誤ってブロックしていないかログで確かめてから Block にする
  5. ALBのセキュリティグループで、CloudFrontのマネージドプレフィックスリストからの通信だけを許可する(またはCloudFrontのVPCオリジンを使う)
  6. WAFのログを有効にし(ロググループ名は aws-waf-logs- で始める)、ブロック件数にアラームを設定する

5. ポイント・注意点

  • アプリ層の攻撃(SQLi・XSS)→ WAF。同じIPからの大量アクセス → レートベースルール。
  • CloudFrontのWeb ACLはus-east-1で作る。ALB用はALBと同じリージョン。
  • WAFは NLB・EC2に直接付けられない。CloudFront・ALB・API Gatewayなどの前段に付ける。
  • オリジンに直接アクセスされるとWAFを迂回されるので、ALBへの経路をCloudFrontからだけに絞る。
  • 大規模なDDoSへの24時間の支援や費用の保護が必要 → Shield Advanced。複数アカウントへ同じルールを展開 → Firewall Manager。
