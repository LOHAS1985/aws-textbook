1. やりたいこと

  • ALB+Auto Scalingで、3つのAZにまたがるWebアプリを動かしている。
  • あるAZだけで、ヘルスチェックは通るのにエラーや遅延が増える(部分的な障害)。
  • そのAZを一時的に切り離し、残りのAZで処理を続けたい。

2. 構成を組み立てる

① ALBが特定のAZに通信を送らないようにするものは?

  • ARCのゾーンシフトApplication Recovery Controllerの機能で、指定したAZへの通信を一時的に止めます。期限が切れると元に戻ります。
  • ALBのヘルスチェックの調整部分的な障害はヘルスチェックを通ってしまうため、確実に切り離せません。
  • Route 53のフェイルオーバーリージョンやエンドポイントの単位の切り替えで、ALBの中の特定のAZを外すものではありません。

② 切り離した後も処理を続けるための備えは?

  • 残りのAZに、あらかじめ容量の余裕を持たせておく障害時にスケールアウトが間に合うとは限らないので、2つのAZだけでも負荷を受けられるようにしておきます。
  • AZ-aのインスタンスを大きくする切り離すAZを強くしても意味がありません。
  • Auto Scalingグループを1つのAZにまとめるそのAZの障害で全体が止まります。

③ AWSが障害を検知して、自動でAZを切り離すようにするには?

  • ゾーンオートシフトを有効にするAWSがAZの障害を検知すると、自動でゾーンシフトを行います。
  • CloudWatchアラームでインスタンスを終了するAuto Scalingが同じAZに入れ替えを起動するだけで、通信は止まりません。
  • Multi-AZのRDSを使うDBの障害対策で、ALBの通信の切り離しではありません。

3. 構成図

ヘルスチェックで分からない部分的な障害は、ARCのゾーンシフトで人の判断で切り離し、AWSに任せるならゾーンオートシフトを有効にします。リージョン全体の障害への備えは、マルチリージョンの構成で行います(DR戦略)。

4. 使うサービスと役割

  • Amazon Application Recovery Controller(ARC):ゾーンシフト(手動・一時的)、ゾーンオートシフト(AWSが自動で実行)
  • Elastic Load Balancing:複数AZへの振り分けとヘルスチェック
  • Amazon EC2 Auto Scaling:複数AZへのインスタンスの配置と台数の維持
  • Amazon CloudWatch:AZ別のエラー率・レイテンシーの監視

5. 構築の流れ

  1. アプリを3つ以上のAZに配置し、1つのAZが使えなくても残りで処理できる台数(静的安定性)を確保する
  2. CloudWatchで、ALBのメトリクスをAZ別に見て、特定のAZだけエラーや遅延が多くないかを監視する
  3. ALBとAuto ScalingグループをARCのゾーンシフトの対象として有効にする
  4. 特定のAZの問題が分かったら、そのAZへのゾーンシフトを開始する(有効期限を指定。最長3日で延長可)。問題が解消したら終了する
  5. AWS側の障害に自動で対応させたい場合はゾーンオートシフトを有効にし、定期的に行われる練習の実行で問題がないことを確認する

6. ポイント・注意点

  • 1つのAZの障害から通信を一時的に移す → ゾーンシフト。AWSの判断で自動で → ゾーンオートシフト。
  • ゾーンシフトは一時的な措置。期限が切れるか終了すると元に戻る。
  • 切り離した後も処理できるよう、残りのAZに事前に容量の余裕を持たせておく(障害時にスケールアウトが間に合うとは限らない)。
  • ヘルスチェックで分からない部分的な障害も、ゾーンシフトなら人の判断で切り離せる。
  • リージョン全体の障害への備えは、マルチリージョン構成とRoute 53・ARCのリージョンスイッチで行う。
