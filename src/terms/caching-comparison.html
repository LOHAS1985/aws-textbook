1. 詳しい説明

キャッシュは、一度取り出した結果を近くに保存しておき、次からはそれを返す仕組みです。後ろのサーバーやDBに届くリクエストが減るので、応答が速くなり、負荷と費用も下がります。AWSでは、リクエストの通り道のどこに置くかによって使うサービスが変わります。利用者に近い場所でキャッシュするほど、後ろの層すべての負荷が減ります。

比較表

サービス置く場所キャッシュするものアプリの変更
CloudFront世界中のエッジロケーションWebページ・画像・動画・APIの応答不要(DNSの向き先を変える)
API GatewayのキャッシュREST APIのステージAPIの応答(TTLは既定300秒、最大3600秒)不要(ステージで有効化)

DynamoDB Accelerator(DAX)VPCの中(DynamoDBの手前)DynamoDBの読み取り結果ほぼ不要(DAXのクライアントに替える)

キャッシュの更新の仕方

キャッシュの中身は、元のデータが変わると古くなります。ElastiCacheでは、主に次の2つの方式と、有効期限(TTL)を組み合わせます。

  • 遅延読み込み(Lazy Loading):キャッシュになければDBから読んでキャッシュに入れる。必要なデータだけが入るが、初回は遅く、古いデータが残ることがある。
  • 書き込みスルー(Write-Through):DBに書くときにキャッシュも更新する。データは新しく保たれるが、読まれないデータもキャッシュに入る。
  • TTL:期限を過ぎたデータを自動で消す。どちらの方式でも、古いデータが残り続けないように設定する。

CloudFrontでは、オリジンの内容を更新したらすぐに反映させたいとき、無効化(Invalidation)でエッジのキャッシュを消します。ファイル名にバージョンを付けて(例: app.v2.js)、別のファイルとして配信する方法もあります。

キャッシュ以外で読み取りの負荷を下げる

次の方法はキャッシュと混同しやすいですが、仕組みが異なります。

方法仕組みキャッシュとの違い
RDS・AuroraのリードレプリカDBのコピーを作り、読み取りを分散するSQLをそのまま使える。データは非同期で複製されるため、少し遅れることがある
Amazon MemoryDBValkey・Redis互換の、データを失わないインメモリDBキャッシュではなく、データの保存先(プライマリDB)として使う
RDS ProxyDBへの接続をプールして使い回す結果は保存しない。接続数が多すぎる問題(Lambdaからの大量接続など)を解決する

選び方のポイント

  • 世界中の利用者への静的コンテンツの配信を速くしたい → CloudFront。
  • 同じ結果を返すAPIへのリクエストを減らしたい → API Gatewayのキャッシュ(REST APIのみ)。
  • RDSへの同じ読み取りが多く、DBのCPUが高い → ElastiCache(運用シナリオ「キャッシュでDBの読み取り負荷を下げる」)。
  • DynamoDBの読み取りをマイクロ秒にしたい・アプリをほとんど変えたくない → DAX。
  • DAXがキャッシュするのは結果整合性の読み取りだけ。強い整合性の読み取りは、DAXを通ってもDynamoDBから読む。
  • 複数のEC2でログイン状態(セッション)を共有したい → ElastiCache(またはDynamoDB)。
  • Valkey・Redis互換で、データを失えないプライマリDBにしたい → キャッシュではなくMemoryDB。
  • キャッシュがよく効いているかを確かめる → CloudFrontはキャッシュヒット率、ElastiCacheは CacheHits・CacheMisses・Evictions(容量不足で追い出された数)を見る。
  • CloudFrontのヒット率が低い → キャッシュキーに含めるヘッダー・Cookie・クエリ文字列を必要なものだけに絞る。
