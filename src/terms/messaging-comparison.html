1. 詳しい説明

システムの部品どうしを直接呼び出さず、メッセージ(イベント)を間に挟んでつなぐと、片方が遅くなったり止まったりしても、もう片方が影響を受けにくくなります(疎結合)。AWSにはそのためのサービスが複数あり、違いは「受け手にどう届けるか」と「データを残しておくか」です。

組み合わせて使う

代表的なのは、SNSとSQSを組み合わせるファンアウトです。SNSトピックに複数のSQSキューを購読させると、1つのメッセージが各キューに複製されます。受け手ごとにキューがあるので、どれかの処理が止まっても、メッセージはそのキューにたまって失われません。

AWSサービスのイベント(EC2の状態変化、AWS Healthの通知など)を受けて処理するときは、EventBridgeのルールでSQSに送り、Lambdaがキューから処理する形もよく使われます。急に大量のイベントが来ても、キューがためてくれるのでLambdaの同時実行数をあふれさせません。

選び方のポイント

  • 処理が追いつかないときにためておき、バックエンドを守りたい → SQS。
  • 1つの出来事を、メール・SMS・複数のシステムに同時に知らせたい → SNS(システム向けはSNS+SQSのファンアウト)。
  • AWSサービスやSaaSのイベントを、内容の条件で振り分けたい → EventBridge。決まった時刻に処理を動かすのもEventBridge(Scheduler)。
  • クリックストリームやログなど大量のデータを順序どおりに、複数の処理で読んだり読み直したりしたい → Kinesis Data Streams。
  • 集めたデータをS3などへ保存するのが目的 → Data Firehose。
  • 順番どおりに1回だけ処理したい → SQSのFIFOキュー(SNSならFIFOトピック)。
  • 処理に何度も失敗するメッセージを退避したい → デッドレターキュー(DLQ)。SQS・SNS・EventBridgeのどれでも設定できる。
  • 複数の処理の順番・分岐・待ち合わせを管理したい → メッセージングではなくStep Functions。
  • オンプレミスのActiveMQやRabbitMQを、コードをあまり変えずに移したい → Amazon MQ。

SQSを使った構成例は、運用シナリオ「キューで処理を分離し、急増や障害に強くする」で説明しています。

2. 関連する用語

  • 高可用性とスケーリング:疎結合にすると、部品ごとにスケールできる
  • サーキットブレーカー:障害を広げないための設計パターン
  • キャッシュの選び方:読み取りの負荷を下げる、もう1つの方法

3. 関連サービス

  • Amazon SQS:メッセージキュー
  • Amazon SNS:Pub/Sub型の通知
  • Amazon EventBridge:イベントバスとスケジューラー
  • Amazon Kinesis:ストリーミングデータの収集・処理
  • Amazon Data Firehose:ストリーミングデータの配送
  • AWS Lambda:メッセージを受けて処理する代表的な受け手
  • AWS Step Functions:処理の流れを管理するワークフロー
