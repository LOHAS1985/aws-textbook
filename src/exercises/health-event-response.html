1. 要件

  • EC2のリタイア予定やサービスの障害など、AWS側の情報をすぐに担当者へ知らせたい。
  • リタイア予定のインスタンスは、自動で別のホストに移したい。
  • 組織の全アカウント分をまとめて受け取りたい。

2. 構成を組み立てる

① 自分のアカウントに影響するAWS側のイベントを出すものは?

  • AWS Health予定メンテナンス・障害・アカウントへの通知を、影響するリソースとあわせてイベントとして出します。
  • AWS CloudTrail利用者が行ったAPIの操作の記録で、AWS側のメンテナンスの情報は出しません。
  • AWS Trusted Advisorベストプラクティスに沿っているかのチェックで、メンテナンスや障害の通知ではありません。

② イベントをサービスや種類で絞り込み、通知や処理に振り分けるものは?

  • Amazon EventBridgeのルールaws.health のイベントをイベントパターンで絞り、SNSやAutomationに渡します。どのサポートプランでも使えます。
  • Amazon SQSメッセージをためるキューで、イベントの内容で振り分ける機能はありません。
  • CloudWatchアラームメトリクスのしきい値で動くもので、Healthのイベントを受け取るものではありません。

③ リタイア予定のEBS-backedのEC2を別のホストに移す操作は?

  • 停止してから起動する停止して起動すると、別の物理ホストで起動します。インスタンスストアのデータは消えます。
  • 再起動する再起動では同じホストのままなので、リタイアの対処になりません。
  • スナップショットを取るデータの保護にはなりますが、インスタンスは同じホストで動き続けます。

④ 組織の全アカウントのイベントをまとめて見るには?

  • AWS Healthの組織ビューを有効にするOrganizationsの管理アカウント(または委任管理者)で、全アカウントのHealthイベントを集約できます。
  • 各アカウントのコンソールに順にサインインして確認する手間がかかり、見落としも起きます。
  • CloudTrailの組織の証跡を作るAPIの操作の記録が集まるだけで、Healthのイベントは集まりません。

3. 解説

解説を見る(答え合わせのあとに読む)

AWS HealthのイベントはEventBridgeに送られるので、ルールで種類を絞ってSNSで通知し、リタイア予定のインスタンスはSSM Automationで停止・起動して別のホストに移します。Health API を使う場合は、上位のサポートプランが必要です。
