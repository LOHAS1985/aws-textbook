1. 要件

  • EC2上のDBのディスクの読み書きが遅い。原因がEBSボリュームかインスタンスかを切り分けたい。
  • サービスを止めずに性能を上げたい。
  • 性能を持て余しているリソースは小さくして、費用を下げたい。

2. 構成を組み立てる

① アタッチしたまま、ボリュームのタイプやIOPSを変える機能は?

  • Elastic Volumesサイズ・タイプ・IOPS・スループットを、インスタンスを止めずに変更できます。gp2からgp3への変更もこれで行います。
  • スナップショットから作り直す新しいボリュームに付け替えるために停止が必要で、要件に合いません。
  • マルチアタッチ1つのボリュームを複数のインスタンスに付ける機能で、性能を上げるものではありません。

② EC2・EBSの過不足を分析し、適切なサイズを推奨するものは?

  • AWS Compute Optimizer使用状況のメトリクスから、大きすぎる・小さすぎるリソースと推奨のタイプを示します。
  • AWS Cost Explorer費用の内訳を見るもので、性能から見たサイズの推奨は出しません。
  • Amazon Inspector脆弱性を見つけるサービスです。

③ I/Oが詰まっていることを示すEBSのメトリクスは?

  • VolumeQueueLength処理待ちの読み書きの数です。高いままなら、ボリュームの性能が足りていません(IOPS・スループット・レイテンシー)。
  • CPUUtilizationEC2のCPUの使用率で、ディスクの詰まりは分かりません。
  • StatusCheckFailedインスタンスやホストの障害を示すもので、性能の指標ではありません。

3. 解説

解説を見る(答え合わせのあとに読む)

CloudWatchのメトリクスで、ボトルネックがボリュームかインスタンスかを切り分けます。ボリューム側ならElastic Volumesでgp3のIOPSを足し、インスタンス側ならEBS帯域の大きいタイプに変えます。サイズを増やしたら、OS側でファイルシステムの拡張も必要です。
