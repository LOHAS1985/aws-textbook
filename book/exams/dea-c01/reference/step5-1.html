AWS IAM

AWSの認証・認可を管理するサービス

1. サービス概要#

AWS IAM(Identity and Access Management)は、AWSの認証・認可を管理するサービスです。

  • 認証:ユーザーが「誰か」を確認する
  • 認可:ユーザーが「何をしてよいか」を決める

2. 主な機能・特徴#

用語#

  • ルートユーザー:アカウント作成時に作られる、全権限を持つユーザー。日常の運用での使用は非推奨。
  • IAMユーザー・グループ:日常業務で必要な権限はポリシーで付与し、一時的に必要な権限はロールを使う権限を付与する。
  • IAMロール:ポリシーを持たせて特定の権限を一時的に付与する仕組み。信頼ポリシー(誰が引き受けられるか)と権限ポリシー(何ができるか)の両方の設定が必要。
  • IAMポリシー:アイデンティティベースの権限設定。IAMユーザー・グループ・ロールに設定してリソースへのアクセスを制御する。
    ※リソースベースのポリシー:リソース側から見てアクセスを制御する(S3バケットポリシーなど)。

Organizationsで複数のアカウントを使う場合は、各アカウントにIAMユーザーを作るのではなく、IAM Identity Centerでユーザーを一元管理し、パーミッションセットで各アカウントの権限を割り当てるのが推奨です。

ポリシーJSONの書き方#

IAMポリシーはJSONで書き、1つ以上のステートメント(Statement)からなります。次の例は「my-bucket の読み書きを許可し、ただしMFAで認証していないときの削除は拒否する」ポリシーです。

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::my-bucket/*"
    },
    {
      "Effect": "Deny",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
      }
    }
  ]
}
要素意味
Versionポリシー言語のバージョン。常に "2012-10-17" を書く
EffectAllow(許可)か Deny(拒否)
Action対象の操作。サービス:アクション の形式で、s3:Get* のようにワイルドカードも使える
Resource対象のリソースをARNで指定する
Condition適用する条件(送信元IP、MFAの有無、タグ、リージョンなど)。省略すると常に適用
Principal誰に対するポリシーか。リソースベースのポリシー(バケットポリシーや信頼ポリシー)でだけ書く

要素の詳しい書き方と例は用語ページ「IAMポリシーと評価ロジック」を参照してください。

評価ロジック(明示的なDenyが最優先)#

1つのリクエストに複数のポリシーが関係するとき、AWSは次の順番で判断します。

  1. どこかに明示的なDenyがあれば → 拒否(ほかにAllowがあっても覆らない)
  2. Denyがなく、明示的なAllowがあれば → 許可
  3. どちらもなければ → 暗黙的な拒否(既定はすべて拒否)

成功・推奨・正常 失敗・非推奨・障害 利用者・外部・送信元 その他の構成要素

さらに、OrganizationsのSCPやアクセス許可の境界、ロールのセッションポリシーが設定されている場合は、そのすべてで許可されている範囲だけが実際に使えます。アイデンティティベースのポリシーでAllowしても、SCPで許可されていなければ使えません。

マネージドポリシーとインラインポリシー#

種類作成・管理する人特徴
AWS管理ポリシーAWSAdministratorAccess、ReadOnlyAccess、AmazonS3ReadOnlyAccess など。AWSが更新する。手軽だが権限が広めになりやすい
カスタマー管理ポリシー利用者自分で作る独立したポリシー。複数のユーザー・グループ・ロールに付けて再利用でき、変更履歴(最大5バージョン)が残り、元のバージョンに戻せる
インラインポリシー利用者特定の1つのユーザー・グループ・ロールに直接埋め込むポリシー。付けた先を削除するとポリシーも消える。再利用やバージョン管理はできない

基本はマネージドポリシー(特にカスタマー管理ポリシー)を使い、「そのロールだけに厳密に1対1で付けたい権限」のときにインラインポリシーを使います。

アクセス許可の境界(Permissions Boundary)#

アクセス許可の境界は、IAMユーザーやロールに設定する「付与できる権限の上限」です。マネージドポリシーで上限を定義して境界に設定すると、そのユーザー・ロールの実際の権限は「アイデンティティベースのポリシーと境界の両方で許可された範囲」になります。境界そのものは権限を与えません。

成功・推奨・正常 その他の構成要素

代表的な用途は権限の委任です。開発者にIAMロールを作る権限を与えつつ、「作るロールには必ずこの境界を付けること」を条件にすると、開発者が自分より強い権限のロールを作って権限昇格するのを防げます。SCPがアカウント全体の上限なのに対して、境界は個々のユーザー・ロールの上限です。

IAM Access Analyzer#

IAM Access Analyzerは、ポリシーを分析して意図しないアクセスや不要な権限を見つける機能です。

機能内容
外部アクセスの分析S3バケット、IAMロール、KMSキー、Lambda関数、SQSキュー、Secrets Managerのシークレットなどのリソースベースのポリシーを調べ、アカウント(または組織)の外部からアクセスできるリソースを検出結果として表示する。無料
未使用のアクセスの分析使われていないロール、アクセスキー、パスワード、付与されているが使われていない権限を検出する(有料)
ポリシーの検証ポリシーを作るときに、文法エラーやセキュリティ上の問題(広すぎる権限など)を指摘する
ポリシーの生成CloudTrailのログから実際に使われたアクションを調べ、最小権限のポリシーのひな形を作る

「信頼ゾーン」(アナライザーを作ったアカウント、または組織全体)の外からのアクセスが検出の対象です。

認証情報レポート#

認証情報レポートは、アカウント内のすべてのIAMユーザー(ルートユーザーを含む)の認証情報の状態をまとめたCSVファイルです。コンソールやCLIから生成・ダウンロードできます(生成は4時間に1回まで)。

  • パスワードの有無・最終使用日時・最終変更日時
  • MFAが有効かどうか
  • アクセスキーの有無・作成(ローテーション)日時・最終使用日時と使われたサービス

「90日以上ローテーションしていないアクセスキー」「MFAが無効なユーザー」「長期間使われていないユーザー」を洗い出す監査に使います。ユーザーやロールごとに「どのサービスを最後にいつ使ったか」を見る場合は、最終アクセス情報(アクセスアドバイザー)を使います。

OIDCとの連携#

IAMにOIDC IdP(プロバイダーURL、クライアントID=IdPが発行するトークンの受信者)を登録します。

  1. アプリがOIDC IdPからIDトークンを取得
  2. アプリがトークンを持って、STSの AssumeRoleWithWebIdentity を呼び出す
  3. STSが、IAMに登録したIdP情報をもとにトークンの署名・発行者を検証
  4. 検証に通り、IAMロールの信頼ポリシーが許可していれば、一時的な認証情報を発行

認証情報の優先順位(AWS CLI/SDK)#

優先順位認証情報

2環境変数(AWS_ACCESS_KEY_ID など)
3~/.aws/credentials
4~/.aws/config のプロファイル
5ECSタスクロール
6EC2インスタンスプロファイル(IAMロール)

3. ユースケース#

  • 開発者ごとにIAMユーザーを作り、グループで権限を管理
  • EC2・Lambda・ECSにIAMロールを付けて、アクセスキーなしでAWSサービスを利用
  • 別アカウントのリソースへロールを引き受けてアクセス(クロスアカウント)
  • GitHub ActionsなどのOIDC連携で、アクセスキーを使わずにデプロイ

4. 料金の考え方#

IAMは無料で利用できます。

5. 関連サービス#

  • AWS STS:ロールの一時認証情報を発行
  • AWS Organizations:複数アカウントの権限上限(SCP)
  • AWS IAM Identity Center:複数アカウントへのシングルサインオンとパーミッションセット
  • Amazon EC2:インスタンスプロファイル
  • Amazon Cognito:アプリユーザーへの一時的なAWS権限
  • AWS CloudTrail:APIの操作履歴
  • 関連する用語:IAMポリシーと評価ロジック、ARN、OIDC、IAMロールと一時的な認証情報、iam:PassRoleとサービスにリンクされたロール、JSONとYAMLの読み方、ルートユーザーとアカウントの保護、タグ

6. 試験・実務でのポイント#

基本

  • ルートユーザーは日常で使わない。
  • アクセスキーをコードやインスタンスに置かず、ロールを使う。
  • 環境変数のキーが、インスタンスプロファイルより優先される。意図しない権限で動くときは優先順位を確認。
  • ロールは信頼ポリシー+権限ポリシーの両方が必要。AssumeRoleできないときは信頼ポリシーを確認。

ポリシーの評価と種類

  • AllowとDenyが両方ある → 明示的なDenyが優先。どこにもAllowがなければ暗黙的に拒否。
  • 複数のロールで再利用・バージョン管理したい → カスタマー管理ポリシー。特定のロールだけに1対1 → インラインポリシー。
  • 開発者にロール作成を任せつつ権限昇格を防ぐ → アクセス許可の境界。
  • 他アカウントからのS3アクセスは、バケットポリシー(リソースベース)と相手側IAMポリシーの両方で許可。

監査

  • 外部アカウントに公開されているリソースを見つける → IAM Access Analyzer。CloudTrailから最小権限のポリシーを作るのもAccess Analyzer。
  • 全ユーザーのMFA・アクセスキーのローテーション状況を監査 → 認証情報レポート。

7. まとめ#

  • IAMは「誰か(認証)」と「何ができるか(認可)」を管理する。
  • ユーザー・グループ・ロール・ポリシーの役割を区別する。
  • 認証情報は優先順位に従って選ばれる。

AWS IAM Identity Center

複数のAWSアカウントやアプリへのシングルサインオンと権限を一元管理するサービス

1. サービス概要#

AWS IAM Identity Center(旧称 AWS Single Sign-On)は、AWS Organizationsの複数のアカウントや業務アプリへのシングルサインオン(SSO)を提供し、誰がどのアカウントでどの権限を使えるかを一か所で管理するサービスです。

  • 利用者はAWSアクセスポータルに1回ログインするだけで、割り当てられたアカウントとロールを選んでコンソールやCLIを使える
  • アカウントごとにIAMユーザーを作る必要がなく、長期のアクセスキーも配らない(一時的な認証情報を使う)
  • 権限はパーミッションセットとして定義し、ユーザー・グループとアカウントの組み合わせに割り当てる

説明の中心 成功・推奨・正常 利用者・外部・送信元 その他の構成要素

2. 主な機能・特徴#

IDソース#

ユーザーとグループをどこで管理するか(IDソース)を1つ選びます。

IDソース内容
Identity CenterディレクトリIdentity Centerの中で直接ユーザー・グループを作る(既定)
Active DirectoryAWS Directory ServiceのAWS Managed Microsoft ADや、AD Connector経由でオンプレミスのADのユーザーを使う
外部IDプロバイダーMicrosoft Entra ID、Okta などのIdPとSAML 2.0で連携する。ユーザー・グループの同期にはSCIMを使う

パーミッションセット#

パーミッションセットは、ユーザー・グループに与える権限のテンプレートです。中身は次のようなIAMポリシーの組み合わせです。

  • AWS管理ポリシー(例:AdministratorAccess、ViewOnlyAccess)
  • カスタマー管理ポリシー(各アカウントにある同じ名前のポリシーを参照する)
  • インラインポリシー
  • アクセス許可の境界
  • セッション時間(1〜12時間、既定は1時間)

パーミッションセットを「ユーザー/グループ × アカウント」に割り当てると、そのアカウントに AWSReservedSSO_パーミッションセット名_… というIAMロールが自動で作られます。利用者がアクセスポータルでアカウントとパーミッションセットを選ぶと、このロールを引き受けた一時的な認証情報でログインします。パーミッションセットを変更すると、割り当て済みのすべてのアカウントのロールに反映されます。

グループ本番アカウント開発アカウント
開発者ReadOnlyPowerUser
運用担当OperatorOperator
管理者AdministratorAdministrator

このように「グループごと・アカウントごとにどのパーミッションセットを使えるか」を一覧として管理できます。

AWSアクセスポータルとCLI#

  • AWSアクセスポータル:ログイン後、使えるアカウントとパーミッションセットが一覧で表示され、選ぶとそのアカウントのコンソールに入れる
  • AWS CLI:aws configure sso でプロファイルを作り、aws sso login でブラウザ認証すると、一時的な認証情報でCLIを使える。アクセスキーを端末に保存しない
  • MFAを必須にできる

アプリケーションへのSSO#

AWSアカウントだけでなく、SAML 2.0やOAuth 2.0に対応したSaaSや自社アプリ、Amazon Managed Grafana・Amazon Q などのAWSのアプリにも、同じユーザーでシングルサインオンできます。

組織インスタンスと委任管理者#

  • Organizationsと組み合わせる組織インスタンスが基本。管理アカウントで有効にし、組織内のすべてのアカウントに権限を割り当てられる
  • 日常の管理は、委任管理者として登録したメンバーアカウントから行える(管理アカウントの利用を最小限にするため)
  • Organizationsを使わない単独アカウント用の「アカウントインスタンス」もあるが、AWSアカウントへのアクセス管理はできない(アプリへのSSO用)

3. ユースケース#

  • 数十のAWSアカウントへのログインを、社員1人1つのユーザーで一元化する
  • 社内のEntra ID・Oktaのアカウントで、そのままAWSにログインさせる(退職時はIdP側で無効にすれば全アカウントで使えなくなる)
  • 開発者には開発アカウントで強い権限、本番アカウントでは読み取りだけ、と環境ごとに権限を分ける
  • CLIの長期アクセスキーを廃止し、aws sso login の一時的な認証情報に置き換える

4. 料金の考え方#

IAM Identity Center自体は無料です。IDソースにAWS Managed Microsoft ADを使う場合などは、そのサービスの料金がかかります。

5. 関連サービス#

  • AWS Organizations:管理する複数アカウントのまとまり
  • AWS IAM:パーミッションセットの中身(ポリシー)と、各アカウントに作られるロール
  • AWS STS:ログイン時に一時的な認証情報を発行
  • AWS Directory Service:Active DirectoryをIDソースにする
  • AWS CloudTrail:誰がどのパーミッションセットでログインし、何をしたかの記録
  • 関連する用語:IAMポリシーと評価ロジック、ルートユーザーとアカウントの保護、AWSの操作方法

6. 試験・実務でのポイント#

  • 複数アカウントへのログインを一元化・SSO → IAM Identity Center(各アカウントにIAMユーザーを作らない)。
  • 権限のテンプレート → パーミッションセット。割り当てると各アカウントに AWSReservedSSO_ のロールが作られる。
  • 既存のEntra ID・Oktaと連携 → 外部IdPをSAML 2.0でIDソースにし、SCIMでユーザーを自動同期。
  • オンプレミスのADのユーザーでログイン → IDソースにAD(AD Connector・AWS Managed Microsoft AD)。
  • CLIで長期キーを使わない → aws configure sso/aws sso login。
  • 管理アカウントでの作業を減らす → 委任管理者を設定する。

7. まとめ#

  • IAM Identity Centerは、複数アカウントとアプリへのSSOと権限を一元管理する。
  • IDソース(内蔵ディレクトリ・AD・外部IdP)のユーザー・グループに、パーミッションセットとアカウントを組み合わせて割り当てる。
  • ログインは一時的な認証情報で行われ、長期のアクセスキーが不要になる。
セキュリティ・認証

iam:PassRoleとサービスにリンクされたロール

AWSのサービスにロールを渡すときに必要な権限と、サービスが自動で作る専用のロール

1. 詳しい説明#

iam:PassRole とは#

EC2にインスタンスプロファイルを付ける、Lambda関数に実行ロールを設定する、といった操作では、利用者がAWSのサービスにロールを渡し、サービスがそのロールで動きます。このとき、渡す人には操作そのもの(lambda:CreateFunction など)の権限に加えて、そのロールに対する iam:PassRole の権限が必要です。

PassRoleはAPIの名前ではなく、ロールを渡す操作のときに確認される権限です。もしこの確認がなければ、自分には権限がなくても、強い権限のロールをEC2やLambdaに渡してそこから何でもできてしまいます(権限の昇格)。PassRoleは「どのロールなら渡してよいか」を絞るための権限です。

説明の中心 成功・推奨・正常 利用者・外部・送信元 その他の構成要素

PassRoleが必要になる主な操作#

操作渡すロール
EC2インスタンスの起動(RunInstances)、起動中のインスタンスへのロールの付与インスタンスプロファイルのロール
Lambda関数の作成・設定の変更実行ロール
ECSのタスク定義の登録タスクロール・タスク実行ロール
CloudFormationのスタックの作成・更新(サービスロールを指定したとき)CloudFormationのサービスロール
SSM Automationの実行、Config・EventBridgeのターゲットの設定Automationやターゲットが使うロール
Auto Scalingの起動テンプレートを使った起動起動テンプレートのインスタンスプロファイル

権限が足りないと、User: arn:aws:iam::111122223333:user/dev is not authorized to perform: iam:PassRole on resource: arn:aws:iam::111122223333:role/MyRole のようなエラーになります。

PassRoleの書き方#

渡してよいロールを Resource で絞り、iam:PassedToService の条件で渡し先のサービスも絞ります。

{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-lambda-*",
  "Condition": {
    "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" }
  }
}

CloudFormationのサービスロールを使うと、開発者自身にはリソースを作る権限を与えず、「スタックの操作」と「決められたサービスロールのPassRole」だけを与えて、リソースはサービスロールの権限で作らせることができます。最小権限でデプロイさせる定番の方法です。

サービスロールとサービスにリンクされたロール#

サービスロールサービスにリンクされたロール
作る人利用者サービスが自動で作る(機能を最初に使ったとき)
権限の変更自由に変更できる変更できない(サービスが決めた内容)
信頼ポリシー利用者が書くそのサービスだけに固定
名前の例任意(例:MyLambdaRole)AWSServiceRoleForAutoScaling、AWSServiceRoleForElasticLoadBalancing(パスは /aws-service-role/)
削除いつでも削除できるそのロールを使うリソースをなくしてから削除する
PassRoleサービスに設定するとき必要不要(初回の作成時に iam:CreateServiceLinkedRole の権限が必要)

Auto ScalingやELB、Organizationsなどは、サービスにリンクされたロールで動きます。Auto ScalingグループのEC2が暗号化されたEBSボリュームで起動できないときは、そのKMSキーのキーポリシーで、Auto Scalingのサービスにリンクされたロールにキーの利用を許可しているかを確認します。
