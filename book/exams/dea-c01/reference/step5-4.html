マネジメントとガバナンス

AWS CloudTrail

「誰が・いつ・何をしたか」を記録する監査サービス

1. サービス概要#

AWS CloudTrailは、AWSアカウント内の「誰が」「いつ」「何をしたか」を記録する監査サービスです。

  • 誰が:IAMユーザー/ロール/AWSサービス、送信元IPアドレス
  • いつ:タイムスタンプ
  • 何をしたか:呼び出したAPI、リクエストパラメータ、レスポンス

2. 主な機能・特徴#

証跡(トレイル)#

記録したイベントをS3などに配信します(S3にはJSON形式で配信)。

  • 過去90日分の履歴は、証跡を作らなくてもCloudTrailコンソールで確認できる。
  • 作成手順:コンソールで「証跡の作成」 → 証跡名を指定 → 保存先S3バケットを指定 → 記録するイベントタイプを選択
  • ログファイルの整合性検証:ログが改ざん・削除・変更されていないかを確認できる。

イベントの種類#

種類内容例備考
管理イベントリソースを管理・設定する操作EC2・VPCの作成、IAMポリシーの変更デフォルトで記録
データイベントリソースそのものに対する操作S3オブジェクトの取得・削除有効化が必要
Insightsイベント普段と異なる異常なAPI操作API呼び出し・エラー率の急増有効化・追加料金が必要。EventBridge経由で通知・自動対応も可能
ネットワークアクティビティイベントVPCエンドポイントを通ったAPI呼び出し組織外のアカウントのS3へ、VPCエンドポイント経由でアクセスしようとした有効化が必要。データの持ち出しの調査に使う

データイベントは件数が多く、料金が大きくなりがちです。高度なイベントセレクターを使うと、「特定のバケットだけ」「書き込み(削除など)だけ」のように、記録するイベントを絞り込めます。

リージョン・グローバルの証跡#

  • リージョン:そのリージョンで発生したイベントのみを記録。「すべてのリージョンに適用」を有効にすると、全リージョンのイベントを1つの証跡で記録できる。
  • グローバル:IAMなどグローバルサービスのイベントは特定のリージョンに記録される。「グローバルサービスイベントを含める」オプションを有効にする。

CloudWatch Logsとの統合#

  • リアルタイムに近い監視が可能(S3への配信は最大5分ほどの遅延)。
  • 検知結果をSNS通知やLambdaによるアクションにつなげられる。
  • CloudWatch Logs Insightsでクエリ分析もできる。
  • 設定の流れ:証跡でCloudWatch Logsへの配信を有効化 → ロググループを指定 → CloudTrailからCloudWatch Logsへ送信するためのIAMロールを付与
  • 例:メトリクスフィルターで「ルートユーザーのログイン」「セキュリティグループの変更」「コンソールへのログイン失敗」を数え、CloudWatchアラームからSNSで通知する。

組織の証跡#

Organizationsの管理アカウント(または委任管理者)で組織の証跡を作ると、組織内のすべてのアカウントのイベントを、1つの証跡でまとめて記録できます。あとから組織に入ったアカウントも自動で対象になります。メンバーアカウントからは証跡を見られますが、変更・削除はできません。

ログの保護#

証跡のログは、不正の証拠になるため、消されたり書き換えられたりしないように守ります。

  • ログファイルの整合性検証:有効にすると、1時間ごとにダイジェストファイル(ログファイルのハッシュ値に電子署名を付けたもの)が作られる。aws cloudtrail validate-logs で、ログが変更・削除されていないかを確かめられる。
  • 保存先を分ける:ログ専用のアカウントのS3バケットに保存し、バケットポリシーでCloudTrail以外からの書き込みと削除を制限する。S3オブジェクトロックで削除を防ぐこともできる。
  • 暗号化:ログは標準でSSE-S3で暗号化される。SSE-KMS(カスタマーマネージドキー)にすると、ログを読める人をキーの権限でも絞れる。
  • 止めさせない:SCPで cloudtrail:StopLogging・cloudtrail:DeleteTrail を拒否する。証跡の停止はEventBridgeで検知して通知できる。

ログの分析とCloudTrail Lake#

方法内容
イベント履歴コンソールで過去90日分の管理イベントを、ユーザー名・イベント名・リソースで絞り込んで見る
AthenaS3に保存した証跡のログに、SQLで問い合わせる。長期間のログの分析に向く
CloudWatch Logs InsightsCloudWatch Logsに送ったログに、クエリで問い合わせる
CloudTrail Lakeイベントをイベントデータストアに集め、SQLで問い合わせる。S3やAthenaを準備しなくてよく、長期間(最長10年)保存できる。AWS以外のソースのイベントも取り込める

イベントデータストアは、高度なイベントセレクターで対象を選ぶイベントのコレクションです。管理・データイベント、Insightsイベント、AWS Config項目、AWS外のイベントなど、種類ごとに作成します(1つのデータストアには1種類のイベントカテゴリを保存)。Organizations全体の複数アカウント・リージョンを対象にすることもできます。

  • SQLで複数のイベント項目を検索・集計でき、複数のイベントデータストアを結合した分析も可能。
  • 保持期間は料金オプションにより最長約7年または約10年。クエリ結果は最大7日間参照でき、S3に保存できる。
  • 取り込み・保持と、クエリでスキャンしたデータ量に応じて料金がかかる。

提供状況:2026年5月31日以降、新規顧客はCloudTrail Lakeを利用開始できません。既存顧客は継続利用できます。新たに長期保存したイベントをSQL分析する場合は、証跡をS3に保存してAthenaで分析します。

ログが届かないときの確認#

  • 証跡の記録が停止されていないか(StopLogging がイベント履歴に残っていないか)。
  • S3のバケットポリシーで、CloudTrailからの書き込みを許可しているか。
  • SSE-KMSで暗号化している場合、キーポリシーでCloudTrailにキーの利用を許可しているか。
  • 見たいのがデータイベントなら、証跡でデータイベントを有効にしているか。

3. ユースケース#

  • 「誰がこのEC2を削除したか」の調査
  • セキュリティ監査・コンプライアンス対応のための操作履歴の長期保存
  • ルートユーザーのログインやセキュリティグループの変更をリアルタイムに通知

4. 料金の考え方#

過去90日分のイベント履歴の閲覧と、管理イベントの最初の1つの証跡は無料です。データイベント、Insightsイベント、追加の証跡には料金がかかります。保存先のS3やCloudWatch Logsの料金も別途かかります。CloudTrail Lakeはイベントの取り込み・保持とクエリのスキャン量に応じて課金されます。

5. 関連サービス#

  • Amazon S3:証跡の保存先
  • Amazon CloudWatch:ログの監視・アラーム
  • Amazon EventBridge:API操作をトリガーにした自動処理
  • AWS Config:「何がどう変わったか」の記録(CloudTrailは「誰がやったか」)
  • AWS Organizations:組織全体の証跡、証跡の停止を禁止するSCP
  • Amazon Athena:S3に保存したログのSQLでの分析
  • AWS KMS:ログの暗号化
  • AWS Control Tower:ログアーカイブアカウントへのログの集約
  • 関連する用語:ルートユーザーとアカウントの保護、コンプライアンスとAWS Artifact

6. 試験・実務でのポイント#

記録の設定

  • 「誰が」「いつ」「どのAPIを」→ CloudTrail。「設定がどう変わったか・準拠しているか」→ Config。
  • S3のオブジェクト操作を記録 → データイベントを有効化。料金を抑えるには高度なイベントセレクターで絞り込む。
  • 90日より前の履歴が必要 → 証跡を作成してS3に保存。
  • 全アカウント・全リージョンをまとめて記録し、メンバーに消させない → 組織の証跡。
  • 普段と違うAPIの呼び出しの急増に気付きたい → Insightsイベント。

保護と分析

  • ログの改ざん・削除を検知 → ログファイルの整合性検証(ダイジェストファイル)。
  • 証跡を止めさせない → SCPで StopLogging・DeleteTrail を拒否する。
  • リアルタイムに近い通知 → CloudWatch Logsと統合し、メトリクスフィルターとアラームで通知。
  • S3に保存したログをSQLで調べる → Athena。S3を用意せずSQLで長期保存・分析 → CloudTrail Lake。
  • CloudTrail Lakeは2026年5月31日以降、新規顧客は利用開始できない。新規利用ではS3+Athenaを検討する。
  • ログが届かない → 記録の停止、バケットポリシー、KMSのキーポリシーを確認する。
  • CloudWatch・CloudTrail・Config・X-Rayの使い分け → 監視・記録のサービスの選び方。

7. まとめ#

  • CloudTrailはAPI操作の監査ログ。90日分は自動で見られる。
  • イベントは管理・データ・Insightsの3種類。データイベントは有効化が必要。
  • 長期保存はS3、リアルタイム監視はCloudWatch Logs、SQLでの分析はAthenaかCloudTrail Lake。
  • 組織の証跡で全アカウントをまとめ、整合性検証・保存先の分離・SCPでログを守る。
マネジメントとガバナンス

AWS Config

リソースの設定状態を記録・評価し、違反を検出して修復

1. サービス概要#

AWS Configは、AWSリソースの設定状態を記録・評価し、コンプライアンス違反を検出して修復するサービスです。

2. 主な機能・特徴#

設定レコーダー#

有効にすると、対象リージョン・リソースの設定変更を記録します。

  • 設定内容:対象リソース、設定情報を保存するS3バケット、通知先のSNSトピック
  • 記録する情報:
    • リソースID(例:i-0123456789abcdef0)
    • リソースタイプ(例:AWS::EC2::Instance)
    • 設定属性(インスタンスタイプ、サブネットIDなど現在の設定)
    • リレーションシップ(他リソースとの関係)
    • タグ(例:Environment=Production)
    • 設定変更の時刻

記録した1件1件を設定項目(Configuration Item)といい、リソースごとに並べた設定タイムラインで「いつ・どう変わったか」と、その変更をしたCloudTrailのイベントを確認できます。

  • 記録の範囲:すべての種類のリソースを記録するか、種類を選ぶかを決める。記録していない種類のリソースは、Configルールでも評価されない。
  • 記録の頻度:変更のたびに記録する(継続的な記録)か、1日に1回まとめて記録する(日次の記録)かを選べる。変更の多いリソースを日次にすると料金を下げられる。
  • グローバルなリソース(IAMのユーザー・ロール・ポリシーなど)は、どのリージョンで記録しても同じ内容になるため、1つのリージョンだけで記録して重複を避ける。
  • Configはリージョンごとに有効にする。使っていないリージョンで不正にリソースが作られても気付けるように、すべてのリージョンで有効にしておく。

Configルール#

リソースの設定が要件に適合しているかを評価します。

  • 種類:AWSマネージドルール(AWSが提供)、カスタムルール(Lambdaなどで作成)
  • 例:EBSボリュームが暗号化されているか/S3バケットのパブリックアクセスが禁止されているか
  • 評価結果:COMPLIANT(準拠)、NON_COMPLIANT(非準拠)、NOT_APPLICABLE(評価対象外)、INSUFFICIENT_DATA(情報不足)
設定選択肢
評価のきっかけ(トリガー)設定変更:対象のリソースが変わったときに評価する。定期的:1・3・6・12・24時間ごとに評価する(例:アクセスキーが90日以上ローテーションされていないか)
評価のモード検出:作られたリソースを評価する(通常)。プロアクティブ:CloudFormationでリソースを作る前に、設定を評価する
カスタムルールの書き方Lambdaで評価のコードを書く、またはGuard(CloudFormation Guardの記法)でルールを宣言的に書く

AWSマネージドルールの例:encrypted-volumes(EBSの暗号化)、s3-bucket-public-read-prohibited(S3の公開読み取りの禁止)、restricted-ssh(SSHを0.0.0.0/0に開けていない)、required-tags(必須のタグが付いている)、cloudtrail-enabled(CloudTrailが有効)。

目的サービス用途
変更イベントの通知EventBridgeConfigの変更・非準拠イベントを検出
通知SNS管理者や運用チームへ通知
自動処理Lambda独自の検査・修復ロジックを実行
修復の自動化Systems Manager Automation定義済みのランブック(手順書)で設定を修復
セキュリティ統合Security Hubセキュリティ・コンプライアンス結果を集約
一括評価Conformance Packs複数のルールと修復処理をパッケージ化

API操作の監査CloudTrail変更を実行したユーザーやロールを記録

自動修復の例#

  1. ConfigルールがS3バケットのパブリックアクセスを検出
  2. リソースが NON_COMPLIANT になる
  3. Configの修復アクションが起動
  4. Systems Manager AutomationまたはLambdaが設定を修正
  5. Configが再評価し、COMPLIANT になったことを確認
  • 修復アクションは、手動(コンソールで選んで実行)か自動(非準拠になったらすぐ実行)を選べる。自動の場合は、失敗したときの再試行の回数も決める。
  • 修復には、AWSが用意したAutomationのランブック(例:AWS-DisableS3BucketPublicReadWrite、AWSConfigRemediation- で始まるもの)を使える。
  • ランブックが操作するためのIAMロール(AutomationAssumeRole)を、パラメータで渡す。権限が足りないと修復が失敗する。

コンフォーマンスパック#

コンフォーマンスパックは、複数のConfigルールと修復アクションを、1つのYAMLのテンプレートにまとめたものです。「CISのベンチマーク」「PCI DSS」などの基準に合わせたサンプルのテンプレートが用意されていて、そのまま展開できます。Organizationsと組み合わせると、組織内のすべてのアカウントに同じパックを展開できます。

複数アカウント・リージョンの集約(アグリゲーター)#

アグリゲーターは、複数のアカウント・リージョンのConfigのデータを、1つのアカウントに集めて表示する仕組みです。組織全体の準拠状況やリソースの一覧を、1か所で確認できます。アグリゲーターで集めたデータは読み取り専用で、ルールの設定はそれぞれのアカウントで行います(組織全体のルールは、管理アカウントか委任管理者から一括で展開できます)。

高度なクエリを使うと、SQLに似た書き方で、記録したリソースの現在の設定を検索できます(例:「暗号化されていないEBSボリュームの一覧」「インスタンスタイプごとのEC2の台数」)。アグリゲーターに対して実行すると、組織全体を検索できます。

評価されないときの確認#

  • 設定レコーダーが停止していないか、そのリージョンで有効になっているか。
  • 評価したいリソースの種類を記録の範囲に含めているか。
  • カスタムルールのLambdaに、Configへ結果を返す権限(config:PutEvaluations)があるか。

3. ユースケース#

  • 暗号化されていないEBSや公開されたS3バケットの検出
  • 「先月この時点でセキュリティグループはどう設定されていたか」の確認
  • 非準拠の設定の自動修復

4. 料金の考え方#

記録した設定項目の数と、Configルールの評価回数に応じて課金されます。Conformance Packsも評価回数で課金されます。

6. 試験・実務でのポイント#

記録と評価

  • 「設定が要件に準拠しているか」「設定の変更履歴」→ Config。
  • AWSに用意されていないチェック → カスタムルール(Lambda または Guard)。
  • リソースが変わったときに評価 → 設定変更トリガー。日数の経過などを確かめる → 定期的トリガー。
  • 作る前に設定を確かめたい → プロアクティブ評価。
  • IAMなどのグローバルなリソースは1つのリージョンだけで記録する。料金を下げたい → 日次の記録。
  • ルールが評価されない → 設定レコーダーの停止や、記録の範囲を確認する。

修復と組織での管理

  • 非準拠の自動修復 → 修復アクション+SSM Automation。失敗したら AutomationAssumeRole の権限を確認する。
  • 複数ルールをまとめて展開・CISなどの基準に合わせる → コンフォーマンスパック。
  • 複数アカウント・リージョンの準拠状況を1か所で見る → アグリゲーター。
  • リソースの現在の設定をSQLで検索したい → 高度なクエリ。
  • CloudWatch・CloudTrail・Config・X-Rayの使い分け → 監視・記録のサービスの選び方。

7. まとめ#

  • Configは設定レコーダーで記録し、Configルールで評価する。
  • 非準拠はSSM AutomationやLambdaで自動修復できる。
  • コンフォーマンスパックでルールをまとめて展開し、アグリゲーターで組織全体の状況を1か所で見る。
サービスの選び方

セキュリティ検出のサービスの選び方

GuardDuty・Inspector・Macie・Config・Security Hub CSPMなどを「何を見つけるか」で使い分ける

1. 詳しい説明#

AWSには、セキュリティ上の問題を見つけるサービスが複数あります。名前からは役割が分かりにくいですが、見つけるもので整理すると区別できます。不正なアクセスなどの「脅威」、ソフトウェアの「脆弱性」、S3の中の「機密データ」、リソースの「設定の不備」です。それぞれの検出結果をSecurity Hub CSPMに集めて、EventBridgeで通知や自動対応につなげるのが基本の形です。

GuardDuty脅威(不正アクセス、乗っ取られたEC2、暗号資産のマイニング、マルウェアなど)アカウント・EC2・S3・EKSなどCloudTrail・VPCフローログ・DNSログを自動で分析。設定やエージェントは不要
Inspectorソフトウェアの脆弱性(CVE)、意図しないネットワークの公開EC2・ECRのコンテナイメージ・LambdaEC2はSSMエージェント(またはエージェントレスのスキャン)。継続的に再スキャン
Macie機密データ(個人情報・認証情報など)、公開されたバケットS3S3のオブジェクトの中身を機械学習とパターンで調べる
AWS Configルールに違反した設定ほぼすべてのリソース設定の変更を記録し、ルールで評価する
Security Hub CSPMセキュリティ基準(AWS基礎セキュリティのベストプラクティス、CISなど)への違反。他サービスの結果の集約アカウント全体(組織全体も可)Configのルールでチェックし、各サービスの結果を共通の形式で集める
Amazon Detective検出結果の原因と影響範囲(調査用)GuardDutyなどの検出結果ログから関係をグラフにして、調査を助ける
IAM Access Analyzer外部のアカウントに公開されたリソース、使われていない権限S3・IAMロール・KMSキーなどポリシーを分析する
Trusted Advisorベストプラクティスからの逸脱(全ポートを開けたSG、ルートユーザーのMFAなど)アカウント定期的にチェックする(全項目はBusiness Support+ 以上のサポートプラン)

2025年に、従来のSecurity Hubは「Security Hub CSPM」という名前になりました。「Security Hub」の名前は、GuardDuty・Inspector・Macie・Security Hub CSPMの結果を関連付けてリスクを分析する新しいサービスに使われています。

見つけたあとの対応#

検出サービスは問題を見つけるだけで、多くは自分では直しません。対応は、検出結果のイベントをEventBridgeで受けて、Lambdaや Systems Manager Automationで自動化します。例えば、GuardDutyが乗っ取られたEC2を見つけたら、隔離用のセキュリティグループに付け替えます(運用シナリオ「乗っ取られたEC2を自動で隔離する」)。Configのルール違反には、Configの自動修復を設定できます。

選び方のポイント#

  • 不審なAPI呼び出しや、EC2が怪しいIPと通信しているのを見つけたい → GuardDuty。
  • EC2やコンテナイメージの脆弱性(CVE)を見つけたい → Inspector(運用シナリオ「脆弱性を継続的に検出し、パッチ適用まで自動化する」)。
  • S3に個人情報が保存されていないかを調べたい → Macie(運用シナリオ「機密データを保存するS3を暗号化・監査する」)。
  • 「暗号化されていないEBSがないか」など、自社の設定ルールを継続的にチェックしたい → AWS Config。
  • CISなどのセキュリティ基準にどれだけ準拠しているかを点数で見たい・複数のサービスの結果を1か所で見たい → Security Hub CSPM。
  • GuardDutyの検出結果について、原因や影響範囲を詳しく調べたい → Detective。
  • S3バケットやIAMロールが外部のアカウントに公開されていないかを知りたい → IAM Access Analyzer。
  • InspectorでEC2がスキャンされない → SSMエージェントが動いていて、Systems Managerの管理対象になっているかを確認する。
  • 組織の全アカウントでまとめて有効にしたい → Organizationsで委任管理者のアカウントを決め、そこから全アカウントに有効化する(GuardDuty・Inspector・Macie・Security Hub CSPMとも対応)。

2. 関連する用語#

  • 監視・記録のサービスの選び方:GuardDutyが分析するログ(CloudTrail・VPCフローログ)
  • VPCフローログ:IP通信の記録
  • IAMポリシーの評価:Access Analyzerが分析するポリシー
  • 暗号化:Configのルールで確認する代表的な設定

3. 関連サービス#

  • Amazon GuardDuty:脅威の検出
  • Amazon Inspector:脆弱性の検出
  • Amazon Macie:S3の機密データの検出
  • AWS Config:設定の記録とルールでの評価
  • AWS Security Hub:検出結果の集約とセキュリティ基準のチェック
  • AWS IAM:IAM Access Analyzer
  • AWS Trusted Advisor:ベストプラクティスのチェック
  • Amazon EventBridge:検出結果を通知・自動対応に振り分ける
