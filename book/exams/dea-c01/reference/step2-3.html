AWS Glue

データの発見・カタログ化・ETLをサーバーレスで行うデータ統合サービス

1. サービス概要#

AWS Glueは、複数のデータソースを発見・接続し、データカタログに登録して、分析用に抽出・変換・ロード(ETL)するマネージドサービスです。サーバーを管理せずに、バッチとストリーミングのデータ統合を行えます。

2. 主な機能・特徴#

AWS Glue Data Catalog#

データベース、テーブル、列、形式、S3上の場所などのメタデータを一元管理します。データそのものを保存する場所ではなく、データをどう読むかを記録するカタログです。Athena、Redshift Spectrum、EMRなどが同じテーブル定義を参照できます。

クローラーと接続#

クローラーはS3やJDBC接続先などのデータを調べ、形式やスキーマを推測してData Catalogにテーブルを作成・更新します。スキーマ変更の検出にも使えます。既知のスキーマを厳密に管理したいときは、クローラー任せにせずテーブル定義を明示します。

ETLジョブ#

  • AWS Glue Studioのビジュアルエディター、ノートブック、スクリプトでジョブを作成する。
  • Apache SparkまたはRayを実行エンジンとして、データの結合・整形・形式変換などを行う。
  • ジョブブックマークで処理済みデータを追跡し、再実行時に新しいデータだけを処理できる。ソースや変換の種類によって対応範囲が異なる。
  • トリガーやワークフローでジョブ・クローラーの順序や依存関係を管理する。

データ品質と準備#

AWS Glue Data Qualityでは、ルールを定義して欠損・重複・値の範囲などを評価し、結果を確認できます。AWS Glue DataBrewはビジュアル操作でデータのプロファイル確認や変換レシピ作成を行うデータ準備機能です。詳細はデータ品質を参照してください。

ストリーミングETL#

Kinesis Data StreamsやAmazon MSKなどのストリームを継続的に読み取り、変換して保存先へ書き込めます。リアルタイム処理にはチェックポイントや重複処理への考慮が必要です。

3. ユースケース#

  • 複数形式のデータをS3に集め、Parquetに変換して分析しやすくする。
  • データカタログとクローラーで、Athenaから検索できるテーブルを作る。
  • データ品質ルールをETLパイプラインに組み込み、不正なデータを検出する。
  • ストリーミングデータを変換してデータレイクへ取り込む。

4. 料金の考え方#

ジョブやクローラーの実行に使う処理能力と実行時間などに応じて課金されます。実行エンジンや機能によって料金体系が異なるため、ジョブの規模・頻度・ワーカー設定を見直します。S3、CloudWatch Logs、データ転送などの利用料は別途発生します。

5. 関連サービス#

  • Amazon S3:データレイクの保存先
  • Amazon Athena:Data Catalogを参照してS3をSQL分析
  • AWS Lake Formation:Data Catalogとデータレイクのアクセス制御
  • Amazon Redshift:データウェアハウスへのロード・分析
  • Amazon Kinesis/Amazon MSK:ストリーミングデータの取り込み
  • Amazon MWAA:複数ジョブを含むパイプラインのオーケストレーション

6. 試験・実務でのポイント#

  • データの場所・形式・スキーマを共有するメタデータの保管先 → AWS Glue Data Catalog。
  • S3上のデータを調べてスキーマを推測し、カタログ登録 → クローラー。
  • 大規模なデータ変換 → GlueのSparkジョブ。画面上で変換処理を作る → Glue Studio。
  • ルールに基づく品質評価 → Glue Data Quality。対話的なプロファイル・レシピ作成 → Glue DataBrew。
  • データカタログはメタデータであり、実データはS3やデータベースに存在する。

7. まとめ#

  • AWS Glueは、データのカタログ化・ETL・品質評価を統合するマネージドサービス。
  • Data Catalogがテーブル定義を保持し、クローラーがスキーマを検出する。
  • ジョブ・トリガー・ワークフローでバッチやストリーミングの処理を構成できる。

Amazon EMR

Apache SparkやHadoopなどの分散処理フレームワークを実行するマネージドサービス

1. サービス概要#

Amazon EMRは、Apache Spark、Hadoop、HiveなどのビッグデータフレームワークをAWS上で実行するマネージドサービスです。大規模なデータ処理や分析に必要なクラスターを作成し、S3などのデータを並列に処理します。

2. 主な機能・特徴#

実行方式#

  • EMR on EC2:クラスターのEC2インスタンスとソフトウェア構成を管理し、柔軟なカスタマイズを行う。
  • EMR Serverless:クラスターを常時管理せず、SparkやHiveのジョブ実行に必要なリソースを利用する。
  • EMR on EKS:Amazon EKS上でEMRの処理を実行し、既存のKubernetes基盤と共存させる。

分散処理#

処理対象を複数のノードに分け、並列に読み込み・変換・集計します。S3をデータレイクとして使う処理では、クラスターディスクにすべてのデータを置かずに済みます。HDFSを使う構成では、クラスター内の一時・分散ストレージの容量と耐障害性を考慮します。

Glueとの使い分け#

AWS Glueはサーバーレスなデータ統合・ETLを簡潔に実行したい場合に向きます。EMRはフレームワークや実行環境の選択、クラスター構成、ライブラリなどを細かく制御したい大規模処理に向きます。どちらもSparkを使えるため、既存コード・運用負荷・処理時間・コストで選びます。

3. ユースケース#

  • 大量のログやイベントをSparkで集計・変換する。
  • 複雑なデータ処理や機械学習向け前処理を分散実行する。
  • 既存のHadoop/SparkアプリケーションをAWS上で実行する。
  • データレイクのデータを変換し、分析用の保存先へ出力する。

4. 料金の考え方#

実行方式により、EC2インスタンスの稼働、EMRの利用、ジョブ処理に使うリソースなどが主な課金要因です。EMR on EC2では未使用ノードを停止し、ジョブに適したインスタンスタイプとクラスターサイズを選びます。S3、EKS、データ転送などの料金は別に確認します。

5. 関連サービス#

  • Amazon S3:データレイクと処理結果の保存
  • AWS Glue:サーバーレスETLとData Catalog
  • AWS Lake Formation:データレイクの細粒度アクセス制御
  • Amazon Redshift:分析データウェアハウス
  • Amazon EKS:EMR on EKSの実行基盤

6. 試験・実務でのポイント#

  • SparkやHadoopなどのOSSフレームワークを大規模分散実行 → Amazon EMR。
  • インフラ管理を避けてジョブ単位で処理する → EMR Serverless。
  • ノードやソフトウェアを柔軟に制御する → EMR on EC2。
  • 既存のKubernetes基盤を使う → EMR on EKS。
  • GlueはサーバーレスETL、EMRはOSS処理基盤の柔軟な実行を軸に比較する。

7. まとめ#

  • EMRは、SparkやHadoopなどをマネージドなクラスター環境で実行する。
  • EC2、Serverless、EKSの実行方式から、制御性と管理負荷に合わせて選ぶ。

Amazon Managed Service for Apache Flink

Apache Flinkでストリーミングデータを継続処理するマネージドサービス

1. サービス概要#

Amazon Managed Service for Apache Flinkは、Apache Flinkを使ってストリーミングデータを継続的に処理・分析するサービスです。AWSが実行基盤を管理し、利用者はJava、Scala、Python、SQLなどで処理ロジックを作成します。

2. 主な機能・特徴#

ステートフルなストリーム処理#

Flinkアプリケーションはイベントを継続的に読み取り、時間窓集計、イベント結合、異常検知などを行います。チェックポイントやスナップショットは、状態を復旧して処理を再開するために使います。イベント時刻、遅延到着、重複、状態の保持期間を設計します。

アプリケーションとStudio#

長時間稼働するアプリケーションは、IDEとFlink APIを使って作成し、バージョン管理・テスト・CI/CDに組み込めます。StudioノートブックはSQLなどでストリームを対話的に探索する用途に向きます。運用に移すアプリケーションでは、コードの変更管理と状態の互換性を確認します。

他のストリーミングサービスとの違い#

Kinesis Data StreamsやAmazon MSKはデータを保持・配信するストリーム基盤です。Managed Service for Apache Flinkは、そこからレコードを読み取って継続的な変換・集計を行います。Data Firehoseは処理済みデータを保存先へ配送する役割です。

3. ユースケース#

  • ストリームのイベントを時間窓で集計し、リアルタイムダッシュボードへ出力する。
  • イベントの結合や状態管理が必要なストリームETLを実行する。
  • ストリーミングデータの異常や傾向を検出する。

4. 料金の考え方#

アプリケーションに割り当てる処理能力と実行時間などが課金要因です。ソース・出力先、チェックポイント用ストレージ、CloudWatchログ、データ転送などの料金も考慮します。必要な並列度と状態サイズを監視し、過剰な処理能力を避けます。

5. 関連サービス#

  • Amazon Kinesis:Kinesis Data Streams
  • Amazon MSK:Kafka互換ストリーム
  • Amazon Data Firehose:ストリームの配送
  • AWS Glue:ETLとData Catalog
  • Amazon CloudWatch:アプリケーション監視

6. 試験・実務でのポイント#

  • 継続的なストリーミング変換・状態管理 → Managed Service for Apache Flink。
  • イベントを保持する基盤(Kinesis/MSK)と、イベントを処理するエンジン(Flink)を区別する。
  • 障害後の復旧にはチェックポイントを使い、状態・イベント時刻・再処理を設計する。
  • 対話的な探索にはStudio、長時間稼働しCI/CDで管理する処理にはFlinkアプリケーションを比較する。

7. まとめ#

  • Managed Service for Apache FlinkはFlinkアプリケーションの実行基盤をマネージドで提供する。
  • 状態を持つストリーミング処理と、Kinesis/MSKなどのデータ基盤を組み合わせる。

AWS Lambda

サーバーレスでプログラムを実行するサービス

1. サービス概要#

AWS Lambdaは、サーバーを用意せずにプログラム(関数)を実行できるサーバーレスサービスです。関数はAWSが管理するLambda専用のネットワーク環境で実行されます。

デフォルトではVPC内のリソースにはアクセスできません。アクセスさせたい場合は後述の「VPC接続」を設定します。

2. 主な機能・特徴#

基本の制限値#

  • 関数1回の最大実行時間は15分(タイムアウトは1〜900秒で設定)
  • 非同期呼び出し(S3・SNS・EventBridgeなどからの呼び出し)で関数がエラーになると、Lambdaが最大2回リトライする(初回+リトライ2回=最大3回実行。回数は0〜2で変更可)。同期呼び出し(API Gatewayなど)では呼び出し元がリトライを判断し、SQSやKinesisなどのイベントソースマッピングでは、メッセージやレコードが期限切れになるか成功するまでリトライされる、というように呼び出し方式によって動きが違う。
  • デプロイパッケージの上限は250MB(解凍後)。デプロイパッケージ=コード+依存関係+実行に必要なファイル一式。上限を超える場合は、S3経由でのアップロードや、ECR経由でコンテナイメージとしてデプロイする。

用語#

  • ハンドラー:最初に呼び出される入口の関数/メソッド。再利用する処理(DB接続など)はハンドラーの外で定義する。
  • レイヤー(Lambda Layers):複数の関数で共有するライブラリ・SDK・共通コード・証明書などを切り出したパッケージ。デプロイの肥大化・管理の重複・更新作業の負荷を解消する。
  • バージョン:発行したバージョンの中身は修正できない。
  • エイリアス:バージョンの別名。エイリアスを呼び出すと紐づけたバージョンが実行される。
  • デスティネーション(送信先):関数実行後の結果を送る先。成功時・失敗時それぞれに設定できる。
  • Function URLs:関数にWebエンドポイントを付けて直接呼び出せるようにする。

主な設定値#

項目設定可能範囲用途
メモリ128〜10,240MB実行性能の調整(CPU性能もメモリに比例)
タイムアウト1〜900秒最大実行時間
一時ストレージ(/tmp)512〜10,240MB一時ファイルの保存
予約された同時実行0〜アカウント上限同時実行数の制御
プロビジョニングされた同時実行0以上コールドスタート対策
環境変数任意設定値の管理

同時実行数#

  • 予約(Reserved):同時に実行できる上限数。上限を超えるとスロットリングが発生する。
  • プロビジョニング(Provisioned):設定した数だけ実行環境をあらかじめ作成しておく(ウォームスタート)。超えた分はコールドスタートで作成される。

どちらも「同時実行」の設定ですが、目的がまったく違います。名前が似ているので、違いを表で押さえておきましょう。

予約された同時実行(Reserved)プロビジョニングされた同時実行(Provisioned)
目的同時実行数の確保と上限(ほかの関数に枠を取られない/この関数が使いすぎない)コールドスタートをなくす(実行環境を事前に初期化しておく)
設定する単位関数単位バージョンかエイリアス単位($LATEST には設定できない)
料金追加料金なし有料(呼び出しがなくても、設定した数と時間に応じて課金)
設定した数を超えたときスロットリング(同期呼び出しなら429エラー)超えた分は通常どおり(コールドスタートで)実行される。予約の上限までは動く
アカウント全体の枠との関係アカウントの同時実行数(既定でリージョンあたり1,000)から差し引かれ、ほかの関数は使えなくなる。予約されていない枠を最低100残す必要があるこれもアカウントの枠を使う。予約された同時実行を設定している関数では、その数を超えて設定できない
よくある使い方下流のDBを守るために上限をかける。0にすると関数を止められる(緊急停止)レイテンシーが重要なAPI。Application Auto Scalingで、時間帯や使用率に合わせて数を増減する

アカウント全体の同時実行数の上限(1,000)は、Service Quotasで引き上げを申請できます。プロビジョニングされた同時実行の使用状況は、CloudWatchの ProvisionedConcurrencyUtilization、足りずに通常の実行に回った回数は ProvisionedConcurrencySpilloverInvocations で確認できます。

実行環境のライフサイクル#

  1. 初期化:実行環境作成 → ランタイム作成 → コードのロード
  2. 実行:ハンドラー関数を実行し、event / context が渡される(同時実行時は自動スケーリング)
  3. 待機:実行終了後、CPUは停止するがメモリ内容を保持してイベントを待つ
  4. 再利用:初期化をスキップして実行フェーズから始めるので高速
  5. シャットダウン:AWSの判断で実行環境を破棄

エラーの種類#

  • 呼び出しエラー:イベントソースに権限がない/呼び出し先の関数が存在しない/スロットリングが発生している
  • 関数エラー:Lambda関数内のコードでエラーが起きている

呼び出し方式の3種類と再試行・DLQ・デスティネーション#

Lambdaの呼び出され方は3種類あり、エラーになったときの再試行と、失敗したイベントの行き先が方式ごとに違います。

方式主な呼び出し元エラー時の再試行失敗したイベントの行き先
同期呼び出しAPI Gateway、ALB、Function URLs、CLIの invokeLambdaは再試行しない。呼び出し元がエラーを受け取り、再試行するか判断する呼び出し元に返る(DLQ・デスティネーションは使わない)
非同期呼び出しS3、SNS、EventBridge、CloudWatch LogsLambdaの内部キューに入り、最大2回再試行する(0〜2回で変更可)。イベントの最大保持期間も設定できる(最大6時間)失敗時のデスティネーション(SQS・SNS・Lambda・EventBridge・S3)、またはDLQ(SQS・SNS)
イベントソースマッピングSQS、Kinesis Data Streams、DynamoDB Streams、Amazon MSKLambdaがポーリングして取得する。SQSは可視性タイムアウト後にメッセージがキューに戻って再処理され、ストリームは成功するかレコードの期限が切れるまで再試行する(最大再試行回数・最大レコード期間で制限できる)SQS:キュー側のDLQ(再処理ポリシー)。ストリーム:失敗時の送信先(SQS・SNS・S3)
  • DLQ(デッドレターキュー):失敗したイベントの内容だけをSQS・SNSに送る。失敗時にしか使えない
  • デスティネーション:成功時・失敗時それぞれに送信先を設定でき、イベントの内容に加えてエラーの内容や関数の応答も含まれる。新しく作るならデスティネーションが推奨
  • SQSのイベントソースマッピングでは、関数側のDLQやデスティネーションではなく、SQSキューの再処理ポリシー(DLQ)で失敗したメッセージを退避する。可視性タイムアウトは関数のタイムアウトより長くする
  • ストリームでは、失敗したレコードがシャードの処理を止めてしまうため、「バッチを分割して再試行」や「部分的なバッチの失敗の報告(ReportBatchItemFailures)」を使う
  • 再試行で同じイベントが2回以上処理されることがあるため、関数は同じイベントを何度処理しても結果が変わらない(冪等な)作りにする

実行ロールとリソースベースのポリシー#

Lambdaの権限は、向きの違う2つのポリシーで決まります。

ポリシー決めること例
実行ロール(IAMロール)関数が何にアクセスできるか(関数から外への権限)DynamoDBへの書き込み、S3の読み取り、CloudWatch Logsへのログ出力、SQSのポーリング(イベントソースマッピング)
リソースベースのポリシー誰が関数を呼び出せるか(外から関数への権限)S3・SNS・EventBridge・API Gatewayや、別のアカウントに lambda:InvokeFunction を許可する
  • 実行ロールの信頼ポリシーでは lambda.amazonaws.com がロールを引き受けられるようにする。ログを出すにはAWS管理ポリシー AWSLambdaBasicExecutionRole の権限が必要
  • イベントソースマッピング(SQS・Kinesisなど)はLambdaがポーリングするため、sqs:ReceiveMessage などの権限は実行ロールに付ける
  • S3やSNSからの非同期呼び出しは相手がLambdaを呼び出すため、リソースベースのポリシーで許可する(コンソールでトリガーを追加すると自動で設定される)
  • 「AccessDenied」が関数の中で出るなら実行ロール、関数が呼び出されないなら呼び出し元の権限(リソースベースのポリシー)を確認する

バージョン管理とエイリアス#

バージョンを発行するたびに新しいARNが発行されるため、イベントソースマッピング(イベント発生元とLambda関数を接続し自動起動する仕組み)が古いARNを参照し続けてしまう問題があります。

解決策は、イベントソースマッピングをエイリアスのARNに向け、新バージョン発行時はエイリアスの向き先だけを更新することです。

旧:S3 → prod(エイリアス) → v1
新:S3 → prod(エイリアス) → v2

また、1つのエイリアスを複数バージョンに紐づけてトラフィックを分割(例:v1=90%、v2=10%)し、段階的に移行できます。

VPC接続#

Lambdaに仮想ENIを割り当て、サブネットとセキュリティグループに所属させることで、VPC内のリソースと通信できるようになります。

  1. VPC・サブネットを作成
  2. Lambda用のセキュリティグループを作成
  3. Lambda実行ロールにENI操作の権限を付与:ec2:CreateNetworkInterface、ec2:DescribeNetworkInterfaces、ec2:DeleteNetworkInterface
  4. LambdaにVPC/サブネット/セキュリティグループを設定

VPCに接続したLambdaは、インターネットやAWSサービスのパブリックなエンドポイントにそのままでは接続できなくなります。LambdaのENIにはプライベートIPしか付かず、パブリックサブネットに置いてもパブリックIPは付かないためです。

  • インターネット(外部API、VPCエンドポイントのないAWSサービス)に出るには、Lambdaをプライベートサブネットに置き、そのルートテーブルでパブリックサブネットのNATゲートウェイに向ける
  • S3・DynamoDB・Secrets ManagerなどのAWSサービスだけなら、VPCエンドポイントを作ればNATゲートウェイなしで使える
  • VPC内のリソースにアクセスする必要がない関数は、VPCに接続しない方がシンプル

Lambda@Edge#

CloudFrontのエッジサーバー上でLambdaを実行する仕組みで、低レイテンシーを実現します。単純な処理はCloudFront Functionsを使い、AWSサービスにアクセスする処理はLambda@Edgeを使います。

  • 作成できるリージョンはus-east-1のみ
  • 環境変数は使用不可
  • VPC接続は不可

3. ユースケース#

  • S3へのファイルアップロードをきっかけにした画像変換などのイベント駆動処理
  • API GatewayやFunction URLsと組み合わせたサーバーレスAPI
  • CloudFrontのエッジでのリクエスト加工(Lambda@Edge)
  • 15分以内に終わる定期バッチ処理

4. 料金の考え方#

Lambdaは「リクエスト数」と「実行時間×割り当てメモリ量」で課金されます。関数が動いていない時間は料金がかかりません。プロビジョニングされた同時実行は、設定している間ずっと料金が発生します。

メモリを増やすとCPU性能も上がるため、実行時間が短くなり結果的に安くなる場合もあります。

5. 関連サービス#

  • Amazon API Gateway:LambdaをバックエンドにしたAPIを公開
  • Amazon CloudFront:Lambda@Edgeの実行場所
  • Amazon ECR:コンテナイメージとしてデプロイする際の保存先
  • Amazon S3:代表的なイベントソース
  • Amazon VPC:VPC接続でVPC内リソースにアクセス
  • AWS SAM:サーバーレスアプリのデプロイ
  • AWS X-Ray:関数のトレース
  • 関連する用語:スロットリングとリトライ、iam:PassRoleとサービスにリンクされたロール、マネージドサービスとサーバーレス

6. 試験・実務でのポイント#

制限と性能

  • 15分を超える処理はLambdaに向かない(ECS/Fargateなどを検討)。
  • デプロイパッケージが250MBを超える → コンテナイメージ(ECR)でデプロイ。
  • コールドスタート対策 → プロビジョニングされた同時実行。同時実行の上限制御 → 予約された同時実行。
  • 予約は無料・関数単位で、上限を超えるとスロットリング。プロビジョニングは有料・バージョン/エイリアス単位で、超えた分はコールドスタートで動く。関数を緊急停止 → 予約された同時実行を0。
  • ある関数が同時実行を使い切って、ほかの関数がスロットリングされる → 重要な関数に予約された同時実行を設定する。

呼び出しとエラー処理

  • 非同期呼び出しは最大2回再試行し、失敗したイベントは失敗時のデスティネーションかDLQへ。同期呼び出しは呼び出し元が再試行する。
  • SQSから処理して失敗したメッセージを退避 → SQSキュー側のDLQ(再処理ポリシー)。
  • 成功/失敗の結果を他サービスに送る → デスティネーション。
  • イベントソースはバージョンARNではなくエイリアスARNに向ける。

権限・ネットワーク

  • 関数から他のサービスへの権限 → 実行ロール。S3・SNSなどから関数を呼び出す権限 → リソースベースのポリシー。SQSのポーリングは実行ロール。
  • VPC接続には実行ロールにENI作成・参照・削除の権限が必要。
  • VPC接続したLambdaがインターネットに出られない → プライベートサブネット+NATゲートウェイ(パブリックサブネットに置いてもパブリックIPは付かない)。AWSサービスだけならVPCエンドポイント。
  • Lambda@Edgeはus-east-1で作成。

7. まとめ#

  • Lambdaはサーバー管理不要の関数実行サービス。最大15分、パッケージ250MB。
  • 同時実行は「予約=上限」「プロビジョニング=事前ウォーム」。
  • バージョン+エイリアスで安全にリリースし、トラフィック分割で段階移行できる。
コンピューティング

AWS Batch

必要なコンピューティング容量を自動調整してバッチジョブを実行するサービス

1. サービス概要#

AWS Batchは、コンテナ化されたバッチ処理を登録・スケジュールし、必要な計算資源を自動的に用意して実行するサービスです。ジョブの量や要求リソースに応じて容量を調整し、EC2、Fargate、ECS、EKSなどの実行基盤を利用します。

2. 主な機能・特徴#

ジョブ実行の構成要素#

  • ジョブ定義:コンテナイメージ、vCPU・メモリ、環境変数、再試行などを定義する。
  • ジョブキュー:投入されたジョブの優先度や実行順序を管理する。
  • コンピューティング環境:ジョブを実行するEC2やFargateなどの容量を指定する。
  • ジョブ間の依存関係や配列ジョブを使い、大量の独立した処理をまとめて実行する。

パイプラインとの使い分け#

Batchはコンテナ化された計算ジョブのスケジューリングと実行を担います。複数サービスをまたぐ処理の順序・分岐・エラー制御はStep FunctionsやMWAAなどで管理できます。ジョブのスケジュールをEventBridgeから起動する構成もあります。

3. ユースケース#

  • 大量のファイル変換や定期的な集計を並列に実行する。
  • 必要なCPU・メモリに応じたコンテナジョブを優先度付きで処理する。
  • ピーク時だけ計算容量を増やし、処理終了後に容量を減らす。

4. 料金の考え方#

AWS Batch自体に追加料金がない場合でも、ジョブを実行するEC2、Fargate、EKSなどの計算資源、ストレージ、ログ、データ転送に料金が発生します。実行時間、リソース要求、再試行、Spot利用の可否を見積もります。

5. 関連サービス#

  • Amazon ECS/Amazon EKS:コンテナ実行基盤
  • AWS Lambda:短時間のイベント駆動処理
  • AWS Step Functions:処理ステップの制御
  • Amazon MWAA:Airflowによるデータパイプライン管理
  • Amazon EventBridge:スケジュール起動

6. 試験・実務でのポイント#

  • コンテナ化されたバッチジョブをキューで管理し、実行容量を自動調整 → AWS Batch。
  • ジョブのコンテナ・リソース定義はジョブ定義、投入順序はジョブキュー、計算資源はコンピューティング環境で設定する。
  • 処理フローの分岐・状態管理はワークフローサービス、計算処理の実行はBatchと役割を分ける。

7. まとめ#

  • AWS Batchはバッチジョブをキューイングし、実行に必要な容量を調整する。
  • ジョブ定義・キュー・コンピューティング環境を組み合わせる。
ネットワークとコンテンツ配信

Amazon API Gateway

APIの作成・公開・管理のためのサービス

1. サービス概要#

Amazon API Gatewayは、APIの作成・公開・管理のためのサービスです。クライアントからのリクエストを受け付け、LambdaやHTTPサーバー、他のAWSサービスへ中継します。

2. 主な機能・特徴#

APIの種類#

  • HTTP API:シンプルで低コストなAPI(実体はHTTPS)。
  • REST API:多機能なAPI。
    • ステージ変数:API Gateway内部だけで使う変数。バックエンドや呼び出し先URL、環境固有の設定値を切り替える。${stageVariables.xxx} で値を参照する。
      例:prodステージは lambdaAlias="prod"、testステージは lambdaAlias="test" とし、arn:aws:lambda:ap-northeast-1:123456789012:function:MyFunction:${stageVariables.lambdaAlias} で呼び出し先を切り替える。
    • ステージレベルのキャッシュ:ステージ単位でAPIの応答をキャッシュする。有効にすると既定ではGETメソッドだけがキャッシュされ、POSTなど他のメソッドはメソッドごとの設定で個別に有効にする。
  • WebSocket API:双方向通信。

リクエスト処理の流れ#

  1. メソッドリクエスト:クライアントから受け取るリクエストの定義
  2. 統合リクエスト:バックエンドへ送る前の変換処理(Lambda・HTTPサーバー・他AWSサービス向けに変換)
  3. 統合レスポンス:バックエンドから返ってきたデータの変換処理
  4. メソッドレスポンス:クライアントへ返すレスポンスの仕様

3. ユースケース#

  • API Gateway+Lambda(プロキシ統合)によるサーバーレスAPI
  • 既存のHTTPシステムの前段にAPIの入り口を置く(HTTP統合)
  • APIキーと使用量プランで、外部パートナーごとに利用量を制限
  • チャットなどのリアルタイム双方向通信(WebSocket API)

4. 料金の考え方#

APIの呼び出し回数とデータ転送量で課金されます(WebSocketは接続時間とメッセージ数)。HTTP APIはREST APIより安価です。REST APIのキャッシュを有効にすると、キャッシュサイズに応じた時間料金が加わります。

5. 関連サービス#

  • AWS Lambda:代表的なバックエンド、Lambdaオーソライザー
  • Amazon Cognito:ユーザー認証(Cognitoオーソライザー)
  • AWS IAM:SigV4によるIAM認証
  • Amazon CloudFront/AWS Certificate Manager:カスタムドメインと証明書
  • Amazon VPC:プライベートAPIのVPCエンドポイント
  • AWS X-Ray:リクエストのトレース
  • 関連する用語:HTTPステータスコードと切り分け、スロットリングとリトライ

6. 試験・実務でのポイント#

  • APIを変更したら再デプロイ(createDeployment)しないと反映されない。
  • APIキーは使用量プランに関連付け(createUsagePlanKey)て初めて使える。
  • 環境ごとにLambdaのエイリアスを切り替える → ステージ変数。
  • オーソライザーの結果はキャッシュされる。権限変更がすぐ反映されないときはキャッシュを疑う。
  • リクエストをそのまま渡す → プロキシ統合、変換が必要 → 非プロキシ+マッピングテンプレート。
  • VPC内からのみ使わせたい → プライベートAPI(VPCエンドポイント必須)。
  • CloudFront・API Gateway・ElastiCache・DAXのキャッシュの使い分け → キャッシュの選び方。

7. まとめ#

  • API GatewayはHTTP/REST/WebSocketのAPIを提供する。
  • 処理はメソッドリクエスト → 統合リクエスト → 統合レスポンス → メソッドレスポンス。
  • 認可はオーソライザー、利用制限はAPIキー+使用量プラン。
