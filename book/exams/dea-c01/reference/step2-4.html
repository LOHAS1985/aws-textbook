AWS Step Functions

複数の処理をつなぎ合わせてワークフローを作る

1. サービス概要#

AWS Step Functionsは、複数の処理をつなぎ合わせてワークフローを作成するサービスです。Lambdaや各種AWSサービスの呼び出しを、順番・分岐・並列・リトライを含めて定義できます。SQSやEventBridgeなどのメッセージングとの使い分けは用語ページ「メッセージングサービスの選び方」を参照してください。

2. 主な機能・特徴#

用語#

  • ステートマシン:ワークフロー全体を定義するもの
  • ステート:ワークフロー内の1つ1つの処理ステップ
  • 状態遷移:各ステート間のつながり

説明の中心 成功・推奨・正常 失敗・非推奨・障害 利用者・外部・送信元 その他の構成要素

ステートマシンの属性#

  • StartAt:開始ステート
  • TimeoutSeconds:全体の最大実行時間
  • DefinitionSubstitutions:デプロイ時に差し込む動的な値(API GatewayのURLなど)

ステート共通の属性#

  • Type:ステートの種類(Task/Pass/Choiceなど)
  • InputPath/OutputPath:入出力のフィルタリング
  • ResultPath:結果のマージ先
  • Retry(失敗時のリトライ):
    • ErrorEquals:対象のエラーの種類(配列で指定)
    • IntervalSeconds:リトライまでの待機時間
    • MaxAttempts:最大リトライ回数
    • BackoffRate:待機時間の増加倍率

AWSの仕様では MaxAttempts は「初回実行を含まないリトライ回数」です(MaxAttempts=3なら、初回+最大3回のリトライ)。また、失敗後の遷移先は Catch(ErrorEquals・Next・ResultPath)で指定します。リトライの待ち方(バックオフ)の考え方は用語ページ「スロットリングとリトライ」を参照してください。

ステートの種類#

ステート役割主な属性
TaskLambda関数や別サービスを呼び出すResource(実行対象)、TimeoutSeconds、HeartbeatSeconds(生存確認)、ResultPath(エラー情報の格納先)、Next(次の処理)
Choice条件分岐Choices(条件)、Default(どれにも当てはまらない場合)
Wait指定時間待機-
Parallel複数の処理を並列実行-
Fail/Succeed終了(エラー/成功)-

APIアクション(外部サービスの直接呼び出し)#

  1. AWS SDK統合:Lambdaを使わずに、各サービスのAPIをSDKで直接呼び出す
  2. サービス統合(最適化された統合):特定のサービス向けに最適化されたStep Functions専用のAPI(内部ではSDKを使用)

3. ユースケース#

  • 注文処理(在庫確認 → 決済 → 発送)のように複数ステップの業務フロー
  • 失敗時のリトライ・エラー処理を含むバッチ処理
  • Lambdaの15分制限を超える長い処理を、小さなステップに分割
  • 人の承認待ちを含むワークフロー

4. 料金の考え方#

Standardワークフローは状態遷移の回数、Expressワークフローは実行回数と実行時間・メモリに応じて課金されます。Standardは最大1年の長時間実行向け、Expressは大量・短時間の処理向けです。

5. 関連サービス#

  • AWS Lambda:Taskステートの代表的な実行対象
  • Amazon EventBridge:ワークフローの起動
  • Amazon API Gateway:APIからワークフローを起動
  • Amazon DynamoDB/Amazon SQS/Amazon SNS:サービス統合で直接呼び出し

6. 試験・実務でのポイント#

  • 複数のLambdaの順序制御・分岐・並列・リトライ → Step Functions。
  • 一時的なエラーで再実行 → Retry(BackoffRateでエクスポネンシャルバックオフ)。
  • 失敗時に別の処理へ → Catch。
  • Lambdaを書かずにDynamoDBなどを呼ぶ → SDK統合/サービス統合。
  • 入出力の加工 → InputPath/ResultPath/OutputPath。

7. まとめ#

  • Step Functionsはステートマシンでワークフローを定義するサービス。
  • Task・Choice・Wait・Parallel・Fail/Succeedのステートを組み合わせる。
  • Retryで自動リトライ、SDK統合でLambdaなしにAWSサービスを呼べる。

Amazon MWAA

Apache Airflowでデータパイプラインを管理するマネージドサービス

1. サービス概要#

Amazon Managed Workflows for Apache Airflow (Amazon MWAA)は、Apache Airflowを使ってデータパイプラインを作成・スケジュール・監視するマネージドサービスです。AirflowのDAGとPythonコードでタスクや依存関係を定義し、実際の処理はGlueやEMRなどのサービスに実行させます。

2. 主な機能・特徴#

DAGとタスク#

DAG(有向非巡回グラフ)に、処理単位のタスクと実行順序を定義します。スケジューラーが実行タイミングを管理し、ワーカーがタスクを実行します。成功・失敗・再試行の状態をAirflowの画面で確認できます。

説明の中心 成功・推奨・正常 利用者・外部・送信元 その他の構成要素

管理と運用#

  • 環境の最小・最大ワーカー数を設定し、タスク数に応じてワーカーをスケールする。
  • DAGやプラグインなどをS3に配置し、IAMロールでタスクからAWSサービスへアクセスする。
  • Webサーバーをパブリックまたはプライベートに公開し、VPC・IAM・暗号化を設定する。
  • AirflowのログやメトリクスをCloudWatchに出力して、失敗・遅延・リソース不足を調べる。

Step Functionsとの使い分け#

Apache AirflowのDAG・Python・豊富な演算子を活用し、複雑なデータワークフローを管理する場合はMWAAが候補です。AWSサービスを中心とした状態遷移や分岐・リトライをサーバーレスに実装する場合はStep Functionsが候補です。

3. ユースケース#

  • 日次のデータ取り込み・変換・品質確認・集計を依存関係に沿って実行する。
  • 複数のAWSサービスや外部システムにまたがるワークフローを管理する。
  • 失敗したタスクの再試行や、完了・失敗の通知を実装する。

4. 料金の考え方#

MWAA環境の稼働時間や環境クラス、ワーカー・スケジューラーなどのリソースが主な課金要因です。CloudWatch、S3、VPCエンドポイント、タスクが呼び出す各サービスの料金も発生します。常時稼働する環境が必要か、より軽量なサーバーレスワークフローで代替できるかを検討します。

5. 関連サービス#

  • AWS Glue:ETLジョブとデータカタログ
  • Amazon EMR:大規模な分散処理
  • AWS Step Functions:サーバーレスの状態遷移ワークフロー
  • Amazon EventBridge:イベントやスケジュールによる起動
  • Amazon CloudWatch:ログ・メトリクスの監視

6. 試験・実務でのポイント#

  • Apache AirflowでDAGを管理するマネージドサービス → Amazon MWAA。
  • MWAAはオーケストレーションを担い、データ変換そのものはGlueやEMRなどが行う。
  • タスクの依存関係・スケジュール・再試行・実行履歴をDAG単位で確認する。
  • CloudWatchログ、ワーカーのスケーリング、VPC接続、IAMロールをトラブル調査で確認する。
  • Airflowを必要としないAWS中心の状態遷移ならStep Functionsと比較する。

7. まとめ#

  • MWAAはApache Airflowによるデータパイプラインのオーケストレーションをマネージドで提供する。
  • DAGがタスク順序を定義し、各タスクはGlue・EMRなどの処理を呼び出す。

Amazon EventBridge

サーバーレスなイベント駆動型の統合サービス

1. サービス概要#

Amazon EventBridgeは、サーバーレスなイベント駆動型の統合サービスです。AWSサービスやアプリで発生したイベントを、条件に応じてさまざまなターゲットへ届けます。

  • 複数のターゲットに送信できる
  • API Destination:外部のHTTPSエンドポイントへイベントを送信
  • アカウント間・リージョン間のイベント転送も可能

説明の中心 利用者・外部・送信元 その他の構成要素

2. 主な機能・特徴#

用語#

  • イベントバス:イベントを送受信する仕組み。
    • デフォルト:AWSサービス同士の連携
    • カスタム:独自アプリのイベント
    • パートナー:AWS以外(SaaS)のアプリのイベント
  • イベントソース:イベントの送信元となるサービスやアプリ
  • ルール:イベントパターンやスケジュールに基づいて実行
  • ターゲット:送信先

EventBridge Rules#

イベントバス上のイベントをフィルタリングし、複数のターゲットへファンアウト配信します。

  1. ルールを作成
  2. イベントバスを選択(デフォルト/カスタム)
  3. イベントパターンを定義(例:S3からのイベントだけに絞る)
  4. ターゲットを選択(SNSトピック、Lambda関数、Step Functionsなど)。送信前にイベントデータを変換・拡張できる
  5. ルールを保存

EventBridge Pipes#

イベントソースとターゲットを1対1で接続するサービスです。

  1. ソース:DynamoDB Streams、Kinesis Data Streams、SQS、Amazon MSK、Amazon MQ
  2. フィルタリング:条件に一致するイベントだけを通す
  3. エンリッチメント:送る前に内容を補完・変換(Lambda、Step Functions、API Gateway、API Destinations)
  4. ターゲット:Lambda、Step Functions、SNS、SQS、API Gatewayなど

説明の中心 利用者・外部・送信元 その他の構成要素

Systems Manager Automationによる自動修復#

ターゲットとしてSSM Automation(ランブック)を指定できます。例:異常なEC2の修復

  1. CloudWatchアラームがEC2のステータスチェック失敗を検出
  2. EventBridgeルールがアラームの状態変化を検出
  3. SSM Automationのランブックを起動
  4. EC2インスタンスを再起動
  5. CloudWatchが状態を再評価

トラブルシューティング#

チェック項目内容
イベントが実際に発生しているか発生元サービスやCloudTrailのイベント履歴を確認
イベントパターンが一致しているかコンソールのパターンテスト機能やサンプルイベントで確認
ルールが有効かルールが ENABLED か確認
ターゲットの権限ターゲットを呼び出すためのIAM権限を確認
ターゲットの実行結果ターゲットごとのログや実行履歴を確認
CloudWatchメトリクスとDLQDLQで配信できなかったイベントを後から調査
ArchiveとReplayArchiveでイベントを保存し、Replayで後から再送

3. ユースケース#

  • EC2の状態変化やConfigの非準拠をトリガーに自動修復
  • cron式などのスケジュールでLambdaを定期実行
  • SaaS(パートナー)のイベントをAWSで処理
  • イベントをアーカイブしておき、障害後にリプレイ

4. 料金の考え方#

カスタムイベント・パートナーイベントの発行数に応じて課金されます(AWSサービスからのデフォルトバスのイベントは無料)。Pipes、API Destinations、Archive/Replay、スケジューラーはそれぞれ別の料金です。

5. 関連サービス#

  • AWS Health Dashboard:AWS Healthのイベント(aws.health)の送信元
  • Amazon SNS:シンプルなファンアウト通知
  • AWS Lambda/AWS Step Functions:代表的なターゲット
  • AWS Systems Manager:Automationによる自動修復
  • AWS CloudTrail:API操作をイベント化
  • Amazon SQS/Amazon DynamoDB/Amazon Kinesis:Pipesのソース
  • 関連する用語:イベント駆動の自動修復、cron式とrate式

6. 試験・実務でのポイント#

  • 条件付きルーティング・変換・SaaS連携・アーカイブ/リプレイ → EventBridge。
  • イベントをトリガーに自動修復 → EventBridgeルール+SSM Automation。
  • ソースとターゲットを1対1でつなぎ、途中で加工 → Pipes。
  • ルールが発火しない → パターン一致・ENABLED・ターゲットの権限を確認。
  • 外部のHTTPS APIへ送信 → API Destination。
  • SQS・SNS・EventBridge・Kinesisの使い分け → メッセージングサービスの選び方。

7. まとめ#

  • EventBridgeはイベントバス・ルール・ターゲットで構成されるイベント駆動の統合サービス。
  • Rulesはファンアウト、Pipesは1対1の加工付き接続。

Amazon SQS

システム間でメッセージを受け渡すメッセージキュー

1. サービス概要#

Amazon SQS(Simple Queue Service)は、メッセージキューイングサービスです。送信側と受信側の間にキューを置くことで、システム同士を疎結合にします。

プル型:受信者がキューをポーリングしてメッセージを取得します。

説明の中心 成功・推奨・正常 失敗・非推奨・障害 利用者・外部・送信元

2. 主な機能・特徴#

用語#

  • プロデューサー:送信者
  • コンシューマー:受信者
  • デッドレターキュー(DLQ):処理に失敗したメッセージを別のキューに移す機能(分析や再処理に使う)。StartMessageMoveTask APIで、DLQから元のキューへメッセージを戻せる。
  • 可視性タイムアウト:コンシューマーがメッセージを受信した後、他の受信者から見えなくなる期間。二重処理を防ぐ。

説明の中心 成功・推奨・正常 失敗・非推奨・障害 利用者・外部・送信元

キューの種類#

種類スループット順序重複
標準キューほぼ無制限ベストエフォート同じメッセージが届く可能性あり
FIFOキュー上限あり順序を保証重複排除

主な設定値#

設定内容
Visibility Timeout可視性タイムアウト
DelaySecondsメッセージがキューに送信されてから一定時間、コンシューマーに見えなくする(すぐ処理させたくないとき。最大15分)。例:注文後5分以内ならキャンセル可能 → DelaySeconds = 300
Retention Periodメッセージの保持期間
Receive Wait Timeキューが空のとき、受信APIに対してどれくらい待ってから応答するか(ロングポーリング)
maxReceiveCount何回失敗したらDLQに移動するか

イベントソースマッピング(Lambdaの機能)#

SQSキューを監視し、どのようにメッセージを取得して関数を起動するかを定義します。LambdaがSQSのポーリング、メッセージ取得、関数の起動を行います。

  • 対象SQSキュー:どのキューを読むか
  • バッチサイズ:何件まとめて取得するか
  • 最大同時実行数:並列数(API呼び出し速度の制御、Lambdaが増えすぎるのを防ぐ)
  • Enabled/Disabled:有効・無効
  • バッチウィンドウ:どれくらい待ってバッチにまとめるか
  • Failure Handling:失敗時の処理

暗号化#

キュー内のメッセージ本文を SSE-SQS または SSE-KMS で暗号化できます。

説明の中心 成功・推奨・正常 その他の構成要素

3. ユースケース#

  • Webサーバーと重い処理(画像変換など)のワーカーの間に置いて非同期化
  • アクセス急増時にリクエストをためておき、バックエンドを守る(バッファ)
  • 注文処理など順序が重要な処理(FIFOキュー)
  • SNSからのファンアウト先

4. 料金の考え方#

APIリクエスト数(送信・受信・削除など)に応じて課金されます。FIFOキューは標準キューより単価が高めです。空のキューへの無駄な受信リクエストは、ロングポーリング(Receive Wait Time)で減らせます。

5. 関連サービス#

  • AWS Lambda:イベントソースマッピングでキューを処理
  • Amazon SNS:プッシュ型の通知。SNS→SQSのファンアウト
  • Amazon EventBridge:イベントのルーティング
  • AWS KMS:SSE-KMS
  • Amazon CloudWatch:ApproximateNumberOfMessagesVisible でバックログ監視

6. 試験・実務でのポイント#

  • 順序保証・重複排除 → FIFOキュー。
  • 同じメッセージが二重処理される → 可視性タイムアウトを処理時間より長くする。
  • 何度も失敗するメッセージ → DLQ(maxReceiveCount)。戻すときは StartMessageMoveTask。
  • 処理開始を遅らせる → DelaySeconds。
  • 空振りの受信を減らしコスト削減 → ロングポーリング(Receive Wait Time)。
  • SQS→LambdaのポーリングはLambda側(イベントソースマッピング)が行う。
  • SQS・SNS・EventBridge・Kinesisの使い分け → メッセージングサービスの選び方。

7. まとめ#

  • SQSはプル型のメッセージキュー。標準とFIFOの2種類。
  • 可視性タイムアウト・DLQ・DelaySeconds・ロングポーリングを使い分ける。

Amazon SNS

複数の購読者へメッセージをプッシュ配信するPub/Subサービス

1. サービス概要#

Amazon SNS(Simple Notification Service)は、メッセージングサービスです。プッシュ型(Pub/Sub)で、SNS自らが受信者にメッセージを送ります。保存されたメッセージはAWS KMSで暗号化できます。

説明の中心 利用者・外部・送信元 その他の構成要素

2. 主な機能・特徴#

用語#

  • トピック:通信チャネルとして機能するアクセスポイント。
    • FIFO:順序の保証、重複排除。SQS FIFOキューのみに配信できる。
    • 標準:順序の保証なし、重複配信の可能性あり。
  • パブリッシュ:メッセージをトピックに発行すること。
  • サブスクリプション:メッセージの受信者を登録すること。配信に失敗すると、SNSが配信ポリシーに従って再試行する。
    • HTTP/HTTPSの宛先:デフォルトでは最大3回、20秒間隔で再試行する。HTTP/HTTPSだけは、再試行の回数や間隔(バックオフ)を配信ポリシーで変更できる。
    • SQS・LambdaなどAWSが管理する宛先:SNSが定めた配信ポリシーで、より長い期間にわたって多くの回数再試行する(変更はできない)。
    • 再試行をすべて使い切ると、DLQが設定されていない限りメッセージは破棄される。

メッセージフィルタリング#

購読者ごとに受信するメッセージを選別します。メッセージ属性(本文とは別に付けるキーと値)や本文で選別し、不要な配信を減らしてコストを下げます。

デッドレターキュー(DLQ)#

配信に失敗し、再試行にも失敗したメッセージを保存します。サブスクリプション単位で設定し、実体はSQSキューです。

SNSトピック → 購読者へ配信 → 成功:通常処理/失敗:再試行 → 失敗が続く:SNS DLQ(SQS)

保存後の調査手順:

  1. 配信失敗のメトリクスを確認(NumberOfMessagesPublished=受け付けた数、NumberOfNotificationsDelivered=配信成功数、NumberOfNotificationsFailed=配信失敗数)
  2. 購読者の状態を確認
  3. サブスクリプションの設定を確認
  4. メッセージを調査

説明の中心 失敗・非推奨・障害 その他の構成要素

代表的な構成に、1つのSNSトピックから複数のSQSキューへ同じメッセージを配るファンアウトがあります。

4. 料金の考え方#

パブリッシュしたリクエスト数と、配信先の種類(HTTP、メール、SMS、モバイルプッシュなど)ごとの配信数で課金されます。SQSやLambdaへの配信は無料です。SMSは送信先の国によって料金が異なります。

5. 関連サービス#

  • Amazon SQS:ファンアウト先、DLQの実体
  • Amazon EventBridge:条件付きのイベントルーティング
  • Amazon CloudWatch:アラームの通知先
  • AWS Lambda:購読者
  • AWS KMS:メッセージの暗号化
  • Amazon SES:顧客向けのメール送信(SNSのメール通知は運用者向け)

6. 試験・実務でのポイント#

  • SNSはプッシュ型、SQSはプル型。
  • 1つのメッセージを複数の処理へ → SNS→複数SQSのファンアウト。
  • 購読者ごとに必要なメッセージだけ → メッセージフィルタリング。
  • 配信失敗の保存 → サブスクリプションにDLQ(SQS)。
  • FIFOトピックの配信先はSQS FIFOキューのみ。
  • メール・SMS通知 → SNS、複雑なルーティング・変換 → EventBridge。
  • SQS・SNS・EventBridge・Kinesisの使い分け → メッセージングサービスの選び方。

7. まとめ#

  • SNSはトピックへパブリッシュし、サブスクリプションへプッシュ配信するPub/Subサービス。
  • フィルタリング・DLQ・FIFOトピックで配信を制御する。
