分析

AWS Lake Formation

データレイクとカタログのアクセス権を一元管理するサービス

1. サービス概要#

AWS Lake Formationは、Amazon S3上のデータレイクとAWS Glue Data Catalogのメタデータへのアクセスを一元的に管理するサービスです。データベース・テーブルだけでなく、列・行・セル単位のアクセス制御や、アカウントをまたぐデータ共有に対応します。

2. 主な機能・特徴#

権限の仕組み#

Lake Formationの権限はIAMやS3バケットポリシーを置き換えるものではなく、それらに加えてデータレイク内の細かいアクセスを制御します。利用者には、サービスAPIを呼ぶIAM権限と、テーブルデータを読むLake Formation権限の両方が必要です。実際にアクセスできる範囲は、関係する権限の組み合わせで決まります。

  • データベース・テーブル単位の権限に加え、列・行・セルを絞るデータフィルターを設定できる。
  • Lake Formationのタグをデータベースやテーブルに付け、タグに基づいて権限を付与できる。
  • ハイブリッドアクセスモードでは、対象のデータベースやテーブルごとにLake Formation権限を段階的に導入できる。

データ共有#

Data Catalogと基盤データを、AWSアカウント・組織をまたいで共有できます。共有先はAWS Resource Access Managerなどを介してカタログ資産を利用します。共有設定だけでなく、共有先のIAM権限やデータ側の権限も適切に整えます。

監査と統合#

Athena、AWS Glue、Amazon EMR、Redshift Spectrumなどの分析サービスと連携します。AWS CloudTrailでAPI操作やデータアクセスに関するイベントを記録し、アクセス状況の監査に利用できます。

3. ユースケース#

  • 部門ごとに異なるS3上のデータを一元管理し、分析サービスから安全に利用させる。
  • 個人情報の列を隠す、または行条件で閲覧データを制限する。
  • タグを用いてデータ分類とアクセス権をまとめて管理する。
  • 他アカウントの分析チームに、元データを複製せずにデータを共有する。

4. 料金の考え方#

Lake Formationの機能料金のほか、基盤となるAmazon S3、AWS Glue Data Catalog、AWS RAM、クエリ・処理サービスなどの料金が発生する場合があります。共有やクエリの利用料がどのアカウントに発生するかを構成ごとに確認します。

5. 関連サービス#

  • AWS Glue:カタログ、クローラー、ETLジョブ
  • Amazon S3:データレイクの実データ
  • Amazon Athena:データレイクのクエリ
  • Amazon Redshift:Spectrumやデータ共有との連携
  • Amazon Macie:S3内の機密データ・個人情報の検出
  • AWS CloudTrail:操作やアクセスの監査
  • 関連する用語:データガバナンス

6. 試験・実務でのポイント#

  • データレイクのカタログとデータに対する細粒度の権限管理 → Lake Formation。
  • IAM権限はサービスAPIへのアクセス、Lake Formation権限はデータ資産へのアクセスを制御する。
  • 列・行単位の制限やタグベースの権限を使い、最小権限にする。
  • データ共有では、共有元・共有先の設定と各アカウントの権限を確認する。
  • 既存のIAM・S3権限を保ちながら段階導入する選択肢 → ハイブリッドアクセスモード。

7. まとめ#

  • Lake FormationはデータレイクとGlue Data Catalogへのアクセスを一元管理する。
  • IAMと連携し、列・行・タグ単位の制御やアカウント間共有を提供する。
ストレージ

オープンテーブル形式

データレイク上の複数ファイルをテーブルとして一貫して管理する形式

1. 詳しい説明#

CSVやParquetは個々のファイルのデータ形式です。Apache Icebergなどのオープンテーブル形式は、データレイク上の複数ファイルをテーブルとして管理するメタデータやトランザクションの仕組みを定めます。データ形式とテーブル形式は異なる層です。

Apache Iceberg#

  • スナップショットとメタデータでテーブルの状態を管理し、一貫した読み取りや変更を支援する。
  • 列の追加・変更などのスキーマ進化や、パーティション仕様の変更をデータファイルの再配置を抑えて行える。
  • 対応する複数の処理エンジンから同じテーブルを扱いやすくする。
  • スナップショットによる過去状態の参照や、変更データの追跡を利用できる機能がある。

実際に使える書き込み・更新・削除・タイムトラベルの機能は、エンジン、カタログ、テーブル形式のバージョンに依存します。利用予定の組み合わせで公式の対応表を確認します。

ファイル形式との組み合わせ#

ParquetやORCのような列指向ファイル形式は、必要な列だけを読み、圧縮してスキャン量を減らすのに有効です。Icebergはこれらのデータファイルを管理するテーブル層です。パーティション設計、圧縮、スナップショットの期限切れや古いファイルの削除も運用に含めます。

  • データストアの選び方:データレイクと分析基盤の選択
  • データ品質:スキーマと内容の検証
  • ストレージの種類:オブジェクトストレージの特徴

3. 関連サービス#

  • Amazon S3:テーブルデータファイルの保存先
  • AWS Glue:カタログ、ETL、Iceberg読み書き
  • Amazon Athena:データレイクのSQLクエリ
  • Amazon Data Firehose:S3上のIcebergテーブルへの配送
  • AWS Lake Formation:カタログ・データへの権限管理
分析

Amazon Redshift

大規模な分析クエリを実行するマネージドデータウェアハウス

1. サービス概要#

Amazon Redshiftは、大量の構造化データをSQLで集計・分析するデータウェアハウスです。列指向の保存と並列処理で分析クエリを実行し、S3のデータレイクやBIツールとも連携します。

2. 主な機能・特徴#

プロビジョンドとServerless#

  • プロビジョンド:クラスターのノード構成を選び、継続的なワークロードの容量を管理する。
  • Redshift Serverless:データウェアハウスの容量を個別に管理せず、ワークロードに応じて処理能力を利用する。

どちらもSQLで分析できます。継続的で予測しやすい処理か、変動が大きく管理負荷を下げたい処理かで選びます。

データの取り込みと連携#

  • COPYでS3などからデータをロードし、UNLOADでクエリ結果をS3へ出力する。
  • Redshift Spectrumで、S3上のデータをクラスターのテーブルにロードせずにクエリする。外部テーブルの定義にGlue Data Catalogを利用できる。
  • フェデレーテッドクエリでRDSやAuroraなどの外部データソースを参照する。
  • データ共有で別のRedshiftデータウェアハウスへデータを共有し、複製を抑えた分析を行う。

説明の中心 成功・推奨・正常 利用者・外部・送信元 その他の構成要素

テーブル設計と同時実行#

クエリのアクセスパターンに応じて、列のデータ型、ソートキー、分散方法を設計します。列指向形式や圧縮はスキャン量を抑えます。テーブルや行のロック、トランザクションの競合が発生した場合は、長時間トランザクションや同時更新を調査します。分析性能はクエリプラン、スキャン量、分散キーのデータ偏りも確認します。

3. ユースケース#

  • 業務システムやS3のデータを統合した大規模なSQL分析。
  • BIダッシュボード向けの集計テーブルやマテリアライズドビュー。
  • S3データレイクとデータウェアハウスを組み合わせた分析。
  • 別のRedshift利用者への管理されたデータ共有。

4. 料金の考え方#

プロビジョンドでは主に利用するノードの容量と稼働時間、Serverlessでは処理容量の利用量などが課金要因です。ストレージ、バックアップ、データ転送、Spectrumのスキャンなども確認します。アイドル時間が長いか、負荷が一定か変動するかを踏まえて方式を選びます。

5. 関連サービス#

  • Amazon S3:ロード元、UNLOAD先、Spectrumのデータレイク
  • AWS Glue:カタログとETL
  • AWS Lake Formation:データレイクのアクセス制御
  • Amazon Athena:サーバーレスSQLでのデータレイク分析
  • Amazon Quick:Quick SightのBIダッシュボード
  • Amazon AppFlow:SaaSデータの取り込み

6. 試験・実務でのポイント#

  • 大規模な分析用SQLデータウェアハウス → Amazon Redshift。
  • データをS3からロードする → COPY。クエリ結果をS3へ出力する → UNLOAD。
  • S3のデータをロードせずに分析 → Redshift Spectrum。
  • 負荷変動が大きく容量管理を減らしたい → Serverless。一定負荷で容量を管理したい → プロビジョンドを比較する。
  • 他のデータウェアハウスへ読み取り用データを渡す → データ共有。データベース間の移送方法と区別する。

7. まとめ#

  • Redshiftは、SQLによる大規模分析向けのデータウェアハウス。
  • COPY/UNLOAD、Spectrum、フェデレーテッドクエリ、データ共有で複数のデータソースと連携する。
  • ノード容量・クエリ・ストレージなど、方式別の料金要因を比較する。
