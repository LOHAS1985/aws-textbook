マネジメントとガバナンス

AWS CloudFormation

AWSリソースをテンプレート(コード)で定義し、自動構築・管理

1. サービス概要#

AWS CloudFormationは、AWSリソースをコード(テンプレート)として定義し、自動で構築・管理するサービスです(Infrastructure as Code)。

2. 主な機能・特徴#

構成要素#

  • テンプレート:インフラの設計図(YAML/JSON形式)
  • スタック:テンプレートから作られるリソースの集合(環境そのもののイメージ)
  • ネストスタック:スタックを入れ子構造にする

主な機能#

  • 構文の拡張:サーバーレス用に AWS SAM がある。
  • Transformセクション:デプロイ前にテンプレートを別のテンプレートへ変換する。例:Transform: AWS::Serverless-2016-10-31(SAM)
  • カスタムリソース:実行時の独自処理を作成(ほとんどの場合Lambdaを使う)。例:RDSのDBユーザー作成、Slack通知のWebhook登録
  • DeletionPolicy:リソース削除時の扱い。Delete(削除する。デフォルト)/Retain(残す)/Snapshot(スナップショットを取ってから削除)
  • NoEcho:機密情報を画面・ログに表示しない
  • 変更セット:実行中のリソースに変更がどう影響するか(追加・変更・置き換え・削除)を事前に確認する。
  • Lambdaのコード更新の注意:Lambdaのコードを S3Bucket/S3Key で指定している場合、S3上のファイルを同じキーで上書きしただけでは、テンプレートに変化がないためCloudFormationはコードの変更を検知しない。S3のキー(ファイル名)か S3ObjectVersion を変えて更新する。
  • ドリフト検出:テンプレート(理想の状態)と実際のリソースのズレを検出
  • スタックポリシー:スタック更新時に特定のリソースの変更を禁止する
  • ダイナミックリファレンス:テンプレート内でSecrets Manager/Parameter Storeの値を実行時に参照し、秘密情報を直書きしない。記述は {{resolve:xxxx:...}}。xxxxは ssm(Parameter Store)、ssm-secure(SecureString)、secretsmanager(Secrets Manager)。
  • StackSets:複数のAWSアカウント・リージョンへスタックを一括展開する

AWS CLIのコマンドとオプション#

コマンド内容
create-stack新規作成
update-stack更新
delete-stack削除
describe-stacks状態確認
deploy作成/更新

主なオプション:--template-file(テンプレート指定)、--stack-name(スタック名)、--parameter-overrides(パラメータ上書き)、--capabilities(IAMリソース作成の許可)、--tags、--region、--role-arn(実行ロール)、--disable-rollback(ロールバック無効)

テンプレートの例(S3バケットの作成)#

  • Parameters:パラメータ(バケット名、バージョニングのON/OFF。AllowedValues で値の候補を限定)
  • Resources:本体(Properties で設定)
  • Conditions:条件分岐
  • Outputs:外部へ返す情報(!Ref などの組み込み関数で値を取得)
AWSTemplateFormatVersion: '2010-09-09'
Description: Create an S3 bucket with parameters and outputs

Parameters:
  BucketName:
    Type: String
  VersioningEnabled:
    Type: String
    AllowedValues: [true, false]
    Default: false

Conditions:
  EnableVersioning: !Equals [ !Ref VersioningEnabled, true ]

Resources:
  MyS3Bucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Ref BucketName
      VersioningConfiguration:
        Status: !If [ EnableVersioning, Enabled, Suspended ]

Outputs:
  BucketNameOutput:
    Value: !Ref MyS3Bucket
  BucketURL:
    Value: !Sub "https://${MyS3Bucket}.s3.amazonaws.com"

組み込み関数#

テンプレートの中で値を参照・加工するために組み込み関数を使います。YAMLでは !Ref のような短縮形で書けます(正式な形は Fn::GetAtt など)。

関数返すもの例
!Refパラメータの値、またはリソースの物理ID(バケット名、インスタンスID、セキュリティグループIDなど。何が返るかはリソースの種類による)!Ref MyS3Bucket → バケット名
!GetAttリソースの属性(ARN、DNS名など)!GetAtt MyS3Bucket.Arn、!GetAtt MyALB.DNSName
!Sub文字列の中の ${...} を値に置き換えた文字列!Sub "arn:aws:s3:::${MyS3Bucket}/*"
!FindInMapMappings セクションの表から値を引くリージョンごとのAMI ID、環境ごとのインスタンスタイプ
!Join区切り文字で値をつなげた文字列!Join [",", [a, b, c]] → a,b,c
!Select/!Split/!GetAZsリストからの選択/文字列の分割/リージョンのAZの一覧!Select [0, !GetAZs ""] → 1つ目のAZ
!If/!Equals条件(Conditions)による値の切り替え本番だけ大きいインスタンスにする
!ImportValue別のスタックがエクスポートした値下の「スタック間の参照」を参照
!Base64Base64でエンコードした文字列EC2の UserData
Mappings:
  RegionMap:
    ap-northeast-1:
      AMI: ami-0aaaaaaaaaaaaaaaa
    us-east-1:
      AMI: ami-0bbbbbbbbbbbbbbbb

Resources:
  MyInstance:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: !FindInMap [RegionMap, !Ref "AWS::Region", AMI]
      SubnetId: !Select [0, !Ref SubnetIds]

AWS::Region(リージョン)、AWS::AccountId(アカウントID)、AWS::StackName(スタック名)などの疑似パラメータは、定義しなくても !Ref や !Sub で使えます。同じテンプレートを別のリージョン・アカウントで使い回すときに便利です。最新のAMI IDは、Parameter Storeの公開パラメータを AWS::SSM::Parameter::Value<AWS::EC2::Image::Id> 型のパラメータで参照する方法もあります。

Export/ImportValue(スタック間の参照)#

ネットワーク用のスタックで作ったVPCやサブネットのIDを、アプリ用のスタックで使いたいときは、Outputsで値をエクスポートし、使う側で !ImportValue で読み込みます。

# ネットワーク用スタック(エクスポートする側)
Outputs:
  PublicSubnetId:
    Value: !Ref PublicSubnet
    Export:
      Name: network-PublicSubnetId

# アプリ用スタック(インポートする側)
Resources:
  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      SubnetId: !ImportValue network-PublicSubnetId
  • エクスポート名は同じアカウント・同じリージョンの中で一意にする。インポートできるのも同じリージョン内だけ
  • どこかのスタックがインポートしている間は、エクスポートしている側のスタックを削除したり、その出力値を変更したりできない
  • 層ごと(ネットワーク・DB・アプリ)にスタックを分け、担当者やライフサイクルの違いに合わせて管理できる。1つのアプリの部品を再利用するならネストスタックを使う

ロールバックとスタックの状態#

スタックの作成・更新の途中でリソースの作成に失敗すると、CloudFormationは既定でロールバックし、元の状態に戻そうとします。スタックの状態(ステータス)は次のように変わります。

状態意味対処
CREATE_COMPLETE/UPDATE_COMPLETE作成・更新が成功した—
ROLLBACK_COMPLETE作成に失敗し、作成したリソースを削除し終えた更新はできない。スタックを削除して作り直す
UPDATE_ROLLBACK_COMPLETE更新に失敗し、更新前の状態に戻った原因を直して再度更新する
UPDATE_ROLLBACK_FAILED更新のロールバック自体が失敗した(例:手動で削除・変更されたリソースを元に戻せない)原因のリソースを手動で直してから「更新のロールバックを続行」(continue-update-rollback)。戻せないリソースはスキップを指定できる
DELETE_FAILED削除に失敗した(例:中身が残っているS3バケット、他から使われているセキュリティグループ)原因を取り除いて再度削除する。残してよいリソースは保持を指定して削除する
  • 失敗の原因は、スタックのイベントタブで「最初に失敗したリソース」の理由を見ると分かる
  • 調査のために失敗したリソースを残したいときは、ロールバックを無効にする(--disable-rollback)か、「正常にプロビジョニングされたリソースを保持」を選ぶ
  • ロールバックトリガーにCloudWatchアラームを指定すると、更新後の監視期間中にアラームが発生したとき自動でロールバックできる

cfn-init・cfn-signal・CreationPolicy#

EC2インスタンスは「起動した」時点でCloudFormation上は作成完了になりますが、その時点ではまだアプリのインストールが終わっていないことがあります。次のヘルパースクリプトを使うと、インスタンス内の設定が終わるまでスタックの完了を待たせることができます。

仕組み役割
AWS::CloudFormation::Init(メタデータ)インストールするパッケージ、置くファイル、起動するサービス、実行するコマンドを宣言的に書く
cfn-initユーザーデータから実行し、上のメタデータを読み取って設定を行う
cfn-signal設定が成功したか失敗したかをCloudFormationに通知する
CreationPolicyリソースに付け、「指定した数の成功シグナルを、指定した時間内に受け取るまで作成完了にしない」設定
WaitConditionテンプレートの外部の処理などを待つための仕組み。EC2やAuto ScalingグループにはCreationPolicyを使うのが推奨
cfn-hupメタデータの変更を検知して、cfn-initを再実行する常駐プログラム
WebServer:
  Type: AWS::EC2::Instance
  CreationPolicy:
    ResourceSignal:
      Count: 1
      Timeout: PT15M
  Metadata:
    AWS::CloudFormation::Init:
      config:
        packages:
          yum:
            httpd: []
        services:
          sysvinit:
            httpd:
              enabled: true
              ensureRunning: true
  Properties:
    UserData:
      Fn::Base64: !Sub |
        #!/bin/bash
        /opt/aws/bin/cfn-init -s ${AWS::StackName} -r WebServer --region ${AWS::Region}
        /opt/aws/bin/cfn-signal -e $? -s ${AWS::StackName} -r WebServer --region ${AWS::Region}

タイムアウトまでに成功のシグナルが届かない(または失敗のシグナルが届く)と、そのリソースは作成失敗となり、スタックはロールバックします。「スタックがタイムアウトで失敗する」場合は、インスタンスからCloudFormationのエンドポイントへ通信できるか(NATゲートウェイなど)、cfn-signalが実行されているか(/var/log/cfn-init.log)を確認します。

DependsOn属性とWaitCondition#

CloudFormationは、Ref や Fn::GetAtt で参照しているリソースの順番を自動で判断し、依存先を先に作ります。参照がないリソース同士は並行して作成されます。参照がなくても順番を守らせたいときに使うのが DependsOn属性です。

仕組み役割使う場面
暗黙の依存関係Ref・GetAtt・Sub で参照すると、自動で依存先が先に作成される通常はこれで足りる
DependsOn指定したリソースの作成が完了してから、このリソースを作る(削除は逆順)。1つまたは複数のリソースの論理IDを指定する参照はないが順番が必要なとき
WaitCondition(AWS::CloudFormation::WaitCondition)外部からの成功シグナルを、指定した数・時間内に受け取るまで待つ。WaitConditionHandle の署名付きURLにシグナルを送るテンプレートの外の処理(手動の作業や別システムの設定)の完了を待つとき
CreationPolicyリソース自身に付け、EC2やAuto Scalingグループのシグナルを待つEC2・Auto Scalingグループの初期設定を待つ(推奨)
Resources:
  Gateway:
    Type: AWS::EC2::VPCGatewayAttachment
    Properties: { VpcId: !Ref Vpc, InternetGatewayId: !Ref Igw }
  WebServer:
    Type: AWS::EC2::Instance
    DependsOn: Gateway        # IGWのアタッチ完了後に作成
    Properties: { ... }

  WaitHandle:
    Type: AWS::CloudFormation::WaitConditionHandle
  WaitForSetup:
    Type: AWS::CloudFormation::WaitCondition
    DependsOn: WebServer      # 作成後に待ち始める
    Properties:
      Handle: !Ref WaitHandle
      Timeout: '600'
      Count: 1
  • 典型例は、インターネットゲートウェイのアタッチ(VPCGatewayAttachment)が終わってから、パブリックIPを使うEC2やElastic IP、NATゲートウェイを作るケース。参照関係がないため、DependsOnが必要になる。
  • DependsOnに循環した指定(AがBに、BがAに依存)があると、テンプレートはエラーになる。
  • WaitConditionは、タイムアウトまでに必要な数の成功シグナルが届かないと作成失敗→ロールバック。WaitConditionのDependsOnには、待ち始めるタイミングになるリソースを指定する。
  • WaitConditionは「外部の処理を待つ」ためのもので、EC2やAuto Scalingグループの設定待ちにはCreationPolicyを使う。

UpdatePolicy(Auto Scalingグループの更新)#

Auto Scalingグループの起動テンプレート(AMIなど)を変えてスタックを更新しても、既定では既存のインスタンスは置き換わりません(新しく起動するものから適用される)。UpdatePolicyを付けると、スタックの更新時にインスタンスをどう入れ替えるかを指定できます。

ポリシー動作
AutoScalingRollingUpdate既存のグループの中で、インスタンスを数台ずつ新しいものに入れ替える。MaxBatchSize(一度に入れ替える数)、MinInstancesInService(最低限動かしておく数)、PauseTime、WaitOnResourceSignals(cfn-signalを待つ)を指定する
AutoScalingReplacingUpdateWillReplace: true で、新しいAuto Scalingグループを丸ごと作り、成功したら古いグループを削除する。失敗すると古いグループのまま戻せる
AutoScalingScheduledActionスケジュールされたアクションがあるグループで、更新時に台数の設定が元に戻されないようにする

ローリング更新はリソースを節約できますが、途中で失敗すると新旧が混在した状態から戻すことになります。確実に戻せることを重視するなら置き換え更新を選びます。

終了保護#

スタックの終了保護を有効にすると、スタックの削除操作が拒否されます。本番環境のスタックを誤って削除するのを防ぎます。ネストスタックでは、親(ルート)スタックの設定が適用されます。

仕組み防ぐもの単位
終了保護スタックの削除スタック
DeletionPolicyスタックの削除時やリソースを外したときに、リソースが消えること(Retain/Snapshot)リソース
スタックポリシースタックの更新による特定リソースの変更・置き換えリソース(更新時)

DeletionPolicyとSnapshot#

DeletionPolicyはリソースごとに書く属性で、スタックを削除したときやテンプレートからそのリソースを消して更新したときに、実際のリソースをどう扱うかを決めます。

Resources:
  AppDB:
    Type: AWS::RDS::DBInstance
    DeletionPolicy: Snapshot          # 削除の前に最終スナップショットを取る
    UpdateReplacePolicy: Snapshot     # 更新で置き換えになるときも、古いDBのスナップショットを取る
    Properties:
      Engine: mysql
      DBInstanceClass: db.t4g.medium
      AllocatedStorage: "20"
値動き向いている場面
Deleteリソースを削除する(既定)作り直せる一時的なリソース
Retainリソースを残したまま、スタックの管理から外す消したくないS3バケット・DynamoDBテーブル・ログ。残ったリソースの料金はかかり続ける
Snapshotスナップショットを取ってからリソースを削除するデータは残したいが、リソース自体は止めて費用を抑えたいDB・ボリューム
RetainExceptOnCreate作成に失敗してロールバックするときは削除し、それ以外は残す作成失敗で中途半端なリソースが残るのを避けたいとき

Snapshot を指定できるのは、スナップショットの機能があるリソースだけです。

  • AWS::EC2::Volume(EBSボリューム)
  • AWS::RDS::DBInstance・AWS::RDS::DBCluster(Auroraを含む)
  • AWS::ElastiCache::CacheCluster・AWS::ElastiCache::ReplicationGroup
  • AWS::Redshift::Cluster、AWS::Neptune::DBCluster、AWS::DocDB::DBCluster

EC2インスタンスやS3バケットには Snapshot は使えません(S3バケットを残したいなら Retain)。また、DeletionPolicyで残したスナップショットはスタックの管理外になるため、不要になったら自分で削除します。なお、AWS::RDS::DBCluster と、クラスターに属さない AWS::RDS::DBInstance では、DeletionPolicyを書かないときの既定が Snapshot になります。

UpdateReplacePolicy は、更新でリソースが置き換え(新しく作り直し)になるときに、古いリソースをどう扱うかを決める属性です。値はDeletionPolicyと同じです。DBのように置き換えでデータが消えると困るリソースには、両方を書いておくと安全です。

カスタムリソース(Custom::)#

CloudFormationが対応していない処理や、外部のシステムへの登録を、スタックの作成・更新・削除に合わせて実行したいときは、カスタムリソースを使います。リソースのタイプを Custom:: で始まる任意の名前(例:Custom::DBUser)、または AWS::CloudFormation::CustomResource にします。

Resources:
  CreateDBUser:
    Type: Custom::DBUser
    Properties:
      ServiceToken: !GetAtt DBUserFunction.Arn   # 処理を行うLambda関数(またはSNSトピック)のARN
      UserName: app_user                         # Lambdaに渡す値(自由に決める)
Outputs:
  UserArn:
    Value: !GetAtt CreateDBUser.UserArn            # Lambdaが返した値を使える
  1. スタックの作成・更新・削除のとき、CloudFormationが ServiceToken で指定したLambda関数(またはSNSトピック)にリクエストを送る。RequestType は Create・Update・Delete のどれか
  2. Lambda関数が処理を行い、結果(SUCCESS/FAILED)を、リクエストに含まれる署名付きURL(ResponseURL)に返す。Pythonなら cfn-response モジュールが使える
  3. CloudFormationは応答を受け取ってから次のリソースに進む。返した Data の値は !GetAtt で参照できる

よくある失敗は、Lambdaが応答を返さないまま終わることです。例外で落ちたり、Delete の処理を書き忘れたりすると、CloudFormationは応答を待ち続け、最大1時間(既定のタイムアウト)スタックが CREATE_IN_PROGRESS や DELETE_IN_PROGRESS のまま止まります。ServiceTimeout プロパティで待つ時間を短くでき、関数ではエラー時も必ずFAILEDを返すように実装します。

代表的な使い方は、DBのユーザー作成、AMIのIDの検索、S3バケットを削除する前の中身の削除、外部のSaaSへの登録などです。CloudFormationのレジストリに登録して自分のリソースタイプとして使う「リソースタイプ(拡張機能)」もありますが、手軽に処理を足すならカスタムリソースが定番です。

StackSetsとスタックインスタンスの状態(OUTDATEDなど)#

StackSetsは、1つのテンプレートから複数のアカウント・リージョンにスタックを展開します。展開先の1つ1つ(アカウント×リージョン)をスタックインスタンスと呼び、それぞれに状態があります。

状態意味
CURRENTスタックセットの最新の内容で、正常に作成・更新できている
OUTDATEDスタックセットの最新の内容がまだ反映されていない。最後の操作でそのスタックの作成・更新に失敗したか、操作が途中で止まった
INOPERABLEスタックの削除に失敗し、スタックセットから外れた状態。手動で削除してから、スタックインスタンスを外す(RetainStacks)

OUTDATED になる主な原因は次のとおりです。

  • 展開先のアカウントに、必要なIAMロールがない・信頼関係が正しくない(セルフマネージドの権限では、管理者アカウントに AWSCloudFormationStackSetAdministrationRole、展開先に AWSCloudFormationStackSetExecutionRole が必要)
  • 展開先のリージョンが有効になっていない(オプトインが必要なリージョン)
  • テンプレートの中のリソース名の重複(S3バケット名など、グローバルに一意の名前を固定している)や、サービスクォータの上限
  • SCPで、そのアカウント・リージョンでの操作が拒否されている

原因はスタックインスタンスの状態の理由(StatusReason)と、展開先のアカウントのスタックイベントで確認します。原因を直したら、スタックセットの操作(更新やスタックインスタンスの更新)をやり直すと CURRENT に戻ります。

権限モデル内容
セルフマネージドIAMロール(上記の2つ)を自分で各アカウントに作る。Organizationsを使わない場合
サービスマネージドOrganizationsと連携し、ロールは自動で作られる。OUを指定でき、自動デプロイを有効にすると、OUに新しく入ったアカウントにも自動で展開される

展開の速さと安全性は、同時アカウント数(一度にいくつのアカウントに展開するか)と障害耐性(何アカウントの失敗まで続行するか)で調整します。障害耐性を超えて失敗すると、その操作は止まり、残りのアカウントは古い内容のままになります。

3. ユースケース#

  • 開発・ステージング・本番で同じ構成の環境を再現
  • 複数アカウントへ共通のセキュリティ設定を展開(StackSets)
  • 本番のDBを誤って削除しないよう保護(DeletionPolicy: Retain/Snapshot、スタックポリシー)

4. 料金の考え方#

CloudFormation自体は(AWSリソースを扱う範囲では)無料です。作成されたリソースに料金がかかります。

5. 関連サービス#

  • AWS CDK:プログラミング言語で書いてCloudFormationに変換
  • AWS SAM:サーバーレス向けの拡張
  • AWS Secrets Manager/Parameter Store:ダイナミックリファレンス
  • AWS Lambda:カスタムリソース
  • AWS Service Catalog:テンプレートを製品として配布
  • AWS CodePipeline:CI/CDでのデプロイ
  • 関連する用語:JSONとYAMLの読み方、TerraformとGit、iam:PassRoleとサービスにリンクされたロール

6. 試験・実務でのポイント#

テンプレートの書き方

  • リソースのIDや名前 → !Ref、ARNやDNS名などの属性 → !GetAtt、リージョンごとのAMI → Mappings+!FindInMap。
  • 別のスタックの値を使う → Export+!ImportValue(同じリージョンのみ。インポートされている間はエクスポート側を削除・変更できない)。
  • パスワードを直書きしない → ダイナミックリファレンス/NoEcho。
  • IAMリソースを作るテンプレート → --capabilities CAPABILITY_IAM が必要。

更新・変更管理

  • 変更の影響を事前確認 → 変更セット。手動変更によるズレ → ドリフト検出。
  • Lambdaのコードを更新したのに反映されない → S3キーかVersionIdを変える。
  • ROLLBACK_COMPLETE のスタックは更新できない → 削除して作り直す。UPDATE_ROLLBACK_FAILED → 原因を直して更新のロールバックを続行。
  • インスタンス内のアプリの準備ができるまで完了にしない → cfn-init+cfn-signal+CreationPolicy。シグナルが届かないとタイムアウトでロールバック。
  • AMIを変えたらAuto Scalingのインスタンスも入れ替えたい → UpdatePolicy(ローリング更新/置き換え更新)。

保護・展開

  • スタック削除時にリソースを残す → DeletionPolicy: Retain(デフォルトはDelete)。
  • スタックの誤削除を防ぐ → 終了保護。リソースを残す → DeletionPolicy。更新から守る → スタックポリシー。
  • 複数アカウント・リージョンへ展開 → StackSets。
  • StackSetsのスタックインスタンスが OUTDATED → そのアカウント・リージョンへの展開に失敗している。実行ロールの有無・リージョンの有効化・名前の重複・クォータを確認し、操作をやり直す。
  • OUに追加したアカウントにも自動で展開 → サービスマネージドの権限+自動デプロイ。
  • スタック削除時にDBやEBSのデータをスナップショットで残してリソースは削除 → DeletionPolicy: Snapshot(EC2インスタンスやS3バケットには使えない)。置き換え時にも残す → UpdateReplacePolicy。
  • CloudFormationが対応していない処理をスタックに組み込む → カスタムリソース(Custom::+ServiceToken にLambda)。スタックが IN_PROGRESS のまま止まる → Lambdaが応答URLに結果を返していない。

7. まとめ#

  • CloudFormationはテンプレートからスタックを作るIaCサービス。
  • DeletionPolicy・変更セット・ドリフト検出・スタックポリシーで安全に運用する。
  • 秘密情報はダイナミックリファレンス、マルチアカウントはStackSets。
マネジメントとガバナンス

AWS CDK

プログラミング言語でインフラを定義し、CloudFormationとしてデプロイ

1. サービス概要#

AWS CDK(Cloud Development Kit)は、プログラミング言語でインフラを定義し、テンプレートとしてデプロイするためのツールです。CloudFormationをコードで書けるようにしたもので、最終的にはCloudFormationテンプレートに変換されます。

2. 主な機能・特徴#

サポート言語#

TypeScript、JavaScript、Python、Java、C#、Go

アプリ・スタック・Construct#

  • アプリ:CDKのプロジェクト全体。1つのアプリに複数のスタックを入れられる。
  • スタック:CloudFormationのスタック1つに対応する単位。どのアカウント・リージョンに作るか(環境)を指定する。
  • Construct:スタックの中に置く部品。

Construct#

AWSリソースや構成をオブジェクト化したものです。Constructを組み合わせてインフラを定義します。抽象度の違う3つのレベルがあります。

レベル内容例
L1CloudFormationのリソースと1対1で対応する。名前は Cfn で始まり、すべてのプロパティを自分で書くCfnBucket
L2よく使う設定が既定値として入り、便利なメソッドが付いている。ふつうはこれを使うs3.Bucket(bucket.grantRead(fn) で必要なIAMポリシーを自動で作る)
L3(パターン)複数のリソースを組み合わせた構成をまとめて作るApplicationLoadBalancedFargateService(ALB+ECSのFargateサービス)

次は、L2のConstructでS3バケットとLambda関数を作り、関数にバケットの読み取りを許可する例(TypeScript)です。IAMポリシーを書かなくても、grantRead が最小限の権限を作ります。

const bucket = new s3.Bucket(this, 'Reports', {
  encryption: s3.BucketEncryption.S3_MANAGED,
  versioned: true,
});
const fn = new lambda.Function(this, 'Reader', {
  runtime: lambda.Runtime.NODEJS_22_X,
  handler: 'index.handler',
  code: lambda.Code.fromAsset('lambda'),
});
bucket.grantRead(fn);

Aspects#

CDKで作成されたConstruct群を検査・変更し、CDK全体へ共通ルールを適用する機能です。ルール違反やセキュリティのチェックに使います。例えば「すべてのS3バケットが暗号化されているか」を確かめたり、すべてのリソースに共通のタグを付けたりできます。セキュリティのルールをまとめたcdk-nagも、Aspectsのしくみを使っています。

コマンドと開発の流れ#

コマンド内容
cdk initプロジェクトを作る
cdk bootstrapデプロイの準備をする。アカウント・リージョンごとに1回、CDKToolkit スタック(アセット用のS3バケット・ECRリポジトリ・デプロイ用のIAMロール)を作る
cdk synthCloudFormationテンプレートを生成する
cdk diff今のスタックとの差分を表示する。デプロイ前に、リソースの置き換えや削除が起きないかを確かめる
cdk deployデプロイする(内部ではCloudFormationのスタックを作成・更新する)
cdk destroyスタックを削除する
  • Lambdaのコードやコンテナイメージなどのアセットは、bootstrapで作ったS3バケット・ECRリポジトリにアップロードされてからデプロイされる。そのため、bootstrapをしていない環境ではデプロイが失敗する。
  • 別のアカウント(パイプラインのアカウントなど)からデプロイさせるときは、cdk bootstrap --trust でそのアカウントを信頼する。
  • デプロイが失敗したときの原因は、CloudFormationのスタックのイベントで確認する。失敗した変更は、CloudFormationが自動でロールバックする。

運用で気を付けること#

  • 論理IDが変わるとリソースが置き換わる:Constructの名前(ID)を変えたり、別のConstructの下に移したりすると、CloudFormationの論理IDが変わり、リソースが削除されて作り直される。データベースなどでは、cdk diff で置き換えにならないかを必ず確かめる。
  • 削除ポリシー:S3バケットやDynamoDBテーブルなどデータを持つリソースは、既定でスタックを消しても残る(RETAIN)。消してよい開発環境では removalPolicy: DESTROY を指定する(S3は中身を消す設定も必要)。
  • コンソールでの手動変更は、CDKのコードとずれる(ドリフト)。変更はコードで行う。
  • テスト:assertionsモジュールで、生成されるテンプレートに期待するリソースや設定があるかを、単体テストで確かめられる。

CI/CD(CDK Pipelines)#

CDK Pipelinesは、CodePipelineを使ったデプロイのパイプラインをCDKのコードで作る仕組みです。パイプライン自体もコードから更新される(セルフミューテーション)ため、ステージやアカウントを追加するときも、コードを変えてpushするだけで済みます。開発 → 検証 → 本番のように、複数のアカウント・リージョンへ順にデプロイし、本番の前に手動の承認を入れることもできます。

3. ユースケース#

  • ループや条件分岐を使って、似た構成のリソースを効率よく定義
  • アプリと同じ言語でインフラも管理
  • Aspectsで「全S3バケットが暗号化されているか」をチェック

4. 料金の考え方#

CDK自体は無料のオープンソースツールです。作成されたリソースに料金がかかります。

5. 関連サービス#

  • AWS CloudFormation:CDKの変換先・デプロイ先
  • AWS SAM:サーバーレス向けのIaC
  • AWS CodePipeline:CDKアプリのCI/CD(CDK Pipelines)
  • Amazon S3/Amazon ECR:bootstrapで作るアセットの置き場所
  • AWS IAM:grantメソッドで作られるポリシー、デプロイ用のロール
  • 関連する用語:JSONとYAMLの読み方、TerraformとGit

6. 試験・実務でのポイント#

  • CDKはCloudFormationテンプレートに変換されてデプロイされる。
  • 全Constructに共通ルール・チェックを適用 → Aspects。
  • プログラミング言語でIaC → CDK、YAML/JSON → CloudFormation。
  • 初めてデプロイする環境で失敗する(アセットのバケットがない)→ cdk bootstrap。
  • デプロイ前に変更内容・置き換えを確かめる → cdk diff。
  • Constructの名前を変えたらリソースが作り直された → 論理IDが変わったため。
  • スタックを消してもS3バケットが残る → データを持つリソースの既定の削除ポリシーはRETAIN。
  • 権限の付与 → L2の grant メソッドで、最小限のIAMポリシーを自動で作る。
  • CDKで書いたインフラを複数のアカウントへ順にデプロイ → CDK Pipelines。

7. まとめ#

  • CDKはプログラミング言語でインフラを書くツール。中身はCloudFormation。
  • リソースはConstruct(ふつうはL2)、共通チェックはAspects。
  • bootstrap → synth → diff → deploy の流れ。論理IDの変化による置き換えと、削除ポリシーに注意する。

サービスの選び方

メッセージングサービスの選び方

SQS・SNS・EventBridge・Kinesis Data Streamsの違いと使い分け

1. 詳しい説明#

システムの部品どうしを直接呼び出さず、メッセージ(イベント)を間に挟んでつなぐと、片方が遅くなったり止まったりしても、もう片方が影響を受けにくくなります(疎結合)。AWSにはそのためのサービスが複数あり、違いは「受け手にどう届けるか」と「データを残しておくか」です。

比較表#

項目SQSSNSEventBridgeKinesis Data Streams
種類メッセージキューPub/Sub(通知)イベントバスストリーム
届け方受け手がポーリングして取りに行く購読者へプッシュルールに一致したターゲットへプッシュ受け手(コンシューマー)が読みに行く
1件を受け取る数1つの処理(処理したら削除する)すべての購読者一致したルールのターゲット(1ルールに最大5つ)複数のコンシューマーがそれぞれ読む
データの保持既定4日、最大14日保持しない(配信を再試行する)保持しない(アーカイブすれば再生できる)既定24時間、最大365日。読み直せる
順序FIFOキューで保証FIFOトピックで保証保証しないシャードの中で保証
振り分けなし(キューごとに分ける)サブスクリプションのフィルターポリシーイベントパターン(内容の細かい条件)なし(パーティションキーでシャードに分ける)
得意なこと処理を後回しにしてためる1つの出来事を多くの宛先へAWSサービス・SaaSのイベントを条件で振り分け大量のデータをリアルタイムに、複数の処理で使う

受け取ったデータをS3・OpenSearch・Redshiftなどへ保存するだけなら、コードを書かずに配送できるAmazon Data Firehoseを使います。Kinesis Data Streamsの後ろにFirehoseをつないで、リアルタイム処理と保存を両方行う構成もよく使われます。

組み合わせて使う#

代表的なのは、SNSとSQSを組み合わせるファンアウトです。SNSトピックに複数のSQSキューを購読させると、1つのメッセージが各キューに複製されます。受け手ごとにキューがあるので、どれかの処理が止まっても、メッセージはそのキューにたまって失われません。

AWSサービスのイベント(EC2の状態変化、AWS Healthの通知など)を受けて処理するときは、EventBridgeのルールでSQSに送り、Lambdaがキューから処理する形もよく使われます。急に大量のイベントが来ても、キューがためてくれるのでLambdaの同時実行数をあふれさせません。

選び方のポイント#

  • 処理が追いつかないときにためておき、バックエンドを守りたい → SQS。
  • 1つの出来事を、メール・SMS・複数のシステムに同時に知らせたい → SNS(システム向けはSNS+SQSのファンアウト)。
  • AWSサービスやSaaSのイベントを、内容の条件で振り分けたい → EventBridge。決まった時刻に処理を動かすのもEventBridge(Scheduler)。
  • クリックストリームやログなど大量のデータを順序どおりに、複数の処理で読んだり読み直したりしたい → Kinesis Data Streams。
  • 集めたデータをS3などへ保存するのが目的 → Data Firehose。
  • 順番どおりに1回だけ処理したい → SQSのFIFOキュー(SNSならFIFOトピック)。
  • 処理に何度も失敗するメッセージを退避したい → デッドレターキュー(DLQ)。SQS・SNS・EventBridgeのどれでも設定できる。
  • 複数の処理の順番・分岐・待ち合わせを管理したい → メッセージングではなくStep Functions。
  • オンプレミスのActiveMQやRabbitMQを、コードをあまり変えずに移したい → Amazon MQ。

SQSを使った構成例は、運用シナリオ「キューで処理を分離し、急増や障害に強くする」で説明しています。

  • 高可用性とスケーリング:疎結合にすると、部品ごとにスケールできる
  • サーキットブレーカー:障害を広げないための設計パターン
  • キャッシュの選び方:読み取りの負荷を下げる、もう1つの方法
