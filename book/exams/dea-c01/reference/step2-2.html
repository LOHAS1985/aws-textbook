Amazon Kinesis

ストリーミングデータを収集・処理・配信するサービス群

1. サービス概要#

Amazon Kinesisは、ストリーミングデータ(絶え間なく発生し続けるデータ)を扱うサービス群です。

  • データストリームの受け取りとリアルタイム処理:Kinesis Data Streams
  • S3などのデータストアへのデータの配送:Amazon Data Firehose(旧称 Kinesis Data Firehose)
  • 動画ストリームの取り込み・保存:Kinesis Video Streams

ストリームデータの分析・変換には、かつて「Kinesis Data Analytics」と呼ばれていた Amazon Managed Service for Apache Flink を使います。Kafka互換のストリーム基盤は Amazon MSK を参照してください。

2. 主な機能・特徴#

用語#

シャード:データを処理するレーンのようなもの(1本あたりの性能は固定)。シャードを増減することでスケーリングします。

Kinesis Data Streams(リアルタイムのストリーム処理)#

ストリームデータを処理するアプリを独自に構築します。必要なキャパシティを設定してストリームを作成するだけで使えます。

項目プロビジョンドオンデマンド
スケーリングの主体ユーザーが管理AWSが自動管理
シャード管理手動で指定自動で増減
初期設定シャード数を決める必要あり設定不要
スループット上限シャード数に依存トラフィックに応じて自動拡張
コストモデルシャード時間課金+PUTペイロード使用量ベース
高負荷・安定した負荷コスト効率が良い割高になりやすい
ホットシャード対策必須依然として必要(重要)
シャードの見え方明示的に見える論理的に非表示
典型的なユースケース安定した大量のストリーム不規則・予測できないトラフィック

Amazon Data Firehose(データの配送・変換・保存)#

  • ストリームデータを S3、Redshift、OpenSearch Service などへ配信する。
  • Lambdaを呼び出してレコードを変換できる。

Data Streamsは自分でコンシューマー(Lambda・アプリなど)を作ってリアルタイムに処理するサービス、Firehoseはコードをほぼ書かずに保存先へ届けるフルマネージドな配送サービスです。Firehoseはバッファリングしてまとめて配信するため、ほぼリアルタイム(数十秒〜数分の遅延)になります。

3. ユースケース#

  • IoTデバイスやアプリのクリックストリームのリアルタイム処理(Data Streams+Lambda)
  • 大量のログをS3やOpenSearchへ自動で配信・蓄積(Firehose)
  • リアルタイムのダッシュボード・異常検知

4. 料金の考え方#

Data Streamsは、プロビジョンドならシャード時間+PUTペイロード、オンデマンドなら使用量ベースで課金されます。安定した高負荷ならプロビジョンド、不規則な負荷ならオンデマンドが向いています。

Firehoseは取り込んだデータ量に応じて課金されます。

5. 関連サービス#

  • AWS Lambda:Data Streamsのコンシューマー、Firehoseでの変換
  • Amazon S3/Amazon OpenSearch Service:Firehoseの配信先
  • Amazon Athena:S3に蓄積したデータの分析
  • Amazon EventBridge:Pipesのソースとして利用
  • Amazon DynamoDB:DynamoDB Streamsとの違いに注意
  • Amazon Data Firehose:保存先への配送(詳しい説明)
  • Amazon MSK:Apache Kafka互換のストリーム基盤
  • Amazon Managed Service for Apache Flink:ストリーミングデータの継続処理
  • 関連する用語:データパイプラインの基礎

6. 試験・実務でのポイント#

  • 独自処理でリアルタイム → Data Streams。S3などへそのまま配信 → Firehose。
  • スループット不足 → シャードを増やす(プロビジョンド)かオンデマンドに。
  • 特定のシャードに偏る(ホットシャード)→ パーティションキーを分散させる。
  • Firehoseでのデータ変換 → Lambda。
  • SQS・SNS・EventBridge・Kinesisの使い分け → メッセージングサービスの選び方。

7. まとめ#

  • Kinesisはストリーミングデータのサービス群。シャードでスケールする。
  • Data Streamsはリアルタイム処理、Firehoseは配送・変換・保存。

Amazon Data Firehose

ストリーミングデータを受け取り、変換してS3・Redshift・OpenSearchなどへ自動で届ける

1. サービス概要#

Amazon Data Firehose(旧称 Kinesis Data Firehose)は、ログやイベントなどのストリーミングデータを受け取り、S3・Redshift・OpenSearch Service などの保存先へ自動で届けるフルマネージドの配送サービスです。

受け取ったデータを一定量・一定時間ためてから(バッファリング)まとめて書き込むため、届くまでに数秒〜数分かかる「ほぼリアルタイム」の処理になります。サーバーやシャードの管理は不要で、データ量に合わせて自動でスケールします。

2. 主な機能・特徴#

データの送り元(ソース)#

  • アプリやエージェントからの直接の送信(PutRecord/PutRecordBatch)
  • Kinesis Data Streams・Amazon MSK(Kafka)からの読み取り
  • CloudWatch Logs のサブスクリプションフィルター、CloudWatch メトリクスストリーム
  • VPCフローログ・WAFのログ・IoT Coreのルールなど

主な配送先#

配送先主な用途
Amazon S3ログの長期保存、Athenaでの分析(データレイク)
Apache Iceberg テーブルS3上のテーブル形式での保存
Amazon Redshiftデータウェアハウスでの分析(いったんS3に置いてからCOPY)
OpenSearch Service/Serverlessログの検索・可視化
HTTPエンドポイント・SaaSSplunk・Datadog・New Relic・Snowflake など

バッファリング#

配送先への書き込みは、バッファのサイズ(MB)か時間(秒)のどちらかに達したときに行われます。小さくするほど早く届き、大きくするほどファイルの数が減ってS3やAthenaで扱いやすくなります。

変換・加工#

  • Lambdaによる変換:レコードを1件ずつ加工・絞り込みする(例:CloudWatch Logsの圧縮データを展開して整形)。
  • 形式の変換:JSONを Parquet・ORC に変換してS3に保存する(Glueデータカタログのスキーマを使う)。Athenaの検索が速く・安くなる。
  • 動的パーティショニング:レコードの中身(顧客IDなど)でS3のプレフィックスを分ける。
  • 圧縮(GZIP・Snappyなど)と、KMSによる暗号化。

エラー処理と監視#

  • 配送先に書き込めないときは一定時間再試行し、それでも失敗したデータは S3 のバックアップ先に保存される。
  • エラーはCloudWatch Logsに記録できる。CloudWatchメトリクス(DeliveryToS3.Success、DeliveryToS3.DataFreshness など)で、配送の成功や遅れを監視する。
  • VPC内のOpenSearchなどにも配送できる。

Kinesis Data Streams との違い#

項目Data FirehoseKinesis Data Streams
目的保存先への配送自分で作る処理でのリアルタイム処理
遅延ほぼリアルタイム(バッファリングあり)リアルタイム(ミリ秒〜)
管理不要(自動でスケール)シャード数の管理(オンデマンドモードもある)
データの保持・再読み込みできない保持期間内なら何度でも読める

3. ユースケース#

  • 複数アカウントの CloudWatch Logs を、サブスクリプションフィルター経由で中央のS3に集める
  • VPCフローログやWAFのログをParquetに変換してS3に保存し、Athenaで分析する
  • アプリのログをOpenSearchやSplunkに送って検索できるようにする

4. 料金の考え方#

取り込んだデータ量(GB)に応じて課金されます。形式の変換・動的パーティショニング・VPCへの配送などを使うと、その処理量に応じた料金が追加されます。Lambdaによる変換では、Lambdaの料金も別にかかります。

5. 関連サービス#

  • Amazon Kinesis:Data Streams(リアルタイム処理)
  • Amazon MSK:Kafkaストリームの配送元
  • Amazon Managed Service for Apache Flink:ストリームデータの継続的な変換・分析
  • Amazon CloudWatch:サブスクリプションフィルター・メトリクスストリーム・監視
  • Amazon S3/Amazon Athena:保存と分析
  • Amazon OpenSearch Service:ログの検索・可視化
  • AWS Lambda:レコードの変換
  • ログの一元管理(運用シナリオ)

6. 試験・実務でのポイント#

  • 「ストリーミングデータをコードを書かずにS3・Redshift・OpenSearchへ」→ Data Firehose。
  • 「ミリ秒単位のリアルタイム処理」「データを再読み込み」→ Kinesis Data Streams。
  • S3に届くのが遅い・ファイルが細かすぎる → バッファのサイズ・時間を調整する。
  • Athenaを速く安く → Parquetへの形式の変換。配送の失敗分は S3 のバックアップに残る。
  • SQS・SNS・EventBridge・Kinesisの使い分け → メッセージングサービスの選び方。

7. まとめ#

  • Data Firehoseは、ストリーミングデータをバッファリングして保存先へ届けるフルマネージドの配送サービス。
  • Lambdaでの変換・Parquetへの変換・失敗時のS3へのバックアップができる。

Amazon MSK

Apache Kafka互換のストリーミング基盤をマネージドで利用するサービス

1. サービス概要#

Amazon Managed Streaming for Apache Kafka (Amazon MSK)は、Apache Kafkaを使ったストリーミングアプリケーションのためのマネージドサービスです。AWSがクラスターの作成・管理を担い、既存のKafkaプロデューサーやコンシューマーを利用できます。

2. 主な機能・特徴#

Kafkaの基本構成#

  • プロデューサーがイベントをトピックへ書き込む。
  • トピックは複数のパーティションに分かれ、ブローカーに分散して保存される。
  • コンシューマーグループの各コンシューマーがパーティションを分担して読み取る。
  • オフセットで読み取り位置を管理し、保持期間内のレコードを再読込できる。

利用形態と連携#

MSK Provisionedはブローカーの種類や数を選びます。MSK Serverlessはブローカーの容量管理をAWSに任せます。MSK ConnectでKafka Connectコネクターを実行し、外部システムとのデータ連携もできます。MSK Replicatorはクラスター間のレプリケーションに使います。

ストリーム処理サービスとの違い#

MSKはKafka互換のイベントストリームを提供します。Kinesis Data StreamsはAWSネイティブなストリーム基盤で、Data Firehoseは処理済みデータを保存先へ配送するサービスです。Apache Flinkなどの処理エンジンは、ストリーム上のイベントを変換・集計する役割を担います。

3. ユースケース#

  • Kafkaを利用する既存アプリケーションのストリーミング処理。
  • イベントを複数のコンシューマーへ配信し、それぞれで独立して処理する。
  • Kafka Connectを使ったデータソース・保存先との連携。
  • 保持期間内のイベントを再生して、障害後の処理をやり直す。

4. 料金の考え方#

Provisionedはブローカーとストレージなどの稼働、Serverlessは利用量などが課金要因です。データ転送、MSK ConnectやReplicator、連携先サービスの料金も考慮します。保持期間・パーティション数・複製数がストレージ量や処理能力に影響します。

5. 関連サービス#

  • Amazon Kinesis:AWSネイティブなストリーミングデータ処理
  • Amazon Data Firehose:ストリームを保存先へ管理不要で配送
  • AWS Glue:ストリームETLとData Catalog
  • Amazon EMR:Sparkなどによる大規模分散処理
  • Amazon MWAA:データパイプラインのオーケストレーション

6. 試験・実務でのポイント#

  • Apache Kafka互換性を保ったマネージドストリーミング → Amazon MSK。
  • 保持期間内にオフセットを戻して再読込できる。再処理時の重複や冪等性も設計する。
  • スループットを高めるにはパーティション数とコンシューマー並列度を検討する。
  • 運用するKafkaクラスター → Provisioned。ブローカー管理を任せる → Serverless。
  • MSKはストリーム基盤、Data Firehoseは配送、Glue/Flinkは変換処理という役割を区別する。

7. まとめ#

  • MSKはApache Kafka互換のストリーミングサービス。
  • トピック・パーティション・オフセットでイベントを保持し、複数のコンシューマーが処理する。
  • ProvisionedとServerless、Kafka Connect、Replicatorを要件に合わせて使う。
移行と転送

AWS Database Migration Service

データベース間の移行や継続的な変更レプリケーションを行うサービス

1. サービス概要#

AWS Database Migration Service (AWS DMS)は、リレーショナル・NoSQLデータベースやデータウェアハウスなどのデータ移行とレプリケーションを支援するサービスです。AWS内外のソースとターゲットを接続し、1回限りの移行や継続的な変更データキャプチャ(CDC)を実行します。

2. 主な機能・特徴#

移行タスク#

  • ソースとターゲットのエンドポイント、ネットワーク接続、認証情報を設定する。
  • 全件ロードを行い、その後に変更を継続複製して、切り替えまでデータを同期する。
  • 移行タスクの状態、遅延、エラーを監視して、再試行やリソース調整を行う。

データ移行とスキーマ変換#

DMSはデータの移行・レプリケーションを担います。異なるデータベースエンジンへ移行する場合、AWS DMS Schema ConversionやAWS Schema Conversion Toolでスキーマやコードの互換性を評価・変換します。移行元と移行先の型・関数・制約が完全に一致するとは限らないため、変換結果を確認してテストします。

接続と整合性#

ソース・ターゲットのセキュリティグループ、ルーティング、認証情報、ネットワーク到達性を確認します。移行中の更新量が大きい場合は、レプリケーション遅延を監視します。切り替え前には件数・チェックサム・業務上の重要な値を比較します。

3. ユースケース#

  • オンプレミスや別クラウドのデータベースをAWSへ移行する。
  • 移行中も業務を続けるために、初期ロード後の変更を継続同期する。
  • 分析用データベースへ業務DBの変更をレプリケーションする。

4. 料金の考え方#

レプリケーションに使うインスタンスやサーバーレスの処理能力、ストレージ、ログ、データ転送などが課金要因です。移行作業に必要な期間・容量を見積もり、完了後に不要なレプリケーション資源を停止・削除します。

5. 関連サービス#

  • Amazon RDS/Amazon Aurora:移行先データベース
  • Amazon Redshift:分析用ウェアハウス
  • AWS Glue:移行後のETLとData Catalog
  • Amazon CloudWatch:タスクのログ・メトリクス監視

6. 試験・実務でのポイント#

  • 異なるデータベース間のデータ移行や継続同期 → AWS DMS。
  • 全件ロード後も変更を追従させる → CDCタスク。
  • データの移行とスキーマ・コードの変換は別の作業として計画する。
  • レプリケーション遅延、エラー、データ整合性を切り替え前に確認する。

7. まとめ#

  • AWS DMSはデータベースなどの移行と継続レプリケーションを行う。
  • スキーマ変換、ネットワーク、データ整合性の確認は移行計画に含める。
アプリケーション統合

Amazon AppFlow

SaaSアプリケーションとAWSの間でデータを転送するマネージド連携サービス

1. サービス概要#

Amazon AppFlowは、SalesforceなどのSaaSアプリケーションとAmazon S3・Amazon Redshiftなどの間でデータを安全に転送するマネージドサービスです。コードを書かずにフローを定義し、手動・スケジュール・イベントを契機に実行できます。

2. 主な機能・特徴#

フローの設定#

  • ソースと宛先、対象オブジェクト・項目、実行条件を指定する。
  • フィールドの対応付け、フィルター、簡単な変換を設定する。
  • 一括転送だけでなく、変更されたレコードを定期的に同期する構成も選べる。
  • S3への出力をパーティション分割し、Glue Data Catalogに登録して分析サービスから検索しやすくできる。

セキュリティと監視#

転送中と保存時のデータ暗号化に対応し、AWS PrivateLinkを使ってプライベートに転送できる接続先もあります。すべてのコネクターや転送先で同じ接続方式が使えるわけではないため、要件とコネクターの対応状況を確認します。API操作はCloudTrailで監査できます。

3. ユースケース#

  • Salesforceの顧客・商談情報を定期的にS3へ集めて分析する。
  • 業務SaaSのレコードをRedshiftへ取り込み、BIレポートに使う。
  • 複数のSaaSアプリケーションからデータを集約し、データレイクを作る。

4. 料金の考え方#

フローの実行回数や処理したデータ量などに応じて料金が発生します。接続先SaaSのAPI利用制限や契約条件、S3・Redshiftの保存・処理料金も考慮します。頻繁な同期が必要か、定期的な一括取り込みでよいかを見極めます。

5. 関連サービス#

  • Amazon S3:転送データの保存とデータレイク
  • Amazon Redshift:分析用データウェアハウス
  • AWS Glue:カタログ化と複雑なETL
  • AWS CloudTrail:フローの操作履歴の監査
  • Amazon VPC:PrivateLinkを使う接続の基盤

6. 試験・実務でのポイント#

  • SaaSアプリケーションからAWSへコードを書かずに転送 → Amazon AppFlow。
  • 複雑な変換・大規模な統合処理にはGlueなどを組み合わせる。
  • スケジュール実行かイベント駆動かを、データの鮮度とSaaS側API制限に合わせて選ぶ。
  • 外部SaaSへの接続と、AWS内の転送先権限の両方を確認する。

7. まとめ#

  • AppFlowはSaaSとAWSのデータ連携をフローとして設定する。
  • S3やRedshiftを宛先にでき、スケジュール・イベントによる転送が可能。
データベース

Amazon DynamoDB

フルマネージドのキーバリュー型NoSQLデータベース

1. サービス概要#

Amazon DynamoDBは、フルマネージドのキーバリューストア(NoSQLデータベース)です。サーバー管理が不要で、大量のアクセスにも低レイテンシーで応答します。

2. 主な機能・特徴#

テーブルのキー#

  • プライマリキー:アイテムを一意に識別するキー。次の2通りがある。
    • パーティションキーのみ:パーティションキーの値がテーブル内で一意でなければならない。
    • パーティションキー+ソートキー:同じパーティションキーの値を複数のアイテムが持てる。2つの組み合わせがテーブル内で一意になる。
  • パーティションキー:どの物理パーティションに保存するかを決める。値に偏りがあると性能が劣化する。
  • ソートキー:同じパーティションキー内での並び順を決める。

データの読み取り#

1回のリクエストで取得できる最大データ容量は1MBです。

  • GetItem:主キーで1件取得
  • BatchGetItem:主キーで複数件取得
  • Query:パーティションキー・インデックスを条件に取得
  • Scan:全件走査

セカンダリインデックス#

別のキー構成でクエリを実行するための仕組みです。

  • ローカル(LSI):パーティションキーはそのままで、ソートキーを変えたいとき。例:UserID+OrderDate のテーブルで、UserID+OrderStatus で検索したい。
  • グローバル(GSI):パーティションキーを変えたいとき。例:OrderID+OrderStatus で検索したい。

TTL(Time To Live)#

指定時刻を過ぎたアイテムを自動削除する機能です。TTL属性はNumber型+UNIXエポック秒である必要があります。セッション管理・キャッシュ・一時URLや認証コードに使います。ただし削除までにラグが生じるため、正確な時刻で処理したい場合はEventBridge+Lambdaを使います。

エラー処理#

UnprocessedKeys は、スロットリングやサイズ超過で未処理になったキーのリストです。エクスポネンシャルバックオフでリトライして再実行します。

関連機能#

  • DynamoDB Accelerator(DAX):インメモリキャッシュ。読み取りをマイクロ秒レベルに高速化。
  • DynamoDB Streams:テーブルのデータ変更を記録し、外部処理に連携する。
    • Streams+Lambdaの流れ:アプリがテーブルを更新 → Streamsが変更イベントを記録 → Lambdaがポーリング(若干の遅延あり)→ まとめて取得して関数を実行
    • ビュータイプ(記録する内容):KEYS_ONLY(キーのみ)、NEW_IMAGE(更新後のアイテム)、OLD_IMAGE(更新前のアイテム)、NEW_AND_OLD_IMAGES(更新前と更新後の両方)
  • DynamoDB Transactions:複数アイテムの更新を「全成功 or 全失敗」にするACIDトランザクション。TransactWriteItems(複数書き込み)、TransactGetItems(複数読み取り)。

3. ユースケース#

  • セッション管理・ユーザープロファイル(TTLで自動削除)
  • 大量アクセスのあるゲーム・EC・IoTのデータ保存
  • 変更をトリガーにした後続処理(Streams+Lambda)

4. 料金の考え方#

性能はキャパシティユニットで表し、テーブルが1秒間にどれだけ読み書きできるかを示します(1RCU/1WCU=1KB/秒が基準)。

  • RCU(読み込みキャパシティユニット):整合性の違いで消費量が変わる(強い整合性のほうが多く消費)。
  • WCU(書き込みキャパシティユニット)

1RCUは「4KBまでのアイテムを強い整合性で1回/秒、結果整合性なら2回/秒」、1WCUは「1KBまでのアイテムを1回/秒」書き込めます。料金モードは、容量を事前に指定するプロビジョンドと、リクエスト数に応じて課金されるオンデマンドの2種類です。

5. 関連サービス#

  • AWS Lambda:DynamoDB Streamsの処理
  • Amazon EventBridge:正確な時刻での削除処理
  • Amazon ElastiCache:汎用的なキャッシュ
  • Amazon RDS:リレーショナルDBの選択肢
  • AWS Database Encryption SDK:クライアント側での属性暗号化
  • 関連する用語:スロットリングとリトライ

6. 試験・実務でのポイント#

  • パーティションキーは値が分散するものを選ぶ(偏るとホットパーティション)。
  • 後からインデックスを追加 → GSIのみ可能。LSIはテーブル作成時のみ。
  • GSIは結果整合性のみ。強い整合性が必要ならベーステーブルかLSI。
  • 読み取りをマイクロ秒に → DAX。
  • 変更をトリガーに処理 → Streams+Lambda。
  • UnprocessedKeys → エクスポネンシャルバックオフでリトライ。
  • 全件取得の Scan は高コスト。可能なら Query。
  • CloudFront・API Gateway・ElastiCache・DAXのキャッシュの使い分け → キャッシュの選び方。

7. まとめ#

  • DynamoDBはキーバリュー型のフルマネージドNoSQL。
  • キー設計(パーティションキー・ソートキー・LSI/GSI)が性能を左右する。
  • DAX・Streams・TTL・Transactionsで機能を拡張できる。
