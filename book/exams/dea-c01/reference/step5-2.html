AWS Secrets Manager

アプリの機密情報を安全に保管・取得・ローテーション

1. サービス概要#

AWS Secrets Managerは、アプリケーションで使う機密情報(DBのパスワードやAPIキーなど)を安全に保管・取得・ローテーションするサービスです。

2. 主な機能・特徴#

  • 自動暗号化:保存時はKMS、転送時はHTTPSで暗号化される。
  • レプリケーション:設定したリージョンに暗号化されたシークレットを複製し、別リージョンのアプリからも使える。ローテーションは元のシークレットで行えば、複製先にも反映される。
  • ローテーション:パスワードを定期的に自動変更できる。

ローテーションの仕組み#

  • マネージドローテーション:Amazon AuroraやRDSのマスターユーザーなど、サービスが管理する認証情報で使う。Lambda関数は不要で、最短4時間おきに実行できる。
  • Lambda関数によるローテーション:それ以外のシークレットで使う。AWSが用意したローテーション関数テンプレートを使うか、独自のLambda関数を作成する。

Lambda関数によるローテーションは、createSecret・setSecret・testSecret・finishSecret の4つのステップで進みます。

アクセス制御と共有#

シークレットにはリソースポリシーを付けて、複数のユーザーやロールに許可を与えられます。別のAWSアカウントから使わせる場合は、リソースポリシーに加えて、呼び出し側のIAMポリシーでも許可が必要です。

暗号化に使うKMSキーも共有が必要です。AWS管理キー(aws/secretsmanager)は別アカウントからは使えないため、カスタマー管理キーを作成し、キーポリシーで相手アカウントに使用を許可します。許可の判断の仕組みは用語ページ「IAMポリシーと評価ロジック」を参照してください。

暗号化の仕組み#

Secrets Managerはエンベロープ暗号化で値を保護します。KMSキーで256ビットのAESデータキーを生成・暗号化し、そのデータキーでシークレットの値を暗号化します。暗号化されたデータキーはシークレットのメタデータとして保存されます。暗号化の基本は用語ページ「保存時の暗号化と転送時の暗号化」を参照してください。

3. ユースケース#

アプリのDB接続情報の管理

  1. 事前準備:アプリがDBに接続するための認証情報を、1つのシークレットとしてSecrets Managerに保存する(KMSで暗号化される)
    {"username": "app_user", "password": "xxxxx", "host": "db.example.com"}
  2. アプリのコードには、パスワードではなくシークレットの名前(またはARN)だけを設定しておく
  3. アプリが起動時などに GetSecretValue APIでシークレットを取得する(IAMロールに secretsmanager:GetSecretValue とKMSの復号権限が必要)
  4. 取得したユーザー名・パスワードでDBに接続する
  5. ローテーションでパスワードが変わっても、アプリは次に取得したときに新しい値を使うため、コードの変更や再デプロイは不要

「アプリの会員(エンドユーザー)のID/パスワードもSecrets Managerに保存すればよいのでは?」→ 非推奨。Secrets Managerは、DBのパスワードやAPIキーのようなシステムが使う少数の機密情報を管理するためのサービスで、シークレット1件ごとに料金がかかります。会員のパスワードは、DBにハッシュ化して保存するか、Amazon Cognitoなどの認証サービスで管理します。

4. 料金の考え方#

シークレット1件ごとの月額料金と、APIの呼び出し回数で課金されます。公式料金ページの例では、1シークレットあたり月額 $0.40、API呼び出し1万回あたり $0.05です(最新の料金は料金ページで確認してください)。別リージョンに複製したシークレットは、別のシークレットとして課金されます。

Parameter Storeは標準パラメータであれば追加料金がかからないため、ローテーションが不要な設定値はParameter Storeが向いています。

  • Amazon RDS/Amazon Aurora:認証情報の自動ローテーション
  • AWS Systems Manager:Parameter Store
  • AWS Lambda:ローテーション処理の実行
  • Secrets Manager・Parameter Store・AppConfig・KMSの使い分け → 機密情報・設定値の保存先の選び方。

6. 試験・実務でのポイント#

  • DBパスワードの自動ローテーション → Secrets Manager(Parameter Storeは自動ローテーションを提供しない)。
  • Aurora・RDSのマスターユーザー → マネージドローテーション(Lambda関数は不要)。それ以外のシークレットはLambda関数でローテーションする。
  • ダウンタイムをほぼなくしたい → 交代ユーザー方式。クローンのユーザーは元と同じ権限で作られるため、後から権限を変えたら両方に反映する必要がある。
  • ローテーションが不要な設定値 → Parameter Store(標準パラメータは追加料金なし)。
  • 料金はシークレット数とAPI呼び出し数で決まる。レプリカも別のシークレットとして課金される。
  • 別のアカウントに使わせる → リソースポリシーと呼び出し側のIAMポリシーの両方が必要。KMSキーはカスタマー管理キーにする(AWS管理キーは使えない)。
  • DRで別リージョンでも使いたい → レプリケーション。DR戦略の考え方は用語ページ「DR戦略」を参照してください。
  • アプリのコードにはパスワードを書かず、シークレット名(ARN)だけを設定して GetSecretValue で取得する。

7. まとめ#

  • Secrets Managerは機密情報の保管・取得・ローテーションのサービス。
  • ローテーションはシングルユーザーと交代ユーザーの2方式。
  • ローテーション不要の設定値はParameter Storeで十分。
サービスの選び方

機密情報・設定値の保存先の選び方

Secrets Manager・Parameter Store・AppConfig・KMSの違いと使い分け

1. 詳しい説明#

DBのパスワードやAPIキー、接続先などの設定値をプログラムやテンプレートに直接書くと、漏れたときの被害が大きく、変更のたびに作り直しが必要になります。そこで値を外部のサービスに保存し、実行時に読み込みます。保存先は、機密情報かと自動でローテーション(定期的な変更)が必要かで選びます。

Parameter Storeから /aws/reference/secretsmanager/シークレット名 を指定すると、Secrets Managerのシークレットも読み出せます。アプリの読み込み先をParameter Storeにまとめたいときに使えます。

KMSとAppConfigの役割#

  • AWS KMSは、値を保存する場所ではなく暗号化の鍵を管理するサービスです。Secrets ManagerやParameter StoreのSecureStringは、裏側でKMSの鍵を使って暗号化しています。読み出すには、そのKMSキーを使う権限(kms:Decrypt)も必要です。
  • AppConfig(Systems Managerの機能)は、設定値や機能フラグを少しずつ配布し、CloudWatchのアラームが鳴ったら自動で元に戻せます。値を保存すること自体よりも、安全に変更を反映させることが目的です。

選び方のポイント#

  • DBのパスワードを定期的に自動で変更したい → Secrets Manager(運用シナリオ「DBのパスワードを自動でローテーションする」)。
  • 費用をかけずに設定値や機密情報を管理したい・ローテーションは不要 → Parameter Store(標準パラメータは無料)。
  • パラメータに有効期限を付けたい・期限前に通知したい → Parameter Storeのアドバンストパラメータ。
  • DR先のリージョンでも同じシークレットを使いたい → Secrets Managerのレプリカ(他リージョンへの複製)。
  • CloudFormationのテンプレートにパスワードを書きたくない → 動的参照({{resolve:secretsmanager:…}}、{{resolve:ssm-secure:…}})。
  • ECSのタスクに機密情報を渡す → タスク定義の secrets でSecrets ManagerかParameter Storeを参照する(実行ロールに読み取り権限が必要)。
  • Lambdaの環境変数は保存時に暗号化されるが、権限のある人にはコンソールで見える。機密情報はSecrets Managerなどから読み込む。
  • 新機能を一部の利用者にだけ有効にし、問題があればすぐ戻したい → AppConfigの機能フラグ。
  • シークレットを読めないとき → シークレット(またはパラメータ)を読む権限に加えて、暗号化に使ったKMSキーの kms:Decrypt の権限とキーポリシーを確認する。

AWS KMS

暗号化キーを安全に作成・管理・使用するサービス

1. サービス概要#

AWS KMS(Key Management Service)は、データの暗号化に使う暗号化キーを安全に作成・管理・使用できるサービスです。S3・EBS・RDSなど多くのAWSサービスの暗号化に使われます。

2. 主な機能・特徴#

キーの種類#

  • KMSキー:データキーを生成・暗号化する、KMSの中で管理されるキー。以前はCMK(カスタマーマスターキー)と呼ばれていたため、古い資料ではこの名前で出てくる。
  • データキー:実データを暗号化する。
  • HMACキー:改ざん検知用の鍵。
項目AWS所有キーAWS管理キーカスタマー管理キー
作成者AWSAWSユーザー
アカウントに表示されないされるされる
キーポリシーの編集不可不可可能
有効/無効化不可不可可能
削除不可不可可能
ローテーション設定不可AWSが管理設定可能(自動ローテーションは対称暗号キーのみ。対称キー=暗号化・復号に同じ鍵を使う)

暗号化の流れ(エンベロープ暗号化)#

  1. アプリがKMSにデータキーの生成をリクエスト(GenerateDataKey API)
  2. KMSがデータキーを生成し、KMSキーでそのデータキーを暗号化
  3. KMSが平文のデータキーと暗号化されたデータキーをアプリに渡す
  4. アプリが平文のデータキーでデータを暗号化し、平文のデータキーは破棄
  5. 暗号化データと暗号化データキーを一緒に保存

※小さなデータ(4KBまで)は、KMSの Encrypt API で直接暗号化します。

復号の流れ#

  1. アプリが保存先から暗号化データと暗号化データキーを取得
  2. アプリがKMSに復号をリクエスト(Decrypt API。入力=暗号化データキー)
  3. KMSがKMSキーで暗号化データキーを復号し、平文のデータキーを返す
  4. アプリが平文のデータキーでデータを復号し、平文のデータキーは破棄

キーポリシーとIAMポリシー#

KMSキーへのアクセスは、キーポリシー(キーに付けるリソースベースのポリシー)で決まります。すべてのKMSキーには、必ず1つのキーポリシーがあります。ほかのサービスと違い、キーポリシーで許可していないと、IAMポリシーで許可しても使えません。

  • 既定のキーポリシーには、アカウント(ルート)を許可する文が入っている。これがあると、そのアカウントのIAMポリシーでキーの権限を与えられるようになる。
  • キーポリシーでは、キーを管理する人(キーの管理者:削除の予定・ポリシーの変更など)と、キーを使う人(キーのユーザー:Encrypt・Decrypt・GenerateDataKey)を分けて許可する。
  • 条件キー kms:ViaService を使うと、「S3を通したときだけ復号を許可する」のように、使えるサービスを絞れる。
  • グラント:キーポリシーを変えずに、特定のプリンシパルに一時的に権限を渡す仕組み。EBSやRDSなどのAWSサービスが、暗号化したボリュームを使うときに内部で使う。

別アカウントでの利用#

別アカウントにキーを使わせるには、両方のアカウントで許可が必要です。

AWSマネージドキーはキーポリシーを変えられないため、別アカウントでは使えません。暗号化したEBSスナップショットやRDSスナップショットを別アカウントと共有するときは、カスタマーマネージドキーで暗号化しておきます。

キーのローテーション#

  • カスタマーマネージドキー(対称キー)は、自動ローテーションを有効にすると、決めた間隔(90日〜2560日。既定は365日)でキーの中身(キーマテリアル)が新しくなる。すぐにローテーションすることもできる。
  • ローテーションしても、キーIDとARNは変わらず、古いキーマテリアルも残るため、以前に暗号化したデータはそのまま復号できる。アプリの変更はいらない。
  • AWSマネージドキーは、毎年自動でローテーションされる。
  • 自分で用意したキーマテリアルをインポートしたキーは自動ローテーションできない。新しいキーを作り、エイリアス(キーの別名)の向き先を変える手動ローテーションを行う。

キーの無効化と削除#

カスタマーマネージドキーはすぐには削除できず、7〜30日(既定は30日)の待機期間を指定して削除を予定します。待機期間中は取り消せます。削除すると、そのキーで暗号化したデータは二度と復号できません。

  • まだ使われているか分からないときは、先にキーを無効化して様子を見る(無効化はいつでも元に戻せる)。
  • 削除の待機中のキーを使おうとした操作はCloudTrailに記録されるので、CloudWatchのメトリクスフィルターとアラームで検知できる。

マルチリージョンキー#

マルチリージョンキーは、同じキーマテリアルとキーIDを持つキーを、複数のリージョンに置く仕組みです。あるリージョンで暗号化したデータを、別のリージョンでそのまま復号できます。DRで別リージョンにコピーしたデータを復号したい場合や、複数のリージョンでクライアント側の暗号化をする場合に使います。通常のKMSキーは、作ったリージョンの外では使えません。

リクエストの上限#

KMSのAPIには、1秒あたりのリクエスト数の上限があります。超えると ThrottlingException になります。S3のSSE-KMSで大量のオブジェクトを読み書きすると上限に達しやすいため、S3バケットキーを有効にして、KMSへのリクエストを減らします(料金も下がります)。それでも足りなければ、Service Quotasで上限の引き上げを申請します。

キーの保管場所#

キーマテリアルは通常、KMSのハードウェアセキュリティモジュール(HSM)の中で作られ、外に出ることはありません。規制のために専用のHSMが必要な場合は、CloudHSMのクラスターを使うカスタムキーストアや、AWSの外のキー管理システムを使う外部キーストアも選べます。

3. ユースケース#

  • S3(SSE-KMS)・EBS・RDSなどの保存データの暗号化
  • アプリでの大きなデータのエンベロープ暗号化
  • 別アカウントと暗号化データを共有(カスタマー管理キー+キーポリシー)

4. 料金の考え方#

AWS所有キーは無料、AWS管理キーは利用料(APIリクエスト)のみ、カスタマー管理キーはキーごとの月額料金+利用料がかかります。マルチリージョンキーは、リージョンごとのキーにそれぞれ月額料金がかかります。S3バケットキーを使うと、KMSへのリクエストが減り、利用料を下げられます。

5. 関連サービス#

  • Amazon S3/Amazon EBS/Amazon RDS:KMSで暗号化するサービス
  • AWS Secrets Manager:シークレットをKMSで暗号化
  • AWS CloudTrail:キー利用の監査ログ
  • AWS IAM:kms:Decrypt などの権限
  • AWS Database Encryption SDK:KMSを使ったクライアント側暗号化
  • 関連する用語:保存時の暗号化と転送時の暗号化

6. 試験・実務でのポイント#

キーと権限

  • 大きなデータ → GenerateDataKey でエンベロープ暗号化。4KB以下 → Encrypt。
  • キーポリシーの編集・クロスアカウント共有・キーの無効化が必要 → カスタマー管理キー。
  • IAMで許可したのにキーを使えない → キーポリシーで許可されているか確認する。
  • 別アカウントで使う → キーを持つ側のキーポリシーと、使う側のIAMポリシーの両方で許可する。
  • 復号には kms:Decrypt 権限が必要(S3のSSE-KMSオブジェクトの取得でも必要)。

運用

  • 自動ローテーションは対称キーのみ。ローテーションしてもキーIDは変わらず、古いデータも復号できる。
  • インポートしたキーマテリアルのローテーション → 新しいキーを作り、エイリアスを付け替える。
  • キーをすぐには消せない → 削除は7〜30日の待機期間のあと。迷ったら先に無効化。
  • 別リージョンで同じキーで復号したい → マルチリージョンキー。
  • SSE-KMSで ThrottlingException → S3バケットキーでKMSへのリクエストを減らす。
  • Secrets Manager・Parameter Store・AppConfig・KMSの使い分け → 機密情報・設定値の保存先の選び方。

7. まとめ#

  • KMSは暗号化キーの管理サービス。キーはAWS所有・AWS管理・カスタマー管理の3種類。
  • KMSキーでデータキーを暗号化し、データキーで実データを暗号化する(エンベロープ暗号化)。
  • アクセスはキーポリシーが基本。別アカウントではキーポリシーとIAMポリシーの両方で許可する。
  • ローテーション・削除の待機期間・マルチリージョンキー・リクエストの上限を押さえる。
セキュリティ・認証

保存時の暗号化と転送時の暗号化

保存しているデータと、通信中のデータを、それぞれ暗号化して守る考え方

1. 詳しい説明#

データの暗号化は、どの状態のデータを守るかで2つに分けて考えます。

  • 保存時の暗号化(Encryption at rest):ディスクやストレージに保存されているデータを暗号化する。記憶媒体が盗まれたり、権限のない人に読まれたりしても中身が分からないようにする。
  • 転送時の暗号化(Encryption in transit):ネットワークを流れている途中のデータを暗号化する。通信の盗聴や改ざんを防ぐ。

どちらか一方だけでは不十分で、要件に応じて両方を組み合わせます。

保存時の暗号化#

AWSの多くのサービスは、サーバー側の暗号化(サービスが保存するときに自動で暗号化し、読み出すときに自動で復号する)に対応しています。暗号化のキーはAWS KMSで管理します。

サービス保存時の暗号化ポイント
S3すべての新しいオブジェクトが既定でSSE-S3で暗号化される。SSE-KMSなども選べるキーの利用を監査したい・アクセスをキーポリシーでも制御したい → SSE-KMS
EBSボリューム作成時に暗号化を指定。リージョンの「デフォルトで暗号化」設定で、新しいボリュームを常に暗号化できる既存の暗号化されていないボリュームは直接暗号化できない。スナップショットを暗号化してコピーし、そこから新しいボリュームを作る
RDS・AuroraDBの作成時に暗号化を指定後から暗号化するには、スナップショットを暗号化してコピーし、そこから復元する
DynamoDBすべてのテーブルが既定で暗号化されるキーの種類(AWS所有・AWS管理・カスタマー管理)を選べる
EFSファイルシステムの作成時に指定作成後には変更できない

サービスに渡す前に、アプリ側で暗号化してから保存する方法をクライアント側の暗号化といいます(S3のクライアントサイド暗号化、AWS Database Encryption SDKなど)。AWS側でも平文を見られないようにしたい場合に使います。

転送時の暗号化#

転送時の暗号化は、主にTLS(HTTPS)で行います。AWSのサービスのAPIはHTTPSで呼び出されます。自分のシステムの通信も、要件に応じて暗号化します。

通信暗号化の方法
利用者 ⇔ ALB・CloudFrontACMの証明書でHTTPSにする。CloudFrontではViewer Protocol Policyで「HTTPSにリダイレクト」などを設定
ALB ⇔ EC2ALBでHTTPSを終端する(以降はHTTP)か、EC2側にも証明書を置いてHTTPSにする(エンドツーエンドの暗号化)
S3へのアクセスバケットポリシーで aws:SecureTransport が false のリクエストを Deny し、HTTPSを強制する
EFSのマウントEFSマウントヘルパーの tls オプションでTLSを使う
オンプレミス ⇔ AWSSite-to-Site VPN(IPsec)。Direct Connectは標準では暗号化されないため、MACsecかDX上のVPNを使う
RDSへの接続SSL/TLSで接続する(DBのパラメータで暗号化された接続だけを許可することもできる)

「保存時の暗号化」はKMS(キー)、「転送時の暗号化」はTLS(証明書=ACM)と結び付けて覚えると整理しやすくなります。
