Amazon Athena

S3上のデータを標準SQLで直接分析するサーバーレスなクエリサービス

1. サービス概要#

Amazon Athenaは、S3に保存されたデータを標準SQLで直接分析できるサーバーレスなクエリサービスです。データベースにデータを読み込む必要がなく、サーバーの管理も不要です。

2. 主な機能・特徴#

  • CSV、JSON、Parquet、ORC、Avroなどの形式に対応。
  • テーブル定義(スキーマ)はAWS Glue データカタログで管理する。
  • クエリ結果はS3に出力される。

仕組み#

Athenaは、Glueデータカタログに登録したテーブル定義(データの場所・形式・列)をもとに、S3のオブジェクトを読みながらSQLを実行します。サーバーの準備は不要で、クエリは並列に実行されて自動で拡張されます。料金はスキャンしたデータ量で決まるため、読むデータを減らすことが費用の削減につながります。

SQLのほかに、Apache SparkのPythonコードをノートブックからAthenaで実行できます。S3以外のデータも、フェデレーテッドクエリでLambda関数のコネクタを経由して分析できます。

スキャン量を減らす#

パーティションは、日付などの値ごとにS3のフォルダを分けておく仕組みです。WHERE句でパーティションのキーを指定すると、Athenaはその値のフォルダだけを読みます。

データを列指向形式(Parquet・ORC)にすると、クエリに必要な列だけを読めます。圧縮(GZIP・SNAPPY・ZSTDなど)をかけると、S3上の容量と読み取る量も減ります。既存のCSVなどは、CTAS(CREATE TABLE AS SELECT)でParquetやORCに変換できます。公式ドキュメントでは、圧縮・パーティション・列指向形式の組み合わせで、クエリあたりのコストを最大90%減らせるとされています。

設定の要点#

  • テーブルの作成:CREATE TABLEで、データの場所(LOCATION・S3のプレフィックス)、形式、パーティションのキー(PARTITIONED BY)を指定する。
  • パーティションの追加:dt=2026-10-01のようなHive形式ならMSCK REPAIR TABLEで登録する。それ以外の形式はALTER TABLE ... ADD PARTITIONで追加する。
  • ワークグループ:チームや用途ごとに、クエリ結果の保存先、暗号化の設定、IAMによるアクセス制御を分けて管理する。暗号化はワークグループ単位で決まるため、暗号化が必要な結果と不要な結果は別のワークグループにする。
  • データ使用量の制御:クエリ単位とワークグループ単位で、スキャンするデータ量のしきい値を設定する。しきい値を超えたときの動作を決められ、CloudWatchアラームで通知もできる。

制限#

  • 1回のクエリの文字列は256KBまで(変更できない)。長いクエリは分けて実行する。
  • 1回のスキャンで読めるパーティションは100万個まで。
  • DMLクエリ(SELECT・CTAS・INSERT INTO)には、同時に実行できる数の上限(リージョンにより異なる)と実行時間の上限がある。実行時間は申請により最長240分まで延ばせる。
  • キャンセルや失敗したクエリの途中までの結果が、S3に残ることがある。S3のライフサイクルルールで削除する。

3. ユースケース#

  • S3に出力されたCloudTrail・ALB・VPCフローログのアドホックな分析
  • データレイク(S3)に対する集計クエリ
  • BIツール(Amazon QuickのQuick Sightなど)のデータソース

4. 料金の考え方#

クエリでスキャンしたデータ量に応じて課金されます。スキャン量は1MB単位で切り上げられ、1クエリあたり最低10MBで計算されます。CREATE・ALTER・DROPなどのDDLと、失敗したクエリは無料です。キャンセルしたクエリは、キャンセルまでにスキャンした分が課金されます。パーティション分割・列指向形式・圧縮でスキャン量を減らすと、コストを大きく下げられます。料金の考え方は用語ページ「料金の基本」を参照してください。

5. 関連サービス#

  • Amazon S3:分析対象のデータの保存先
  • AWS CloudTrail:S3に出力したログの分析
  • Amazon Data Firehose:ストリーミングデータをS3に配信し、Athenaで分析する
  • AWS Lambda:フェデレーテッドクエリで、S3以外のデータに接続するコネクタの実行
  • Amazon OpenSearch Service:全文検索・リアルタイム分析
  • Amazon CloudWatch:スキャン量のアラーム
  • AWS Glue:テーブル定義・クローラー・ETL
  • AWS Lake Formation:データレイクの細粒度アクセス制御
  • Amazon Redshift:データウェアハウス・Spectrum
  • Amazon Quick:分析結果の可視化
  • 関連する用語:マネージドサービスとサーバーレス、料金の基本

6. 試験・実務でのポイント#

  • 「S3のデータ」「SQL」「サーバーレス」「アドホック分析」→ Athena。
  • コスト削減 → パーティション+Parquet/ORC+圧縮でスキャン量を減らす。
  • 特定の期間だけを分析したい → WHEREでパーティションのキーを指定する(読むのはその範囲だけ)。
  • Hive形式でないパーティションを追加したい → MSCK REPAIR TABLEは使えず、ALTER TABLE ... ADD PARTITIONで追加する。
  • 誤って大量のデータをスキャンして高額になるのを防ぎたい → クエリ単位・ワークグループ単位のデータ使用量の制御とCloudWatchアラーム。
  • テーブルの定義を一元管理したい → AWS Glue データカタログ。

7. まとめ#

  • AthenaはS3のデータをSQLで直接分析するサーバーレスサービス。料金はスキャン量で決まる。

Amazon Quick

データを可視化してダッシュボードや分析結果を共有するサービス

1. サービス概要#

Amazon Quickは、自然言語による分析や業務自動化などを含むAIサービスです。その中のQuick Sight機能が、データソースへの接続、可視化、BIダッシュボード作成を担います。Quick Sightは以前のAmazon QuickSightを引き継ぐ機能で、既存のAPIや統合は継続して利用できます。

2. 主な機能・特徴#

Quick SightによるBI#

  • Athena、Redshift、S3などのデータソースを使って分析し、グラフやダッシュボードを作る。
  • SPICEインメモリエンジンにデータを取り込む方式と、対応データソースに直接クエリする方式を使い分ける。
  • ダッシュボードを組織内で共有し、ユーザー・グループごとに閲覧権限を管理する。

データ更新と権限#

SPICEを使う場合はデータセットの更新を設定し、更新失敗や容量を監視します。直接クエリは基盤側のクエリ性能と同時実行の影響を受けます。利用者に必要な閲覧権限を付与し、データセットやダッシュボードの共有範囲を確認します。

3. ユースケース#

  • 分析者が作成したレポートを部署や経営層に共有する。
  • AthenaやRedshiftのデータをグラフ・ダッシュボードで可視化する。
  • SPICEを使ってダッシュボードの応答性を高める。

4. 料金の考え方#

契約するユーザー機能・プラン、利用者数、容量、セッションなどに応じて料金が異なります。SPICE容量やデータソース側のクエリ料金も別途考慮します。組織向けの契約条件と最新の料金表を確認してください。

5. 関連サービス#

  • Amazon Athena:S3データのSQLクエリ
  • Amazon Redshift:分析用データウェアハウス
  • AWS Glue:データカタログとETL
  • Amazon S3:データレイク

6. 試験・実務でのポイント#

  • データをグラフやダッシュボードで可視化し、共有する → Quick Sight。
  • 応答性を優先してデータをインメモリに取り込む → SPICE。最新データを基盤から直接読む → 直接クエリを比較する。
  • データ分析や可視化サービスと、データ変換・保存サービスの役割を区別する。
  • 名称はAmazon Quick、BI機能はQuick Sight。旧称や既存APIに関する記述と混同しない。

7. まとめ#

  • Amazon QuickのQuick Sight機能は、データ可視化とBIダッシュボードを提供する。
  • SPICEへの取り込みと直接クエリを、鮮度・性能・料金で使い分ける。

Amazon Redshift

大規模な分析クエリを実行するマネージドデータウェアハウス

1. サービス概要#

Amazon Redshiftは、大量の構造化データをSQLで集計・分析するデータウェアハウスです。列指向の保存と並列処理で分析クエリを実行し、S3のデータレイクやBIツールとも連携します。

2. 主な機能・特徴#

プロビジョンドとServerless#

  • プロビジョンド:クラスターのノード構成を選び、継続的なワークロードの容量を管理する。
  • Redshift Serverless:データウェアハウスの容量を個別に管理せず、ワークロードに応じて処理能力を利用する。

どちらもSQLで分析できます。継続的で予測しやすい処理か、変動が大きく管理負荷を下げたい処理かで選びます。

データの取り込みと連携#

  • COPYでS3などからデータをロードし、UNLOADでクエリ結果をS3へ出力する。
  • Redshift Spectrumで、S3上のデータをクラスターのテーブルにロードせずにクエリする。外部テーブルの定義にGlue Data Catalogを利用できる。
  • フェデレーテッドクエリでRDSやAuroraなどの外部データソースを参照する。
  • データ共有で別のRedshiftデータウェアハウスへデータを共有し、複製を抑えた分析を行う。

テーブル設計と同時実行#

クエリのアクセスパターンに応じて、列のデータ型、ソートキー、分散方法を設計します。列指向形式や圧縮はスキャン量を抑えます。テーブルや行のロック、トランザクションの競合が発生した場合は、長時間トランザクションや同時更新を調査します。分析性能はクエリプラン、スキャン量、分散キーのデータ偏りも確認します。

3. ユースケース#

  • 業務システムやS3のデータを統合した大規模なSQL分析。
  • BIダッシュボード向けの集計テーブルやマテリアライズドビュー。
  • S3データレイクとデータウェアハウスを組み合わせた分析。
  • 別のRedshift利用者への管理されたデータ共有。

4. 料金の考え方#

プロビジョンドでは主に利用するノードの容量と稼働時間、Serverlessでは処理容量の利用量などが課金要因です。ストレージ、バックアップ、データ転送、Spectrumのスキャンなども確認します。アイドル時間が長いか、負荷が一定か変動するかを踏まえて方式を選びます。

5. 関連サービス#

  • Amazon S3:ロード元、UNLOAD先、Spectrumのデータレイク
  • AWS Glue:カタログとETL
  • AWS Lake Formation:データレイクのアクセス制御
  • Amazon Athena:サーバーレスSQLでのデータレイク分析
  • Amazon Quick:Quick SightのBIダッシュボード
  • Amazon AppFlow:SaaSデータの取り込み

6. 試験・実務でのポイント#

  • 大規模な分析用SQLデータウェアハウス → Amazon Redshift。
  • データをS3からロードする → COPY。クエリ結果をS3へ出力する → UNLOAD。
  • S3のデータをロードせずに分析 → Redshift Spectrum。
  • 負荷変動が大きく容量管理を減らしたい → Serverless。一定負荷で容量を管理したい → プロビジョンドを比較する。
  • 他のデータウェアハウスへ読み取り用データを渡す → データ共有。データベース間の移送方法と区別する。

7. まとめ#

  • Redshiftは、SQLによる大規模分析向けのデータウェアハウス。
  • COPY/UNLOAD、Spectrum、フェデレーテッドクエリ、データ共有で複数のデータソースと連携する。
  • ノード容量・クエリ・ストレージなど、方式別の料金要因を比較する。
