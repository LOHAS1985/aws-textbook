EC2に接続できない原因を調査する

最終更新:2026-10-26

1. やりたいこと#

  • インターネットからEC2のWebサーバーにアクセスできない。
  • どこで通信が止まっているかを、記録と解析で特定したい。

2. 構成を組み立てる#

① インターネットとVPCの間の出入り口は?

  • インターネットゲートウェイVPCにアタッチし、サブネットのルートテーブルに 0.0.0.0/0 への経路を作ります。EC2にはパブリックIPも必要です。
  • NATゲートウェイ内から外への通信のためのもので、外から内へのアクセスは受け付けません(インバウンド通信)。
  • VPCエンドポイントAWSのサービスへのプライベートな経路で、インターネットの出入り口ではありません。

② 通信が許可・拒否されたかを記録するものは?

  • VPCフローログENIごとの通信を ACCEPT・REJECT とともに記録します(VPCフローログ)。
  • AWS CloudTrailAPIの操作の記録で、パケットの通信は記録しません。設定を変えた人を調べるのには使えます。
  • AWS X-Rayアプリの処理の流れを追うもので、ネットワークの拒否は記録しません。

③ 受信はACCEPTなのに、戻りの通信がREJECTのときの原因は?

  • ネットワークACLのアウトバウンドでエフェメラルポートを許可していないネットワークACLはステートレスなので、戻りの通信(1024〜65535)も許可が必要です(ネットワークACLとセキュリティグループ)。
  • セキュリティグループのアウトバウンドが空セキュリティグループはステートフルで、戻りの通信は自動で許可されます。
  • ルートテーブルが拒否しているルートテーブルは経路を決めるだけで、許可・拒否はしません。

④ 実際に通信せずに、設定上の経路を自動で解析するものは?

  • VPC Reachability Analyzer送信元と宛先を指定すると、どの設定で止まるかを解析して示します。
  • VPCフローログ実際に流れた通信の記録で、設定の解析はしません。
  • Trusted Advisorベストプラクティスのチェックで、2点間の経路は解析しません。

3. 構成図#

ルートテーブル → インターネットゲートウェイ → セキュリティグループ → ネットワークACL → パブリックIPの順に確認し、VPCフローログのREJECTをLogs Insightsで検索して止まっている場所を絞り込みます。設定上の経路はReachability Analyzerで自動で解析できます。

4. 使うサービスと役割#

  • Amazon VPC:ルートテーブル、IGW、セキュリティグループ、ネットワークACL、VPCフローログ
  • Amazon CloudWatch:フローログの保存とLogs Insightsでの検索
  • Amazon EC2:ステータスチェック、パブリックIPの確認
  • AWS CloudTrail:最近SGやルートテーブルを変更した人を調べる

5. 構築の流れ(調査手順)#

  1. ルートテーブル:サブネットに 0.0.0.0/0 → IGW の経路があるか(ルートテーブル)
  2. IGW/NAT:IGWがVPCにアタッチされているか、NATゲートウェイが正常か
  3. セキュリティグループ:80/443番のインバウンドが許可されているか
  4. ネットワークACL:インバウンドに加えて、戻りのアウトバウンド(エフェメラルポート)も許可されているか
  5. パブリックIP:EC2にパブリックIPまたはElastic IPが割り当てられているか
  6. VPCフローログを有効にし、Logs Insightsで REJECT の記録を確認する

6. ポイント・注意点#

  • SGはステートフルで戻りの通信は自動で許可。NACLはステートレスで戻りの通信も許可が必要(NACLとSG)。
  • ルートテーブルは経路を決めるだけで、許可・拒否はしない。
  • フローログで、インバウンドがACCEPTなのにアウトバウンドがREJECTなら、NACLのアウトバウンド(戻り)ルールが原因であることが多い。
  • 設定上の経路を自動で解析するには、VPC Reachability Analyzerも使える。
