負荷に応じて自動でスケールするWebシステム

最終更新:2026-10-26

1. やりたいこと#

  • WebアプリをEC2で動かし、1つのAZが止まってもサービスを続けたい。
  • アクセスの増減に合わせて、台数を自動で増減したい(CPU使用率をおよそ50%に保つ)。
  • アプリが応答しなくなったインスタンスは、自動で入れ替えたい。
  • 将来、URLのパス(/api など)で振り分け先を変えたい。

2. 構成を組み立てる#

① 利用者からのリクエストを、複数AZのEC2に分散するものは?

  • Application Load Balancer(ALB)HTTP/HTTPSの中身を見て振り分けるので、パスによる振り分け(パスベースルーティング)ができます。ヘルスチェックで異常なEC2には送りません。
  • Network Load Balancer(NLB)TCP/UDPの段階で振り分けるため、URLのパスによる振り分けができません。固定IPや非常に高い性能が必要なときに選びます。
  • Amazon CloudFrontエッジでのキャッシュと配信のサービスです。後ろに置いたALBなどと組み合わせますが、単独でEC2の台数に合わせた分散やヘルスチェックによる切り離しはしません。

② 台数を自動で増減し、異常なインスタンスを入れ替える仕組みは?

  • EC2 Auto Scalingグループ希望する台数を保ち、スケーリングポリシーで台数を増減します。複数のAZのサブネットを指定すると、AZにまたがって均等に配置します。
  • EC2の自動復旧(アラームの復旧アクション)ハードウェアの障害時に、同じインスタンスを別のハードウェアで復旧するだけです。台数は増えず、AZの障害にも対応できません。
  • 起動テンプレート起動するインスタンスの設定(AMI・インスタンスタイプなど)をまとめたもので、それだけでは台数を管理しません。Auto Scalingグループが使う部品です。

③ 「CPU使用率をおよそ50%に保つ」に最も合うスケーリングポリシーは?

  • ターゲット追跡スケーリング(CPU使用率 50%)目標の値を決めるだけで、必要なアラームの作成と台数の計算をAuto Scalingが行います。最も手間の少ない方法です。
  • スケジュールされたアクション決まった時刻に台数を変えるもので、予測できないアクセスの増減には対応できません。
  • 希望する容量を手作業で変更する自動ではないので要件を満たしません。

④ 「アプリが応答しなくなったインスタンス」も入れ替えるための、Auto Scalingグループのヘルスチェックの種類は?

  • ELBのヘルスチェックを有効にするALBのヘルスチェック(例:/health に200が返るか)に失敗したインスタンスも異常とみなして入れ替えます。
  • EC2のヘルスチェックだけ(既定)EC2のステータスチェックしか見ないため、OSは動いているがアプリが止まっている状態を検知できません。
  • ヘルスチェックの猶予期間を0秒にする起動直後のアプリの準備中にも異常と判定され、入れ替えがくり返されるおそれがあります。猶予期間は起動にかかる時間に合わせます。

⑤ Auto Scalingグループに指定するサブネットは?

  • 2つ以上のAZのプライベートサブネット複数のAZに分けることで1つのAZの障害に耐えられます。EC2はALBの後ろにあるので、インターネットから直接見える必要はありません。
  • 1つのAZのプライベートサブネットそのAZが止まると全台が止まるため、要件を満たしません。
  • 2つのAZのパブリックサブネット(パブリックIPあり)動きはしますが、EC2が直接インターネットから見え、攻撃を受ける面が増えます。ALBだけをパブリックサブネットに置くのが基本です。

3. 構成図#

パブリックサブネットに置いたALBが、2つのAZのプライベートサブネットにあるEC2に分散し、Auto Scalingグループが台数を管理します。スケーリングはターゲット追跡(CPU 50%)、ヘルスチェックはELBも使う設定にすると、アプリの異常でも自動で入れ替わります。

この構成の可用性の考え方は「高可用性とスケーリング」と「SLAと可用性」で説明しています。

4. 使うサービスと役割#

  • Elastic Load Balancing(ALB):複数AZのインスタンスにトラフィックを分散し、ヘルスチェックで異常を検知する
  • Amazon EC2:アプリケーションを動かすインスタンス
  • Amazon EC2 Auto Scaling:起動テンプレートをもとにインスタンスを自動で起動・終了し、指定した台数(最小・最大・希望)を保つ
  • Amazon CloudWatch:CPU使用率やリクエスト数などのメトリクスでスケーリングを判断する

5. 構築の流れ#

  1. AMIとインスタンスタイプなどを指定した起動テンプレートを作成する
  2. 複数AZのサブネットを指定してAuto Scalingグループを作成し、最小・最大・希望の台数を決める
  3. ALBとターゲットグループを作成し、Auto Scalingグループに関連付ける
  4. ターゲット追跡スケーリング(例:平均CPU使用率50%を維持)を設定する
  5. Auto Scalingグループのヘルスチェックの種類を「ELB」にして、アプリの異常でも入れ替わるようにする

6. ポイント・注意点#

  • ELBはリージョン内の複数AZに分散する。インスタンスも複数AZに配置して、AZ障害に備える。
  • ヘルスチェックの種類がEC2のままだと、OSは動いているがアプリが落ちている状態を検知できない → ELBヘルスチェックを使う。
  • 決まった時間に負荷が増えるならスケジュールされたスケーリング、指標を一定に保つならターゲット追跡。
  • インスタンスのサイズ見直しにはCompute Optimizerの推奨を使う。
