リージョン障害に備えて別リージョンへ切り替える

最終更新:2026-10-26

1. やりたいこと#

  • 東京リージョン全体の障害でも、数分〜数十分で大阪リージョンで再開したい(ウォームスタンバイ)。
  • データの損失は、できるだけ小さくしたい。

2. 構成を組み立てる#

① プライマリの異常を検知して、利用者の行き先を大阪へ切り替えるものは?

  • Route 53のフェイルオーバールーティングヘルスチェックが失敗すると、DNSの応答をセカンダリに切り替えます。
  • Application Load BalancerALBはリージョンの中のリソースなので、リージョンをまたいで切り替えられません。
  • AWS CloudTrail操作の記録で、切り替えの機能はありません。

② データを小さな遅延で大阪に複製するDBの機能は?

  • Auroraグローバルデータベース通常1秒未満の遅延で別リージョンに複製し、障害時にはセカンダリを昇格させて書き込めるようにします。
  • RDSのMulti-AZ同じリージョンの中の別のAZへの複製で、リージョンの障害には備えられません。
  • 1日1回のスナップショットのコピー最大で1日分のデータを失うため、「損失を小さく」に合いません。

③ 大阪のアプリ層を、東京と同じ構成で用意しておくには?

  • CloudFormation(StackSets)で両方のリージョンに同じテンプレートを展開する手作業の差が出ず、構成のずれも防げます。
  • 障害が起きてから手作業で作る時間がかかり、ウォームスタンバイの復旧時間を満たせません。
  • 東京のEC2をそのまま大阪に移動するEC2はリージョンをまたいで移動できません(AMIのコピーは可能)。

3. 構成図#

Route 53のフェイルオーバールーティングでプライマリを監視し、異常なら大阪に切り替えます。データはAuroraグローバルデータベースで複製し、大阪には縮小した構成を常に動かしておきます。切り替えをより安全に行うには、ARCのルーティングコントロールも使えます(DR戦略)。

4. 使うサービスと役割#

  • Amazon Route 53:フェイルオーバールーティングとヘルスチェック
  • Amazon Aurora:グローバルデータベースで別リージョンにレプリケート
  • Amazon S3:クロスリージョンレプリケーションで静的ファイルを複製
  • AWS CloudFormation:両リージョンに同じ構成を作る(StackSets)
  • Elastic Load Balancing/Amazon EC2:各リージョンのアプリ層

5. 構築の流れ#

  1. CloudFormationで、大阪にも同じ構成(縮小版)を作成する
  2. Auroraグローバルデータベースを作成し、大阪をセカンダリリージョンにする
  3. S3バケットはクロスリージョンレプリケーションを設定する(両方でバージョニングを有効化)
  4. Route 53でプライマリ(東京)とセカンダリ(大阪)のフェイルオーバーレコードを作り、プライマリにヘルスチェックを付ける
  5. 障害時の手順(DBの昇格、台数の拡張)をランブック化して訓練しておく

6. ポイント・注意点#

  • 復旧時間(RTO)とコストのバランスで、バックアップと復元/パイロットライト/ウォームスタンバイ/マルチサイトから選ぶ。
  • リージョン障害対策のDB → Auroraグローバルデータベース。
  • 切り替えを安全・確実に行いたい → Route 53 Application Recovery Controller(ルーティングコントロール・準備状況チェック)。
  • DNSのキャッシュに左右されずに切り替えたい場合はGlobal Acceleratorも候補。
