静的サイトを独自ドメイン・HTTPSで安全に配信する

最終更新:2026-10-26

1. やりたいこと#

  • 会社のWebサイト(静的ファイル)を、独自ドメインとHTTPSで世界中に高速配信したい。
  • S3バケットは公開せず、CloudFront経由のアクセスだけを許可したい。

2. 構成を組み立てる#

① 世界中のエッジでキャッシュして配信するものは?

  • Amazon CloudFrontエッジロケーションでキャッシュして返し、オリジンのS3にはOACでアクセスします。
  • S3の静的ウェブサイトホスティングだけバケットの公開が必要で、HTTPSにも対応しません。
  • Application Load Balancerリージョンの中の振り分けで、S3をオリジンにしたキャッシュ配信はできません。

② 独自ドメインのHTTPSに使う証明書は?

  • us-east-1で発行したACMの証明書CloudFrontはus-east-1のACM証明書だけを使えます(TLS終端と証明書の配置)。
  • 東京リージョンのACMの証明書CloudFrontには関連付けられません(ALB用ならこちら)。
  • 自己署名の証明書ブラウザに警告が出るので、公開のサイトには使えません。

③ ファイルを更新しても、古い内容が表示されるときの対処は?

  • キャッシュの無効化(インバリデーション)を行うエッジのキャッシュを消して、次のアクセスで新しい内容を取りに行かせます。TTLを短くする方法もあります。
  • S3のバージョニングを有効にするS3の中の履歴が残るだけで、エッジのキャッシュは消えません。
  • OACを削除するS3にアクセスできなくなります。

3. 構成図#

Route 53のエイリアスレコードで独自ドメインをCloudFrontに向け、us-east-1のACM証明書でHTTPSにします。S3はOACでCloudFrontからのアクセスだけを許可し、ビューワープロトコルポリシーでHTTPをHTTPSにリダイレクトします。

4. 使うサービスと役割#

  • Amazon S3:静的ファイルの保存先(オリジン)
  • Amazon CloudFront:エッジでキャッシュして高速配信、OACでS3へアクセス
  • AWS Certificate Manager:独自ドメインの証明書(CloudFront用はus-east-1)
  • Amazon Route 53:独自ドメインをCloudFrontに向ける(エイリアスレコード)

5. 構築の流れ#

  1. S3バケットにファイルを置き、ブロックパブリックアクセスを有効にしたままにする
  2. us-east-1のACMで独自ドメインの証明書を発行する
  3. CloudFrontのディストリビューションを作成し、オリジンにS3、OACを設定する。代替ドメイン名と証明書を指定し、Viewer Protocol PolicyでHTTPSにリダイレクトする
  4. S3のバケットポリシーで、そのディストリビューション(OAC)からの読み取りだけを許可する
  5. Route 53でドメインをCloudFrontに向けるエイリアスレコードを作成する

6. ポイント・注意点#

  • S3への直接アクセスを禁止 → OAC。
  • CloudFrontで使うACM証明書はus-east-1で発行する。
  • 利用者側をHTTPSに強制 → Viewer Protocol Policy。
  • ファイルを更新してもキャッシュが残って古い内容が表示される → キャッシュの無効化(インバリデーション)を実行するか、TTLを短くする。
