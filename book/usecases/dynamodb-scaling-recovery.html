DynamoDBを負荷に合わせてスケールし、誤操作から復旧する

最終更新:2026-10-26

1. やりたいこと#

  • アクセスの急増時に、DynamoDBでスロットリングが出る。
  • 負荷に合わせて容量が自動で増減するようにしたい。
  • バグで大量のデータを上書きしたときに、直前の状態に戻したい。

2. 構成を組み立てる#

① 過去35日以内の任意の時点に戻せる機能は?

  • ポイントインタイムリカバリ(PITR)有効にしておくと、秒単位で指定した時点の状態を、新しいテーブルとして復元できます。
  • グローバルテーブル別のリージョンに複製する機能で、誤った上書きも複製されてしまいます。
  • DynamoDB Accelerator(DAX)読み取りを速くするキャッシュで、復旧の機能はありません。

② 予測できない急増に最も強いキャパシティモードは?

  • オンデマンドモードリクエストに応じて自動で処理し、容量の設定が不要です。自動スケーリングは反応に数分かかります。
  • プロビジョンドモード(自動スケーリングなし)設定した容量を超えるとスロットリングします。
  • 読み取りキャパシティだけを増やす書き込みのスロットリングは解消しません。

③ PITRで復元したあとに、手作業で設定し直すものは?

  • 自動スケーリング・IAMポリシー・アラームなど復元先は新しいテーブルなので、これらは引き継がれません。アプリの接続先の切り替えも必要です。
  • テーブルのデータデータは指定した時点の状態で復元されます。
  • 何もない(元のテーブルが上書きされる)PITRは元のテーブルを上書きせず、新しいテーブルに復元します。

3. 構成図#

急増にはオンデマンドモード、または自動スケーリングで容量を保ちます。特定のキーにアクセスが集中すると、全体の容量に余裕があってもスロットリングするので、キーの設計も見直します。誤った上書きにはPITRで新しいテーブルに復元し、アプリの接続先を切り替えます(スロットリングとリトライ)。

4. 使うサービスと役割#

  • Amazon DynamoDB:キャパシティモード(オンデマンド/プロビジョンド)、自動スケーリング、PITR、オンデマンドバックアップ、グローバルテーブル
  • Amazon CloudWatch:ThrottledRequests・消費キャパシティの監視
  • AWS Backup:バックアップの一元管理・別リージョン/アカウントへのコピー

5. 構築の流れ#

  1. アクセスが予測できない・急増する → オンデマンドモードにする。予測できて安定している → プロビジョンドモード+自動スケーリング(目標の使用率を設定)
  2. グローバルセカンダリインデックス(GSI)にも容量の設定が必要。GSIのスロットリングは元のテーブルへの書き込みも止める
  3. 特定のキーにアクセスが集中しないよう、パーティションキーを分散させる。アプリ側はエクスポネンシャルバックオフで再試行する(AWS SDKは自動)
  4. テーブルのポイントインタイムリカバリ(PITR)を有効にする。長期保管が必要ならAWS Backupでもバックアップを取る
  5. リージョン障害にも備えるなら、グローバルテーブルで別リージョンにレプリカを置く

6. ポイント・注意点#

  • 予測できない急増 → オンデマンドモード。自動スケーリングは反応に数分かかり、瞬間的な急増には間に合わないことがある。
  • 特定のキーにアクセスが集中する(ホットパーティション)と、全体の容量に余裕があってもスロットリングする。
  • PITRの復元先は新しいテーブル。復元後にアプリの接続先を切り替えるか、データを戻す。自動スケーリングの設定・IAMポリシー・アラームなどは引き継がれない。
  • PITRは過去35日以内(設定で1〜35日)の秒単位の時点に戻せる。
  • 読み取りの高速化・負荷の軽減 → DAX。マルチリージョンでの読み書き・リージョン障害への備え → グローバルテーブル。
