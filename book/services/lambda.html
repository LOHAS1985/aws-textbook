1. サービス概要#

AWS Lambdaは、サーバーを用意せずにプログラム(関数)を実行できるサーバーレスサービスです。関数はAWSが管理するLambda専用のネットワーク環境で実行されます。

デフォルトではVPC内のリソースにはアクセスできません。アクセスさせたい場合は後述の「VPC接続」を設定します。

2. 主な機能・特徴#

基本の制限値#

  • 関数1回の最大実行時間は15分(タイムアウトは1〜900秒で設定)
  • 非同期呼び出し(S3・SNS・EventBridgeなどからの呼び出し)で関数がエラーになると、Lambdaが最大2回リトライする(初回+リトライ2回=最大3回実行。回数は0〜2で変更可)。同期呼び出し(API Gatewayなど)では呼び出し元がリトライを判断し、SQSやKinesisなどのイベントソースマッピングでは、メッセージやレコードが期限切れになるか成功するまでリトライされる、というように呼び出し方式によって動きが違う。
  • デプロイパッケージの上限は250MB(解凍後)。デプロイパッケージ=コード+依存関係+実行に必要なファイル一式。上限を超える場合は、S3経由でのアップロードや、ECR経由でコンテナイメージとしてデプロイする。

用語#

  • ハンドラー:最初に呼び出される入口の関数/メソッド。再利用する処理(DB接続など)はハンドラーの外で定義する。
  • レイヤー(Lambda Layers):複数の関数で共有するライブラリ・SDK・共通コード・証明書などを切り出したパッケージ。デプロイの肥大化・管理の重複・更新作業の負荷を解消する。
  • バージョン:発行したバージョンの中身は修正できない。
  • エイリアス:バージョンの別名。エイリアスを呼び出すと紐づけたバージョンが実行される。
  • デスティネーション(送信先):関数実行後の結果を送る先。成功時・失敗時それぞれに設定できる。
  • Function URLs:関数にWebエンドポイントを付けて直接呼び出せるようにする。

主な設定値#

項目設定可能範囲用途
メモリ128〜10,240MB実行性能の調整(CPU性能もメモリに比例)
タイムアウト1〜900秒最大実行時間
一時ストレージ(/tmp)512〜10,240MB一時ファイルの保存
予約された同時実行0〜アカウント上限同時実行数の制御
プロビジョニングされた同時実行0以上コールドスタート対策
環境変数任意設定値の管理

同時実行数#

  • 予約(Reserved):同時に実行できる上限数。上限を超えるとスロットリングが発生する。
  • プロビジョニング(Provisioned):設定した数だけ実行環境をあらかじめ作成しておく(ウォームスタート)。超えた分はコールドスタートで作成される。

実行環境のライフサイクル#

  1. 初期化:実行環境作成 → ランタイム作成 → コードのロード
  2. 実行:ハンドラー関数を実行し、event / context が渡される(同時実行時は自動スケーリング)
  3. 待機:実行終了後、CPUは停止するがメモリ内容を保持してイベントを待つ
  4. 再利用:初期化をスキップして実行フェーズから始めるので高速
  5. シャットダウン:AWSの判断で実行環境を破棄

エラーの種類#

  • 呼び出しエラー:イベントソースに権限がない/呼び出し先の関数が存在しない/スロットリングが発生している
  • 関数エラー:Lambda関数内のコードでエラーが起きている

呼び出し方式の3種類と再試行・DLQ・デスティネーション#

Lambdaの呼び出され方は3種類あり、エラーになったときの再試行と、失敗したイベントの行き先が方式ごとに違います。

方式主な呼び出し元エラー時の再試行失敗したイベントの行き先
同期呼び出しAPI Gateway、ALB、Function URLs、CLIの invokeLambdaは再試行しない。呼び出し元がエラーを受け取り、再試行するか判断する呼び出し元に返る(DLQ・デスティネーションは使わない)
非同期呼び出しS3、SNS、EventBridge、CloudWatch LogsLambdaの内部キューに入り、最大2回再試行する(0〜2回で変更可)。イベントの最大保持期間も設定できる(最大6時間)失敗時のデスティネーション(SQS・SNS・Lambda・EventBridge・S3)、またはDLQ(SQS・SNS)
イベントソースマッピングSQS、Kinesis Data Streams、DynamoDB Streams、Amazon MSKLambdaがポーリングして取得する。SQSは可視性タイムアウト後にメッセージがキューに戻って再処理され、ストリームは成功するかレコードの期限が切れるまで再試行する(最大再試行回数・最大レコード期間で制限できる)SQS:キュー側のDLQ(再処理ポリシー)。ストリーム:失敗時の送信先(SQS・SNS・S3)
  • DLQ(デッドレターキュー):失敗したイベントの内容だけをSQS・SNSに送る。失敗時にしか使えない
  • デスティネーション:成功時・失敗時それぞれに送信先を設定でき、イベントの内容に加えてエラーの内容や関数の応答も含まれる。新しく作るならデスティネーションが推奨
  • SQSのイベントソースマッピングでは、関数側のDLQやデスティネーションではなく、SQSキューの再処理ポリシー(DLQ)で失敗したメッセージを退避する。可視性タイムアウトは関数のタイムアウトより長くする
  • ストリームでは、失敗したレコードがシャードの処理を止めてしまうため、「バッチを分割して再試行」や「部分的なバッチの失敗の報告(ReportBatchItemFailures)」を使う
  • 再試行で同じイベントが2回以上処理されることがあるため、関数は同じイベントを何度処理しても結果が変わらない(冪等な)作りにする

実行ロールとリソースベースのポリシー#

Lambdaの権限は、向きの違う2つのポリシーで決まります。

ポリシー決めること例
実行ロール(IAMロール)関数が何にアクセスできるか(関数から外への権限)DynamoDBへの書き込み、S3の読み取り、CloudWatch Logsへのログ出力、SQSのポーリング(イベントソースマッピング)
リソースベースのポリシー誰が関数を呼び出せるか(外から関数への権限)S3・SNS・EventBridge・API Gatewayや、別のアカウントに lambda:InvokeFunction を許可する
  • 実行ロールの信頼ポリシーでは lambda.amazonaws.com がロールを引き受けられるようにする。ログを出すにはAWS管理ポリシー AWSLambdaBasicExecutionRole の権限が必要
  • イベントソースマッピング(SQS・Kinesisなど)はLambdaがポーリングするため、sqs:ReceiveMessage などの権限は実行ロールに付ける
  • S3やSNSからの非同期呼び出しは相手がLambdaを呼び出すため、リソースベースのポリシーで許可する(コンソールでトリガーを追加すると自動で設定される)
  • 「AccessDenied」が関数の中で出るなら実行ロール、関数が呼び出されないなら呼び出し元の権限(リソースベースのポリシー)を確認する

バージョン管理とエイリアス#

バージョンを発行するたびに新しいARNが発行されるため、イベントソースマッピング(イベント発生元とLambda関数を接続し自動起動する仕組み)が古いARNを参照し続けてしまう問題があります。

解決策は、イベントソースマッピングをエイリアスのARNに向け、新バージョン発行時はエイリアスの向き先だけを更新することです。

旧:S3 → prod(エイリアス) → v1
新:S3 → prod(エイリアス) → v2

また、1つのエイリアスを複数バージョンに紐づけてトラフィックを分割(例:v1=90%、v2=10%)し、段階的に移行できます。

VPC接続#

Lambdaに仮想ENIを割り当て、サブネットとセキュリティグループに所属させることで、VPC内のリソースと通信できるようになります。

  1. VPC・サブネットを作成
  2. Lambda用のセキュリティグループを作成
  3. Lambda実行ロールにENI操作の権限を付与:ec2:CreateNetworkInterface、ec2:DescribeNetworkInterfaces、ec2:DeleteNetworkInterface
  4. LambdaにVPC/サブネット/セキュリティグループを設定

VPCに接続したLambdaは、インターネットやAWSサービスのパブリックなエンドポイントにそのままでは接続できなくなります。LambdaのENIにはプライベートIPしか付かず、パブリックサブネットに置いてもパブリックIPは付かないためです。

  • インターネット(外部API、VPCエンドポイントのないAWSサービス)に出るには、Lambdaをプライベートサブネットに置き、そのルートテーブルでパブリックサブネットのNATゲートウェイに向ける
  • S3・DynamoDB・Secrets ManagerなどのAWSサービスだけなら、VPCエンドポイントを作ればNATゲートウェイなしで使える
  • VPC内のリソースにアクセスする必要がない関数は、VPCに接続しない方がシンプル

Lambda@Edge#

CloudFrontのエッジサーバ上でLambdaを実行する仕組みで、低レイテンシーを実現します。単純な処理はCloudFront Functionsを使い、AWSサービスにアクセスする処理はLambda@Edgeを使います。

  • 作成できるリージョンはus-east-1のみ
  • 環境変数は使用不可
  • VPC接続は不可

3. ユースケース#

  • S3へのファイルアップロードをきっかけにした画像変換などのイベント駆動処理
  • API GatewayやFunction URLsと組み合わせたサーバーレスAPI
  • CloudFrontのエッジでのリクエスト加工(Lambda@Edge)
  • 15分以内に終わる定期バッチ処理

4. 料金の考え方#

Lambdaは「リクエスト数」と「実行時間×割り当てメモリ量」で課金されます。関数が動いていない時間は料金がかかりません。プロビジョニングされた同時実行は、設定している間ずっと料金が発生します。

メモリを増やすとCPU性能も上がるため、実行時間が短くなり結果的に安くなる場合もあります。

5. 関連サービス#

  • Amazon API Gateway:LambdaをバックエンドにしたAPIを公開
  • Amazon CloudFront:Lambda@Edgeの実行場所
  • Amazon ECR:コンテナイメージとしてデプロイする際の保存先
  • Amazon S3:代表的なイベントソース
  • Amazon VPC:VPC接続でVPC内リソースにアクセス
  • AWS SAM:サーバーレスアプリのデプロイ
  • AWS X-Ray:関数のトレース
  • 関連する用語:スロットリングとリトライ、iam:PassRoleとサービスにリンクされたロール

6. 試験・実務でのポイント#

制限と性能

  • 15分を超える処理はLambdaに向かない(ECS/Fargateなどを検討)。
  • デプロイパッケージが250MBを超える → コンテナイメージ(ECR)でデプロイ。
  • コールドスタート対策 → プロビジョニングされた同時実行。同時実行の上限制御 → 予約された同時実行。

呼び出しとエラー処理

  • 非同期呼び出しは最大2回再試行し、失敗したイベントは失敗時のデスティネーションかDLQへ。同期呼び出しは呼び出し元が再試行する。
  • SQSから処理して失敗したメッセージを退避 → SQSキュー側のDLQ(再処理ポリシー)。
  • 成功/失敗の結果を他サービスに送る → デスティネーション。
  • イベントソースはバージョンARNではなくエイリアスARNに向ける。

権限・ネットワーク

  • 関数から他のサービスへの権限 → 実行ロール。S3・SNSなどから関数を呼び出す権限 → リソースベースのポリシー。SQSのポーリングは実行ロール。
  • VPC接続には実行ロールにENI作成・参照・削除の権限が必要。
  • VPC接続したLambdaがインターネットに出られない → プライベートサブネット+NATゲートウェイ(パブリックサブネットに置いてもパブリックIPは付かない)。AWSサービスだけならVPCエンドポイント。
  • Lambda@Edgeはus-east-1で作成。

7. まとめ#

  • Lambdaはサーバー管理不要の関数実行サービス。最大15分、パッケージ250MB。
  • 同時実行は「予約=上限」「プロビジョニング=事前ウォーム」。
  • バージョン+エイリアスで安全にリリースし、トラフィック分割で段階移行できる。

このサービスが登場するユースケース#

  • アプリのエラーログを検知して通知するCloudWatch Logsのメトリクスフィルターでエラーを数え、アラームで通知する
  • 外形監視と、誤報の少ないアラームを作るSynthetics Canaryで利用者の視点から監視し、異常検出と複合アラームで本当に必要な通知だけを送る
  • マイクロサービスの遅延の原因をトレースで特定するX-Rayのトレースで、どのサービス・どの処理が遅いか・エラーを出しているかを突き止める
  • キューで処理を分離し、急増や障害に強くするSQSで受付と処理を切り離し、キューの長さに応じて処理側をスケールし、失敗したメッセージをDLQに隔離する
  • Lambdaを段階的にリリースするSAMとCodeDeployのCanaryで、新バージョンへ少しずつトラフィックを移す
  • DBのパスワードを自動でローテーションするSecrets Managerで認証情報を保管し、定期的に自動で変更する
  • 乗っ取られたEC2を自動で隔離するGuardDutyの検出結果をEventBridgeで受け、隔離用のセキュリティグループへの付け替えと証拠の保全を自動で行う
