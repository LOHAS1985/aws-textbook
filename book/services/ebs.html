1. サービス概要#

Amazon EBS(Elastic Block Store)は、EC2にアタッチして使うブロックストレージサービスです。PCの内蔵ディスクのように使え、EC2を停止してもデータは残ります。

2. 主な機能・特徴#

  • EC2を停止してもEBSのデータは残る(インスタンスストアとの違い)。
  • マルチアタッチ:同一AZの別のEC2インスタンスへもアタッチできる。
  • 暗号化に対応。
  • スナップショットを取得できる(S3に保存される)。
  • バーストクレジット:ベースラインの性能に加え、一時的にそれを超える性能を発揮するための「クレジット」が付与される仕組み。

EBSボリュームは特定のAZに作成され、同じAZのインスタンスにしかアタッチできません。マルチアタッチはプロビジョンドIOPS SSD(io1/io2)でのみ利用できます。別のAZで使う場合はスナップショットから復元します。

スナップショットは増分#

EBSスナップショットは増分バックアップです。最初のスナップショットはボリュームで使われているブロック全体を保存し、2回目以降は前回から変更されたブロックだけを保存します。

  • 保存料金は実際に保存したブロック分だけなので、頻繁に取っても容量は増えにくい
  • 古いスナップショットを削除しても、後のスナップショットから復元できる(他のスナップショットが参照しているブロックは残され、どこからも参照されないブロックだけが削除される)
  • スナップショットは取得を開始した時点の内容になる。DBなど整合性が必要な場合は、書き込みを止めるかアプリ側で静止させてから取る
  • 別リージョンへのコピー(災害対策)や、別アカウントとの共有ができる(暗号化されている場合は、カスタマー管理のKMSキーで、そのキーの利用も相手に許可する)
  • スナップショットから作ったボリュームは、ブロックが初めて読まれるときにS3から読み込まれるため、最初は遅い。すぐに全性能が必要なら高速スナップショット復元(FSR)を使う
  • めったに使わない長期保存用には、料金が安いスナップショットのアーカイブ階層がある(復元に24〜72時間、最低90日)

Data Lifecycle Manager(DLM)#

Amazon Data Lifecycle Manager(DLM)は、EBSスナップショット(とEBSを使うAMI)の作成・保持・削除を自動化する機能です。

  • 対象はタグで指定する(例:Backup=daily が付いたボリューム・インスタンス)
  • スケジュール(12時間ごと、24時間ごと、cron式など)と、保持する数・期間を決める。古いものは自動で削除される
  • 別リージョンへのコピー、別アカウントとの共有、高速スナップショット復元の有効化もポリシーで自動化できる
  • DLM自体は無料(スナップショットの保存料金だけがかかる)

EBSだけを対象にするならDLM、RDS・DynamoDB・EFSなど複数のサービスのバックアップをまとめて管理したいならAWS Backupを使います。

ごみ箱(Recycle Bin)#

ごみ箱(Recycle Bin)は、削除したEBSスナップショットとEBSを使うAMIを、すぐに消さずに一定期間残しておく機能です。誤って削除しても、保持期間内ならごみ箱から復元できます。

  • 保持ルールで対象(リージョン内のすべて、または特定のタグが付いたもの)と保持期間(1日〜1年)を決める
  • ルールをロックすると、ルールの変更・削除ができなくなり、悪意のある削除やランサムウェアへの対策になる
  • ごみ箱にある間も、通常のスナップショットと同じ保存料金がかかる

既存の暗号化されていないボリュームを暗号化する手順#

EBSの暗号化はボリュームの作成時に決まり、既存のボリュームの暗号化をそのまま有効にすることはできません。暗号化されていないボリュームは、次の手順で暗号化したボリュームに置き換えます。

  1. ボリュームのスナップショットを取る
  2. スナップショットを、暗号化を有効にしてコピーする(KMSキーを指定)。スナップショットからボリュームを作るときに暗号化を指定してもよい
  3. 暗号化されたスナップショットから、同じAZに新しいボリュームを作る
  4. インスタンスを停止し、古いボリュームをデタッチして、新しいボリュームを同じデバイス名でアタッチしてから起動する(ルートボリュームは「ルートボリュームの置き換え」でも行える)

今後作るボリュームを必ず暗号化するには、リージョンごとの設定「EBSのデフォルト暗号化」を有効にします。暗号化されたボリュームでは、保存データ・インスタンスとの間の通信・スナップショット・そこから作るボリュームがすべて暗号化され、性能への影響はほとんどありません。

Elastic Volumes#

Elastic Volumesは、アタッチしたまま(インスタンスを止めずに)サイズ・ボリュームタイプ・IOPS・スループットを変更できる機能です。gp2からgp3への変更も、この機能でオンラインで行えます。

  • 変更中の状態は「modifying → optimizing → completed」と進み、optimizingの間も使えるが性能が揺れることがある
  • 同じボリュームを再び変更するには、前回の変更から6時間以上空ける必要がある
  • サイズは増やせるが減らせない。小さくしたいときは新しいボリュームを作ってデータをコピーする

サイズを増やしても、OSから見えるパーティションとファイルシステムは自動では広がりません。変更後に、OSの中で拡張します。

# パーティションの拡張(例:/dev/nvme0n1 の1番目のパーティション)
sudo growpart /dev/nvme0n1 1
# ファイルシステムの拡張
sudo xfs_growfs -d /     # XFSの場合
sudo resize2fs /dev/nvme0n1p1   # ext4の場合

Windowsでは「ディスクの管理」でボリュームを拡張します。「容量を増やしたのにディスクの空きが増えない」ときは、この拡張を忘れていないかを確認します。

ストレージの最適化#

RAIDを構成できます。ストライピング(RAID 0)はデータを複数ボリュームに分散して並列処理し、性能を上げます。

3. ユースケース#

  • OSディスク(Windows/Linux)
  • データベースの保存領域(MySQL/PostgreSQL)
  • アプリケーションのログ保存
  • アップロードファイルなどの永続データ

4. 料金の考え方#

プロビジョニングした容量(GB/月)に対して課金され、gp3やio1/io2では追加のIOPS・スループットにも料金がかかります。EC2が停止中でもボリュームの料金は発生します。スナップショットは保存量に応じて課金されます。

5. 関連サービス#

  • Amazon EC2:EBSをアタッチするインスタンス
  • Amazon S3:スナップショットの保存先
  • Amazon EFS:複数インスタンス・複数AZで共有できるファイルストレージ
  • AWS Backup:スナップショットの一元管理
  • AWS KMS:ボリューム・スナップショットの暗号化キー
  • Amazon CloudWatch:メトリクスの監視

6. 試験・実務でのポイント#

ボリュームタイプと性能

  • 迷ったらgp3。高IOPSのDB → io2。大量の順次読み書き → st1。
  • gp3はサイズに関係なく3,000IOPS・125MiB/sのベースライン。gp2は1GiBあたり3IOPSでサイズに比例する。st1・sc1はブートボリュームにできない。
  • gp2で性能が落ちる → BurstBalance(バーストクレジット残量)を確認。
  • I/Oが詰まっている → VolumeQueueLength を確認。
  • 性能を上げたい → RAID 0(ストライピング)。

スナップショット・バックアップ

  • EBSはAZに紐づく。別AZへはスナップショット経由。
  • スナップショットは増分。古いスナップショットを削除しても、残ったスナップショットから完全に復元できる。
  • タグで対象を決めてスナップショットを自動作成・削除 → Data Lifecycle Manager。複数サービスのバックアップ → AWS Backup。
  • 誤って削除したスナップショット・AMIを復元したい → ごみ箱(Recycle Bin)の保持ルール。

暗号化・変更

  • 既存のボリュームを暗号化 → スナップショット → 暗号化してコピー → 新しいボリュームを作って付け替える。今後のボリュームはデフォルト暗号化で強制。
  • 止めずにサイズ・タイプを変更 → Elastic Volumes。その後OSでパーティションとファイルシステムを拡張する。サイズは縮小できない。

7. まとめ#

  • EBSはEC2用の永続ブロックストレージ。停止してもデータは残る。
  • 標準はgp3、高性能はio2、HDDはst1/sc1。
  • 性能のトラブルはCloudWatchメトリクスで切り分ける。

このサービスが登場するユースケース#

  • EC2・EBSの性能不足を見つけて改善するCloudWatchのメトリクスとCompute Optimizerでボトルネックを特定し、止めずに性能を上げる
