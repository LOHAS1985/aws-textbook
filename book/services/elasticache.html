1. サービス概要#

Amazon ElastiCacheは、アプリケーションで利用するデータをインメモリでキャッシュするサービスです。よく使うデータをメモリに置くことで、DBの負荷を下げ、応答を高速化します。

2. 主な機能・特徴#

キャッシュする対象#

  • DBのキャッシュ:RDS、Aurora、DynamoDB
  • API呼び出しの結果:外部APIやマイクロサービスのレスポンス
  • セッションデータ:Webアプリのユーザーセッション情報
  • 計算結果:重い計算処理やクエリ集計の結果(再計算を回避)

エンジンは、Redisと互換のオープンソースValkey、Redis OSS、Memcachedから選びます。ValkeyとRedis OSSは同じように使え、レプリケーション・自動フェイルオーバー・バックアップに対応し、ソート済みセット(ランキング)などのデータ構造も使えます。

キャッシュ戦略#

  • リードスルー:アプリがキャッシュを読む → なければキャッシュがソースから読み込み、キャッシュに書き込む。
  • レイジーローディング:アプリがキャッシュを読む → なければアプリがソースから読み込み、キャッシュに書き込む。
  • ライトスルー(同期):アプリがキャッシュに書き込み → キャッシュがソースに書き込む。
  • ライトビハインド(非同期):アプリがキャッシュに書き込み → キャッシュが後からソースに書き込む。
戦略読み込み書き込みDB同期特徴
リードスルー自動取得-即キャッシュ主導
レイジーローディング必要時に取得-即アプリ主導
ライトスルー高速同期即整合性重視
ライトビハインド高速非同期遅延性能重視

レイジーローディングでは、DBを更新してもキャッシュに古いデータが残ります。キーにTTL(有効期限)を付けて、一定時間が過ぎたら自動で消えるようにし、ライトスルーと組み合わせるのが基本です。

レプリケーションとマルチAZ(Valkey・Redis OSS)#

ノードベースのクラスターは、1つのプライマリノード(読み書き)と、最大5つのレプリカノード(読み取り)をまとめたシャードでできています。

  • マルチAZと自動フェイルオーバーを有効にすると、プライマリに障害が起きたとき、別のAZのレプリカが自動で新しいプライマリに昇格する。
  • アプリは、ノードのアドレスではなくプライマリエンドポイント(書き込み)とリーダーエンドポイント(読み取り)に接続する。フェイルオーバー後も、エンドポイントは新しいプライマリを指す。
  • クラスターモードを有効にすると、データを複数のシャードに分けて置けるため、メモリと書き込みの性能を横に広げられる。無効の場合はシャードが1つで、読み取りだけをレプリカで増やせる。
  • フェイルオーバーの動作は、TestFailover で実際に試せる。

グローバルデータストアを使うと、別のリージョンに読み取り専用のクラスターを置き、データを1秒未満の遅れで複製できます。リージョン障害時は、別リージョンのクラスターを昇格させて書き込みを続けられます。

スケーリング#

  • 縦のスケーリング:ノードのタイプを大きくする(オンラインで変更できる)。
  • 読み取りのスケーリング:レプリカを増やし、リーダーエンドポイントから読む。
  • 横のスケーリング:クラスターモードでシャードを増やす(サービスを止めずにデータを移せる)。
  • クラスターモードでは、シャードとレプリカの数を、メトリクスに応じてAuto Scalingで増減できる。

メモリが足りないとき(エビクション)#

メモリがいっぱいになると、エンジンは設定された方針(パラメータグループの maxmemory-policy)に従って、古いキーやあまり使われないキーを消します。これをエビクションといいます。エビクションが増えるとキャッシュヒット率が下がり、DBへのアクセスが増えるため、ノードを大きくするかシャードを増やします。

監視するメトリクス#

メトリクス見るポイント
EngineCPUUtilizationValkey・Redis OSSのコマンドを処理するスレッドのCPU使用率。コマンドは1本のスレッドで処理されるため、ノード全体の CPUUtilization より、こちらを見る
DatabaseMemoryUsagePercentage使えるメモリのうち、使っている割合
Evictionsメモリ不足で消されたキーの数。増えていたら容量を増やす
CacheHits・CacheMissesキャッシュヒット率。低いとキャッシュの効果が出ていない(TTLが短すぎる、容量が足りない)
CurrConnections・NewConnections接続数。アプリが接続を使い回していないと急に増える
ReplicationLagレプリカの遅れ。大きいとレプリカから古いデータを読む
SwapUsageスワップの使用量。増えると性能が落ちる(Memcachedで特に注意)

セキュリティとバックアップ#

  • VPCの中に置き、セキュリティグループでアプリからの接続だけを許可する。
  • 通信の暗号化(TLS)と保存時の暗号化(KMS)を有効にできる。
  • Valkey・Redis OSSでは、AUTHトークンやユーザーごとのアクセス制御(RBAC)、IAM認証で接続を制限できる。
  • Valkey・Redis OSSの自動バックアップは最大35日間保持でき、手動のスナップショットはS3にエクスポートできる。復元すると新しいクラスターが作られる。
  • メンテナンスウィンドウ(パッチ適用などを行う時間帯)は、利用の少ない時間に設定する。

3. ユースケース#

  • RDSの読み取り負荷の軽減
  • 複数のWebサーバー間でのセッション共有
  • ランキングや集計結果のキャッシュ

4. 料金の考え方#

キャッシュノードのタイプと稼働時間で課金されます(サーバーレス版はデータ保存量と処理量で課金)。リザーブドノードで割引も可能です。

  • Amazon RDS/Amazon Aurora/Amazon DynamoDB:キャッシュ対象のDB
  • Amazon MemoryDB:Redis互換の永続的なインメモリDB
  • DynamoDB DAX:DynamoDB専用のキャッシュ
  • Amazon CloudWatch:メトリクスの監視とアラーム
  • Amazon VPC:キャッシュを置くネットワークとセキュリティグループ
  • 関連する用語:キャッシュの選び方、高可用性とスケーリング、性能のメトリクス

6. 試験・実務でのポイント#

設計

  • レプリケーション・フェイルオーバー・バックアップ・高機能なデータ構造 → Valkey/Redis OSS、シンプル・マルチスレッド → Memcached。
  • 必要なデータだけをキャッシュ(アプリ主導)→ レイジーローディング。ただし初回はキャッシュミスで遅く、古いデータが残る可能性がある → TTLを付ける。
  • キャッシュとDBの整合性重視 → ライトスルー。書き込み性能重視 → ライトビハインド(DBへの反映は遅延)。
  • 容量の見積もりをしたくない・負荷が読めない → ElastiCache Serverless。
  • AZ障害でも止めたくない → レプリカを別のAZに置き、マルチAZと自動フェイルオーバーを有効にする。アプリはエンドポイントに接続する。
  • リージョン障害に備える → グローバルデータストア。
  • CloudFront・API Gateway・ElastiCache・DAXのキャッシュの使い分け → キャッシュの選び方。

運用と監視

  • Valkey・Redis OSSのCPUは CPUUtilization ではなく EngineCPUUtilization を見る。
  • Evictions が増えた・ヒット率が下がった → メモリ不足。ノードを大きくするかシャードを増やす。
  • 読み取りの負荷が高い → レプリカを追加し、リーダーエンドポイントから読む。
  • アプリから接続できない → セキュリティグループ(ポート6379・11211)と、TLSの設定がアプリ側と合っているかを確認する。

7. まとめ#

  • ElastiCacheはインメモリキャッシュ。DB負荷の軽減と高速化に使う。
  • エンジンはValkey・Redis OSS・Memcached。
  • キャッシュ戦略は読み込み2種・書き込み2種の特徴を押さえる。古いデータにはTTLで備える。
  • 可用性はレプリカとマルチAZ、容量はノードのサイズ・シャード、監視は EngineCPUUtilization・Evictions・ヒット率。

このサービスが登場する運用シナリオ#

  • RDSの遅いクエリと接続数の問題を解消する
  • キャッシュでDBの読み取り負荷を下げる
