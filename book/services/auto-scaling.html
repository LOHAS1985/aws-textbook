1. サービス概要#

Amazon EC2 Auto Scalingは、EC2インスタンスの台数を自動で増減・維持するサービスです。インスタンスを「Auto Scalingグループ(ASG)」という単位でまとめ、次の2つを自動化します。

  • 台数の維持(自己修復):異常なインスタンスを終了し、代わりを起動して決めた台数を保つ。
  • スケーリング:負荷が上がったら台数を増やし(スケールアウト)、下がったら減らす(スケールイン)。

ELBと組み合わせると、増えたインスタンスは自動でターゲットに登録され、減ったインスタンスは登録を解除されます。

Auto Scalingグループの3つの台数#

設定意味
最小(Minimum)これより少なくはしない台数
希望(Desired)今この台数で動かしたい、という目標の台数。スケーリングで変わる
最大(Maximum)これより多くはしない台数(コストの上限にもなる)

起動テンプレート#

起動するインスタンスの設定(AMI、インスタンスタイプ、キーペア、セキュリティグループ、IAMロール、ユーザーデータなど)をまとめたものです。バージョン管理ができ、オンデマンドとスポットを混ぜる設定(混合インスタンスポリシー)にも使えます。古い仕組みの「起動設定(Launch Configuration)」は非推奨のため、起動テンプレートを使います。

混合インスタンスポリシーと割り当て戦略#

1つのグループでオンデマンドとスポット、複数のインスタンスタイプを混ぜて使う設定です。コストを下げつつ、スポットの中断(容量不足による回収)に強くできます。「どのインスタンスタイプ・どの購入オプションで起動するか」を決めるルールが割り当て戦略です。

  • オンデマンドの基本容量:最低限、必ずオンデマンドで確保する台数。
  • 基本容量を超えた分のオンデマンドの割合:それ以降の台数のうち、オンデマンドにする%(残りはスポット)。
  • インスタンスタイプの候補:複数指定する。属性(vCPU・メモリなど)で条件を指定して候補を自動選択する方法もある。
対象割り当て戦略動き
オンデマンドprioritized(既定)候補に付けた優先順位の順に使う。使えなければ次の候補
lowest-price最も安いタイプから使う
スポットprice-capacity-optimized中断されにくく、かつ価格が安いプールを選ぶ。推奨
capacity-optimized空き容量が最も多い(中断されにくい)プールを選ぶ
capacity-optimized-prioritized優先順位を尊重しつつ、容量の面でも最適化する
lowest-price最も安いプールを選ぶ(指定した数のプールに分散)。中断されやすい

「プール」は、インスタンスタイプとAZの組み合わせのことです。候補のタイプとAZを多くするほどプールが増え、スポットの確保と中断への耐性が高まります。キャパシティの再調整を有効にすると、スポットの中断リスクが高まったインスタンスを、中断される前に新しいインスタンスへ入れ替えます。

スケーリングの方法#

方法動き向いている場面
ターゲット追跡「平均CPU使用率50%」のような目標値を保つように自動で増減するまず検討する基本の方法
ステップアラームの超過幅に応じて増減数を変える(例:70%超で+1、90%超で+3)急な負荷に段階的に対応したい
シンプルアラームで決まった台数だけ増減し、クールダウン中は次の動作を待つ古い方式。ステップの利用が推奨
スケジュール決めた日時に希望・最小・最大の台数を変える毎朝9時のアクセス増など、時間で予測できる負荷
予測過去の負荷の傾向から需要を予測し、前もって台数を増やす日・週単位で周期的な負荷

ヘルスチェックと自己修復#

  • EC2ヘルスチェック(既定):EC2のステータスチェックで異常なら入れ替える。
  • ELBヘルスチェック:ロードバランサーのヘルスチェックに失敗した場合も入れ替える。アプリの異常も検知できるため、ELBと組み合わせるときは有効にする。
  • ヘルスチェックの猶予期間:起動直後はアプリの準備が終わっていないため、一定時間ヘルスチェックの結果を無視する。短すぎると「起動してすぐ終了される」を繰り返す。

ライフサイクルフック#

インスタンスの起動時・終了時に一時停止(Pending:Wait/Terminating:Wait)させて、独自の処理を入れる仕組みです。例えば、起動時にソフトウェアの設定を終えてからサービスに入れる、終了前にログをS3へ退避する、といった使い方をします。待機時間を過ぎるか、完了の通知を送ると次へ進みます。

説明の中心 成功・推奨・正常 失敗・非推奨・障害 その他の構成要素

そのほかの機能#

  • インスタンスの更新(Instance Refresh):起動テンプレートを新しくしたとき、インスタンスを少しずつ入れ替える(ローリング更新)。
  • 終了ポリシー:スケールインのとき、どのインスタンスから終了するかを決める。既定では、まずAZ間の台数のバランスを保ち、その中で古い起動テンプレートのインスタンスから終了する。
  • スケールイン保護:特定のインスタンスをスケールインで終了させない。
  • スタンバイ:インスタンスを一時的にグループのサービスから外し、調査や更新を行う。
  • プロセスの中断:ReplaceUnhealthy や Terminate などの処理を一時的に止める(障害調査中にインスタンスが入れ替わらないようにする、など)。
  • ウォームプール:初期化済みのインスタンスを停止状態で待機させ、スケールアウトを速くする。

関連する「Auto Scaling」#

  • Application Auto Scaling:EC2以外(ECSのタスク数、DynamoDBの読み書き容量、Auroraのレプリカ数、Lambdaのプロビジョニング済み同時実行数など)をスケーリングする仕組み。
  • AWS Auto Scaling(スケーリングプラン):複数のリソースのスケーリングをまとめて設定する仕組み。

Auto Scalingグループの範囲は1つのリージョン#

Auto Scalingグループは1つのリージョンの中だけで動きます。同じリージョンの複数のAZにまたがることはできますが、複数のリージョンにまたがるグループは作れません。

範囲できること
1つのAZできるが、AZの障害で全台が止まるため本番には向かない
複数のAZ(同じリージョン)推奨。AZ間で台数のバランスをとり、AZに障害が起きると残りのAZで台数を補う
複数のリージョン1つのグループではできない。リージョンごとにAuto Scalingグループ(とELB)を作る

複数リージョンで動かしたいときは、次のように組み立てます。

  • リージョンごとに、Auto Scalingグループ・起動テンプレート・ELBを作る(CloudFormationのStackSetsで同じ構成を展開すると楽)。
  • AMIもリージョンごとのリソースなので、使うリージョンへAMIをコピーし、そのリージョンのAMI IDを起動テンプレートに指定する(Amazon EC2の「AMIのリージョン間コピーと共有」を参照)。起動テンプレート・キーペア・セキュリティグループもリージョンごとに必要。
  • リージョン間の振り分けとフェイルオーバーは、Route 53(フェイルオーバー・レイテンシー・加重ルーティング)やGlobal Acceleratorで行う。

同じように、ELB(ALB・NLB)も1つのリージョンの中だけで動くサービスです。リージョンの範囲で動くサービスとグローバルなサービスの違いは、用語ページ「リージョンとアベイラビリティーゾーン」を参照してください。

3. ユースケース#

  • アクセス数が変動するWebアプリを、ALBの後ろで必要な台数だけ動かす
  • 障害が起きたインスタンスを自動で入れ替え、常に最低台数を保つ(台数が1でも自己修復に使える)
  • SQSキューのメッセージ数に応じて、ワーカーの台数を増減する
  • 夜間・休日は台数を減らしてコストを下げる(スケジュール)

4. 料金の考え方#

EC2 Auto Scaling自体は無料です。起動したEC2インスタンスやEBS、CloudWatch(詳細モニタリングや追加のアラーム)の料金がかかります。スポットインスタンスを混ぜたり、夜間の台数を減らしたりするとコストを下げられます。

6. 試験・実務でのポイント#

  • まずはターゲット追跡。時間で予測できる負荷はスケジュール、周期的な負荷は予測スケーリング。
  • メモリ使用率でスケーリングしたい → CloudWatchエージェントでメモリのメトリクスを送る(標準では取れない)。
  • アプリが応答しないのに入れ替わらない → ヘルスチェックの種類をELBにする。
  • 起動してすぐ終了されるのを繰り返す → ヘルスチェックの猶予期間を延ばす。
  • 終了前にログを退避したい・起動時に設定を済ませたい → ライフサイクルフック。
  • インスタンスが起動できない → AMI・キーペア・セキュリティグループの存在、vCPUのクォータ、AZの容量不足を確認する(アクティビティ履歴に理由が出る)。
  • 起動テンプレートを変えたあと既存インスタンスを入れ替えたい → インスタンスの更新。
  • 高可用性のため、ASGは複数AZのサブネットにまたがるように設定する。
  • ASGは1つのリージョンの中だけ(複数AZは可、複数リージョンは不可)。別リージョンにも置く → リージョンごとにASGを作り、AMIをコピーし、Route 53などで振り分ける。

7. まとめ#

  • 起動テンプレートとASG(最小・希望・最大)で、EC2の台数を自動で増減・維持する。
  • スケーリングはターゲット追跡が基本。ステップ・スケジュール・予測も使い分ける。
  • ELBヘルスチェック・猶予期間・ライフサイクルフックが運用のポイント。
  • サービス自体は無料で、EC2などの料金だけがかかる。

このサービスが登場する運用シナリオ#

  • 負荷に応じて自動でスケールするWebシステム
  • キューで処理を分離し、急増や障害に強くする
  • 1つのAZの障害からアプリを切り離す
  • パッチ適用済みのAMIを定期的に作り、Auto Scalingに反映する
  • 開発環境を夜間・休日に自動で停止して費用を下げる
