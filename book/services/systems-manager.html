1. サービス概要#

AWS Systems Manager(SSM)は、EC2・オンプレミス・他クラウドのサーバーを含むシステム運用を一元管理・自動化するためのサービスです。1つのサービスというより、「接続」「コマンド実行」「パッチ適用」「設定値の管理」「運用の自動化」などの機能の集合体です。

機能は次の4つの分類に分かれています。このページでは、共通の仕組みを説明したあと、機能を1つずつ紹介します。

分類機能
ノード管理Session Manager、Run Command、State Manager、Patch Manager、Inventory、Compliance、Fleet Manager、Distributor、ハイブリッドアクティベーション
変更管理Automation、Maintenance Windows、Change Manager、Change Calendar
アプリケーション管理Parameter Store、AppConfig
運用管理OpsCenter、Explorer

2. 主な機能・特徴#

共通の仕組み:SSM AgentとSSMドキュメント#

SSM Agentは、サーバーにインストールしてSystems Managerとの橋渡しをするソフトウェアです。Amazon Linux・Windows Serverなどの多くのAMIには最初から入っています。Agentの方からSystems Managerへ接続しに行く(ポーリングする)ため、サーバー側のインバウンドポートを開ける必要がありません。

  1. SSM AgentがSystems ManagerのエンドポイントへHTTPS(443)で接続し、指示を待つ
  2. Systems Managerからタスク(コマンド・パッチ適用など)が届く
  3. Agentがサーバー上で実行し、結果をSystems Managerへ返す

Systems Managerで管理できるサーバーを管理対象ノードと呼びます。EC2を管理対象ノードにするには、次の3つがそろっている必要があります。

  • SSM Agentがインストールされ、起動している
  • インスタンスのIAMロールに AmazonSSMManagedInstanceCore などの権限がある(またはアカウント全体の設定「デフォルトのホスト管理設定」を有効にする)
  • Systems Managerのエンドポイントへのアウトバウンド通信ができる(NATゲートウェイ、または ssm・ssmmessages・ec2messages のVPCエンドポイント)

SSMドキュメントは、Systems Managerが実行する処理を定義したJSON/YAMLのファイルです。AWSが用意したもの(AWS- で始まる)をそのまま使うことも、自作することもできます。Run Command用の「コマンドドキュメント」、Automation用の「ランブック」などの種類があります。

ノード管理の機能#

Session Manager

ブラウザやCLIから、SSH・RDPのポートを開けずにサーバーへ接続してシェルを操作できる機能です。

できること
シェルでの操作、ポートフォワーディング(手元のPCからRDSなどへ接続)、SSHのトンネル
特徴
踏み台サーバー・SSHキー・パブリックIPが不要。誰が接続できるかはIAMで制御し、操作ログをS3やCloudWatch Logsに保存できる。通信はKMSで暗号化できる
使いどころ
プライベートサブネットのEC2に安全にログインしたい

Run Command

多数のサーバーに、コマンドやスクリプトを一括で実行する機能です。

できること
シェルスクリプト(AWS-RunShellScript)やPowerShell(AWS-RunPowerShellScript)の実行、ソフトウェアのインストール、サービスの再起動など
特徴
対象はインスタンスIDのほかタグやリソースグループで指定できる。同時実行数とエラーのしきい値で、少しずつ安全に実行できる。実行結果はS3・CloudWatch Logsに出力でき、SNSで完了を通知できる
使いどころ
その場で1回だけ、複数台に同じ作業をしたい

State Manager

サーバーを決めた状態に保ち続ける機能です。

できること
関連付け(Association)で「どのノードに、どのドキュメントを、どのスケジュールで適用するか」を定義する。例:「タグ Role=Web のEC2に、30分ごとにApacheが起動していることを確認し、止まっていれば起動する」
特徴
新しく起動したノードにも自動で適用される。設定がずれても(ドリフト)、次の実行で元に戻る
使いどころ
CloudWatchエージェントやウイルス対策ソフトを、全サーバーで常に動かしておきたい

Run Commandが「1回だけ実行」なのに対し、State Managerは「繰り返し実行して状態を保つ」点が違います。

Patch Manager

OS(と一部のアプリ)のパッチ適用を自動化する機能です。

構成要素
パッチベースライン(どのパッチを承認するか。例:重要度Criticalのパッチをリリース7日後に自動承認)、パッチグループ(タグで対象ノードを分類)
実行方法
AWS-RunPatchBaseline ドキュメントを、Maintenance Windowsやパッチポリシー(Quick Setup)で定期的に実行する。Scan(不足パッチの確認のみ)とInstall(適用)を選べる
使いどころ
多数のサーバーに、決まった時間帯に計画的にパッチを当てたい

Inventory

サーバーのソフトウェアや設定の情報を収集する機能です。

できること
OSのバージョン、インストール済みのアプリ、ネットワーク設定、Windowsの更新プログラムなどを定期的に収集する
特徴
リソースデータの同期で、複数アカウント・リージョンの情報をS3に集め、Athenaで分析できる
使いどころ
「特定のバージョンのソフトが入っているサーバーはどれか」を調べたい

Compliance

管理対象ノードがルールに準拠しているかを一覧で確認する機能です。

できること
Patch Managerのパッチ適用状況と、State Managerの関連付けの適用状況を、「準拠/非準拠」で表示する
使いどころ
パッチを当てられていないサーバーを見つけたい

Fleet Manager

サーバーをコンソール上のGUIで管理する機能です。

できること
ファイルの閲覧、CPU・メモリなどの状態の確認、ログの確認、OSのユーザー管理、Windowsのレジストリ操作。WindowsにはブラウザからRDPで接続できる
使いどころ
ログインせずに、サーバーの状態をまとめて確認したい

Distributor

ソフトウェアをパッケージにして配布する機能です。

できること
AWSが用意したパッケージ(CloudWatchエージェントなど)や自社のソフトを、Run Command(1回)やState Manager(継続)でインストール・更新する
使いどころ
社内の監視エージェントを全サーバーに配りたい

ハイブリッドアクティベーション

オンプレミスや他クラウドのサーバーを、管理対象ノードとして登録する仕組みです。

手順
Systems Managerでアクティベーション(コードとID)を作成し、サーバーにSSM Agentを入れて登録する。登録されたサーバーは mi- で始まるIDで管理される
使いどころ
EC2とオンプレミスのサーバーを、同じ方法でパッチ適用・コマンド実行したい

変更管理の機能#

Automation

ランブック(複数のステップからなる手順書)に従って、運用作業を自動で実行する機能です。サーバーの中だけでなく、AWSのAPIを呼び出してリソースを操作できる点がRun Commandと違います。

ランブックの例
AWS-RestartEC2Instance(インスタンスの再起動)、AWS-StopEC2Instance(停止)、AWS-CreateImage(AMIの作成)、AWS-UpdateLinuxAmi(パッチ適用済みのAMIの作成)、AWS-DisablePublicAccessForSecurityGroup(SGの公開設定の削除)
実行のきっかけ
手動、EventBridgeのルール、AWS Configの修復アクション、Maintenance Windows、CloudWatchアラーム
特徴
途中に承認のステップを入れられる。複数のアカウント・リージョンで一度に実行できる。同時実行数とエラーのしきい値を設定できる
使いどころ
障害の復旧手順や、設定違反の自動修復を、毎回同じ手順で確実に行いたい

Maintenance Windows

運用作業を実行してよい時間帯(メンテナンスウィンドウ)を決め、その時間に作業を自動で実行する機能です。

設定内容
スケジュール(cron式など)、時間の長さ、新しいタスクを開始しない締め切り時間、対象(ターゲット)、実行するタスク
実行できるタスク
Run Command、Automation、Lambda関数、Step Functionsのステートマシン
使いどころ
パッチ適用やバックアップを、業務時間外に実行したい

Change Manager

本番環境への変更の申請・承認・実行を管理する機能です。

できること
変更テンプレートで、必要な承認者と実行するランブックを決めておく。申請が承認されると、Automationで変更が実行される
使いどころ
本番環境の変更に、承認のワークフローを必ず通したい

Change Calendar

変更をしてよい期間・してはいけない期間をカレンダーで定義する機能です。

できること
期間を「OPEN(変更可)」「CLOSED(変更禁止)」で管理する。AutomationやChange Managerは、CLOSEDの期間には実行を止められる
使いどころ
年末のセール期間中は本番環境を変更しないようにしたい

アプリケーション管理の機能#

Parameter Store

アプリの設定値や機密情報を保存するキーバリューストアです。

パラメータの種類
String(通常の文字列)、StringList(カンマ区切り)、SecureString(KMSで暗号化した機密情報)
階層と履歴
/prod/db/endpoint のように階層で整理し、IAMでパスごとにアクセスを制御できる。値を変更するとバージョンが残る
標準とアドバンスト
標準は無料(1つ4KBまで)。アドバンストは有料で、8KBまでの値と、有効期限などのポリシーを使える
使いどころ
DBの接続先やAPIキーを、コードから切り離して管理したい。CloudFormationやECS・Lambdaからも参照できる
項目Parameter StoreSecrets Manager
主な用途設定値全般(機密情報も可)機密情報
自動ローテーションなしあり(RDSのパスワードなど)
料金標準パラメータは無料シークレットごとに月額料金

AppConfig

アプリの設定(機能フラグなど)の変更を、段階的に安全に配布する機能です。設定ミスが全員に一斉に反映されて障害になるのを防ぎます。

流れ
新しい設定のバージョンを作成 → Validator(JSONスキーマやLambda)で検証 → 一部のクライアントから段階的に配布 → CloudWatchアラームで監視し、異常なら自動でロールバック
使いどころ
アプリを再デプロイせずに、設定や機能のON/OFFを安全に切り替えたい

運用管理の機能#

OpsCenter

運用上の問題をOpsItemとして1か所に集め、調査・対応を管理する機能です。

できること
CloudWatchアラームやEventBridgeのイベントからOpsItemを自動で作成する。関連するリソースの情報やログをまとめて表示し、OpsItemからAutomationのランブックを実行して対応できる
使いどころ
アラートを一覧で管理し、決まった手順ですばやく対応したい

Explorer

運用データをダッシュボードで横断的に表示する機能です。

できること
OpsItemの件数、パッチの準拠状況、インスタンスの数などを、複数のアカウント・リージョンにまたがって表示する
使いどころ
組織全体の運用状況をひと目で把握したい

3. ユースケース#

  • 踏み台サーバーなしでプライベートサブネットのEC2にログインする(Session Manager)
  • 数百台のサーバーへ、毎週決まった時間にパッチを適用する(Patch Manager+Maintenance Windows)
  • Configで検出した設定違反を自動で修復する(Automation)
  • 全サーバーでCloudWatchエージェントが動いている状態を保つ(State Manager+Distributor)
  • アプリの設定値・パスワードを集中管理する(Parameter Store)
  • 機能フラグを段階的に有効にし、問題があれば自動で戻す(AppConfig)

4. 料金の考え方#

Session Manager・Run Command・State Manager・Patch Manager・Inventory・Parameter Store(標準パラメータ)など、多くの機能は追加料金なしで使えます(EC2・S3・CloudWatch Logsなど、使ったほかのサービスの料金はかかります)。

有料になるのは、Parameter Storeのアドバンストパラメータや高スループット設定、Automationのステップ実行、AppConfigの設定の取得、OpsCenterのOpsItem、オンプレミスのアドバンストインスタンス(Session Managerで接続する場合など)です。

5. 関連サービス#

  • Amazon EC2:管理対象ノード
  • AWS IAM:インスタンスのロール、Session Managerの接続権限
  • AWS Secrets Manager:自動ローテーションが必要な機密情報
  • AWS KMS:SecureStringやセッションの暗号化
  • AWS Config/AWS Security Hub:Automationによる修復の起点
  • Amazon EventBridge:AutomationやOpsCenterのトリガー
  • Amazon CloudWatch:ログの保存先、AppConfigのロールバック条件
  • Amazon Athena:Inventoryのデータの分析

6. 試験・実務でのポイント#

  • EC2がSystems Managerに表示されない → SSM Agent・IAMロール・アウトバウンド通信(NATまたはVPCエンドポイント)を確認。
  • ポート22を開けずに安全にログイン、操作ログも残したい → Session Manager。
  • 複数サーバーへ1回だけ一括でコマンド → Run Command。状態を保ち続ける → State Manager。
  • 定期的なパッチ適用 → Patch Manager+Maintenance Windows。適用状況の確認 → Compliance。
  • AWSリソースの操作を含む復旧・修復の自動化 → Automationランブック(Configの修復アクションからも実行)。
  • 変更禁止期間を設けたい → Change Calendar。変更に承認を必須にしたい → Change Manager。
  • 設定値の保存 → Parameter Store。パスワードの自動ローテーション → Secrets Manager。
  • 設定変更の段階デプロイと自動ロールバック → AppConfig。
  • オンプレミスのサーバーも管理したい → ハイブリッドアクティベーション。

7. まとめ#

  • Systems Managerは運用管理機能の集合体。SSM Agentを通じてサーバーを管理する。
  • ノード管理:接続はSession Manager、コマンドはRun Command、状態維持はState Manager、パッチはPatch Manager。
  • 変更管理:手順の自動化はAutomation、時間帯はMaintenance Windows、承認・禁止期間はChange Manager・Change Calendar。
  • アプリ管理:設定値はParameter Store、設定の安全な配布はAppConfig。運用管理はOpsCenter・Explorer。
