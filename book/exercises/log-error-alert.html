アプリのエラーログを検知して通知する構成を組み立てる

最終更新:2026-10-26

1. 要件#

  • アプリのログに「ERROR」が出たら、すぐに開発者へメールで知らせたい。
  • 原因を調べるために、過去のログを条件で検索したい。

2. 構成を組み立てる#

① ログの「ERROR」の数をメトリクスにするものは?

  • メトリクスフィルターロググループに設定し、パターンに一致したログの数をメトリクスにします。そのメトリクスでアラームを作れます。
  • サブスクリプションフィルターログをLambdaやData Firehoseへそのまま流す仕組みで、数を数えてアラームにするものではありません。
  • AWS CloudTrailAWSのAPIの呼び出しの記録で、アプリが出したログは扱いません(監視・記録のサービスの選び方)。

② 過去のログを条件で検索・集計するものは?

  • CloudWatch Logs Insightsロググループに対して、専用のクエリで検索・集計できます。ログを別の場所に移す必要はありません。
  • AWS X-Rayリクエストがどのサービスでどれだけ時間がかかったかを追うトレースのサービスで、ログの検索はしません。
  • AWS Configリソースの設定の履歴を記録するサービスで、アプリのログは扱いません。

③ エラーがない時間にアラームを「OK」にする欠落データの扱いは?

  • notBreaching(正常として扱う)一致するログがない時間はデータが送られないことがあるため、欠落を正常とみなします(CloudWatchアラームの状態と評価)。
  • breaching(しきい値超えとして扱う)エラーがないのにALARMになり、誤報になります。
  • missing(既定のまま)データがない期間が続くと INSUFFICIENT_DATA になり、状態が分かりにくくなります。

④ ログの保存の費用を抑えるには?

  • 保持期間を決め、長期保存するログはS3に移すCloudWatch Logsの保持期間は既定で無期限です。必要な期間を決め、長く残すログは安いS3に置きます。
  • アラームの評価期間を短くするアラームの設定はログの保存の費用に関係しません。
  • メトリクスフィルターを削除する通知ができなくなるだけで、ログの保存量は変わりません。

3. 解説#

解説を見る(答え合わせのあとに読む)

アプリのログをCloudWatch Logsのロググループに送り、メトリクスフィルターで「ERROR」の数をメトリクスにして、アラームからSNSでメールを送ります。調査はLogs Insightsで行います。ログを即座に別の処理に流したいときは、サブスクリプションフィルターを使います。
