マイクロサービスの遅延を特定する構成を組み立てる

複数のサービスをまたぐ処理のどこが遅いか・どこでエラーが出ているかを、トレースで突き止める

最終更新:2026-10-26

1. 要件#

  • API Gateway → Lambda → DynamoDB・外部APIの処理が、ときどき遅い。
  • どの区間で時間がかかっているかを、ログを1つずつ見ずに特定したい。

2. 構成を組み立てる#

① リクエストごとの各区間の処理時間を集めて、図で示すものは?

  • AWS X-Rayリクエストの経路と、区間ごとの処理時間・エラーをトレースとして記録し、トレースマップで表示します。
  • AWS CloudTrailAPIの操作の記録で、処理時間の内訳は分かりません。
  • VPCフローログIPアドレスとポートの通信の記録で、アプリの処理の区間は分かりません。

② 特定の顧客IDのトレースを検索できるよう記録するには?

  • 注釈(annotation)として記録する注釈は検索・絞り込みに使えます。検索しない付加情報はメタデータに記録します。
  • メタデータとして記録するメタデータはトレースに付くだけで、検索の条件には使えません。
  • サンプリングを0%にするトレースが記録されなくなります。

③ Lambdaのトレースが届かないとき、まず確かめることは?

  • アクティブトレースの有効化と、実行ロールのX-Rayへの書き込み権限どちらかが欠けると、トレースは送られません(IAMロール)。
  • ロググループの保持期間ログの保存の設定で、トレースには関係しません。
  • 関数のメモリの量性能には関係しますが、トレースが届かない原因ではありません。

3. 解説#

解説を見る(答え合わせのあとに読む)

API Gatewayのステージと、Lambdaのアクティブトレースを有効にすると、X-Rayがリクエストの区間ごとの時間を記録し、トレースマップで遅い区間が分かります。既定のサンプリングは毎秒1件+5%なので、すべてのリクエストは記録されません。
