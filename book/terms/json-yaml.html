JSONとYAMLの読み方

IAMポリシー・CloudFormationのテンプレート・イベントパターンなどを書くための2つのデータの書き方

最終更新:2026-10-26

1. 詳しい説明#

AWSの設定の多くは、JSONかYAMLで書きます。どちらも「名前と値の組」と「並び(リスト)」を組み合わせてデータを表す書き方で、同じ内容をどちらでも表せます。試験でもポリシーやテンプレートの一部が示され、内容を読み取る問題が出ます。

使う場所書き方
IAMポリシー・バケットポリシー・キーポリシーJSON
CloudFormationのテンプレートJSON または YAML(YAMLが一般的)
EventBridgeのイベントパターン、Step Functionsの定義JSON
Systems Managerのドキュメント(ランブック)JSON または YAML
CodeBuildの buildspec、CodeDeployの appspec、SAMのテンプレートYAML
AWS CLIの出力、APIのリクエストと応答JSON(CLIは --output yaml なども可)

同じ内容をJSONとYAMLで書く#

次の2つは、どちらも「名前が web、ポートが 80 と 443、公開する」という同じデータです。

{
  "Name": "web",
  "Ports": [80, 443],
  "Public": true
}
Name: web
Ports:
  - 80
  - 443
Public: true
要素JSONYAML
名前と値の組(オブジェクト){ "キー": 値 }。キーは必ず " で囲むキー: 値(コロンのあとに空白)
並び(リスト・配列)[値1, 値2]行頭の - (または [値1, 値2])
入れ子{ } と [ ] の中に書く字下げ(インデント)で表す。タブは使えず空白だけ
文字列必ず " で囲む多くの場合、囲まなくてよい
コメント書けない# から行末まで

YAMLは字下げの深さで構造が決まるので、空白が1つずれただけで意味が変わったりエラーになったりします。JSONはカンマの付け忘れ・付けすぎ(最後の要素のあとにカンマを付けるとエラー)が典型的な間違いです。

読み方の例:IAMポリシー#

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::logs", "arn:aws:s3:::logs/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}

Statement は [ ] なので、許可・拒否のかたまりを複数並べられます。この例は1つだけで、「HTTPSでない(aws:SecureTransport が false の)S3の操作をすべて拒否する」という意味です。Resource にバケット自体(logs)と中のオブジェクト(logs/*)の両方を並べている点もよく問われます。

読み方の例:CloudFormationのテンプレート(YAML)#

Resources:
  LogBucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
    Properties:
      VersioningConfiguration:
        Status: Enabled
Outputs:
  BucketName:
    Value: !Ref LogBucket

字下げから、LogBucket は Resources の中の1つのリソースで、DeletionPolicy(スタックを消してもバケットを残す)と Properties を持つことが読み取れます。!Ref のような ! で始まる書き方は、YAMLで使えるCloudFormationの組み込み関数の短縮形です(JSONでは {"Ref": "LogBucket"} と書く)。
