データベース

Amazon DynamoDB

フルマネージドのキーバリュー型NoSQLデータベース

1. サービス概要#

Amazon DynamoDBは、フルマネージドのキーバリューストア(NoSQLデータベース)です。サーバー管理が不要で、大量のアクセスにも低レイテンシーで応答します。

2. 主な機能・特徴#

テーブルのキー#

  • プライマリキー:アイテムを一意に識別するキー。次の2通りがある。
    • パーティションキーのみ:パーティションキーの値がテーブル内で一意でなければならない。
    • パーティションキー+ソートキー:同じパーティションキーの値を複数のアイテムが持てる。2つの組み合わせがテーブル内で一意になる。
  • パーティションキー:どの物理パーティションに保存するかを決める。値に偏りがあると性能が劣化する。
  • ソートキー:同じパーティションキー内での並び順を決める。

データの読み取り#

1回のリクエストで取得できる最大データ容量は1MBです。

  • GetItem:主キーで1件取得
  • BatchGetItem:主キーで複数件取得
  • Query:パーティションキー・インデックスを条件に取得
  • Scan:全件走査

セカンダリインデックス#

別のキー構成でクエリを実行するための仕組みです。

  • ローカル(LSI):パーティションキーはそのままで、ソートキーを変えたいとき。例:UserID+OrderDate のテーブルで、UserID+OrderStatus で検索したい。
  • グローバル(GSI):パーティションキーを変えたいとき。例:OrderID+OrderStatus で検索したい。
ローカル(LSI)グローバル(GSI)

TTL(Time To Live)#

指定時刻を過ぎたアイテムを自動削除する機能です。TTL属性はNumber型+UNIXエポック秒である必要があります。セッション管理・キャッシュ・一時URLや認証コードに使います。ただし削除までにラグが生じるため、正確な時刻で処理したい場合はEventBridge+Lambdaを使います。

エラー処理#

UnprocessedKeys は、スロットリングやサイズ超過で未処理になったキーのリストです。エクスポネンシャルバックオフでリトライして再実行します。

関連機能#

  • DynamoDB Accelerator(DAX):インメモリキャッシュ。読み取りをマイクロ秒レベルに高速化。
  • DynamoDB Streams:テーブルのデータ変更を記録し、外部処理に連携する。
    • Streams+Lambdaの流れ:アプリがテーブルを更新 → Streamsが変更イベントを記録 → Lambdaがポーリング(若干の遅延あり)→ まとめて取得して関数を実行
    • ビュータイプ(記録する内容):KEYS_ONLY(キーのみ)、NEW_IMAGE(更新後のアイテム)、OLD_IMAGE(更新前のアイテム)、NEW_AND_OLD_IMAGES(更新前と更新後の両方)
  • DynamoDB Transactions:複数アイテムの更新を「全成功 or 全失敗」にするACIDトランザクション。TransactWriteItems(複数書き込み)、TransactGetItems(複数読み取り)。

3. ユースケース#

  • セッション管理・ユーザープロファイル(TTLで自動削除)
  • 大量アクセスのあるゲーム・EC・IoTのデータ保存
  • 変更をトリガーにした後続処理(Streams+Lambda)

4. 料金の考え方#

性能はキャパシティユニットで表し、テーブルが1秒間にどれだけ読み書きできるかを示します(1RCU/1WCU=1KB/秒が基準)。

  • RCU(読み込みキャパシティユニット):整合性の違いで消費量が変わる(強い整合性のほうが多く消費)。
  • WCU(書き込みキャパシティユニット)

1RCUは「4KBまでのアイテムを強い整合性で1回/秒、結果整合性なら2回/秒」、1WCUは「1KBまでのアイテムを1回/秒」書き込めます。料金モードは、容量を事前に指定するプロビジョンドと、リクエスト数に応じて課金されるオンデマンドの2種類です。

5. 関連サービス#

  • AWS Lambda:DynamoDB Streamsの処理
  • Amazon EventBridge:正確な時刻での削除処理
  • Amazon ElastiCache:汎用的なキャッシュ
  • Amazon RDS:リレーショナルDBの選択肢
  • AWS Database Encryption SDK:クライアント側での属性暗号化
  • 関連する用語:スロットリングとリトライ

6. 試験・実務でのポイント#

  • パーティションキーは値が分散するものを選ぶ(偏るとホットパーティション)。
  • 後からインデックスを追加 → GSIのみ可能。LSIはテーブル作成時のみ。
  • GSIは結果整合性のみ。強い整合性が必要ならベーステーブルかLSI。
  • 読み取りをマイクロ秒に → DAX。
  • 変更をトリガーに処理 → Streams+Lambda。
  • UnprocessedKeys → エクスポネンシャルバックオフでリトライ。
  • 全件取得の Scan は高コスト。可能なら Query。
  • CloudFront・API Gateway・ElastiCache・DAXのキャッシュの使い分け → キャッシュの選び方。

7. まとめ#

  • DynamoDBはキーバリュー型のフルマネージドNoSQL。
  • キー設計(パーティションキー・ソートキー・LSI/GSI)が性能を左右する。
  • DAX・Streams・TTL・Transactionsで機能を拡張できる。
データベース

Amazon RDS

リレーショナルデータベースの構築・運用を任せられるマネージドDB

1. サービス概要#

Amazon RDS(Relational Database Service)は、リレーショナルデータベース(SQL)の構築・運用を提供するマネージドサービスです。パッチ適用やバックアップなどの面倒な運用作業をAWSに任せられます。

対応DBエンジン:MySQL、PostgreSQL、MariaDB、Oracle Database、Microsoft SQL Server、Amazon Aurora

2. 主な機能・特徴#

RDSが代行するDB運用タスク#

  • プロビジョニング:DBサーバーの起動
  • パッチ適用:OS/DBエンジン
  • バックアップ
    • 自動バックアップ:保持期間は最大35日
    • 手動スナップショット:無期限(削除するまで残る)
    • ポイントインタイムリカバリ:特定時点のデータに復元
  • 障害時のフェイルオーバー:Multi-AZ構成
  • スケーリング:スペック変更、リードレプリカ(プライマリから非同期でレプリケーションするためわずかな遅延が発生)

Multi-AZは別AZにスタンバイを置く可用性のための仕組みで、スタンバイは読み取りに使えません(同期レプリケーション)。リードレプリカは読み取り性能を上げる仕組みです。目的の違いを区別しましょう。

試験では「どちらを選ぶか」と「障害時に何が起きるか」がよく問われます。次の表で違いを整理しておきましょう。

Multi-AZ(スタンバイ)リードレプリカ
目的可用性(障害時の引き継ぎ)読み取り性能(読み取りの分散)
レプリケーション同期(データの損失がない)非同期(わずかに遅れる=レプリカラグ)
読み取りに使えるか使えない(Multi-AZ DBクラスターのスタンバイは読める)使える(レプリカごとのエンドポイントに接続)
置ける場所同じリージョンの別AZ同じAZ・別AZ・別リージョン(クロスリージョンリードレプリカ)
障害時の切り替え自動でスタンバイが昇格し、エンドポイントのDNSが切り替わる自動では昇格しない。手動で「昇格」すると独立したDBになる
接続先の変更不要(エンドポイント名は同じ)必要(昇格したDBのエンドポイントへ切り替える)
バックアップ・メンテナンスバックアップはスタンバイから取るため、プライマリのI/Oが止まらないレプリカの作成にはソースDBの自動バックアップの有効化が必要

RDS(MySQL・PostgreSQLなど)のリードレプリカを手動で昇格すると、レプリケーションが切れて書き込みできる独立したDBになります。元に戻すことはできず、ほかのレプリカも新しいDBには付いてきません。別リージョンのリードレプリカを昇格させるのは、リージョン障害に備えたDRの定番の手順です。

これに対してAuroraは、プライマリに障害が起きるとリードレプリカ(Auroraレプリカ)が自動でプライマリに昇格します。Auroraのレプリカはプライマリと同じストレージを共有しているため、スタンバイと読み取り用のレプリカを兼ねられるのです。「リードレプリカが自動でプライマリに昇格する」のはAuroraだけと覚えておきましょう。

RDS Proxy#

大量のクライアントからのアクセスを、少数のDB接続に集約・再利用する仕組みです。

  • 前提:DBクエリの時間は短く、DB接続を行うのはアプリサーバー。
  • 例:アプリサーバーから1万人がDBにアクセスしても、実際に同時にクエリを投げているのは一部。RDS Proxyは50接続を1万人で使い回す。Proxyがないと1万接続を使い、接続数の上限を超える可能性が高い。

RDS Proxyとフェイルオーバー#

  • Multi-AZのフェイルオーバーが起きると、Proxyは新しいプライマリへの接続を振り分け直す。アプリはProxyのエンドポイントに接続したままでよい。
  • ProxyはDNSのキャッシュを使わずに切り替え先へ接続するため、DNS名の切り替えを待たずに済む。Multi-AZ DBインスタンスでは、フェイルオーバー時間を最大66%短くできる。
  • フェイルオーバーに備えて、Proxyは一部の接続を監視用に確保している。
  • フェイルオーバー中に実行していたトランザクションは失敗する。Proxyが自動で再実行するわけではないので、アプリ側で再試行の処理を用意する。
  • Proxyは書き込み側(プライマリ)にだけ関連付けられる。リードレプリカには関連付けられない。

DBサブネットグループ#

DBサブネットグループは、RDSのDBインスタンスを配置してよいVPC内のサブネットの組です。DBインスタンスを作るときに指定し、RDSはこの中のサブネットにインスタンスを置きます。

  • 2つ以上のAZのサブネットを含める必要がある(Multi-AZのスタンバイや、障害時の配置先に使われる)
  • 通常はプライベートサブネットだけで構成し、DBをインターネットから切り離す
  • DBへのアクセスはセキュリティグループで、アプリサーバーのセキュリティグループからのDBポート(MySQLなら3306)だけを許可する

パラメータグループとオプショングループ#

種類設定するもの例
パラメータグループDBエンジンの設定値(設定ファイルの内容に当たるもの)max_connections、文字コード、タイムゾーン、スロークエリログの出力、rds.force_ssl(SSL接続の強制)
オプショングループエンジンに追加する機能OracleのTDE(透過的データ暗号化)、SQL ServerのS3へのネイティブバックアップ
  • RDSではOSにログインして設定ファイルを直接編集できないため、エンジンの設定はパラメータグループで行う
  • デフォルトのパラメータグループは変更できない。カスタムのパラメータグループを作ってDBに関連付ける
  • パラメータには、すぐに反映される動的パラメータと、再起動するまで反映されない静的パラメータがある(状態が「pending-reboot」になる)
  • オプショングループはMySQL・MariaDB・Oracle・SQL Serverで使う(PostgreSQLは拡張機能をパラメータで有効にする)

メンテナンスウィンドウ#

メンテナンスウィンドウは、OSやDBエンジンのパッチ適用など、RDSが行うメンテナンスの時間帯です。週1回・30分以上の枠を指定します(指定しないとリージョンごとの時間帯から自動で割り当てられる)。

  • 「マイナーバージョンの自動アップグレード」を有効にすると、新しいマイナーバージョンがメンテナンスウィンドウで適用される
  • インスタンスクラスの変更なども、「すぐに適用」を選ばなければ次のメンテナンスウィンドウで適用される
  • メンテナンス中はDBが停止することがある。Multi-AZでは、先にスタンバイに適用してからフェイルオーバーし、最後に旧プライマリに適用するため、停止時間を短くできる
  • 予定されているメンテナンスは、コンソールやAWS Health Dashboardで確認できる

暗号化#

RDSの保存時の暗号化はKMSキーで行い、ストレージだけでなく自動バックアップ・スナップショット・リードレプリカ・ログもすべて暗号化されます。

  • 暗号化はDBインスタンスの作成時にしか有効にできない。作成後に有効・無効を切り替えることはできない
  • 暗号化されたDBのリードレプリカは暗号化される(別リージョンのレプリカでは、そのリージョンのKMSキーを使う)
  • 転送時の暗号化はSSL/TLSで行い、パラメータグループで接続時のSSLを強制できる

暗号化されていない既存のDBを暗号化するには、次の手順で新しいDBに作り直します。

ストレージの自動スケーリング#

ストレージの自動スケーリングを有効にすると、空き容量が少なくなったときにストレージが自動で拡張されます。拡張の上限(最大ストレージしきい値)を指定しておきます。

  • 拡張される条件:空き容量が割り当て容量の10%未満の状態が5分以上続き、前回のストレージ変更から6時間以上経っている
  • 拡張量は10GiB、割り当て容量の10%、直近の増え方から予測した7時間分のうち最も大きい値
  • 拡張中もDBは止まらない。ただしストレージを縮小することはできない

容量不足でDBが止まるのを防げるため、データ量の増え方が読みにくい場合に有効です。CloudWatchメトリクス FreeStorageSpace にアラームを設定して監視も併用します。

Multi-AZのDNS切り替え#

Multi-AZでは、アプリはDBのエンドポイント(DNS名)に接続します。プライマリに障害が起きると、RDSは自動でスタンバイを新しいプライマリに昇格し、エンドポイントのDNSレコードをスタンバイに向け直します。

  • エンドポイント名は変わらないので、アプリの設定変更は不要。切り替えには通常1〜2分かかり、その間の接続は切れるため、アプリは再接続できるようにしておく
  • DNSの結果を長くキャッシュするアプリ(JavaのDNSキャッシュなど)は、古いIPに接続し続けないようTTLを短くする
  • フェイルオーバーが起きるのは、AZの障害、プライマリの故障、インスタンスクラスの変更やパッチ適用、「フェイルオーバーを伴う再起動」を実行したとき。RDSイベント通知で検知できる
  • 読み取り可能なスタンバイを2つ持つ「Multi-AZ DBクラスター」構成もあり、フェイルオーバーがより速い

Performance Insightsと拡張モニタリング#

機能見られるもの使う場面
CloudWatchの標準メトリクスCPU使用率、空きメモリ、空きストレージ、接続数、IOPS、レイテンシーなど(1分間隔)基本の監視・アラーム
拡張モニタリングDBインスタンス上のエージェントが集めるOSレベルのメトリクス(プロセスごとのCPU・メモリ、ファイルシステムなど)。1〜60秒間隔で、CloudWatch Logsに出力「OSのどのプロセスがCPUを使っているか」を細かく見たい
Performance InsightsDBの負荷(平均アクティブセッション数)を、SQL文・待機イベント・ユーザー・ホスト別に分解して表示する「どのSQLが遅いのか」「何を待っているのか」を特定したい

CloudWatchの標準メトリクスはハイパーバイザー側から取るため、OS内部の詳細は見えません。OSの中を見るなら拡張モニタリング、DBの中(SQL)を見るならPerformance Insights、と使い分けます。これらはCloudWatch Database Insightsとしてもまとめて表示できます。

Blue/Green Deployments#

RDS Blue/Green Deploymentsは、本番のDB(ブルー)をコピーしたステージング環境(グリーン)を作り、ブルーの変更をレプリケーションで同期させながらグリーン側で変更・テストし、準備ができたら短時間で切り替える機能です。

  • メジャーバージョンアップグレード、スキーマ変更、パラメータの変更などを、本番への影響を抑えて行える
  • 切り替え(スイッチオーバー)は通常1分以内で、グリーンがブルーと同じエンドポイント名になるため、アプリの接続先を変えなくてよい
  • 切り替え後も旧ブルー環境は残るので、確認が終わってから削除する
  • MySQL・MariaDB・PostgreSQL(とAurora)で使える

停止は最大7日#

開発用のDBなど、使わない時間はDBインスタンスを停止してインスタンスの料金を節約できます。ただし、停止できるのは最大7日間で、7日を過ぎると自動で起動します(メンテナンスを適用できなくなるのを防ぐため)。

  • 停止中もストレージとスナップショットの料金はかかる
  • 長期間止めておきたい場合は、EventBridgeのスケジュールとLambdaで定期的に停止し直すか、スナップショットを取ってDBを削除し、必要なときに復元する
  • リードレプリカがあるDBなど、構成によっては停止できない

3. ユースケース#

  • Webアプリの業務データベース
  • 既存のMySQL/Oracle/SQL ServerをAWSへ移行
  • Lambdaなど接続数が急増しやすい環境からのDB接続(RDS Proxy)

4. 料金の考え方#

DBインスタンスの稼働時間(インスタンスクラス)、ストレージ容量、バックアップ容量、データ転送量で課金されます。Multi-AZはスタンバイ分の料金も加わります。リザーブドインスタンスで割引も可能です。

5. 関連サービス#

  • Amazon Aurora:AWSが開発した高性能なRDSエンジン
  • Amazon DynamoDB:NoSQLの選択肢
  • Amazon ElastiCache:DBの前段のキャッシュ
  • AWS Lambda:RDS Proxyと相性の良い接続元
  • AWS Secrets Manager:DB認証情報の管理・ローテーション
  • AWS Backup:バックアップの一元管理
  • 関連する用語:IOPS・スループット・レイテンシー、よく使うポート番号、マネージドサービスとサーバーレス、責任共有モデル

6. 試験・実務でのポイント#

構成・設定

  • DBを置くサブネットの指定 → DBサブネットグループ(2つ以上のAZのサブネットが必要)。
  • max_connections などエンジンの設定を変える → カスタムのパラメータグループ(デフォルトは変更不可)。静的パラメータは再起動で反映。TDEなど機能の追加 → オプショングループ。
  • パッチ適用の時間帯を決める → メンテナンスウィンドウ。Multi-AZなら停止時間が短くなる。

可用性・性能

  • 障害対策 → Multi-AZ、読み取り性能 → リードレプリカ(非同期なので遅延あり)。
  • RDSのリードレプリカは障害時に自動で昇格しない(手動で昇格すると独立したDBになり、接続先の変更が必要)。レプリカが自動で昇格するのはAuroraだけ。
  • リージョン障害に備えて別リージョンにコピーを持つ → クロスリージョンリードレプリカ(障害時に手動で昇格)。Auroraならグローバルデータベース。
  • Multi-AZのフェイルオーバーではエンドポイント名は変わらず、DNSがスタンバイに切り替わる。アプリは再接続できるようにする。
  • 「DB接続数が多すぎる」「Lambdaから大量接続」→ RDS Proxy。フェイルオーバーを速くしたい場合も、DNSのキャッシュを使わないProxyが向く(進行中のトランザクションは失敗するので再試行を実装する)。
  • 遅いSQLや待機イベントの特定 → Performance Insights。OSのプロセス単位のメトリクス → 拡張モニタリング。

バックアップ・暗号化

  • 自動バックアップは最大35日。それ以上残したい → 手動スナップショット。
  • 特定時点に戻したい → ポイントインタイムリカバリ。
  • 既存の暗号化されていないDBを暗号化 → スナップショット → 暗号化してコピー → 復元。暗号化は作成時にしか設定できない。

運用

  • 空き容量不足を自動で防ぐ → ストレージの自動スケーリング(縮小はできない)。
  • メジャーバージョンアップを短い停止時間で安全に → Blue/Green Deployments。
  • 停止したDBが勝手に起動した → 停止は最大7日で自動起動する。

7. まとめ#

  • RDSはリレーショナルDBのマネージドサービス。運用タスクをAWSが代行する。
  • バックアップは自動(最大35日)と手動(無期限)。
  • 可用性はMulti-AZ、読み取り拡張はリードレプリカ、接続集約はRDS Proxy。
データベース

Amazon Aurora

MySQL/PostgreSQL互換の高性能リレーショナルデータベース

1. サービス概要#

Amazon Auroraは、MySQL/PostgreSQL互換のリレーショナルデータベースです。RDSのDBエンジンの1つで、AWSが独自に設計したストレージにより高い性能と可用性を持ちます。

2. 主な機能・特徴#

アーキテクチャの特徴#

  • 共有クラスターボリューム:データは3つのAZにまたがって6コピー保持される。
  • インスタンス構成:1つのプライマリ(書き込み)と最大15のレプリカ(読み取り)。全インスタンスがボリュームを共有するため、レプリカのラグは通常ミリ秒レベル。
  • 自己修復:ストレージ側でディスク障害を自動検出して修復する。

エンドポイント#

エンドポイント向き先
クラスターエンドポイント常にプライマリ(書き込み用)
リーダーエンドポイントレプリカへ負荷分散(読み取り用)
カスタムエンドポイント任意のインスタンスの組み合わせ
インスタンスエンドポイント特定のインスタンス

可用性とフェイルオーバー#

  • プライマリに障害が起きると、レプリカが自動で昇格する。
  • レプリカがない場合は新しいインスタンスを作成するため、復旧に時間がかかる。可用性を重視するなら別AZにレプリカを置く。高可用性の考え方は用語ページ「高可用性とスケーリング」を参照してください。
  • 通常のRDS Multi-AZと違い、スタンバイ専用インスタンスはなく、レプリカが読み取りとフェイルオーバーを兼ねる。
  • リードレプリカが自動でプライマリに昇格するのはAuroraだけ。RDS(MySQL・PostgreSQLなど)のリードレプリカは自動では昇格せず、手動で昇格すると独立したDBになる(違いはAmazon RDSのページの表を参照)。
  • どのレプリカを昇格させるかはフェイルオーバー優先度(ティア0〜15)で決める。数字が小さいほど優先され、同じ優先度ならサイズが大きいレプリカが選ばれる。プライマリと同じインスタンスクラスのレプリカを優先度の高いティアに置くと、昇格後に性能が落ちない。
  • フェイルオーバーは通常30秒〜1分程度。クラスターエンドポイントは新しいプライマリを自動で指すため、アプリはクラスターエンドポイントに接続しておけば接続先を変えなくてよい。

主な機能#

機能概要
レプリカのAuto Scaling負荷に応じてレプリカ数を増減する
Aurora Serverless v2負荷に応じてACU(Auroraキャパシティーユニット)を細かく自動調整する。変動の大きいワークロード向け
Auroraグローバルデータベース複数リージョンにレプリケートする。通常は1秒未満の遅延で、DRやグローバルな読み取りに使う
バックトラックAurora MySQLのみ。スナップショットから復元せず、クラスターを過去の時点へ巻き戻せる
クローンコピーオンライトで短時間に複製する。本番データを使ったテスト環境の作成に便利
RDS Proxy接続をプールし、フェイルオーバー時間の短縮と接続数の抑制に有効。Lambdaからの接続にも向く
Database Activity Streamsデータベースアクティビティをほぼリアルタイムでストリーミングする(監査用)

バックアップと復元#

  • 継続的バックアップ:自動バックアップはS3に保存され、保持期間は1〜35日。ポイントインタイムリカバリが使える。
  • 復元は常に新しいクラスターとして作成される(既存クラスターは上書きされない)。
  • 手動スナップショットは削除するまで残り、リージョン間でコピーできる。

3. ユースケース#

  • 高い可用性・性能が必要な業務システムのDB
  • 読み取りが多いWebサービス(最大15レプリカ+リーダーエンドポイント)
  • 負荷の変動が大きいアプリ(Serverless v2)
  • 複数リージョンでの災害対策・グローバル読み取り(グローバルデータベース)。災害対策の4つの方式は用語ページ「DR戦略」を参照してください。

4. 料金の考え方#

インスタンスの稼働時間(Serverless v2ではACUの使用量)、ストレージの使用量、I/Oリクエスト、バックアップ容量で課金されます。ストレージは使った分だけ自動で拡張されます。従量課金の仕組みは用語ページ「料金の基本」を参照してください。

5. 関連サービス#

  • Amazon RDS:Auroraを含むマネージドDBサービス
  • AWS Lambda:RDS Proxy経由での接続
  • Amazon ElastiCache:前段のキャッシュ
  • AWS Backup:バックアップの一元管理

6. 試験・実務でのポイント#

  • データは3AZに6コピー。レプリカは最大15。
  • 書き込み → クラスターエンドポイント、読み取り → リーダーエンドポイント。
  • フェイルオーバーを速くしたい → 別AZにレプリカを置く。
  • リードレプリカがプライマリに自動で昇格する → Aurora(RDSのリードレプリカは手動で昇格)。昇格の順番はフェイルオーバー優先度(ティア)で決める。
  • 誤操作をすばやく戻したい(MySQL)→ バックトラック。
  • 本番データでテスト環境を素早く作る → クローン。
  • リージョン障害対策 → グローバルデータベース。
  • PITRやスナップショットからの復元は新しいクラスターになる(接続先の切り替えが必要)。

7. まとめ#

  • AuroraはMySQL/PostgreSQL互換の高性能DB。共有ストレージで3AZ・6コピー。
  • エンドポイントで書き込み・読み取りを使い分ける。
  • Serverless v2、グローバルDB、バックトラック、クローンなど独自機能が豊富。
データベース

Amazon DocumentDB

MongoDB互換のドキュメントデータベースをマネージドで利用するサービス

1. サービス概要#

Amazon DocumentDBは、JSON形式のドキュメントを保存・検索するMongoDB互換のマネージドデータベースです。MongoDB用のドライバーやAPIを使うアプリケーションをAWS上で実行できます。

DocumentDBはMongoDBそのものではありません。APIの互換性や利用できる機能はエンジンのバージョンによって異なるため、移行前にアプリケーションが使うコマンド・集計機能・ドライバーを検証します。

2. 主な機能・特徴#

ドキュメントモデルとクラスター#

  • データを柔軟なJSON形式のドキュメントとして保存し、フィールドや配列を条件に検索する。
  • インスタンスベースのクラスターでは、書き込みを処理するインスタンスと読み取りレプリカを組み合わせる。
  • Elastic Clustersは、シャーディングによって水平にスケールするワークロード向けの選択肢。
  • ストレージはデータ量に応じて拡張され、バックアップや複数AZ構成を利用できる。

データモデルの選択#

ドキュメント内のフィールドを柔軟に扱いたいときや、MongoDB互換アプリを移行するときに候補になります。関係データやトランザクションをSQLで扱う場合はAmazon RDS、キーを指定した低遅延アクセスはAmazon DynamoDBと比較します。

3. ユースケース#

  • MongoDB互換のアプリケーションをAWSへ移行する。
  • 商品カタログやユーザープロファイルなど、属性が異なるドキュメントを保存する。
  • JSON形式のデータをアプリケーションの読み書きに合わせて検索する。

4. 料金の考え方#

クラスターのインスタンスやElastic Clustersの処理能力、データストレージ、バックアップ、データ転送などが料金に影響します。必要な読み取り性能、冗長性、保持期間を見積もり、クラスター構成を調整します。

5. 関連サービス#

  • Amazon RDS/Amazon DynamoDB:リレーショナル・キー値データとの使い分け
  • AWS DMS:データベース移行と継続レプリケーション
  • AWS Backup:データベースのバックアップ管理
  • AWS KMS:暗号化キーの管理
  • 関連する用語:データストアの選び方

6. 試験・実務でのポイント#

  • MongoDB互換のドキュメントデータベース → Amazon DocumentDB。
  • MongoDBとの機能互換性を前提にせず、アプリが使うAPI・ドライバー・クエリーを移行前に確認する。
  • 関係データのSQLクエリーやトランザクションが必要なら、RDS・Auroraとの要件を比較する。

7. まとめ#

  • DocumentDBはMongoDB互換のドキュメントデータベース。
  • データモデルとAPI互換性を確かめて、適切なクラスター方式を選ぶ。
データベース

Amazon Keyspaces

Apache Cassandra互換のワイドカラムデータベースをサーバーレスで利用するサービス

1. サービス概要#

Amazon Keyspaces (for Apache Cassandra)は、Apache Cassandra互換のマネージドなワイドカラムデータベースです。Cassandra Query Language (CQL) と既存のCassandraアプリケーション用ツールを使って、サーバーを管理せずにデータを読み書きできます。

2. 主な機能・特徴#

サーバーレスのテーブル#

  • テーブルの保存容量や処理能力をサービス側が管理し、需要に応じてスケールする。
  • オンデマンド容量モードとプロビジョンド容量モードから、トラフィックの予測可能性に合わせて選ぶ。
  • CQLでテーブルを定義し、アプリケーションから読み書きする。
  • マルチリージョン構成では、複数リージョン間のレプリケーションを設定できる。

アクセスパターンに合わせた設計#

パーティションキーはデータの分散と検索範囲に影響します。Cassandra互換のワイドカラム設計では、実行するクエリーを先に定め、その検索条件に合う主キーとテーブルを設計します。任意の列を自由に検索する用途には向きません。

3. ユースケース#

  • 既存のApache Cassandraアプリケーションをマネージド環境へ移行する。
  • 大量の時系列データやイベントを、キーに基づいて継続的に読み書きする。
  • サーバー運用を避けながら、CQL互換のアプリケーションを構築する。

4. 料金の考え方#

書き込み・読み取り容量、データストレージ、バックアップ、データ転送などが料金に影響します。オンデマンドとプロビジョンドの容量モード、アクセスパターン、保持期間を合わせて見積もります。

5. 関連サービス#

  • Amazon DynamoDB:キー値・ドキュメント型のサーバーレスデータベース
  • Amazon MSK/Amazon Kinesis:ストリームの取り込み
  • AWS DMS:データベース移行とレプリケーション
  • 関連する用語:データストアの選び方

6. 試験・実務でのポイント#

  • Apache Cassandra互換のワイドカラムデータベース → Amazon Keyspaces。
  • パーティションキーとアクセスパターンを先に設計する。任意の条件での検索を前提にしない。
  • CQL互換が必要か、DynamoDBなど別のNoSQLデータベースが適するかを要件で比べる。

7. まとめ#

  • KeyspacesはCassandra互換のサーバーレスなワイドカラムデータベース。
  • クエリーとパーティションキーに合わせてデータモデルを設計する。
データベース

Amazon Neptune

ノードと関係で表すデータをクエリーするマネージドグラフデータベース

1. サービス概要#

Amazon Neptuneは、エンティティ間の関係をグラフとして保存・検索するマネージドデータベースです。人物・商品・端末などのノードと、その関係を表すエッジをたどるクエリーに適しています。

Neptune Databaseは運用データを保持してクエリーするエンジンです。大規模なグラフをメモリ内で分析するAmazon Neptune Analyticsとは、用途と実行方法が異なります。

2. 主な機能・特徴#

グラフモデルとクエリー言語#

  • プロパティグラフではノード・エッジ・属性でデータを表し、GremlinやopenCypherで検索する。
  • RDFグラフでは主語・述語・目的語のトリプルでデータを表し、SPARQLで検索する。
  • クエリー言語はデータモデルやアプリケーションの要件に合わせて選ぶ。
  • リードレプリカ、複数AZ、バックアップなど、運用データベース向けの機能を利用できる。

3. ユースケース#

  • 不正検知や推薦で、複数段階の関係をたどる。
  • 顧客・商品・取引の関係をナレッジグラフとして管理する。
  • ネットワークや依存関係をグラフとして分析する。

4. 料金の考え方#

Neptune Databaseでは、データベースインスタンス、ストレージ、I/O、バックアップ、転送などが料金に影響します。Neptune Analyticsは別の分析用エンジンで、料金の単位や構成が異なるため、用途に合うサービスを選びます。

5. 関連サービス#

  • Amazon DocumentDB:ドキュメントモデルとの使い分け
  • Amazon OpenSearch Service:全文検索やベクトル検索
  • Amazon S3:グラフデータセットの保存
  • 関連する用語:データストアの選び方、ベクトル検索

6. 試験・実務でのポイント#

  • 複雑な関係をたどるグラフクエリー → Amazon Neptune。
  • Gremlin・openCypherはプロパティグラフ、SPARQLはRDFグラフのクエリー言語。
  • SQLの表形式分析や全文検索とは異なるデータモデルを選ぶ。

7. まとめ#

  • Neptuneはノードと関係を扱うマネージドグラフデータベース。
  • データモデルに合わせてGremlin・openCypher・SPARQLを使い分ける。
データベース

Amazon MemoryDB

Redis互換の永続的なインメモリデータベース

1. サービス概要#

Amazon MemoryDBは、Redis(Valkey)互換の耐久性のあるインメモリデータベースです。インメモリならではの高速な応答と、データを失わない耐久性を両立し、キャッシュではなくメインのデータベースとして使えます。

2. 主な機能・特徴#

  • データはマルチAZのトランザクションログに書き込まれ、ノード障害でも失われない。
  • 読み取りはマイクロ秒、書き込みは1桁ミリ秒のレイテンシー。
  • Redisのデータ構造・APIをそのまま使える。
  • シャーディングとレプリカでスケールし、障害時は自動フェイルオーバー。

3. ユースケース#

  • 超低レイテンシーが必要なアプリのプライマリDB(ゲームのリーダーボード、セッション、在庫など)
  • 「キャッシュ+DB」の2層構成を1つにまとめたい

4. 料金の考え方#

ノードのタイプと稼働時間、書き込みデータ量、スナップショットの保存量で課金されます。

5. 関連サービス#

  • Amazon ElastiCache:キャッシュ用途のインメモリサービス
  • Amazon DynamoDB:キーバリュー型NoSQL

6. 試験・実務でのポイント#

  • Redis互換で耐久性が必要なプライマリDB → MemoryDB。
  • DBの前段に置くキャッシュ → ElastiCache。
  • CloudFront・API Gateway・ElastiCache・DAXのキャッシュの使い分け → キャッシュの選び方。

7. まとめ#

  • MemoryDBは、高速なインメモリと耐久性を両立したRedis互換DB。
