サービスの選び方

監視・記録のサービスの選び方

CloudWatch・CloudTrail・Config・X-Ray・VPCフローログを「何を知りたいか」で使い分ける

1. 詳しい説明#

AWSには、システムの状態や出来事を記録するサービスがいくつもあります。どれも「ログ」や「履歴」を扱うので混同しやすいですが、記録しているものが違います。調べたいことから逆に考えると選びやすくなります。

ログの種類と取得するサービス・機能#

「ログ」と呼ばれるものには、記録する対象によって種類があります。種類ごとに、取得を有効にする場所と、保存先が違います。

組み合わせて調べる#

実際の調査では、複数のサービスを順に見ていきます。例えば「夜中に急にエラーが増えた」なら、CloudWatchのアラームで気づき、CloudWatch Logsでエラーの内容を確認し、CloudTrailとConfigでその直前に誰かが設定を変えていないかを調べます。

選び方のポイント#

  • 誰がEC2を削除したか・セキュリティグループを変えたかを調べたい → CloudTrail。
  • リソースの設定が過去にどうだったか、ルールに違反していないかを知りたい → AWS Config。違反を自動で直すこともできる(運用シナリオ「公開されたS3バケットを検出して自動で修復する」)。
  • EC2のメモリ・ディスクの使用率は標準のメトリクスにない → CloudWatchエージェントを入れる(運用シナリオ「EC2のメモリ・ディスク使用率を監視する」)。
  • ログに出る特定の文字列(ERRORなど)の数でアラームを出したい → CloudWatch Logsのメトリクスフィルター。
  • マイクロサービスのどこで遅いかを知りたい → X-Ray(運用シナリオ「マイクロサービスの遅延の原因をトレースで特定する」)。
  • EC2に接続できない原因がSGかネットワークACLかを切り分けたい → VPCフローログ(REJECTの記録)。経路の設定ミスはReachability Analyzer(運用シナリオ「EC2に接続できない原因を調査する」)。
  • CloudTrailは管理イベントだけが既定で記録される。S3のオブジェクトの操作やLambdaの呼び出し(データイベント)は、証跡で有効にする。
  • CloudTrailのログが改ざんされていないことを示したい → ログファイルの整合性の検証を有効にする。
  • 複数アカウントの記録をまとめたい → 組織の証跡(CloudTrail)、アグリゲーター(Config)、ログの集約(運用シナリオ「複数アカウントのログを集約して分析する」)。
  • AWS側のメンテナンスや障害に自動で対応したい → Healthのイベントを EventBridge で受ける(運用シナリオ「AWSの予定メンテナンスや障害の通知に自動で対応する」)。

Amazon CloudWatch

システムの状態を記録・監視・通知する統合監視サービス

1. サービス概要#

Amazon CloudWatchは、AWS上のシステムの状態を記録・監視・通知するための統合監視サービスです。メトリクス(数値)とログの両方を扱います。

2. 主な機能・特徴#

メトリクス・アラーム・ダッシュボード#

  • メトリクス:リソースの時系列の数値データ。
    • デフォルトは5分間隔(詳細モニタリングで1分間隔)。
    • アプリからカスタムメトリクスを送信できる(PutMetricData API)。カスタムメトリクス=標準にないメトリクス。EC2のメモリ・ディスク使用率は標準メトリクスにない。
  • アラーム:しきい値を設定し、異常時にアクションを実行。メトリクスを選択 → しきい値と比較演算子 → 評価期間を設定。連携先はSNS通知・Auto Scaling・EC2の再起動など。
  • ダッシュボード:クロスアカウント/クロスリージョンのメトリクスもまとめて表示できる。

ダッシュボードの共有と定義の再利用#

ダッシュボードの中身(どのウィジェットで、どのメトリクスをどう表示するか)は、JSON形式の「ダッシュボードの本文(DashboardBody)」で定義されています。この定義を取り出して配ることで、同じ表示項目を別の環境でも再現できます。

目的方法
定義を確認・コピーするコンソールの「アクション → 表示/編集のソース」でJSONを表示してコピー、またはCLIの aws cloudwatch get-dashboard
別のアカウント・リージョンへ複製するJSONを貼り付けて作成、またはCLIの put-dashboard(PutDashboard API)
チームで共通の定義をコードで管理するCloudFormationの AWS::CloudWatch::Dashboard(DashboardBody)やテンプレートに書き、複数環境へ展開
見る人に共有する(AWSのアカウントを持たない人を含む)コンソールの「共有」で、特定のメールアドレス(Cognitoで認証)・公開リンク・シングルサインオン(SSO)プロバイダーのいずれかを選ぶ
別アカウントのメトリクスを1つのダッシュボードで見るCloudWatchのクロスアカウント機能で、モニタリングアカウントにソースアカウントを連携する

ダッシュボードの共有は、閲覧だけを許可します。公開リンクは、リンクを知っていれば誰でも見られるため、機密性のある数値を含む場合は使わないでください。

メトリクスの基本#

メトリクスは「どのサービスの(名前空間)」「何の値を(メトリクス名)」「どのリソースについて(ディメンション)」の3つで特定します。アラームやグラフでは、それを「どの統計で・何秒ごとに集計するか」を指定して使います。

用語意味例・ポイント
名前空間メトリクスの入れ物(サービス単位)AWS/EC2、AWS/RDS。エージェントのメトリクスは既定で CWAgent。カスタムメトリクスは自由に命名できる(AWS/ で始まる名前は使えない)
ディメンションリソースを区別するキーと値InstanceId、AutoScalingGroupName、LoadBalancer。ディメンションが違えば別のメトリクスとして扱われる
統計期間内のデータの集計方法Average・Sum・Maximum・Minimum・SampleCount・パーセンタイル(p99など)
期間・解像度何秒ごとの値かEC2は標準5分、詳細モニタリングで1分。カスタムメトリクスは高解像度で1秒まで(アラームは10秒・30秒周期も可)
保持期間データが残る期間1分未満は3時間、1分は15日、5分は63日、1時間は455日(最大15か月)。古いデータほど粗い粒度にまとめられる。メトリクスは手動で削除できない

統計の選び方#

同じメトリクスでも、統計を間違えると意味のない値になります。「回数は合計、使用率は平均、残量は最小、遅延はパーセンタイル」と覚えます。

統計向いているメトリクス例
Sum回数・件数(期間内に何回起きたか)Errors、RequestCount、HTTPCode_Target_5XX_Count、ThrottledRequests
Average使用率・割合CPUUtilization、mem_used_percent
Maximum一瞬でも超えたら困る値・ピークDuration(タイムアウト接近)、ApproximateAgeOfOldestMessage、IteratorAge
Minimum残量(少ないほど危険)FreeStorageSpace、CPUCreditBalance、BurstBalance、HealthyHostCount
p99 など応答時間(平均だと一部の遅いリクエストが埋もれる)TargetResponseTime、Latency

標準では取れないメトリクス#

EC2の標準メトリクスは、ハイパーバイザー(仮想化の層)の外から見える値だけです。OSの中の値はCloudWatchエージェントでカスタムメトリクスとして送る必要があります。

取りたい値メトリクス(Linux)メトリクス(Windows)
メモリ使用率mem_used_percentMemory % Committed Bytes In Use
ディスク(ファイルシステム)使用率disk_used_percentLogicalDisk % Free Space(空き率)
スワップ使用率swap_used_percentPaging File % Usage
特定プロセスの状態procstat プラグイン(プロセスごとのCPU・メモリ・起動数)

エージェント設定の append_dimensions で InstanceId を付け、aggregation_dimensions で AutoScalingGroupName 単位に集計すると、Auto Scalingグループ全体のメモリ使用率でアラームを作れます。設定ファイルはSystems ManagerのParameter Storeに保存して複数台へ配布するのが定番です。

サービス別メトリクス一覧#

SOA-C03で出題されうるメトリクスをサービス別にまとめます。赤字は特に出題されやすいメトリクスです。

  • コンピューティング(EC2・Auto Scaling・Lambda)
  • コンテナ(ECS・EKS)
  • ストレージ(EBS・EFS・S3)
  • データベース(RDS・Aurora・DynamoDB・ElastiCache)
  • ネットワーク・コンテンツ配信(ELB・CloudFront・Route 53・API Gateway・NAT・VPN・Direct Connect・Transit Gateway)
  • アプリケーション統合・分析(SQS・SNS・Kinesis・Step Functions・EventBridge)
  • 料金・アカウント・監視自体(Billing・Usage・Synthetics・Logs)
  • 症状からメトリクスを逆引き

CloudWatch Logs#

ログの収集・保存・検索・分析を行います。

  • 用語:ロググループ(アプリ・サービス単位)、ログストリーム(インスタンスや実行単位)、ログイベント(実際のログ1行)
  • 収集方法:Lambda・API GatewayなどはAWSサービスから自動出力。EC2はCloudWatchエージェントをインストールして送信。
  • 分析
    • Logs Insights:SQLライクなクエリでログを分析。データ保護ポリシーでマスキングされた値を表示するには、logs:Unmask 権限を持つ利用者がクエリに unmask コマンドを加える
    • メトリクスフィルター:ログからメトリクスを生成(例:"error"が出たらアラーム+SNSで通知)
    • サブスクリプションフィルター:ログを他サービスへリアルタイムにストリーミング
  • データ保護ポリシー:ログイベントの機密情報を検出・監査し、Logs Insights・メトリクスフィルター・サブスクリプションフィルターなどへの出力時にマスキングする。ポリシー設定前に取り込んだログイベントはマスキングされない
  • 保持期間:デフォルトは無期限(1日〜10年で指定可能)。短期・頻繁に検索するログはCloudWatch Logs、長期・たまに検索するログはS3(Standard-IA・Glacierなど)へ。
  • 暗号化:KMSキーを関連付ける(associate-kms-key)
fields @timestamp, @message
| unmask
| sort @timestamp desc
| limit 20

unmask を実行できるのは logs:Unmask 権限を持つ利用者だけです。必要な担当者に限定して権限を付与してください。

CloudWatchエージェント#

EC2やオンプレミスのサーバーから、詳細なメトリクスやログをCloudWatchへ送信します。

  1. CloudWatchエージェントをインストール
  2. エージェントの設定ファイル(JSON)を作成(例:メモリ使用率 mem_used_percent と /var/log/app.log を送信)
  3. EC2にIAMロール(CloudWatchAgentServerPolicy)をアタッチ
  4. エージェントを起動し、メトリクスがCloudWatchに送信される

設定ファイルの metrics の中で、送るメトリクスに付けるディメンション(メトリクスを見分けるための名前と値の組)を指定します。特に試験で問われるのが append_dimensions です。

{
  "metrics": {
    "append_dimensions": {
      "InstanceId": "${aws:InstanceId}",
      "InstanceType": "${aws:InstanceType}",
      "ImageId": "${aws:ImageId}",
      "AutoScalingGroupName": "${aws:AutoScalingGroupName}"
    },
    "aggregation_dimensions": [["AutoScalingGroupName"], ["InstanceId"]],
    "metrics_collected": {
      "mem": { "measurement": ["mem_used_percent"] },
      "disk": { "measurement": ["used_percent"], "resources": ["/"] }
    }
  }
}
設定役割
append_dimensionsエージェントが送るすべてのメトリクスに、EC2の情報をディメンションとして追加する。使える値は ${aws:InstanceId}・${aws:InstanceType}・${aws:ImageId}・${aws:AutoScalingGroupName} の4つ。これがないと、どのインスタンスのメモリ使用率なのか見分けられない
aggregation_dimensions指定したディメンション単位にまとめたメトリクスも作る。[["AutoScalingGroupName"]] なら、Auto Scalingグループ全体のメモリ使用率でアラームやスケーリングができる
append_dimensions(各メトリクスの中)メトリクスごとに、独自のディメンション(例:"Environment": "prod")を追加する

「メモリ使用率のメトリクスは届いているのに、インスタンスごとに見分けられない」「Auto Scalingグループ単位で集計できない」という問題は、append_dimensions と aggregation_dimensions の設定で解決します。なお、ディメンションの組み合わせが違うと、CloudWatchでは別のメトリクスとして扱われる点に注意してください(カスタムメトリクスの料金も別々にかかります)。

CloudWatch Synthetics#

CloudWatch Syntheticsは、利用者の操作を模擬してWebサイトやAPIを定期的に確認する外形監視の機能です。監視用スクリプトをCanaryと呼び、Lambda関数として実行します。実際のアクセスがない時間帯でも、利用者の経路が正常に動くか確認できます。

  • Canaryはスケジュールに従ってURLやAPIにアクセスし、ログインや画面操作などの一連の処理を検証する。
  • 実行結果はCloudWatchメトリクス(SuccessPercent、Durationなど)として確認でき、失敗率や応答時間にアラームを設定できる。
  • スクリーンショット・HTTPアーカイブ(HAR)・ログなどの実行結果はS3に保存される。
  • インターネットに公開されていないエンドポイントは、CanaryをVPC内で実行するように設定する。

Canaryの設計図(ブループリント)

ブループリントは、Canaryを作るときに選ぶひな形です。用途に合ったスクリプトの雛形があらかじめ用意されており、URLなどを指定するだけで、自分でコードを書かずに始められます。作成後にスクリプトを編集して、処理を足すこともできます。スクリプトは Node.js(Puppeteer)または Python(Selenium)で書きます。

ブループリント内容主な用途
ハートビートモニタリング指定したURLを開き、画面のスクリーンショットとHTTPアーカイブ(HAR)を保存するサイトが生きているか(死活監視)、表示できているかの確認
APIキャナリーREST APIにリクエストを送り、応答コードや内容を検証する(読み取り・書き込みを含む)APIの可用性・正しい応答の監視
リンク切れチェッカーページ内のリンクをたどり、リンク先がエラーにならないかを検査するサイト内外のリンク切れの検出
Canary Recorderブラウザの拡張機能で操作を記録し、スクリプトに変換するログインなど、画面の操作手順の再現
GUIワークフロービルダー「入力欄に文字を入れる」「ボタンをクリックする」「文字が表示されるか確認する」といった手順を、画面で組み立てるログインや購入などの一連の操作の監視(コードを書かない)

クロスアカウントオブザーバビリティ#

クロスアカウントオブザーバビリティは、複数のAWSアカウントのメトリクス・ログ・トレースを、1つのモニタリングアカウントからまとめて見て、検索し、アラームを作れる機能です。各アカウントにサインインし直したり、ログを1か所にコピーしたりする必要がありません。

用語意味
モニタリングアカウントデータを見る側のアカウント(運用・監視チームのアカウント)。ここでシンク(受け口)を作る
ソースアカウントデータを見せる側のアカウント(各アプリのアカウント)。シンクへのリンクを作り、共有するデータの種類を選ぶ
共有できるデータCloudWatchのメトリクス、CloudWatch Logsのロググループ、X-Ray・Application Signalsのトレースなど
仕組みCloudWatchのObservability Access Manager(OAM)がシンクとリンクを管理する。リージョンごとに設定する

設定の流れは次のとおりです。

  1. モニタリングアカウントのCloudWatchの設定で、モニタリングアカウントとして有効にする(シンクを作り、どのアカウント・組織からのリンクを受け付けるかを決める)
  2. ソースアカウントをリンクする。Organizationsを使っている場合は、コンソールが作るCloudFormationテンプレートやStackSetsで、組織やOUの全アカウントをまとめてリンクできる
  3. モニタリングアカウントで、ソースアカウントのメトリクスやロググループを選んでダッシュボード・Logs Insights・アラームに使う

1つのモニタリングアカウントには最大100,000のソースアカウントを、1つのソースアカウントは最大5つのモニタリングアカウントにリンクできます。データはコピーされず、ソースアカウントに残ったまま参照されるため、ログの保管料金が二重にかかることはありません。

以前からある「CloudWatchのクロスアカウント・クロスリージョンのダッシュボード」(IAMロールで別アカウントのメトリクスを読む方式)よりも、ログやトレースまで横断して検索できる点が違います。複数アカウントのログを長期保管・分析のために1つにまとめたいときは、サブスクリプションフィルターでFirehoseなどに送る集約の仕組みを使います(運用シナリオ「複数アカウントのログを集約して分析する」)。

その他の機能#

  • Application Insights:アプリケーションと基盤リソースを監視し、異常の検出や関連情報の調査を支援する。
  • Application Signals:アプリの性能と可用性を自動で計測・可視化。サービス単位・APIパス単位でメトリクスを確認できる。CloudWatchエージェントとADOT(AWS Distro for OpenTelemetry)が必要。
  • Contributor Insights:ログやAWSサービスのメトリクスから、影響の大きい寄与者(トップN)を特定する。
  • Lambda Insights:Lambdaの詳細なパフォーマンス監視。有効化には拡張レイヤーの追加(収集用エージェントが入っている)と、IAMポリシー CloudWatchLambdaInsightsExecutionRolePolicy の付与が必要。
  • Embedded Metric Format(EMF):ログにメトリクス情報を埋め込み、CloudWatch Logsからメトリクスを生成する。アプリにEMF形式のログ出力を実装する。

設計・運用

CloudWatchアラームの状態と評価

アラームの3つの状態(OK・ALARM・INSUFFICIENT_DATA)と、期間・データポイント数・欠落データの扱いでアラームが鳴る条件が決まる仕組み

1. 詳しい説明#

CloudWatchアラームは、1つのメトリクス(またはメトリクスの計算結果)を一定の間隔で調べ、しきい値を超えているかどうかで状態を切り替えます。アクション(通知や自動修復)は、状態が変わったときに実行されます。そのため「なぜ鳴らないのか」「なぜ鳴りすぎるのか」は、状態と評価の設定から切り分けます。

3つの状態#

状態意味よくある原因
OKメトリクスがしきい値の範囲内正常
ALARMメトリクスがしきい値を超えた(条件を満たした)負荷の増加、エラーの発生
INSUFFICIENT_DATA判定に使えるデータが足りない作成した直後、メトリクスが送られていない(エージェントの停止・インスタンスの停止)、メトリクス名やディメンションの指定の誤り

アクションは状態ごとに設定できます。ALARMになったときだけでなく、OKに戻ったとき(復旧の通知)や、INSUFFICIENT_DATAになったとき(監視が止まったことの通知)にも通知できます。

評価の設定(いつALARMになるか)#

設定意味例
統計期間内のデータを何でまとめるか平均(Average)、合計(Sum)、最大(Maximum)、パーセンタイル(p99)
期間(Period)1つのデータポイントにまとめる時間60秒、300秒。高解像度メトリクスなら10秒・30秒も可
評価期間の数(N)直近いくつのデータポイントを見るか5
アラームを実行するデータポイント数(M)N個のうちいくつが超えたらALARMにするか3(「5個中3個」)
欠落データの扱いデータがないときにどう数えるか下の表を参照

例えば「期間60秒・5個中3個」なら、直近5分のうち3分でしきい値を超えたときにALARMになります。「M/N」にすると一瞬の急増では鳴らず、誤報を減らせます。逆に、検知を早くしたいときは期間を短くし、M・Nを小さくします。なお、EC2の基本モニタリングはメトリクスが5分ごとなので、1分単位で判定したい場合は詳細モニタリング(1分ごと)を有効にします。

欠落データの扱い#

設定動き向いているメトリクス
missing(既定)欠落したデータポイントは数えない。評価範囲がすべて欠落すると INSUFFICIENT_DATA になる常に送られてくるメトリクス
notBreaching欠落を「正常」として数える何か起きたときだけ送られるメトリクス(エラー数、ALBの5xxの数など)
breaching欠落を「しきい値超え」として数えるデータが来ないこと自体が異常なもの(ハートビート、定期処理の完了数)
ignore今の状態を保つまばらに送られるメトリクスで、状態をむやみに変えたくないとき

エラー数のアラームがエラーのないときに INSUFFICIENT_DATA のままになるのは、エラーがない時間はメトリクス自体が送られないためです。欠落データを notBreaching(正常として扱う)にすると、エラーがないときはOKになります。

アラームのアクション#

  • SNSトピックへの通知:メール・チャットツール・Lambdaなどへ届ける
  • EC2アクション:インスタンスの停止・終了・再起動・復旧(StatusCheckFailed_System のアラームで別のハードウェアに移す)
  • Auto Scalingアクション:ステップスケーリング・シンプルスケーリングのポリシーを実行する
  • Lambda関数の実行、Systems ManagerのOpsItemの作成

アラームの状態の変化はEventBridgeにもイベントとして送られるので、SSM Automationなど、アラームのアクションにない処理にもつなげられます(イベント駆動の自動修復)。

アラームの種類#

  • メトリクスアラーム:1つのメトリクス、またはメトリクスの計算(Metric Math)の結果を監視する。例:エラー数 ÷ リクエスト数 でエラー率にしてから判定する
  • 異常検出のアラーム:固定のしきい値の代わりに、過去の傾向から学習した「予測の幅」から外れたらALARMにする
  • 複合アラーム:複数のアラームの状態を AND・OR・NOT で組み合わせる。「CPUが高い AND 応答が遅い」のときだけ通知して、誤報と通知の数を減らす

AWS CloudTrail

「誰が・いつ・何をしたか」を記録する監査サービス

1. サービス概要#

AWS CloudTrailは、AWSアカウント内の「誰が」「いつ」「何をしたか」を記録する監査サービスです。

  • 誰が:IAMユーザー/ロール/AWSサービス、送信元IPアドレス
  • いつ:タイムスタンプ
  • 何をしたか:呼び出したAPI、リクエストパラメータ、レスポンス

2. 主な機能・特徴#

証跡(トレイル)#

記録したイベントをS3などに配信します(S3にはJSON形式で配信)。

  • 過去90日分の履歴は、証跡を作らなくてもCloudTrailコンソールで確認できる。
  • 作成手順:コンソールで「証跡の作成」 → 証跡名を指定 → 保存先S3バケットを指定 → 記録するイベントタイプを選択
  • ログファイルの整合性検証:ログが改ざん・削除・変更されていないかを確認できる。

イベントの種類#

種類内容例備考
管理イベントリソースを管理・設定する操作EC2・VPCの作成、IAMポリシーの変更デフォルトで記録
データイベントリソースそのものに対する操作S3オブジェクトの取得・削除有効化が必要
Insightsイベント普段と異なる異常なAPI操作API呼び出し・エラー率の急増有効化・追加料金が必要。EventBridge経由で通知・自動対応も可能
ネットワークアクティビティイベントVPCエンドポイントを通ったAPI呼び出し組織外のアカウントのS3へ、VPCエンドポイント経由でアクセスしようとした有効化が必要。データの持ち出しの調査に使う

データイベントは件数が多く、料金が大きくなりがちです。高度なイベントセレクターを使うと、「特定のバケットだけ」「書き込み(削除など)だけ」のように、記録するイベントを絞り込めます。

リージョン・グローバルの証跡#

  • リージョン:そのリージョンで発生したイベントのみを記録。「すべてのリージョンに適用」を有効にすると、全リージョンのイベントを1つの証跡で記録できる。
  • グローバル:IAMなどグローバルサービスのイベントは特定のリージョンに記録される。「グローバルサービスイベントを含める」オプションを有効にする。

CloudWatch Logsとの統合#

  • リアルタイムに近い監視が可能(S3への配信は最大5分ほどの遅延)。
  • 検知結果をSNS通知やLambdaによるアクションにつなげられる。
  • CloudWatch Logs Insightsでクエリ分析もできる。
  • 設定の流れ:証跡でCloudWatch Logsへの配信を有効化 → ロググループを指定 → CloudTrailからCloudWatch Logsへ送信するためのIAMロールを付与
  • 例:メトリクスフィルターで「ルートユーザーのログイン」「セキュリティグループの変更」「コンソールへのログイン失敗」を数え、CloudWatchアラームからSNSで通知する。

組織の証跡#

Organizationsの管理アカウント(または委任管理者)で組織の証跡を作ると、組織内のすべてのアカウントのイベントを、1つの証跡でまとめて記録できます。あとから組織に入ったアカウントも自動で対象になります。メンバーアカウントからは証跡を見られますが、変更・削除はできません。

ログの保護#

証跡のログは、不正の証拠になるため、消されたり書き換えられたりしないように守ります。

  • ログファイルの整合性検証:有効にすると、1時間ごとにダイジェストファイル(ログファイルのハッシュ値に電子署名を付けたもの)が作られる。aws cloudtrail validate-logs で、ログが変更・削除されていないかを確かめられる。
  • 保存先を分ける:ログ専用のアカウントのS3バケットに保存し、バケットポリシーでCloudTrail以外からの書き込みと削除を制限する。S3オブジェクトロックで削除を防ぐこともできる。
  • 暗号化:ログは標準でSSE-S3で暗号化される。SSE-KMS(カスタマーマネージドキー)にすると、ログを読める人をキーの権限でも絞れる。
  • 止めさせない:SCPで cloudtrail:StopLogging・cloudtrail:DeleteTrail を拒否する。証跡の停止はEventBridgeで検知して通知できる。

ログの分析とCloudTrail Lake#

方法内容
イベント履歴コンソールで過去90日分の管理イベントを、ユーザー名・イベント名・リソースで絞り込んで見る
AthenaS3に保存した証跡のログに、SQLで問い合わせる。長期間のログの分析に向く
CloudWatch Logs InsightsCloudWatch Logsに送ったログに、クエリで問い合わせる

イベントデータストアは、高度なイベントセレクターで対象を選ぶイベントのコレクションです。管理・データイベント、Insightsイベント、AWS Config項目、AWS外のイベントなど、種類ごとに作成します(1つのデータストアには1種類のイベントカテゴリを保存)。Organizations全体の複数アカウント・リージョンを対象にすることもできます。

  • SQLで複数のイベント項目を検索・集計でき、複数のイベントデータストアを結合した分析も可能。
  • 保持期間は料金オプションにより最長約7年または約10年。クエリ結果は最大7日間参照でき、S3に保存できる。
  • 取り込み・保持と、クエリでスキャンしたデータ量に応じて料金がかかる。

提供状況:2026年5月31日以降、新規顧客はCloudTrail Lakeを利用開始できません。既存顧客は継続利用できます。新たに長期保存したイベントをSQL分析する場合は、証跡をS3に保存してAthenaで分析します。

ログが届かないときの確認#

  • 証跡の記録が停止されていないか(StopLogging がイベント履歴に残っていないか)。
  • S3のバケットポリシーで、CloudTrailからの書き込みを許可しているか。
  • SSE-KMSで暗号化している場合、キーポリシーでCloudTrailにキーの利用を許可しているか。
  • 見たいのがデータイベントなら、証跡でデータイベントを有効にしているか。

  • ルートユーザーのログインやセキュリティグループの変更をリアルタイムに通知

4. 料金の考え方#

過去90日分のイベント履歴の閲覧と、管理イベントの最初の1つの証跡は無料です。データイベント、Insightsイベント、追加の証跡には料金がかかります。保存先のS3やCloudWatch Logsの料金も別途かかります。CloudTrail Lakeはイベントの取り込み・保持とクエリのスキャン量に応じて課金されます。

5. 関連サービス#

  • Amazon S3:証跡の保存先
  • Amazon CloudWatch:ログの監視・アラーム
  • Amazon EventBridge:API操作をトリガーにした自動処理
  • AWS Config:「何がどう変わったか」の記録(CloudTrailは「誰がやったか」)
  • AWS Organizations:組織全体の証跡、証跡の停止を禁止するSCP
  • Amazon Athena:S3に保存したログのSQLでの分析
  • AWS KMS:ログの暗号化
  • AWS Control Tower:ログアーカイブアカウントへのログの集約
  • 関連する用語:ルートユーザーとアカウントの保護、コンプライアンスとAWS Artifact

6. 試験・実務でのポイント#

記録の設定

  • 「誰が」「いつ」「どのAPIを」→ CloudTrail。「設定がどう変わったか・準拠しているか」→ Config。
  • S3のオブジェクト操作を記録 → データイベントを有効化。料金を抑えるには高度なイベントセレクターで絞り込む。
  • 90日より前の履歴が必要 → 証跡を作成してS3に保存。
  • 全アカウント・全リージョンをまとめて記録し、メンバーに消させない → 組織の証跡。
  • 普段と違うAPIの呼び出しの急増に気付きたい → Insightsイベント。

保護と分析

  • ログの改ざん・削除を検知 → ログファイルの整合性検証(ダイジェストファイル)。
  • 証跡を止めさせない → SCPで StopLogging・DeleteTrail を拒否する。
  • リアルタイムに近い通知 → CloudWatch Logsと統合し、メトリクスフィルターとアラームで通知。
  • S3に保存したログをSQLで調べる → Athena。S3を用意せずSQLで長期保存・分析 → CloudTrail Lake。
  • CloudTrail Lakeは2026年5月31日以降、新規顧客は利用開始できない。新規利用ではS3+Athenaを検討する。
  • ログが届かない → 記録の停止、バケットポリシー、KMSのキーポリシーを確認する。
  • CloudWatch・CloudTrail・Config・X-Rayの使い分け → 監視・記録のサービスの選び方。

7. まとめ#

  • CloudTrailはAPI操作の監査ログ。90日分は自動で見られる。
  • イベントは管理・データ・Insightsの3種類。データイベントは有効化が必要。
  • 長期保存はS3、リアルタイム監視はCloudWatch Logs、SQLでの分析はAthenaかCloudTrail Lake。
  • 組織の証跡で全アカウントをまとめ、整合性検証・保存先の分離・SCPでログを守る。
