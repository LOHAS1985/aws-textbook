1. サービス概要#

AWS Configは、AWSリソースの設定状態を記録・評価し、コンプライアンス違反を検出して修復するサービスです。

2. 主な機能・特徴#

設定レコーダー#

有効にすると、対象リージョン・リソースの設定変更を記録します。

  • 設定内容:対象リソース、設定情報を保存するS3バケット、通知先のSNSトピック
  • 記録する情報:
    • リソースID(例:i-0123456789abcdef0)
    • リソースタイプ(例:AWS::EC2::Instance)
    • 設定属性(インスタンスタイプ、サブネットIDなど現在の設定)
    • リレーションシップ(他リソースとの関係)
    • タグ(例:Environment=Production)
    • 設定変更の時刻

記録した1件1件を設定項目(Configuration Item)といい、リソースごとに並べた設定タイムラインで「いつ・どう変わったか」と、その変更をしたCloudTrailのイベントを確認できます。

  • 記録の範囲:すべての種類のリソースを記録するか、種類を選ぶかを決める。記録していない種類のリソースは、Configルールでも評価されない。
  • 記録の頻度:変更のたびに記録する(継続的な記録)か、1日に1回まとめて記録する(日次の記録)かを選べる。変更の多いリソースを日次にすると料金を下げられる。
  • グローバルなリソース(IAMのユーザー・ロール・ポリシーなど)は、どのリージョンで記録しても同じ内容になるため、1つのリージョンだけで記録して重複を避ける。
  • Configはリージョンごとに有効にする。使っていないリージョンで不正にリソースが作られても気付けるように、すべてのリージョンで有効にしておく。

Configルール#

リソースの設定が要件に適合しているかを評価します。

  • 種類:AWSマネージドルール(AWSが提供)、カスタムルール(Lambdaなどで作成)
  • 例:EBSボリュームが暗号化されているか/S3バケットのパブリックアクセスが禁止されているか
  • 評価結果:COMPLIANT(準拠)、NON_COMPLIANT(非準拠)、NOT_APPLICABLE(評価対象外)、INSUFFICIENT_DATA(情報不足)
設定選択肢
評価のきっかけ(トリガー)設定変更:対象のリソースが変わったときに評価する。定期的:1・3・6・12・24時間ごとに評価する(例:アクセスキーが90日以上ローテーションされていないか)
評価のモード検出:作られたリソースを評価する(通常)。プロアクティブ:CloudFormationでリソースを作る前に、設定を評価する
カスタムルールの書き方Lambdaで評価のコードを書く、またはGuard(CloudFormation Guardの記法)でルールを宣言的に書く

AWSマネージドルールの例:encrypted-volumes(EBSの暗号化)、s3-bucket-public-read-prohibited(S3の公開読み取りの禁止)、restricted-ssh(SSHを0.0.0.0/0に開けていない)、required-tags(必須のタグが付いている)、cloudtrail-enabled(CloudTrailが有効)。

自動処理Lambda独自の検査・修復ロジックを実行
修復の自動化Systems Manager Automation定義済みのランブック(手順書)で設定を修復
セキュリティ統合Security Hubセキュリティ・コンプライアンス結果を集約
一括評価Conformance Packs複数のルールと修復処理をパッケージ化

API操作の監査CloudTrail変更を実行したユーザーやロールを記録

自動修復の例#

  1. ConfigルールがS3バケットのパブリックアクセスを検出
  2. リソースが NON_COMPLIANT になる
  3. Configの修復アクションが起動
  4. Systems Manager AutomationまたはLambdaが設定を修正
  5. Configが再評価し、COMPLIANT になったことを確認
  • 修復アクションは、手動(コンソールで選んで実行)か自動(非準拠になったらすぐ実行)を選べる。自動の場合は、失敗したときの再試行の回数も決める。
  • 修復には、AWSが用意したAutomationのランブック(例:AWS-DisableS3BucketPublicReadWrite、AWSConfigRemediation- で始まるもの)を使える。
  • ランブックが操作するためのIAMロール(AutomationAssumeRole)を、パラメータで渡す。権限が足りないと修復が失敗する。

コンフォーマンスパック#

コンフォーマンスパックは、複数のConfigルールと修復アクションを、1つのYAMLのテンプレートにまとめたものです。「CISのベンチマーク」「PCI DSS」などの基準に合わせたサンプルのテンプレートが用意されていて、そのまま展開できます。Organizationsと組み合わせると、組織内のすべてのアカウントに同じパックを展開できます。

複数アカウント・リージョンの集約(アグリゲーター)#

アグリゲーターは、複数のアカウント・リージョンのConfigのデータを、1つのアカウントに集めて表示する仕組みです。組織全体の準拠状況やリソースの一覧を、1か所で確認できます。アグリゲーターで集めたデータは読み取り専用で、ルールの設定はそれぞれのアカウントで行います(組織全体のルールは、管理アカウントか委任管理者から一括で展開できます)。

高度なクエリを使うと、SQLに似た書き方で、記録したリソースの現在の設定を検索できます(例:「暗号化されていないEBSボリュームの一覧」「インスタンスタイプごとのEC2の台数」)。アグリゲーターに対して実行すると、組織全体を検索できます。

評価されないときの確認#

  • 設定レコーダーが停止していないか、そのリージョンで有効になっているか。
  • 評価したいリソースの種類を記録の範囲に含めているか。
  • カスタムルールのLambdaに、Configへ結果を返す権限(config:PutEvaluations)があるか。

3. ユースケース#

  • 暗号化されていないEBSや公開されたS3バケットの検出
  • 「先月この時点でセキュリティグループはどう設定されていたか」の確認
  • 非準拠の設定の自動修復

4. 料金の考え方#

記録した設定項目の数と、Configルールの評価回数に応じて課金されます。Conformance Packsも評価回数で課金されます。

6. 試験・実務でのポイント#

記録と評価

  • 「設定が要件に準拠しているか」「設定の変更履歴」→ Config。
  • AWSに用意されていないチェック → カスタムルール(Lambda または Guard)。
  • リソースが変わったときに評価 → 設定変更トリガー。日数の経過などを確かめる → 定期的トリガー。
  • 作る前に設定を確かめたい → プロアクティブ評価。
  • IAMなどのグローバルなリソースは1つのリージョンだけで記録する。料金を下げたい → 日次の記録。
  • ルールが評価されない → 設定レコーダーの停止や、記録の範囲を確認する。

修復と組織での管理

  • 非準拠の自動修復 → 修復アクション+SSM Automation。失敗したら AutomationAssumeRole の権限を確認する。
  • 複数ルールをまとめて展開・CISなどの基準に合わせる → コンフォーマンスパック。
  • 複数アカウント・リージョンの準拠状況を1か所で見る → アグリゲーター。
  • リソースの現在の設定をSQLで検索したい → 高度なクエリ。
  • CloudWatch・CloudTrail・Config・X-Rayの使い分け → 監視・記録のサービスの選び方。

7. まとめ#

  • Configは設定レコーダーで記録し、Configルールで評価する。
  • 非準拠はSSM AutomationやLambdaで自動修復できる。
  • コンフォーマンスパックでルールをまとめて展開し、アグリゲーターで組織全体の状況を1か所で見る。

このサービスが登場する運用シナリオ#

  • 手作業による設定変更(ドリフト)を見つけて戻す
  • 複数アカウント・リージョンに共通設定を展開する
  • 組織全体にセキュリティのガードレールを設ける
  • 公開されたS3バケットを検出して自動で修復する
