1. サービス概要#

Amazon RDS(Relational Database Service)は、リレーショナルデータベース(SQL)の構築・運用を提供するマネージドサービスです。パッチ適用やバックアップなどの面倒な運用作業をAWSに任せられます。

対応DBエンジン:MySQL、PostgreSQL、MariaDB、Oracle Database、Microsoft SQL Server、Amazon Aurora

2. 主な機能・特徴#

RDSが代行するDB運用タスク#

  • プロビジョニング:DBサーバーの起動
  • パッチ適用:OS/DBエンジン
  • バックアップ
    • 自動バックアップ:保持期間は最大35日
    • 手動スナップショット:無期限(削除するまで残る)
    • ポイントインタイムリカバリ:特定時点のデータに復元
  • 障害時のフェイルオーバー:Multi-AZ構成
  • スケーリング:スペック変更、リードレプリカ(プライマリから非同期でレプリケーションするためわずかな遅延が発生)

Multi-AZは別AZにスタンバイを置く可用性のための仕組みで、スタンバイは読み取りに使えません(同期レプリケーション)。リードレプリカは読み取り性能を上げる仕組みです。目的の違いを区別しましょう。

RDS Proxy#

大量のクライアントからのアクセスを、少数のDB接続に集約・再利用する仕組みです。

  • 前提:DBクエリの時間は短く、DB接続を行うのはアプリサーバー。
  • 例:アプリサーバーから1万人がDBにアクセスしても、実際に同時にクエリを投げているのは一部。RDS Proxyは50接続を1万人で使い回す。Proxyがないと1万接続を使い、接続数の上限を超える可能性が高い。

DBサブネットグループ#

DBサブネットグループは、RDSのDBインスタンスを配置してよいVPC内のサブネットの組です。DBインスタンスを作るときに指定し、RDSはこの中のサブネットにインスタンスを置きます。

  • 2つ以上のAZのサブネットを含める必要がある(Multi-AZのスタンバイや、障害時の配置先に使われる)
  • 通常はプライベートサブネットだけで構成し、DBをインターネットから切り離す
  • DBへのアクセスはセキュリティグループで、アプリサーバーのセキュリティグループからのDBポート(MySQLなら3306)だけを許可する

パラメータグループとオプショングループ#

種類設定するもの例
パラメータグループDBエンジンの設定値(設定ファイルの内容に当たるもの)max_connections、文字コード、タイムゾーン、スロークエリログの出力、rds.force_ssl(SSL接続の強制)
オプショングループエンジンに追加する機能OracleのTDE(透過的データ暗号化)、SQL ServerのS3へのネイティブバックアップ
  • RDSではOSにログインして設定ファイルを直接編集できないため、エンジンの設定はパラメータグループで行う
  • デフォルトのパラメータグループは変更できない。カスタムのパラメータグループを作ってDBに関連付ける
  • パラメータには、すぐに反映される動的パラメータと、再起動するまで反映されない静的パラメータがある(状態が「pending-reboot」になる)
  • オプショングループはMySQL・MariaDB・Oracle・SQL Serverで使う(PostgreSQLは拡張機能をパラメータで有効にする)

メンテナンスウィンドウ#

メンテナンスウィンドウは、OSやDBエンジンのパッチ適用など、RDSが行うメンテナンスの時間帯です。週1回・30分以上の枠を指定します(指定しないとリージョンごとの時間帯から自動で割り当てられる)。

  • 「マイナーバージョンの自動アップグレード」を有効にすると、新しいマイナーバージョンがメンテナンスウィンドウで適用される
  • インスタンスクラスの変更なども、「すぐに適用」を選ばなければ次のメンテナンスウィンドウで適用される
  • メンテナンス中はDBが停止することがある。Multi-AZでは、先にスタンバイに適用してからフェイルオーバーし、最後に旧プライマリに適用するため、停止時間を短くできる
  • 予定されているメンテナンスは、コンソールやAWS Health Dashboardで確認できる

暗号化#

RDSの保存時の暗号化はKMSキーで行い、ストレージだけでなく自動バックアップ・スナップショット・リードレプリカ・ログもすべて暗号化されます。

  • 暗号化はDBインスタンスの作成時にしか有効にできない。作成後に有効・無効を切り替えることはできない
  • 暗号化されたDBのリードレプリカは暗号化される(別リージョンのレプリカでは、そのリージョンのKMSキーを使う)
  • 転送時の暗号化はSSL/TLSで行い、パラメータグループで接続時のSSLを強制できる

暗号化されていない既存のDBを暗号化するには、次の手順で新しいDBに作り直します。

ストレージの自動スケーリング#

ストレージの自動スケーリングを有効にすると、空き容量が少なくなったときにストレージが自動で拡張されます。拡張の上限(最大ストレージしきい値)を指定しておきます。

  • 拡張される条件:空き容量が割り当て容量の10%未満の状態が5分以上続き、前回のストレージ変更から6時間以上経っている
  • 拡張量は10GiB、割り当て容量の10%、直近の増え方から予測した7時間分のうち最も大きい値
  • 拡張中もDBは止まらない。ただしストレージを縮小することはできない

容量不足でDBが止まるのを防げるため、データ量の増え方が読みにくい場合に有効です。CloudWatchメトリクス FreeStorageSpace にアラームを設定して監視も併用します。

Multi-AZのDNS切り替え#

Multi-AZでは、アプリはDBのエンドポイント(DNS名)に接続します。プライマリに障害が起きると、RDSは自動でスタンバイを新しいプライマリに昇格し、エンドポイントのDNSレコードをスタンバイに向け直します。

  • エンドポイント名は変わらないので、アプリの設定変更は不要。切り替えには通常1〜2分かかり、その間の接続は切れるため、アプリは再接続できるようにしておく
  • DNSの結果を長くキャッシュするアプリ(JavaのDNSキャッシュなど)は、古いIPに接続し続けないようTTLを短くする
  • フェイルオーバーが起きるのは、AZの障害、プライマリの故障、インスタンスクラスの変更やパッチ適用、「フェイルオーバーを伴う再起動」を実行したとき。RDSイベント通知で検知できる
  • 読み取り可能なスタンバイを2つ持つ「Multi-AZ DBクラスター」構成もあり、フェイルオーバーがより速い

Performance Insightsと拡張モニタリング#

機能見られるもの使う場面
CloudWatchの標準メトリクスCPU使用率、空きメモリ、空きストレージ、接続数、IOPS、レイテンシーなど(1分間隔)基本の監視・アラーム
拡張モニタリングDBインスタンス上のエージェントが集めるOSレベルのメトリクス(プロセスごとのCPU・メモリ、ファイルシステムなど)。1〜60秒間隔で、CloudWatch Logsに出力「OSのどのプロセスがCPUを使っているか」を細かく見たい
Performance InsightsDBの負荷(平均アクティブセッション数)を、SQL文・待機イベント・ユーザー・ホスト別に分解して表示する「どのSQLが遅いのか」「何を待っているのか」を特定したい

CloudWatchの標準メトリクスはハイパーバイザー側から取るため、OS内部の詳細は見えません。OSの中を見るなら拡張モニタリング、DBの中(SQL)を見るならPerformance Insights、と使い分けます。これらはCloudWatch Database Insightsとしてもまとめて表示できます。

Blue/Green Deployments#

RDS Blue/Green Deploymentsは、本番のDB(ブルー)をコピーしたステージング環境(グリーン)を作り、ブルーの変更をレプリケーションで同期させながらグリーン側で変更・テストし、準備ができたら短時間で切り替える機能です。

  • メジャーバージョンアップグレード、スキーマ変更、パラメータの変更などを、本番への影響を抑えて行える
  • 切り替え(スイッチオーバー)は通常1分以内で、グリーンがブルーと同じエンドポイント名になるため、アプリの接続先を変えなくてよい
  • 切り替え後も旧ブルー環境は残るので、確認が終わってから削除する
  • MySQL・MariaDB・PostgreSQL(とAurora)で使える

停止は最大7日#

開発用のDBなど、使わない時間はDBインスタンスを停止してインスタンスの料金を節約できます。ただし、停止できるのは最大7日間で、7日を過ぎると自動で起動します(メンテナンスを適用できなくなるのを防ぐため)。

  • 停止中もストレージとスナップショットの料金はかかる
  • 長期間止めておきたい場合は、EventBridgeのスケジュールとLambdaで定期的に停止し直すか、スナップショットを取ってDBを削除し、必要なときに復元する
  • リードレプリカがあるDBなど、構成によっては停止できない

3. ユースケース#

  • Webアプリの業務データベース
  • 既存のMySQL/Oracle/SQL ServerをAWSへ移行
  • Lambdaなど接続数が急増しやすい環境からのDB接続(RDS Proxy)

4. 料金の考え方#

DBインスタンスの稼働時間(インスタンスクラス)、ストレージ容量、バックアップ容量、データ転送量で課金されます。Multi-AZはスタンバイ分の料金も加わります。リザーブドインスタンスで割引も可能です。

5. 関連サービス#

  • Amazon Aurora:AWSが開発した高性能なRDSエンジン
  • Amazon DynamoDB:NoSQLの選択肢
  • Amazon ElastiCache:DBの前段のキャッシュ
  • AWS Lambda:RDS Proxyと相性の良い接続元
  • AWS Secrets Manager:DB認証情報の管理・ローテーション
  • AWS Backup:バックアップの一元管理

6. 試験・実務でのポイント#

構成・設定

  • DBを置くサブネットの指定 → DBサブネットグループ(2つ以上のAZのサブネットが必要)。
  • max_connections などエンジンの設定を変える → カスタムのパラメータグループ(デフォルトは変更不可)。静的パラメータは再起動で反映。TDEなど機能の追加 → オプショングループ。
  • パッチ適用の時間帯を決める → メンテナンスウィンドウ。Multi-AZなら停止時間が短くなる。

可用性・性能

  • 障害対策 → Multi-AZ、読み取り性能 → リードレプリカ(非同期なので遅延あり)。
  • Multi-AZのフェイルオーバーではエンドポイント名は変わらず、DNSがスタンバイに切り替わる。アプリは再接続できるようにする。
  • 「DB接続数が多すぎる」「Lambdaから大量接続」→ RDS Proxy。
  • 遅いSQLや待機イベントの特定 → Performance Insights。OSのプロセス単位のメトリクス → 拡張モニタリング。

バックアップ・暗号化

  • 自動バックアップは最大35日。それ以上残したい → 手動スナップショット。
  • 特定時点に戻したい → ポイントインタイムリカバリ。
  • 既存の暗号化されていないDBを暗号化 → スナップショット → 暗号化してコピー → 復元。暗号化は作成時にしか設定できない。

運用

  • 空き容量不足を自動で防ぐ → ストレージの自動スケーリング(縮小はできない)。
  • メジャーバージョンアップを短い停止時間で安全に → Blue/Green Deployments。
  • 停止したDBが勝手に起動した → 停止は最大7日で自動起動する。

7. まとめ#

  • RDSはリレーショナルDBのマネージドサービス。運用タスクをAWSが代行する。
  • バックアップは自動(最大35日)と手動(無期限)。
  • 可用性はMulti-AZ、読み取り拡張はリードレプリカ、接続集約はRDS Proxy。
