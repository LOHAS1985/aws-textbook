1. サービス概要#

AWS Backupは、さまざまなAWSサービスのバックアップを一元管理するサービスです。サービスごとに別々に設定していたバックアップ(EBSのスナップショット、RDSの自動バックアップなど)を、1つのプランでまとめて管理できます。

スケジュールと保持期間の管理だけでなく、別リージョン・別アカウントへのコピー、削除できないバックアップ(ボールトロック)、復元テスト、ルールを守れているかの監査まで、バックアップの運用に必要なことをまとめて扱えます。

2. 主な機能・特徴#

対象サービス#

  • コンピューティング:EC2(AMIとして保存)
  • ストレージ:EBS、EFS、FSx、S3、Storage Gateway(ボリュームゲートウェイ)
  • データベース:RDS、Aurora、DynamoDB、DocumentDB、Neptune、Redshift
  • そのほか:CloudFormationのスタック、オンプレミスのVMware仮想マシンなど

どのリソースの種類を保護するかは、リージョンごとに設定(サービスのオプトイン)します。プランで指定したのにバックアップされない場合は、この設定を確認します。

構成要素#

  • バックアッププラン:いつ・どれだけ残すかを決める。1つのプランに複数のルール(毎日・毎月など)を入れられる。
  • リソースの割り当て:対象リソースをタグまたはARNで指定する。
  • バックアップボールト:バックアップ(復旧ポイント)の保管場所。ボールトごとにKMSキーで暗号化し、アクセスポリシーを設定できる。

バックアッププランのルール#

設定内容
頻度1時間ごと・毎日・毎週・毎月、またはcron式で指定する
バックアップウィンドウ何時から開始し、何時間以内に完了させるか。業務の少ない時間帯にする
保持期間何日(何か月・何年)残すか。過ぎると自動で削除される
ライフサイクル一定の日数が過ぎたら、安いコールドストレージに移す(対応するリソースのみ。コールドストレージには最低90日保存する)
コピー先別リージョン・別アカウントのボールトにも自動でコピーする
継続的なバックアップRDS・Aurora・S3などで、最大35日間の任意の時点に戻せる(ポイントインタイムリカバリ)

タグで割り当てておくと、あとから作ったリソースにも同じタグを付けるだけでバックアップ対象になります。「本番環境のリソースにはタグ Backup=daily を必ず付ける」と決めておけば、バックアップの漏れを防げます。

別リージョン・別アカウントへのコピー#

同じアカウント・同じリージョンにだけバックアップを置くと、リージョン障害や、アカウントの乗っ取り・誤操作でバックアップごと失うおそれがあります。コピー先を分けると、次のことに備えられます。

  • 別リージョンへのコピー:リージョン全体の障害(DR戦略の「バックアップと復元」)。
  • 別アカウントへのコピー:本番アカウントの認証情報が漏れても、バックアップ専用のアカウントのコピーは消されない。Organizationsの組織内で、コピーを許可する設定が必要。
  • 暗号化したバックアップを別アカウントへコピーするときは、コピー先から使えるカスタマーマネージドキーで暗号化しておく。RDSのように元のサービスのAWSマネージドキー(aws/rds)で暗号化したバックアップは、別アカウントへコピーできない。

ボールトロック#

AWS Backup Vault Lockは、ボールト内のバックアップを削除・保持期間の短縮ができないようにする(WORM:一度書いたら変更できない)機能です。ランサムウェアや悪意のある管理者からバックアップを守り、規制で求められる保存期間を確実に守れます。

モード動き
ガバナンスモード十分な権限を持つユーザーなら、ロックの解除や変更ができる。設定のテストや、社内向けの保護に使う
コンプライアンスモード猶予期間(最低72時間)が過ぎると、ルートユーザーやAWSでも解除できない。保持期間が過ぎるまでバックアップを削除できない

さらに、論理的にエアギャップされたボールト(logically air-gapped vault)を使うと、ロックされたバックアップをAWS Resource Access Manager(RAM)で別アカウントへ共有し、そのアカウントから直接復元できます。

復元と復元テスト#

  • 復元は、多くの場合新しいリソースとして作られる(EBSなら新しいボリューム、RDSなら新しいDBインスタンス)。元のリソースは上書きされないので、アプリの接続先を切り替える必要がある。
  • 復元テスト(restore testing):決めたスケジュールで復旧ポイントを自動で復元し、復元できるか・かかった時間を記録して、終わったら復元したリソースを削除する。EventBridgeとLambdaで、復元したデータの中身を確認する処理も追加できる。
  • 復元テストの結果は、RTOを見積もる根拠や、監査の証跡になる。

監視と監査#

  • ジョブの監視:バックアップ・コピー・復元のジョブの結果はEventBridgeのイベントとCloudWatchのメトリクス(失敗したジョブの数など)になる。ボールトの通知でSNSに送ることもできる。失敗したら通知する仕組みを作っておく。
  • AWS Backup Audit Manager:「すべてのリソースがバックアッププランで保護されているか」「保持期間・頻度が基準を満たすか」「別リージョンへコピーしているか」などのコントロールを評価し、レポートを作る。AWS Configの記録を使うため、Configを有効にしておく。
  • リーガルホールド:訴訟や調査のために、特定のバックアップを保持期間が過ぎても削除されないようにする。

複数アカウントでの管理#

Organizationsのバックアップポリシーを使うと、管理アカウント(または委任管理者)から、組織内のすべてのアカウントに同じバックアッププランを配布できます。各アカウントの管理者がプランを消したり変えたりすることはできません。組織全体のジョブの状況も、1か所で確認できます。

3. ユースケース#

  • EC2・RDS・EFS・DynamoDBなど、複数サービスのバックアップを1つのプランで統一したい
  • タグ(例:Backup=daily)を付けたリソースを自動でバックアップ対象にしたい
  • 別リージョンにバックアップをコピーして災害対策をしたい
  • ランサムウェアに備えて、誰にも削除できないバックアップを別アカウントに残したい
  • 「バックアップから実際に戻せるか」を定期的に確かめ、監査に報告したい

4. 料金の考え方#

保存しているバックアップの容量(ウォームストレージ・コールドストレージで単価が違う)、復元したデータ量(一部のリソース)、リージョン間のコピーのデータ転送量に応じて課金されます。復元テストやAudit Managerの評価にも料金がかかります。ライフサイクルでコールドストレージに移すとコストを下げられますが、コールドストレージは最低90日分の料金がかかるため、短期間で消すバックアップには向きません。

5. 関連サービス#

  • Amazon EC2/Amazon EBS/Amazon EFS/Amazon FSx/Amazon S3
  • Amazon RDS/Amazon Aurora/Amazon DynamoDB
  • AWS Organizations:複数アカウントへのバックアップポリシー適用、別アカウントへのコピー
  • AWS KMS:ボールトの暗号化、別アカウントへのコピーに使うキー
  • AWS Config:Audit Managerの評価に使う記録
  • Amazon EventBridge/Amazon SNS:ジョブの失敗の通知
  • AWS RAM:論理的にエアギャップされたボールトの共有
  • AWS Storage Gateway:ボリュームゲートウェイのバックアップ
  • 関連する用語:DR戦略、タグ、cron式とrate式

6. 試験・実務でのポイント#

設定と管理

  • 「複数サービスのバックアップを一元管理」→ AWS Backup。
  • 対象リソースはタグで指定すると、新しいリソースも自動で対象になる。
  • 保持期間・スケジュール・コピー先・コールドストレージへの移行はバックアッププランで定義する。
  • プランに入れたのにバックアップされない → リージョンのサービスのオプトイン、タグの付け忘れ、IAMロールの権限を確認する。
  • 組織内の全アカウントに同じバックアップを強制したい → Organizationsのバックアップポリシー。

保護とDR

  • リージョン障害に備える → プランのコピー先に別リージョンのボールトを指定する。
  • 本番アカウントが侵害されてもバックアップを残したい → 別アカウントへのコピー。暗号化はカスタマーマネージドキーにする。
  • 誰にも削除できないバックアップ(ランサムウェア対策・規制対応)→ ボールトロックのコンプライアンスモード。
  • 最大35日間の任意の時点に戻したい → 継続的なバックアップ(ポイントインタイムリカバリ)。

確認と監査

  • バックアップから戻せるかを定期的に確かめたい → 復元テスト。
  • バックアップの方針を守れているか証明したい → Backup Audit Manager(Configが必要)。
  • バックアップの失敗に気付きたい → EventBridgeのルールやボールトの通知でSNSに送る。

7. まとめ#

  • AWS Backupは「プラン(いつ・どれだけ)」「割り当て(何を)」「ボールト(どこに)」で構成される。
  • 別リージョン・別アカウントへのコピーとボールトロックで、災害や侵害・誤削除からバックアップを守る。
  • 復元テストとAudit Managerで、「戻せること」「方針を守れていること」を確かめる。

このサービスが登場する運用シナリオ#

  • DynamoDBを負荷に合わせてスケールし、誤操作から復旧する
  • 誤操作したRDSのデータを特定の時点に戻す
  • S3のデータを誤削除やリージョン障害から守る
  • バックアップを一元管理して別リージョンに保管する
