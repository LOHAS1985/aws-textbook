1. サービス概要#

Amazon Route 53は、マネージドDNSサービスです。ドメイン名とIPアドレスを結びつける名前解決のほか、ドメイン登録やヘルスチェックもできます。

大きく分けて、次の3つの役割があります。

役割内容
ドメイン登録example.com などのドメインを購入・更新する
DNSの権威サーバー(ホストゾーン)ドメインのレコードを管理し、問い合わせに答える。ルーティングポリシーとヘルスチェックで、返す値を変えられる
VPCの名前解決(Route 53 Resolver)VPC内のリソースからの問い合わせに答える。オンプレミスのDNSとの間で問い合わせを転送できる

DNSの仕組みは用語「DNS」、レコードの種類は「DNSレコードタイプ」を参照してください。

2. 主な機能・特徴#

ホストゾーン#

1つのドメインのDNSレコードをまとめて管理する入れ物です。

  • パブリックホストゾーン:インターネット上での名前解決
  • プライベートホストゾーン:関連付けたVPC内でのみ有効な名前解決
  • パブリックホストゾーンを作ると、4つのネームサーバー(NSレコード)が割り当てられる。ドメインを別の登録事業者で買った場合は、その事業者側でネームサーバーをこの4つに変更する(委任)。
  • プライベートホストゾーンを使うには、VPCのenableDnsHostnames と enableDnsSupport を有効にする。別アカウントのVPCに関連付けるときは、ホストゾーン側で関連付けを許可してから、VPC側で関連付ける(CLI・API で行う)。
  • 同じ名前のパブリックとプライベートのホストゾーンがあると、関連付けたVPC内ではプライベートが優先される(スプリットビューDNS)。

エイリアスレコード#

エイリアスレコードは、Route 53独自のレコードで、ELB・CloudFront・S3の静的ウェブサイトホスティング・API Gateway・別のRoute 53レコードなどのAWSリソースを直接指せます。

比べる点エイリアスレコードCNAMEレコード
ゾーンの頂点(example.com そのもの)作れる作れない(www.example.com などのサブドメインだけ)
向き先AWSのリソース任意のドメイン名
クエリの料金AWSリソースを指す場合は無料有料
IPアドレスの変化ELBなどのIPアドレスが変わっても自動で追従する名前を返すだけ

エイリアスレコードで「ターゲットのヘルスを評価」を有効にすると、別にヘルスチェックを作らなくても、ELBの背後に正常なターゲットがない場合に、そのレコードを異常として扱えます。

TTL#

TTL(Time To Live)は、問い合わせた側のリゾルバーが回答をキャッシュする秒数です。TTLが長いとクエリ料金とレイテンシーは減りますが、レコードを変えてもしばらく古い値が使われます。移行や切り替えの予定があるときは、事前にTTLを短く(例:60秒)しておきます。エイリアスレコードのTTLは、向き先のリソースのTTLが使われます。

ルーティングポリシー#

種類概要主な用途
シンプル1つのレコードに複数の値を書けるが、ヘルスチェックは使えない単純な名前解決
加重(Weighted)重みを指定してトラフィックを分散A/Bテスト、段階的なリリース、負荷分散
レイテンシー最もレイテンシーが低いリージョンのリソースへルーティンググローバルなWebサービスの高速化
フェイルオーバープライマリが利用できない場合にセカンダリへ切り替え可用性向上、DR構成
位置情報(Geolocation)ユーザーの地理的位置(大陸・国など)に基づいてルーティング国・地域ごとのコンテンツ配信、配信の制限
地理的近接性(Geoproximity)ユーザーとリソースの地理的位置に基づく。バイアスで範囲を広げたり狭めたりできる地理的なトラフィック配分
IPベースクライアントのIPアドレスとCIDRの対応付けに基づく特定ネットワーク・IP範囲からのトラフィック制御
複数値回答正常なリソースの値を最大8つ返し、クライアント側で選ぶヘルスチェック付きの簡単な分散
トラフィックフロー複数のポリシーを組み合わせた複雑な制御を、図で編集する複雑なグローバルルーティング
  • 位置情報ルーティングでは、どの場所にも当てはまらない利用者のためにデフォルトのレコードを作っておく。作らないと、その利用者には回答が返らない。
  • ヘルスチェックと組み合わせると、加重・レイテンシー・位置情報などでも、異常なリソースは回答から外れる。

ヘルスチェック#

ヘルスチェックは、リソースが正常かを定期的に確かめ、ルーティングから異常なリソースを外すために使います。種類は3つです。

種類確認する方法向いている場面
エンドポイントの監視世界中のヘルスチェッカーから、IPアドレスかドメイン名にHTTP・HTTPS・TCPで接続する。応答の本文に特定の文字列があるかも確認できるインターネットから届くWebサーバー・ELB
計算済みヘルスチェックほかの複数のヘルスチェックの結果をまとめる(例:3つのうち2つ以上が正常なら正常)複数の部品からなるサービス全体の判定
CloudWatchアラームの監視CloudWatchアラームの状態をそのまま使うプライベートサブネットのリソース、エラー率などのメトリクスでの判定
  • エンドポイントを監視するときは、ヘルスチェッカーのIPアドレス範囲からの通信を、セキュリティグループやネットワークACLで許可しておく。許可していないと、正常なのに異常と判定される。
  • 確認の間隔(標準30秒・高速10秒)と、何回続けて失敗したら異常とするか(しきい値)を設定する。
  • ヘルスチェックの状態はCloudWatchのメトリクスになる(米国東部(バージニア北部)リージョンに出る)。アラームを作って、異常になったらSNSで通知できる。

Route 53 Resolver(VPCとオンプレミスの名前解決)#

VPCには、VPCのCIDRの先頭に2を足したアドレス(例:10.0.0.2)でRoute 53 Resolverが用意されていて、EC2などからの問い合わせに答えます(Amazon Provided DNS)。オンプレミスとつなぐときは、Resolverエンドポイントを使って問い合わせを転送します。

しくみ問い合わせの向き例
インバウンドエンドポイントオンプレミス → VPC社内のDNSサーバーから、プライベートホストゾーンの名前(db.aws.example.internal)を引く
アウトバウンドエンドポイントと転送ルールVPC → オンプレミスEC2から、社内のドメイン(corp.example.local)をオンプレミスのDNSサーバーに問い合わせる
  • 転送ルールはAWS RAMで別アカウントのVPCと共有でき、複数アカウントのVPCから同じルールを使える。
  • VPCから外部への問い合わせを、ドメインのリストで遮断・許可したいときはRoute 53 Resolver DNS Firewallを使う。

DNSSEC#

DNSSEC署名を有効にすると、パブリックホストゾーンの回答に電子署名が付き、途中で回答をすり替える攻撃(DNSスプーフィング)を防げます。署名用のキー(KSK)には、米国東部(バージニア北部)リージョンのKMSのカスタマーマネージドキー(非対称キー)を使います。有効にしたあと、親のゾーン(ドメインの登録事業者)にDSレコードを登録します。VPCからの問い合わせで署名を検証するには、ResolverのDNSSEC検証を有効にします。

ログ#

  • パブリックDNSクエリのログ:パブリックホストゾーンへの問い合わせをCloudWatch Logsに送る(ロググループは米国東部(バージニア北部)リージョンに作る)。
  • Resolverのクエリログ:VPC内のリソースが行った問い合わせを、CloudWatch Logs・S3・Data Firehoseに送る。マルウェアが不審なドメインに問い合わせていないかの調査に使える。
  • レコードの変更などのAPI操作はCloudTrailに記録される。

ドメイン登録#

Route 53でドメインを登録すると、ホストゾーンが自動で作られます。自動更新を有効にしておかないと、期限切れでドメインが使えなくなります。勝手に移管されないよう、移管ロックもかけられます。

Application Recovery Controller(ARC)#

リージョンやAZの切り替えを、安全・確実に行うためのサービスです。以前はRoute 53の機能でしたが、現在は独立したサービスです。ゾーンシフト(1つのAZからトラフィックを外す)、ルーティングコントロール、リージョンスイッチなどの機能があります。詳しくはAmazon Application Recovery Controllerを参照してください。

3. ユースケース#

  • 独自ドメインでWebサイトを公開し、example.com をエイリアスレコードでCloudFrontやALBに向ける
  • フェイルオーバーで障害時に待機系サイト(S3の静的ページなど)へ切り替え
  • 新バージョンへ10%だけトラフィックを流す(加重)
  • VPC内の社内システムの名前解決(プライベートホストゾーン)
  • オンプレミスとVPCの間で、お互いの名前を解決する(Resolverエンドポイント)

4. 料金の考え方#

ホストゾーンごとの月額料金、DNSクエリ数、ヘルスチェック数(AWS以外のエンドポイントや、HTTPS・文字列照合・高速間隔などのオプションは割高)、ドメイン登録料で課金されます。AWSリソース(ELB・CloudFrontなど)を指すエイリアスレコードへのクエリは無料です。Resolverエンドポイントは、エンドポイントのネットワークインターフェイスの数と時間、処理したクエリ数で課金されます。

5. 関連サービス#

  • Elastic Load Balancing/Amazon CloudFront/Amazon S3:エイリアスレコードの向き先
  • Amazon VPC:プライベートホストゾーンの関連付け先、Resolverの置き場所
  • AWS Global Accelerator:DNSのキャッシュに左右されないグローバルなトラフィック制御
  • Amazon CloudWatch:ヘルスチェックのアラーム、クエリログ
  • AWS KMS:DNSSEC署名のキー
  • AWS RAM:Resolverの転送ルールの共有
  • AWS Direct Connect/AWS Site-to-Site VPN:Resolverエンドポイントとオンプレミスの通信経路
  • Route 53 Resolver DNS Firewall:VPCからのDNS問い合わせのフィルタリング
  • Amazon Application Recovery Controller:確実なリージョンのフェイルオーバー
  • 関連する用語:DNS、DNSレコードタイプ、DR戦略、オンプレミスとAWSをつなぐ方法の選び方

6. 試験・実務でのポイント#

レコードとルーティング

  • A/Bテスト・段階リリース → 加重。DR → フェイルオーバー。速いリージョンへ → レイテンシー。
  • 国ごとにコンテンツを分ける(法規制など)→ 位置情報。当てはまらない利用者用にデフォルトのレコードも作る。
  • example.com(ゾーンの頂点)をELBやCloudFrontに向けたい → エイリアスレコード(CNAMEは頂点に作れない)。
  • レコードを変えたのに古い値が返る → TTLの間はキャッシュされる。切り替えの前にTTLを短くしておく。
  • ホストゾーンを作り直したら名前解決できなくなった → 新しいネームサーバーを、ドメインの登録事業者側のNSの設定に反映する。

ヘルスチェック

  • プライベートサブネットのリソースを監視したい → CloudWatchアラームを監視するヘルスチェック。
  • 正常なのにヘルスチェックが失敗する → ヘルスチェッカーのIPアドレス範囲をセキュリティグループで許可しているか確認する。
  • ELBの背後が全滅したら切り替えたい → エイリアスレコードのターゲットのヘルスを評価。
  • 複数の部品の状態をまとめて判定したい → 計算済みヘルスチェック。

VPC・ハイブリッド・セキュリティ

  • VPC内だけで使う名前 → プライベートホストゾーン。解決できないときはVPCのDNS属性(enableDnsHostnames・enableDnsSupport)を確認する。
  • オンプレミスからAWSの名前を引く → インバウンドエンドポイント。AWSから社内の名前を引く → アウトバウンドエンドポイントと転送ルール。
  • DNSの回答のすり替えを防ぐ → DNSSEC署名(KMSキーは米国東部(バージニア北部))。
  • VPC内のどのリソースがどの名前を引いたか調べたい → Resolverのクエリログ。
  • AZ障害時にすばやくトラフィックを外す → ARCのゾーンシフト。

7. まとめ#

  • Route 53はドメイン登録・DNS(ホストゾーン)・VPCの名前解決(Resolver)を提供する。
  • AWSリソースにはエイリアスレコードで向け、ルーティングポリシーとヘルスチェックで返す値を変える。
  • プライベートなリソースはCloudWatchアラームでヘルスチェックし、オンプレミスとはResolverエンドポイントで名前解決をつなぐ。

このサービスが登場する運用シナリオ#

  • 誤操作したRDSのデータを特定の時点に戻す
  • リージョン障害に備えて別リージョンへ切り替える
  • オンプレミスとVPCで互いの名前を解決する
  • 利用者の場所や割合でアクセスを振り分ける
  • 静的サイトを独自ドメイン・HTTPSで安全に配信する
