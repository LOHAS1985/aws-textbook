1. サービス概要#

Amazon CloudWatchは、AWS上のシステムの状態を記録・監視・通知するための統合監視サービスです。メトリクス(数値)とログの両方を扱います。

2. 主な機能・特徴#

メトリクス・アラーム・ダッシュボード#

  • メトリクス:リソースの時系列の数値データ。
    • デフォルトは5分間隔(詳細モニタリングで1分間隔)。
    • アプリからカスタムメトリクスを送信できる(PutMetricData API)。カスタムメトリクス=標準にないメトリクス。EC2のメモリ・ディスク使用率は標準メトリクスにない。
  • アラーム:しきい値を設定し、異常時にアクションを実行。メトリクスを選択 → しきい値と比較演算子 → 評価期間を設定。連携先はSNS通知・Auto Scaling・EC2の再起動など。
  • ダッシュボード:クロスアカウント/クロスリージョンのメトリクスもまとめて表示できる。

メトリクスの基本#

メトリクスは「どのサービスの(名前空間)」「何の値を(メトリクス名)」「どのリソースについて(ディメンション)」の3つで特定します。アラームやグラフでは、それを「どの統計で・何秒ごとに集計するか」を指定して使います。

用語意味例・ポイント
名前空間メトリクスの入れ物(サービス単位)AWS/EC2、AWS/RDS。エージェントのメトリクスは既定で CWAgent。カスタムメトリクスは自由に命名できる(AWS/ で始まる名前は使えない)
ディメンションリソースを区別するキーと値InstanceId、AutoScalingGroupName、LoadBalancer。ディメンションが違えば別のメトリクスとして扱われる
統計期間内のデータの集計方法Average・Sum・Maximum・Minimum・SampleCount・パーセンタイル(p99など)
期間・解像度何秒ごとの値かEC2は標準5分、詳細モニタリングで1分。カスタムメトリクスは高解像度で1秒まで(アラームは10秒・30秒周期も可)
保持期間データが残る期間1分未満は3時間、1分は15日、5分は63日、1時間は455日(最大15か月)。古いデータほど粗い粒度にまとめられる。メトリクスは手動で削除できない

統計の選び方#

同じメトリクスでも、統計を間違えると意味のない値になります。「回数は合計、使用率は平均、残量は最小、遅延はパーセンタイル」と覚えます。

統計向いているメトリクス例
Sum回数・件数(期間内に何回起きたか)Errors、RequestCount、HTTPCode_Target_5XX_Count、ThrottledRequests
Average使用率・割合CPUUtilization、mem_used_percent
Maximum一瞬でも超えたら困る値・ピークDuration(タイムアウト接近)、ApproximateAgeOfOldestMessage、IteratorAge
Minimum残量(少ないほど危険)FreeStorageSpace、CPUCreditBalance、BurstBalance、HealthyHostCount
p99 など応答時間(平均だと一部の遅いリクエストが埋もれる)TargetResponseTime、Latency

標準では取れないメトリクス#

EC2の標準メトリクスは、ハイパーバイザー(仮想化の層)の外から見える値だけです。OSの中の値はCloudWatchエージェントでカスタムメトリクスとして送る必要があります。

取りたい値メトリクス(Linux)メトリクス(Windows)
メモリ使用率mem_used_percentMemory % Committed Bytes In Use
ディスク(ファイルシステム)使用率disk_used_percentLogicalDisk % Free Space(空き率)
スワップ使用率swap_used_percentPaging File % Usage
特定プロセスの状態procstat プラグイン(プロセスごとのCPU・メモリ・起動数)

エージェント設定の append_dimensions で InstanceId を付け、aggregation_dimensions で AutoScalingGroupName 単位に集計すると、Auto Scalingグループ全体のメモリ使用率でアラームを作れます。設定ファイルはSystems ManagerのParameter Storeに保存して複数台へ配布するのが定番です。

サービス別メトリクス一覧#

SOA-C03で出題されうるメトリクスをサービス別にまとめます。赤字は特に出題されやすいメトリクスです。

  • コンピューティング(EC2・Auto Scaling・Lambda)
  • コンテナ(ECS・EKS)
  • ストレージ(EBS・EFS・S3)
  • データベース(RDS・Aurora・DynamoDB・ElastiCache)
  • ネットワーク・コンテンツ配信(ELB・CloudFront・Route 53・API Gateway・NAT・VPN・Direct Connect・Transit Gateway)
  • アプリケーション統合・分析(SQS・SNS・Kinesis・Step Functions・EventBridge)
  • 料金・アカウント・監視自体(Billing・Usage・Synthetics・Logs)
  • 症状からメトリクスを逆引き

WriteProvisionedThroughputExceeded、ReadProvisionedThroughputExceeded、IncomingBytes/IncomingRecords書き込み・読み取りの上限超過/流入量超過 → シャードの分割(オンデマンドモードも選択肢)。シャード単位で見るには拡張(シャードレベル)メトリクスを有効化

メトリクスを活用する機能#

機能できること
メトリクス計算(Metric Math)複数のメトリクスから新しい値を計算してグラフ・アラームに使う(例:エラー率 = Errors ÷ Invocations × 100)
異常検出(Anomaly Detection)過去のデータから機械学習で「普段の値の帯」を作り、帯から外れたらアラーム。曜日・時間帯で変動するメトリクスに向く
複合アラーム複数のアラームをAND・ORで組み合わせ、通知の量(アラート疲れ)を減らす
欠落データの扱いデータが届かないときの扱いを「正常(notBreaching)」「異常(breaching)」「無視(ignore)」「欠落(missing)」から選ぶ。アラームは「N個中M個のデータポイントがしきい値超え」で判定する
Metrics InsightsSQLライクなクエリで多数のメトリクスをまとめて検索・集計(例:CPU使用率の高い上位10台)
メトリクスストリームメトリクスをFirehose経由でS3やサードパーティの監視ツールへほぼリアルタイムに送る

CloudWatch Logs#

ログの収集・保存・検索・分析を行います。

  • 用語:ロググループ(アプリ・サービス単位)、ログストリーム(インスタンスや実行単位)、ログイベント(実際のログ1行)
  • 収集方法:Lambda・API GatewayなどはAWSサービスから自動出力。EC2はCloudWatchエージェントをインストールして送信。
  • 分析
    • Logs Insights:SQLライクなクエリでログを分析
    • メトリクスフィルター:ログからメトリクスを生成(例:"error"が出たらアラーム+SNSで通知)
    • サブスクリプションフィルター:ログを他サービスへリアルタイムにストリーミング
  • データ保護ポリシー:ログに含まれる機密情報を検出してマスキング
  • 保持期間:デフォルトは無期限(1日〜10年で指定可能)。短期・頻繁に検索するログはCloudWatch Logs、長期・たまに検索するログはS3(Standard-IA・Glacierなど)へ。
  • 暗号化:KMSキーを関連付ける(associate-kms-key)

メトリクスフィルターの流れ(ERROR通知)#

  1. ログに"ERROR"が出力される
  2. メトリクスフィルターが検知してカウント
  3. アラーム条件を満たすとSNS通知を送信
  4. 開発者へメール通知

CloudWatchエージェント#

EC2やオンプレミスのサーバーから、詳細なメトリクスやログをCloudWatchへ送信します。

  1. CloudWatchエージェントをインストール
  2. エージェントの設定ファイル(JSON)を作成(例:メモリ使用率 mem_used_percent と /var/log/app.log を送信)
  3. EC2にIAMロール(CloudWatchAgentServerPolicy)をアタッチ
  4. エージェントを起動し、メトリクスがCloudWatchに送信される

その他の機能#

  • CloudWatch Synthetics:ユーザー視点で定期監視。実際のユーザーのようにアクセス・API呼び出し・ログイン・ボタン操作などを自動実行する。監視用スクリプトをCanary(中身はLambda関数)と呼ぶ。
  • Application Signals:アプリの性能と可用性を自動で計測・可視化。サービス単位・APIパス単位でメトリクスを確認できる。CloudWatchエージェントとADOT(AWS Distro for OpenTelemetry)が必要。
  • Lambda Insights:Lambdaの詳細なパフォーマンス監視。有効化には拡張レイヤーの追加(収集用エージェントが入っている)と、IAMポリシー CloudWatchLambdaInsightsExecutionRolePolicy の付与が必要。
  • Embedded Metric Format(EMF):ログにメトリクス情報を埋め込み、CloudWatch Logsからメトリクスを生成する。アプリにEMF形式のログ出力を実装する。

3. ユースケース#

  • CPU使用率が高くなったらAuto Scalingでスケールアウト
  • EC2のメモリ使用率をエージェントで収集して監視
  • アプリのログに"ERROR"が出たらメール通知
  • Webサイトの外形監視(Synthetics)

4. 料金の考え方#

基本メトリクス(5分間隔)は無料です。詳細モニタリング、カスタムメトリクス、アラーム、ダッシュボード、ログの取り込み量・保存量、Logs Insightsのスキャン量などに応じて課金されます。古いログはS3へ移すとコストを下げられます。

5. 関連サービス#

  • Amazon SNS:アラームの通知先
  • Amazon EC2:エージェントによるメトリクス収集
  • AWS Lambda:Lambda Insights、Canary
  • AWS CloudTrail:CloudWatch Logsへの配信
  • AWS X-Ray:分散トレース
  • Amazon Managed Grafana:可視化
  • 関連する用語:CloudWatchアラームの状態と評価、IOPS・スループット・レイテンシ、HTTPステータスコードと切り分け、イベント駆動の自動修復

6. 試験・実務でのポイント#

メトリクス

  • EC2のメモリ・ディスク使用率 → CloudWatchエージェントでカスタムメトリクス。
  • 1分間隔の監視 → 詳細モニタリング。1秒間隔 → 高解像度カスタムメトリクス。
  • 統計は「回数はSum、使用率はAverage、残量はMinimum、遅延はp99」。
  • ハードウェア障害 → StatusCheckFailed_System で「復旧」、OSの問題 → StatusCheckFailed_Instance で「再起動」。
  • Redis系のCPUは EngineCPUUtilization、Kinesis・ストリームの遅れは IteratorAge。
  • 請求(EstimatedCharges)・CloudFront・Route 53ヘルスチェックのメトリクスは us-east-1。
  • Lambdaの詳細監視 → Lambda Insights(拡張レイヤー+IAMポリシー)。
  • CloudWatch・CloudTrail・Config・X-Rayの使い分け → 監視・記録のサービスの選び方。

ログ

  • ログの特定文字列でアラーム → メトリクスフィルター。
  • ログをリアルタイムに他サービスへ → サブスクリプションフィルター。
  • ログ保持期間はデフォルト無期限。コストに注意。

7. まとめ#

  • CloudWatchはメトリクス・アラーム・ダッシュボード・ログの統合監視サービス。
  • 標準にない値はエージェントやPutMetricData、EMFで送る。
  • ログはメトリクスフィルターでアラームに、サブスクリプションフィルターで連携に。

このサービスが登場する運用シナリオ#

  • EC2のメモリ・ディスク使用率を監視するCloudWatchエージェントでカスタムメトリクスを集め、しきい値を超えたら通知する
  • アプリのエラーログを検知して通知するCloudWatch Logsのメトリクスフィルターでエラーを数え、アラームで通知する
  • 外形監視と、誤報の少ないアラームを作るSynthetics Canaryで利用者の視点から監視し、異常検出と複合アラームで本当に必要な通知だけを送る
  • EC2の障害を検知して自動で復旧するステータスチェックの失敗をアラームで検知し、復旧・再起動を自動で行う
  • 複数アカウントのログを集約して分析する各アカウントのログを1つのS3に集め、長期保存とSQL分析を行う
  • コンテナ(ECS・EKS)の性能を監視するContainer Insightsでタスク・Pod単位のメトリクスとログを集め、異常をアラームで知らせる
  • マイクロサービスの遅延の原因をトレースで特定するX-Rayのトレースで、どのサービス・どの処理が遅いか・エラーを出しているかを突き止める
  • EC2・EBSの性能不足を見つけて改善するCloudWatchのメトリクスとCompute Optimizerでボトルネックを特定し、止めずに性能を上げる
  • RDSの遅いクエリと接続数の問題を解消するPerformance Insightsとスロークエリログで原因を特定し、RDS Proxyやリードレプリカで負荷を下げる
  • 負荷に応じて自動でスケールするWebシステムALBとAuto Scalingグループで、複数AZにまたがって台数を自動調整する
  • キューで処理を分離し、急増や障害に強くするSQSで受付と処理を切り離し、キューの長さに応じて処理側をスケールし、失敗したメッセージをDLQに隔離する
  • キャッシュでDBの読み取り負荷を下げるElastiCacheとCloudFrontで同じデータの読み取りを肩代わりし、DBの負荷と応答時間を下げる
  • データベースの高可用性と読み取り分散RDSのMulti-AZ・リードレプリカ・RDS Proxyを組み合わせる
  • 1つのAZの障害からアプリを切り離す複数AZの構成に加え、ARCのゾーンシフト・ゾーンオートシフトで障害の出たAZから通信を移す
  • DynamoDBを負荷に合わせてスケールし、誤操作から復旧するキャパシティモードと自動スケーリングでスロットリングを防ぎ、PITRで任意の時点に戻せるようにする
  • 多数のEC2の設定やソフトウェアを一定に保つSystems ManagerのState ManagerとRun Commandで、タグで選んだインスタンスに設定を一括で適用し続ける
  • CloudFormationで本番環境を安全に更新する変更セット・スタックポリシー・削除ポリシー・ロールバックトリガーで、意図しない置き換えや削除を防ぐ
  • EC2のアプリをCI/CDでBlue/GreenデプロイするCodePipelineで自動化し、CodeDeployのBlue/Greenで安全に切り替える
  • ECSのサービスを止めずに更新し、失敗したら自動で戻すローリング更新の割合を調整し、デプロイサーキットブレーカーとアラームで失敗時に自動ロールバックする
  • Lambdaを段階的にリリースするSAMとCodeDeployのCanaryで、新バージョンへ少しずつトラフィックを移す
  • Webアプリを攻撃や大量アクセスから守るCloudFront+WAFのマネージドルールとレートベースルールで攻撃を防ぎ、ShieldでDDoSに備える
  • 組織全体のVPCのIPアドレスを重ならないように払い出すVPC IPAMのプールをRAMで共有し、各アカウントのVPCに重ならないCIDRを自動で割り当てる
  • 踏み台サーバーなしでプライベートなEC2を操作するSession ManagerとVPCエンドポイントで、ポートを開けずに安全に接続する
  • 外向きの通信を許可したドメインだけに制限するNetwork FirewallとRoute 53 Resolver DNS Firewallで、サーバーから不正な宛先への通信と名前解決を止める
  • 社員の端末からVPCの社内システムに安全に接続するClient VPNとSAML認証で、テレワーク中の社員を部署ごとの権限でVPCやオンプレミスにつなぐ
  • 利用者の場所や割合でアクセスを振り分けるRoute 53のルーティングポリシーとヘルスチェックで、レイテンシー・地域・重み付けによる振り分けと切り替えを行う
  • EC2に接続できない原因を調査する経路と許可を順番に確認し、VPCフローログで通信の拒否を特定する
