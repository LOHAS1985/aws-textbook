1. サービス概要#

Amazon Data Firehose(旧称 Kinesis Data Firehose)は、ログやイベントなどのストリーミングデータを受け取り、S3・Redshift・OpenSearch Service などの保存先へ自動で届けるフルマネージドの配送サービスです。

受け取ったデータを一定量・一定時間ためてから(バッファリング)まとめて書き込むため、届くまでに数秒〜数分かかる「ほぼリアルタイム」の処理になります。サーバーやシャードの管理は不要で、データ量に合わせて自動でスケールします。

2. 主な機能・特徴#

データの送り元(ソース)#

  • アプリやエージェントからの直接の送信(PutRecord/PutRecordBatch)
  • Kinesis Data Streams・Amazon MSK(Kafka)からの読み取り
  • CloudWatch Logs のサブスクリプションフィルター、CloudWatch メトリクスストリーム
  • VPCフローログ・WAFのログ・IoT Coreのルールなど

主な配送先#

配送先主な用途
Amazon S3ログの長期保存、Athenaでの分析(データレイク)
Apache Iceberg テーブルS3上のテーブル形式での保存
Amazon Redshiftデータウェアハウスでの分析(いったんS3に置いてからCOPY)
OpenSearch Service/Serverlessログの検索・可視化
HTTPエンドポイント・SaaSSplunk・Datadog・New Relic・Snowflake など

バッファリング#

配送先への書き込みは、バッファのサイズ(MB)か時間(秒)のどちらかに達したときに行われます。小さくするほど早く届き、大きくするほどファイルの数が減ってS3やAthenaで扱いやすくなります。

変換・加工#

  • Lambdaによる変換:レコードを1件ずつ加工・絞り込みする(例:CloudWatch Logsの圧縮データを展開して整形)。
  • 形式の変換:JSONを Parquet・ORC に変換してS3に保存する(Glueデータカタログのスキーマを使う)。Athenaの検索が速く・安くなる。
  • 動的パーティショニング:レコードの中身(顧客IDなど)でS3のプレフィックスを分ける。
  • 圧縮(GZIP・Snappyなど)と、KMSによる暗号化。

エラー処理と監視#

  • 配送先に書き込めないときは一定時間再試行し、それでも失敗したデータは S3 のバックアップ先に保存される。
  • エラーはCloudWatch Logsに記録できる。CloudWatchメトリクス(DeliveryToS3.Success、DeliveryToS3.DataFreshness など)で、配送の成功や遅れを監視する。
  • VPC内のOpenSearchなどにも配送できる。

Kinesis Data Streams との違い#

項目Data FirehoseKinesis Data Streams
目的保存先への配送自分で作る処理でのリアルタイム処理
遅延ほぼリアルタイム(バッファリングあり)リアルタイム(ミリ秒〜)
管理不要(自動でスケール)シャード数の管理(オンデマンドモードもある)
データの保持・再読み込みできない保持期間内なら何度でも読める

3. ユースケース#

  • 複数アカウントの CloudWatch Logs を、サブスクリプションフィルター経由で中央のS3に集める
  • VPCフローログやWAFのログをParquetに変換してS3に保存し、Athenaで分析する
  • アプリのログをOpenSearchやSplunkに送って検索できるようにする

4. 料金の考え方#

取り込んだデータ量(GB)に応じて課金されます。形式の変換・動的パーティショニング・VPCへの配送などを使うと、その処理量に応じた料金が追加されます。Lambdaによる変換では、Lambdaの料金も別にかかります。

5. 関連サービス#

  • Amazon Kinesis:Data Streams(リアルタイム処理)
  • Amazon CloudWatch:サブスクリプションフィルター・メトリクスストリーム・監視
  • Amazon S3/Amazon Athena:保存と分析
  • Amazon OpenSearch Service:ログの検索・可視化
  • AWS Lambda:レコードの変換
  • ログの一元管理(運用シナリオ)

6. 試験・実務でのポイント#

  • 「ストリーミングデータをコードを書かずにS3・Redshift・OpenSearchへ」→ Data Firehose。
  • 「ミリ秒単位のリアルタイム処理」「データを再読み込み」→ Kinesis Data Streams。
  • S3に届くのが遅い・ファイルが細かすぎる → バッファのサイズ・時間を調整する。
  • Athenaを速く安く → Parquetへの形式の変換。配送の失敗分は S3 のバックアップに残る。
  • SQS・SNS・EventBridge・Kinesisの使い分け → メッセージングサービスの選び方。

7. まとめ#

  • Data Firehoseは、ストリーミングデータをバッファリングして保存先へ届けるフルマネージドの配送サービス。
  • Lambdaでの変換・Parquetへの変換・失敗時のS3へのバックアップができる。

このサービスが登場する運用シナリオ#

  • 複数アカウントのログを集約して分析する
