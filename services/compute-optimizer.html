AWS Compute Optimizer

機械学習でリソースの使用状況を分析し、最適な設定を推奨

最終更新:2026-10-31

1. サービス概要#

AWS Compute Optimizerは、機械学習を使ってリソースの使用状況を分析し、コスト削減・パフォーマンス向上につながる最適なリソース設定を推奨するサービスです。

2. 主な機能・特徴#

CloudWatchの過去のメトリクスを分析して推奨事項を提示します。

  • デフォルトでは無効。Organizations/アカウントで有効化が必要。
  • 分析期間:デフォルトは14日間(最大93日間)。

分析対象のリソース#

リソース推奨の内容
EC2インスタンスインスタンスタイプ・サイズ(Gravitonへの移行を含む)
Auto Scalingグループグループのインスタンスタイプ
EBSボリュームボリュームタイプ・サイズ・IOPS・スループット(例:gp2からgp3へ)
Lambda関数メモリのサイズ
ECS on FargateサービスタスクのCPU・メモリ
RDS・AuroraDBインスタンスのクラスとストレージ
商用ソフトウェアのライセンスEC2で動かすSQL Serverのエディションなど

EC2の推奨を出すには、一定の期間(少なくとも30時間分)のメトリクスが必要です。作ったばかりのリソースには推奨が出ません。

推奨事項#

  • サイズが過大(Over-provisioned):コスト削減のためにダウンサイジングを推奨
  • サイズが過少(Under-provisioned):パフォーマンス改善のためにアップサイジングを推奨
  • 最適化済み(Optimized):今の設定が適切
  • アイドル:ほとんど使われていないリソース(EC2・EBS・RDS・NATゲートウェイなど)。停止や削除を検討する

推奨には、いくつかの候補(オプション)と、それぞれの月額の削減見込みとパフォーマンスのリスク(変えたときに性能が足りなくなる可能性)が示されます。

EC2のメモリ使用率を分析に含めたい場合は、CloudWatchエージェントでメモリのメトリクスを送信しておく必要があります。

推奨の調整(推奨設定)#

  • 拡張インフラストラクチャメトリクス:分析期間を93日に延ばす(有料)。月末だけ負荷が高いなど、周期の長い負荷があるときに使う。
  • 使用率の余裕(ヘッドルーム)としきい値:CPUやメモリにどれだけ余裕を残して推奨するかを調整する。
  • CPUアーキテクチャ:Graviton(Arm)のインスタンスを候補に含めるかを選ぶ。
  • 外部のメトリクス:Datadogなどの監視ツールで集めたメモリのメトリクスも、分析に使える。

組織での利用と、ほかのツールとの関係#

  • Organizationsの管理アカウントか委任管理者で有効にすると、組織内のすべてのアカウントの推奨をまとめて見られる。
  • 推奨はCSV・JSONでS3にエクスポートできる。
  • Cost Optimization Hubは、Compute Optimizerのサイズの推奨や、Savings Plans・リザーブドインスタンスの購入の推奨などを集め、組織全体で削減額の大きい順に並べる。
  • Trusted Advisorのコスト最適化のチェックにも、Compute Optimizerの推奨が使われる。

Compute Optimizerは推奨を出すだけで、リソースを自動では変更しません。EC2のインスタンスタイプを変えるには、インスタンスを停止してから変更します(Auto Scalingグループなら起動テンプレートを更新して入れ替える)。

3. ユースケース#

  • 過剰なスペックのEC2インスタンスを見つけてダウンサイジング
  • Lambdaのメモリ設定の最適化
  • EBSボリュームのタイプ・サイズの見直し

4. 料金の考え方#

基本的な推奨は無料で利用できます。分析期間を延ばす「拡張インフラストラクチャメトリクス」は有料です。

5. 関連サービス#

  • Amazon CloudWatch:分析に使うメトリクス
  • Amazon EC2/Amazon EBS/AWS Lambda/Amazon ECS/Amazon RDS:分析対象
  • AWS Trusted Advisor:幅広い観点のチェック
  • AWS Organizations:組織全体での有効化
  • Amazon EC2 Auto Scaling:推奨したインスタンスタイプへの入れ替え
  • AWS Cost Explorer/Savings Plans:コストの分析と割引の購入
  • 関連する用語:コスト管理ツールの選び方、IOPS・スループット・レイテンシー

6. 試験・実務でのポイント#

  • 「機械学習で」「最適なインスタンスタイプ・サイズを推奨」→ Compute Optimizer。
  • デフォルトでは無効。使う前に有効化(オプトイン)が必要。
  • 分析期間はデフォルト14日、最大93日(拡張インフラストラクチャメトリクス)。
  • EC2のメモリを考えた推奨が欲しい → CloudWatchエージェントでメモリのメトリクスを送る。
  • Lambdaの最適なメモリサイズ → Compute Optimizer。ECS on Fargateのタスクのサイズ、EBSのgp2からgp3への変更も推奨される。
  • 組織全体の推奨をまとめて見る → 管理アカウントか委任管理者で有効にする。削減額の大きい順にまとめる → Cost Optimization Hub。
  • 推奨は自動では適用されない。変更は自分で行う。
  • Cost Explorer・Budgets・CUR・Compute Optimizerの使い分け → コスト管理ツールの選び方。

7. まとめ#

  • Compute OptimizerはCloudWatchの履歴から、過大・過少・アイドルなリソースを見つけて推奨する。
  • 対象はEC2・Auto Scalingグループ・EBS・Lambda・ECS on Fargate・RDSなど。メモリの分析にはCloudWatchエージェントが必要。
  • 推奨設定で分析期間や余裕を調整し、組織全体で使うときはCost Optimization Hubとも組み合わせる。

このサービスが登場する運用シナリオ#

  • EC2・EBSの性能不足を見つけて改善する
  • 負荷に応じて自動でスケールするWebシステム
