1. サービス概要#

Amazon DynamoDBは、フルマネージドのキーバリューストア(NoSQLデータベース)です。サーバー管理が不要で、大量のアクセスにも低レイテンシーで応答します。

2. 主な機能・特徴#

テーブルのキー#

  • プライマリキー:アイテムを一意に識別するキー。次の2通りがある。
    • パーティションキーのみ:パーティションキーの値がテーブル内で一意でなければならない。
    • パーティションキー+ソートキー:同じパーティションキーの値を複数のアイテムが持てる。2つの組み合わせがテーブル内で一意になる。
  • パーティションキー:どの物理パーティションに保存するかを決める。値に偏りがあると性能が劣化する。
  • ソートキー:同じパーティションキー内での並び順を決める。

データの読み取り#

1回のリクエストで取得できる最大データ容量は1MBです。

  • GetItem:主キーで1件取得
  • BatchGetItem:主キーで複数件取得
  • Query:パーティションキー・インデックスを条件に取得
  • Scan:全件走査

セカンダリインデックス#

別のキー構成でクエリを実行するための仕組みです。

  • ローカル(LSI):パーティションキーはそのままで、ソートキーを変えたいとき。例:UserID+OrderDate のテーブルで、UserID+OrderStatus で検索したい。
  • グローバル(GSI):パーティションキーを変えたいとき。例:OrderID+OrderStatus で検索したい。
ローカル(LSI)グローバル(GSI)
対象パーティションキーとソートキーを持つテーブル任意
作成タイミングテーブル作成時のみテーブル作成時/作成後
キャパシティユニットテーブルと同じテーブルと異なる値を設定
削除インデックスのみの削除は不可インデックスのみ削除可能
読み取りの整合性結果整合性/強い整合性結果整合性のみ

TTL(Time To Live)#

指定時刻を過ぎたアイテムを自動削除する機能です。TTL属性はNumber型+UNIXエポック秒である必要があります。セッション管理・キャッシュ・一時URLや認証コードに使います。ただし削除までにラグが生じるため、正確な時刻で処理したい場合はEventBridge+Lambdaを使います。

エラー処理#

UnprocessedKeys は、スロットリングやサイズ超過で未処理になったキーのリストです。エクスポネンシャルバックオフでリトライして再実行します。

関連機能#

  • DynamoDB Accelerator(DAX):インメモリキャッシュ。読み取りをマイクロ秒レベルに高速化。
  • DynamoDB Streams:テーブルのデータ変更を記録し、外部処理に連携する。
    • Streams+Lambdaの流れ:アプリがテーブルを更新 → Streamsが変更イベントを記録 → Lambdaがポーリング(若干の遅延あり)→ まとめて取得して関数を実行
    • ビュータイプ(記録する内容):KEYS_ONLY(キーのみ)、NEW_IMAGE(更新後のアイテム)、OLD_IMAGE(更新前のアイテム)、NEW_AND_OLD_IMAGES(更新前と更新後の両方)
  • DynamoDB Transactions:複数アイテムの更新を「全成功 or 全失敗」にするACIDトランザクション。TransactWriteItems(複数書き込み)、TransactGetItems(複数読み取り)。

3. ユースケース#

  • セッション管理・ユーザープロファイル(TTLで自動削除)
  • 大量アクセスのあるゲーム・EC・IoTのデータ保存
  • 変更をトリガーにした後続処理(Streams+Lambda)

4. 料金の考え方#

性能はキャパシティユニットで表し、テーブルが1秒間にどれだけ読み書きできるかを示します(1RCU/1WCU=1KB/秒が基準)。

  • RCU(読み込みキャパシティユニット):整合性の違いで消費量が変わる(強い整合性のほうが多く消費)。
  • WCU(書き込みキャパシティユニット)

1RCUは「4KBまでのアイテムを強い整合性で1回/秒、結果整合性なら2回/秒」、1WCUは「1KBまでのアイテムを1回/秒」書き込めます。料金モードは、容量を事前に指定するプロビジョンドと、リクエスト数に応じて課金されるオンデマンドの2種類です。

5. 関連サービス#

  • AWS Lambda:DynamoDB Streamsの処理
  • Amazon EventBridge:正確な時刻での削除処理
  • Amazon ElastiCache:汎用的なキャッシュ
  • Amazon RDS:リレーショナルDBの選択肢
  • AWS Database Encryption SDK:クライアント側での属性暗号化
  • 関連する用語:スロットリングとリトライ

6. 試験・実務でのポイント#

  • パーティションキーは値が分散するものを選ぶ(偏るとホットパーティション)。
  • 後からインデックスを追加 → GSIのみ可能。LSIはテーブル作成時のみ。
  • GSIは結果整合性のみ。強い整合性が必要ならベーステーブルかLSI。
  • 読み取りをマイクロ秒に → DAX。
  • 変更をトリガーに処理 → Streams+Lambda。
  • UnprocessedKeys → エクスポネンシャルバックオフでリトライ。
  • 全件取得の Scan は高コスト。可能なら Query。
  • CloudFront・API Gateway・ElastiCache・DAXのキャッシュの使い分け → キャッシュの選び方。

7. まとめ#

  • DynamoDBはキーバリュー型のフルマネージドNoSQL。
  • キー設計(パーティションキー・ソートキー・LSI/GSI)が性能を左右する。
  • DAX・Streams・TTL・Transactionsで機能を拡張できる。

このサービスが登場する運用シナリオ#

  • DynamoDBを負荷に合わせてスケールし、誤操作から復旧する
