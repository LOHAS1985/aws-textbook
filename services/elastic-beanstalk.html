1. サービス概要#

AWS Elastic Beanstalkは、バックエンドアプリケーションを簡単にデプロイ・運用するためのPaaSです。開発者はアプリのコードを渡すだけで、AWSが実行環境を自動で構築してくれます。

2. 主な機能・特徴#

利用フロー#

  1. アプリケーションを作成する(アプリをまとめる入れ物)
  2. アプリケーションバージョンを作成する(コードをまとめたソースバンドルをS3に置き、バージョンとして登録する)
  3. Environment(アプリを実行するAWS環境全体)を作成する(プラットフォームと環境の種類を選ぶ)
  4. Environmentへバージョンをデプロイする
    • Beanstalkが内部でAWSリソースを操作する
    • EC2内にコードを配置する
  5. ヘルスチェックで状態を確認する

デメリットは、ECS/EKSに比べて柔軟性が低いことです。

Beanstalkが自動で作るリソースには、EC2インスタンス、Auto Scalingグループ、ロードバランサーなどが含まれます。裏側ではCloudFormationが使われています。

環境の種類とモード#

Environmentを作るときは、環境のティアを選びます。ティアには、HTTPのリクエストを受けるウェブサーバー環境と、キューからタスクを取り出して処理するワーカー環境があります。

  • ウェブサーバー環境:HTTPのリクエストを受けるアプリを動かす。ロードバランサーを付けた負荷分散の構成と、インスタンス1台だけのシングルインスタンス構成を選べる(シングルインスタンスは主に開発用)
  • ワーカー環境:Amazon SQSのキューからメッセージを読み取るデーモンを、EC2上で動かす。時間のかかる処理を画面の応答から切り離せる。処理に失敗したメッセージはデッドレターキューへ移せ、定期的に実行するタスクも設定できる

Beanstalkには、実行基盤の違いによる2つのモードもあります。Beanstalk StandardはEC2上でアプリを直接動かし、Beanstalk ClusterはEKS上でコンテナとして動かします。

デプロイ方式#

新しいバージョンをEnvironmentへ反映する方法は、デプロイポリシーで選びます。停止時間・追加で必要な容量・完了までの時間のどれを優先するかで使い分けます。

方式仕組み特徴
All at once(一斉)全インスタンスに同時に反映する最も速いが、反映中は短い時間サービスが止まる
Rollingインスタンスをバッチ(まとまり)ごとに順に更新する停止は避けられるが、更新中は処理能力が下がる
Rolling with additional batch追加のバッチを先に起動してから、順に更新する処理能力を保てるが、完了までの時間が長くなる
Immutable新しいAuto Scalingグループに新バージョンのインスタンスを作り、正常と判定されてから旧インスタンスを終了する新しいインスタンスが失敗しても旧バージョンへ戻しやすい。時間は長くなる
Traffic splitting(カナリア)一部のトラフィックだけを新バージョンに送って確認し、残りは旧バージョンが受ける本番の一部で検証してから全体へ広げられる

Immutable と Traffic splitting は、現在 Beanstalk Standard だけで使えます。

Blue/Greenは、デプロイポリシーではなく、別のEnvironmentに新バージョンを作り、2つの環境のCNAMEを入れ替える方法です。既存の環境は残るため、問題があれば入れ替えを戻せます。デプロイポリシーによる更新は同じ環境を書き換えるため、短い時間利用できなくなることがあります。プラットフォームの互換性がないバージョンへの更新では、Blue/Greenが必要です。

説明の中心 成功・推奨・正常 利用者・外部・送信元 その他の構成要素 点線の矢印(使われない・切り替え前・補足)

ヘルスチェックと自動更新#

  • 拡張ヘルスレポート:EC2インスタンス・ロードバランサー・Auto Scalingグループの状態を集めて、Environmentの健全性を判定する。マネージドプラットフォーム更新の前提にもなる
  • マネージドプラットフォーム更新:プラットフォームのマイナー・パッチ更新を、設定した週1回のメンテナンスウィンドウの中で自動で適用する。必要に応じて、ウィンドウ内でインスタンスをすべて入れ替えることもできる

制限(クォータ)#

次の上限はリージョンごとに決められていて、引き上げを申請できます。

項目既定の上限
アプリケーションバージョン1,000(アカウント内の全アプリケーションの合計)
Environment200(アカウント内の全アプリケーションの合計)
アプリケーション75
構成テンプレート2,000
カスタムプラットフォームバージョン50

1つのソースバンドルは500 MBまでです。アプリケーションバージョンが上限に近づくと新しいバージョンを作れなくなるため、ライフサイクルポリシーで古いバージョンを自動で削除できます(Beanstalk Standardの環境で使え、Environmentで使用中のバージョンは削除されない)。上限の考え方は用語ページ「サービスクォータ」を参照してください。

3. ユースケース#

  • インフラの知識が少ないチームで、Webアプリを素早く公開したい
  • Java・Python・Node.jsなどの一般的なWebアプリを、構成を作り込まずに運用したい

4. 料金の考え方#

Elastic Beanstalk自体は無料です。作成されたEC2・ロードバランサー・EBSなどのリソースに対して、それぞれの料金がかかります。

5. 関連サービス#

  • Amazon EC2:アプリが配置される実行環境
  • Elastic Load Balancing:環境のトラフィック分散
  • Amazon EC2 Auto Scaling:環境のインスタンス数の増減
  • AWS CloudFormation:裏側で環境を構築する仕組み
  • AWS CodePipeline:ビルドしたコードをBeanstalkへデプロイするアクション
  • Amazon SQS:ワーカー環境が処理するキュー
  • Amazon ECS/Amazon EKS:より柔軟なコンテナ実行の選択肢
  • 関連する用語:デプロイ戦略、マネージドサービスとサーバーレス、インスタンスプロファイル、サービスクォータ

6. 試験・実務でのポイント#

  • 「インフラ管理を最小限にしてアプリをデプロイしたい」→ Elastic Beanstalk。
  • 細かな制御や柔軟性が必要なら ECS/EKS を選ぶ。
  • デプロイの単位は「アプリケーションバージョン」を「Environment」へ。
  • 停止を避けて更新したい → Rolling(処理能力も保つなら Rolling with additional batch)、または Immutable。All at once は短い時間の停止がある。
  • 本番の一部で新バージョンを試したい → Traffic splitting。環境のURLを切り替えて、問題があれば戻せるようにしたい → Blue/Green(CNAMEの入れ替え)。
  • SQSのメッセージを非同期に処理したい → ワーカー環境。
  • Beanstalk自体には料金がかからず、作られたEC2・ELBなどに料金がかかる。

7. まとめ#

  • Elastic BeanstalkはコードだけでAWS環境を自動構築するPaaS。
  • 手軽さと引き換えに柔軟性は低い。
