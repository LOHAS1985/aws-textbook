1. サービス概要#

Amazon EC2(Elastic Compute Cloud)は、AWS上で仮想サーバー(インスタンス)を動かすサービスです。OSテンプレートであるAMIを選び、インスタンスタイプ(CPU・メモリの組み合わせ)を決めて起動します。

2. 主な機能・特徴#

押さえておきたい用語#

  • AMI:起動イメージ(OSテンプレート)。AMIを暗号化すると、AMIが参照しているEBSスナップショットが暗号化される。
  • 拡張ネットワーキング:仮想化によるネットワーク処理の負担を減らし(SR-IOVという技術で、インスタンスがネットワーク機器を直接使えるようにする)、高帯域・低レイテンシー・パケットの処理性能の向上を実現する機能。追加料金はなく、現在の多くのインスタンスタイプで使える。
  • ENA(Elastic Network Adapter):拡張ネットワーキングを実現するためのネットワークインターフェイス(ドライバー)。最大100Gbps以上の帯域に対応する。AMIにENAのドライバーが入っている必要がある。
  • インスタンスストア:インスタンスが動いている物理ホストに直接接続されたディスクを使う一時的なブロックストレージ。データは永続化しない。
  • インスタンスプロファイル:IAMロールを格納するコンテナ。EC2に直接IAMロールは付与できず、EC2 → インスタンスプロファイル → IAMロール の形になる。

EC2への接続方法(EC2 Instance Connect)#

EC2 Instance Connectは、SSHの鍵を事前に配らずにEC2へSSH接続する仕組みです。接続のたびに一時的な公開鍵をAPIでインスタンスに送り込み(有効期間は60秒)、その間にSSHで接続します。鍵の配布・管理が不要で、誰が接続できるかをIAMポリシー(ec2-instance-connect:SendSSHPublicKey)で制御でき、鍵の送信はCloudTrailに記録されます。

  • マネジメントコンソールのブラウザからも、AWS CLIからも接続できる。
  • Amazon Linux 2以降やUbuntuなど、対応するAMIで使える(それ以外はパッケージを導入する)。
  • 通常の接続では、セキュリティグループでSSH(22番ポート)のインバウンドを許可しておく必要がある。
  • EC2 Instance Connect Endpointを使うと、パブリックIPを持たないプライベートサブネットのEC2にも、踏み台サーバーなしで接続できる。
接続方法鍵の管理22番ポートの開放主な前提
キーペアでSSH秘密鍵を利用者が保管・配布必要パブリックIPまたは踏み台サーバー
EC2 Instance Connect不要(一時的な鍵を毎回送る)必要IAMで送信を許可、対応AMI
Instance Connect Endpoint不要エンドポイントからのみ許可サブネットにエンドポイントを作成
Session Manager不要不要SSM Agent+IAMロール

キーペア#

キーペアは、SSH接続(LinuxのEC2)やWindowsの管理者パスワードの取得に使う、公開鍵と秘密鍵の組です。

  • 起動時にキーペアを指定すると、公開鍵がインスタンスの ~/.ssh/authorized_keys に置かれる
  • 秘密鍵(.pem/.ppk)は作成時に1回だけダウンロードでき、AWSには保存されない。利用者が安全に保管する
  • 鍵の種類はRSAかED25519(ED25519はWindowsでは使えない)。キーペアはリージョンごとに管理される
  • Windowsでは、秘密鍵を使って管理者パスワードを復号する

秘密鍵をなくした場合、AWSから取り出すことはできません。EC2 Instance ConnectやSession Managerで接続して新しい公開鍵を登録するか、インスタンスを停止してルートボリュームを別のインスタンスにアタッチし、authorized_keys を書き換えます(Systems Managerの AWSSupport-ResetAccess オートメーションでも復旧できる)。

ユーザーデータ#

ユーザーデータは、インスタンスの起動時に実行させるスクリプトです。パッケージのインストールや設定ファイルの配置など、起動直後の初期設定を自動化します。

#!/bin/bash
dnf update -y
dnf install -y httpd
systemctl enable --now httpd
  • 既定では最初の起動時に1回だけ、root権限で実行される(Linuxではcloud-init、WindowsではEC2Launchが実行する)
  • サイズは16KBまで。実行のログはLinuxでは /var/log/cloud-init-output.log に出る
  • ユーザーデータは後からインスタンスメタデータで誰でも読めるため、パスワードなどの機密情報を書かない(Secrets ManagerやParameter Storeから取得する)
  • 内容を変更するにはインスタンスを停止する必要がある

Auto Scalingでは起動テンプレートにユーザーデータを書き、起動するインスタンスすべてを同じ状態に設定します。

インスタンスメタデータとIMDSv2#

インスタンスメタデータは、インスタンスの中から自分自身の情報を取得できる仕組みです。http://169.254.169.254/latest/meta-data/ にアクセスすると、インスタンスID、インスタンスタイプ、AZ、プライベートIP、パブリックIP、IAMロールの一時的な認証情報などが取得できます。ユーザーデータは /latest/user-data で取得できます。

この仕組みを提供するのがIMDS(Instance Metadata Service)で、2つのバージョンがあります。

バージョンアクセス方法安全性
IMDSv1GETリクエストを送るだけで取得できるWebアプリの脆弱性(SSRF)を突かれると、外部から認証情報を盗まれるおそれがある
IMDSv2先にPUTリクエストでセッショントークンを取得し、そのトークンをヘッダーに付けてGETするトークンが必要なため、SSRFでの悪用を防げる
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id
  • インスタンスのメタデータオプションで HttpTokens=required にすると、IMDSv2だけを許可(IMDSv1を禁止)できる。Amazon Linux 2023など新しいAMIでは既定でIMDSv2が必須になっている
  • アカウント・リージョン単位で、新しいインスタンスの既定値をIMDSv2必須にできる
  • まだIMDSv1を使っているインスタンスは、CloudWatchメトリクス MetadataNoToken で見つけられる
  • ホップ数の上限(既定1)を超えるとトークンが届かない。コンテナから使う場合は2にする

停止・休止・終了の違い#

操作EBS(ルートボリューム)インスタンスストアメモリの内容パブリックIP料金
再起動保持保持消える変わらない継続
停止保持消える消える変わる(Elastic IPは保持)インスタンス料金なし(EBSは課金)
休止(ハイバネーション)保持消えるEBSに保存され、起動時に復元変わる停止と同じ
終了既定で削除消える消える解放なし
  • 停止:起動し直すと別の物理ホストに移ることがある。インスタンスタイプの変更は停止中に行う
  • 休止:メモリ(RAM)の内容をルートボリュームに書き出してから停止し、起動するとアプリが動いていた状態から再開する。起動に時間がかかるアプリの「温まった状態」を残したいときに使う。起動時に有効にしておく必要があり、ルートボリュームは暗号化されたEBSで、メモリを書き出せる容量が必要
  • 終了:インスタンスは削除され、元に戻せない。ルートボリュームは「終了時に削除」が既定で有効、後から追加したボリュームは既定で残る

終了保護を有効にすると、コンソールやAPIからの終了操作が拒否され、誤って終了するのを防げます。ただし、OSの中からシャットダウンしたときの動作を「終了」にしている場合のシャットダウンと、Auto Scalingのスケールインによる終了は防げません(Auto Scalingでは「スケールイン保護」を使う)。同様に停止を防ぐ停止保護もあります。

ステータスチェックと自動復旧#

EC2は1分ごとにステータスチェックを行い、結果をCloudWatchメトリクスとして記録します。

チェック何を確認するか主な原因対処
システムステータスチェック
StatusCheckFailed_System		インスタンスが動いているAWS側の物理ホストハードウェアの故障、電源・ネットワークの障害停止→起動で別のホストに移す、または自動復旧
インスタンスステータスチェック
StatusCheckFailed_Instance		インスタンス(OS)側カーネルの異常、メモリ不足、ネットワーク設定やファイルシステムの誤り再起動、OSの設定の修正(利用者が対処)
アタッチされたEBSのステータスチェック
StatusCheckFailed_AttachedEBS		アタッチしているEBSボリュームへの到達性ストレージ側の障害インスタンスの置き換えなど

自動復旧では、インスタンスがインスタンスID・プライベートIP・Elastic IP・メタデータを保ったまま別の物理ホストで再起動されます。対応するインスタンスタイプでは既定で「簡易自動復旧」が有効で、CloudWatchアラームの復旧アクションでも設定できます。インスタンスストアを使うインスタンスでは使えず、メモリとインスタンスストアの内容は失われます。

T系インスタンスのCPUクレジット#

T系(t3・t4gなど)はバーストパフォーマンスインスタンスで、普段はベースライン(例:t3.microは1vCPUあたり10%)のCPU性能で動き、必要なときだけそれを超えてバーストします。

  • CPU使用率がベースラインより低いときにCPUクレジットが貯まり、ベースラインを超えるときに消費する(1クレジット=vCPU1個を100%で1分間使う量)
  • 残高はCloudWatchメトリクス CPUCreditBalance で確認できる
モードクレジットがなくなると料金既定
スタンダードベースラインに制限され、処理が遅くなる追加料金なしt2
Unlimited(無制限)クレジットを前借りしてバーストを続けられる24時間の平均がベースラインを超えた分は追加料金t3・t3a・t4g

「T系のインスタンスが時々急に遅くなる」場合は、クレジットの枯渇を疑います。常に高いCPU使用率が続くなら、Unlimitedで追加料金を払い続けるより、M系やC系の固定性能のインスタンスに変えた方が安くなります。

スポットインスタンスの中断通知#

スポットインスタンスは、AWSがその容量を必要としたときに中断されます。中断の2分前に通知が出るので、その間に処理の保存や切り離しを行います。

  • 通知の受け取り方:インスタンスメタデータの spot/instance-action をポーリングする、またはEventBridgeの「EC2 Spot Instance Interruption Warning」イベントでLambdaなどを起動する
  • 中断の可能性が高まったときには、それより早くリバランスの推奨のシグナルも出る(Auto Scalingの「容量の再調整」で事前に置き換えられる)
  • 中断時の動作は終了(既定)・停止・休止から選べる
  • 中断に強くするには、Auto Scalingグループで複数のインスタンスタイプ・複数のAZを指定し、配分戦略に price-capacity-optimized などを使う

4. 料金の考え方#

EC2は「購入モデル」によって料金が大きく変わります。下の図のように、ワークロードの性質から選ぶと迷いません。

購入モデル特徴メリットデメリット主用途
オンデマンド従量課金柔軟高価開発・短期
リザーブドインスタンス1〜3年契約割引安い長期前提常時稼働
Savings Plans使用量コミット割引柔軟な割引契約が必要長期運用
スポットインスタンス余剰リソースを利用超安価中断されるバッチ/HPC
Dedicated Hosts専用物理サーバーライセンス対応高価規制対応
Dedicated Instances専用ハード上のVM分離性高価セキュリティ
キャパシティ予約容量を予約起動保証割引なし災害対策

リザーブドインスタンスとSavings Plansの種類#

どちらも1年または3年の利用を約束して割引を受ける仕組みで、支払い方法は全額前払い・一部前払い・前払いなしから選びます(前払いが多いほど割引が大きい)。

種類割引率(最大)約束するもの柔軟性
Standard RI約72%インスタンスファミリー・リージョン・OSなどAZ・サイズ(同じファミリー内)の変更は可能。ファミリーやOSは変えられない。不要になったらRIマーケットプレイスで売却できる
Convertible RI約66%同上別のファミリー・OS・テナンシーのRIに交換できる(同等以上の価値のものへ)。売却はできない
EC2 Instance Savings Plans約72%1時間あたりの利用額(リージョン内の特定ファミリー)ファミリー内のサイズ・OS・AZ・テナンシーは自由
Compute Savings Plans約66%1時間あたりの利用額ファミリー・リージョン・OSを問わず適用され、FargateとLambdaにも適用される
  • RIは特定のAZを指定して購入すると(ゾーンRI)、そのAZでの容量の予約も付く。リージョンを指定したRIは割引だけ
  • Savings Plansには容量の予約は付かない。容量が必要ならオンデマンドキャパシティ予約と組み合わせる
  • 迷ったら:構成が固まっていて最大の割引 → Standard RIかEC2 Instance Savings Plans、将来の変更に備える → Compute Savings Plans

オンデマンドは秒単位(Linuxの場合)の課金で、停止中のインスタンスにはコンピューティング料金はかかりません。ただしアタッチしたEBSボリュームの料金は停止中も発生します。

6. 試験・実務でのポイント#

起動・接続

  • EC2にIAMロールを渡すときはインスタンスプロファイルを使う(図1)。アクセスキーをインスタンスに置かない。
  • 秘密鍵をなくした → AWSからは取り出せない。Instance Connect・Session Managerで接続するか、ルートボリュームを別のインスタンスにアタッチして authorized_keys を直す。
  • 起動時の初期設定を自動化 → ユーザーデータ(既定は初回起動時のみ、rootで実行)。機密情報は書かない。
  • インスタンスの中から自分の情報やロールの認証情報を取得 → インスタンスメタデータ(169.254.169.254)。SSRF対策でIMDSv2を必須(HttpTokens=required)にする。
  • SSHの鍵を配らずに、IAMで制御しながら接続したい → EC2 Instance Connect(図5)。22番ポートも開けたくない → Session Manager。

停止・障害対応

  • インスタンスストアのデータは永続化しない(図2)。消えて困るデータはEBSやS3へ。
  • インスタンスタイプの変更は停止してから。
  • メモリの内容を残したまま止めたい → 休止(起動時に有効化、ルートボリュームの暗号化が必要)。誤って終了させない → 終了保護。
  • システムステータスチェックの失敗 → AWS側の障害。停止→起動か復旧アクション(IPやIDは保持)。インスタンスステータスチェックの失敗 → OS側。再起動・設定の修正。

性能・配置

  • 低レイテンシー → クラスター、障害分離(大規模分散) → パーティション、少数の重要インスタンス → スプレッド(図3)。
  • T系が急に遅くなる → CPUクレジットの枯渇(CPUCreditBalance)。Unlimitedにするか固定性能のタイプへ。

料金

  • 中断されてもよいバッチ処理はスポット、常時稼働はRI/Savings Plans、起動を保証したいならキャパシティ予約(割引はない)(図8)。
  • ファミリーやOSを将来変えたい → Convertible RIかCompute Savings Plans。Fargate・Lambdaにも割引 → Compute Savings Plans。
  • スポットの中断は2分前に通知される(メタデータ/EventBridge)。

7. まとめ#

  • EC2はAWSの仮想サーバー。AMI+インスタンスタイプで起動する。
  • 配置はプレイスメントグループ、料金は購入モデルで最適化する。
  • IAMロールはインスタンスプロファイル経由、インスタンスストアは一時領域。

このサービスが登場する運用シナリオ#

  • EC2の障害を検知して自動で復旧するステータスチェックの失敗をアラームで検知し、復旧・再起動を自動で行う
  • EC2・EBSの性能不足を見つけて改善するCloudWatchのメトリクスとCompute Optimizerでボトルネックを特定し、止めずに性能を上げる
  • 負荷に応じて自動でスケールするWebシステムALBとAuto Scalingグループで、複数AZにまたがって台数を自動調整する
  • リージョン障害に備えて別リージョンへ切り替えるRoute 53のフェイルオーバーとAuroraグローバルデータベースで、ウォームスタンバイを構成する
  • 多数のEC2の設定やソフトウェアを一定に保つSystems ManagerのState ManagerとRun Commandで、タグで選んだインスタンスに設定を一括で適用し続ける
  • 多数のEC2に定期的にパッチを適用するSystems ManagerのPatch Managerとメンテナンスウィンドウで、パッチ適用を自動化する
  • 開発環境を夜間・休日に自動で停止して費用を下げるEventBridge SchedulerとSSM Automationで、タグの付いたEC2・RDSを決まった時刻に停止・起動する
  • 乗っ取られたEC2を自動で隔離するGuardDutyの検出結果をEventBridgeで受け、隔離用のセキュリティグループへの付け替えと証拠の保全を自動で行う
  • 踏み台サーバーなしでプライベートなEC2を操作するSession ManagerとVPCエンドポイントで、ポートを開けずに安全に接続する
  • EC2に接続できない原因を調査する経路と許可を順番に確認し、VPCフローログで通信の拒否を特定する
