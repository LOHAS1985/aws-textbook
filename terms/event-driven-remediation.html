イベント駆動の自動修復

「何かが起きた」というイベントを受けて、通知や修復の処理を自動で実行する運用の型

最終更新:2026-10-26

1. 詳しい説明#

運用の自動化の多くは、「検知する → 振り分ける → 対処する」という同じ型でできています。どのサービスがどの役割を受け持つかを覚えておくと、選択肢から正しい組み合わせを選べるようになります。

①検知:イベントを出すもの#

イベントの出どころ何が起きたか例
CloudWatchアラームメトリクスがしきい値を超えた(状態が変わった)CPU使用率が高い、ステータスチェックの失敗
AWS Configリソースの設定がルールに違反した暗号化されていないEBS、SSHを全開放したセキュリティグループ
GuardDuty・Security Hub・Inspector脅威・脆弱性を検出した不審な通信をしているEC2
CloudTrail(API呼び出し)誰かが特定のAPIを呼んだバケットポリシーの変更、CloudTrailの停止
AWS HealthAWS側の障害・予定されたメンテナンスEC2のリタイア予定
各サービスの状態の変化リソースの状態が変わったEC2の停止、Auto Scalingの起動失敗
スケジュール決めた時刻になった(cron式・rate式)夜間の停止、定期的な点検

②振り分け:EventBridgeのルール#

EventBridgeのルールは、イベントパターン(JSON)に一致したイベントだけをターゲットに渡します。次の例は「EC2インスタンスが停止した」イベントに一致します。

{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": { "state": ["stopped"] }
}

特定のAPIの呼び出しを捕まえるときは、"detail-type": ["AWS API Call via CloudTrail"] と、detail の eventSource・eventName を指定します。このイベントを受け取るには、CloudTrailの証跡が有効になっている必要があります。

③対処:ターゲット#

ターゲット向いている処理
SSM Automation(ランブック)決まった手順の修復。AWSが用意したランブック(例:AWS-RestartEC2Instance、AWS-DisablePublicAccessForSecurityGroup)をそのまま使える。承認の手順や複数のステップも書ける
Lambdaランブックにない独自の処理、外部のツールとの連携
SNS人への通知(メール・チャット)
Step Functions分岐・待ち・人の承認を含む長い処理
SQSあとでまとめて処理するためにためておく

ターゲットを実行するためのロール(Automationに渡すロールなど)には、修復に必要な権限を与え、ルールを作る人にはiam:PassRoleの権限が必要です。

EventBridgeを通さない近道#

次の組み合わせは、EventBridgeのルールを作らなくても直接つなげられます。試験では「最も手間が少ない方法」として問われます。

  • Configルール → 修復アクション:違反したリソースにSSM Automationのランブックを実行する。自動修復にすると違反のたびに実行され、再試行の回数も決められる
  • CloudWatchアラーム → アラームのアクション:SNS通知、EC2の再起動・復旧、Auto Scaling、Lambda、OpsItemの作成
  • Security Hub → 自動化ルール:検出結果の重要度や状態を自動で更新する

選び方の目安:設定の違反なら Config の修復アクション、メトリクスの異常ならアラームのアクション、それ以外のイベントや複数の処理なら EventBridge のルールでAutomationやLambdaにつなぎます。修復を自動にする前に、まず通知だけで運用して誤検知がないことを確かめると安全です。
