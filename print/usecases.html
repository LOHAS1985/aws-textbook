EC2のメモリ・ディスク使用率を監視する

1. やりたいこと#

  • Amazon LinuxのEC2(複数台)のメモリ使用率とディスク使用率を監視したい。
  • メモリ使用率が80%以上の状態が5分続いたら、担当者にメールで知らせたい。
  • 収集の設定は全台で共通にし、変更するときも1か所を直すだけにしたい。

3. 構成図#

メモリ・ディスクの使用率はOSの中の値なので、CloudWatchエージェントでカスタムメトリクスとして送ります。設定はParameter Storeに置いて全台で共有し、EC2には CloudWatchAgentServerPolicy を付けたIAMロールを付けます。

アラームは CWAgent 名前空間の mem_used_percent で作り、「期間1分・5個中5個」のように評価の設定で「5分続いたら」を表します(CloudWatchアラームの状態と評価)。通知はアラームのアクションでSNSトピックに送ります。

台数が多い場合は、Systems Managerの State Manager でエージェントのインストールと設定の取得を全台に自動で行うと、新しく起動したインスタンスにも漏れなく設定できます。

4. 使うサービスと役割#

  • Amazon CloudWatch:エージェントでメトリクスを収集し、アラームでしきい値を監視する
  • AWS IAM:EC2のロールに CloudWatchAgentServerPolicy を付ける
  • AWS Systems Manager:エージェントの一括インストールや、設定ファイルをParameter Storeで共有する
  • Amazon SNS:アラーム発生時のメール通知

5. 構築の流れ#

  1. EC2のIAMロールに CloudWatchAgentServerPolicy をアタッチする
  2. CloudWatchエージェントをインストールする(多数のEC2にはSystems ManagerのRun CommandやDistributorで一括導入)
  3. 設定ファイル(JSON)に mem_used_percent・disk_used_percent を指定する(Parameter Storeに置くと全EC2で同じ設定を使える)
  4. エージェントを起動し、メトリクスがCloudWatchに届くことを確認する
  5. メトリクスにアラーム(例:80%以上が5分間)を作成し、通知先にSNSトピックを指定する

6. ポイント・注意点#

  • メモリ・ディスク使用率は詳細モニタリングを有効にしても取れない。エージェントが必要。
  • メトリクスが届かない → IAMロール、エージェントの起動状態、設定ファイルを確認する。
  • エージェントのメトリクスは、標準とは別の名前空間(CWAgent)に入る。
  • 同じエージェントでアプリのログファイルもCloudWatch Logsに送れる。

アプリのエラーログを検知して通知する

1. やりたいこと#

  • アプリのログに「ERROR」が出たら、すぐに開発者へメールで知らせたい。
  • 原因を調べるために、過去のログを条件で検索したい。

3. 構成図#

アプリのログをCloudWatch Logsのロググループに送り、メトリクスフィルターで「ERROR」の数をメトリクスにして、アラームからSNSでメールを送ります。調査はLogs Insightsで行います。ログを即座に別の処理に流したいときは、サブスクリプションフィルターを使います。

4. 使うサービスと役割#

  • Amazon CloudWatch:Logs(ログの保存)、メトリクスフィルター(ログの数値化)、アラーム、Logs Insights(検索・分析)
  • Amazon SNS:アラーム時のメール通知
  • AWS Lambda:ログを自動でCloudWatch Logsに出力する(EC2はエージェントで送る)

5. 構築の流れ#

  1. アプリのログをCloudWatch Logsのロググループに送る(Lambdaは自動、EC2はCloudWatchエージェント)
  2. ロググループにメトリクスフィルターを作成し、フィルターパターンに ERROR を指定する
  3. フィルターが作ったメトリクスにアラーム(例:1分間に1件以上)を作成し、SNSトピックを通知先にする
  4. ロググループの保持期間を設定する(デフォルトは無期限)

6. ポイント・注意点#

  • ログの特定の文字列でアラーム → メトリクスフィルター。
  • ログを即座に別の処理(Lambda・Firehoseなど)へ流したい → サブスクリプションフィルター。
  • 過去ログをSQLライクに調べる → Logs Insights。
  • 保持期間はデフォルト無期限。長期保存はS3に移してコストを下げる。
  • ログに機密情報が含まれる場合は、データ保護ポリシーでマスキングできる。

外形監視と、誤報の少ないアラームを作る

1. やりたいこと#

  • サーバーのメトリクスが正常でも「ログインできない」ことがある。利用者と同じ操作を定期的に試したい。
  • アクセス数は時間帯や月末で大きく変わり、固定のしきい値では誤報が多い。
  • 通知が多すぎるので、本当に異常なときだけ1件知らせたい。

3. 構成図#

Canaryで利用者の操作を定期的に試し、時間帯で変わるメトリクスには異常検出のアラームを使います。両方を複合アラームでまとめると、本当に異常なときだけ1件の通知になります。VPCの中の非公開のサイトを監視するときは、CanaryをVPCの中で動かします。

4. 使うサービスと役割#

  • Amazon CloudWatch:Synthetics(Canary)、異常検出、複合アラーム
  • Amazon SNS:通知
  • Amazon S3:Canaryの実行結果(スクリーンショット・HARファイル・ログ)の保存先
  • AWS Lambda:Canaryの実体(実行環境)

5. 構築の流れ#

  1. CloudWatch Syntheticsで、ログインなどの操作を行うCanaryを作り、数分おきに実行する(ブループリントのAPI監視・リンク切れチェックなども使える)
  2. Canaryの SuccessPercent にアラームを作る
  3. 曜日や時間帯で変わるメトリクス(リクエスト数・レイテンシーなど)には、異常検出のアラームを作る(過去のデータから「普段の範囲」のバンドを学習する)
  4. 複数のアラームを AND・OR で組み合わせた複合アラームを作り、SNSへの通知は複合アラームだけに設定する
  5. メンテナンス中は、複合アラームのアクションを抑制する設定で通知を止める

6. ポイント・注意点#

  • 利用者の視点での定期的な確認(外形監視)→ CloudWatch SyntheticsのCanary。
  • 時間帯や曜日で変動するメトリクスのしきい値 → 異常検出。
  • 通知が多すぎる(アラート疲れ)→ 複合アラームで条件を組み合わせる。
  • アラームの「M out of N」(N回中M回の超過で発報)で、一時的な跳ね上がりによる誤報を減らせる。
  • データが届かないとき(欠落データ)の扱い(missing/breaching/notBreaching/ignore)を決めておく。
  • VPC内の非公開のサイトを監視するときは、CanaryをVPC内で動かすよう設定する。

EC2の障害を検知して自動で復旧する

1. やりたいこと#

  • EC2が障害で応答しなくなったら、人手を介さず自動で復旧させたい。
  • 物理ホストの障害と、OSの中の問題とで、対処を分けたい。

3. 構成図#

システムステータスチェックの失敗はAWS側(ホスト)の問題なので、アラームの復旧アクションで別のホストに移します。インスタンスステータスチェックの失敗はOS側の問題なので、EventBridgeからSSM Automationで再起動などの手順を実行します。

4. 使うサービスと役割#

  • Amazon EC2:ステータスチェックのメトリクス(StatusCheckFailed)
  • Amazon CloudWatch:アラームで障害を検知し、EC2のアクション(復旧・再起動)を実行する
  • Amazon EventBridge:アラームの状態変化をきっかけに自動処理を起動する
  • AWS Systems Manager:Automationランブック(例:AWS-RestartEC2Instance)で復旧手順を実行する
  • Amazon SNS:復旧したことの通知

5. 構築の流れ#

  1. StatusCheckFailed_System にアラームを作成し、アクションに「インスタンスの復旧」を設定する
  2. StatusCheckFailed_Instance にアラームを作成し、EventBridgeルールでアラームの状態変化を検知する
  3. EventBridgeのターゲットにSSM Automation(再起動のランブック)を指定する
  4. SNSで運用担当者に通知する

6. ポイント・注意点#

  • システムステータスチェックの失敗はAWS側(ホスト)の問題 → 復旧アクション(停止・起動でも別ホストへ移る)。
  • インスタンスステータスチェックの失敗はOS・設定の問題 → 再起動や設定の修正が必要。
  • 復旧アクションではインスタンスID・プライベートIP・EBSのデータは引き継がれるが、インスタンスストアのデータは失われる。
  • 手順の多い復旧処理は、SSM Automationでランブック化しておく。

AWSの予定メンテナンスや障害の通知に自動で対応する

1. やりたいこと#

  • EC2のリタイア予定やサービスの障害など、AWS側の情報をすぐに担当者へ知らせたい。
  • リタイア予定のインスタンスは、自動で別のホストに移したい。
  • 組織の全アカウント分をまとめて受け取りたい。

3. 構成図#

AWS HealthのイベントはEventBridgeに送られるので、ルールで種類を絞ってSNSで通知し、リタイア予定のインスタンスはSSM Automationで停止・起動して別のホストに移します。Health API を使う場合は、上位のサポートプランが必要です。

4. 使うサービスと役割#

  • AWS Health Dashboard:自分のアカウントに影響するイベント(予定メンテナンス・障害・アカウントへの通知)
  • Amazon EventBridge:aws.health のイベントをルールで受け取る
  • Amazon SNS:メールやチャットへの通知(Amazon Q Developer in chat applications でSlack・Teamsにも送れる)
  • AWS Systems Manager:Automationで対応手順を自動実行
  • AWS Organizations:組織ビューで全アカウントのイベントを集約

5. 構築の流れ#

  1. EventBridgeでイベントパターン "source": ["aws.health"] のルールを作り、必要に応じてサービス(EC2 など)やイベントの種類で絞り込む
  2. ターゲットにSNSトピックを指定して、担当者へ通知する
  3. EC2のリタイア予定(AWS_EC2_INSTANCE_RETIREMENT_SCHEDULED など)には、SSM Automation で該当インスタンスを停止・起動して別のホストに移す処理をつなぐ
  4. Organizationsの管理アカウント(または委任管理者)で Health の組織ビューを有効にし、全アカウントのイベントを1か所で確認する

6. ポイント・注意点#

  • 自分のアカウントに影響するAWS側のイベント → AWS Health(全体の稼働状況は Service Health Dashboard)。
  • Healthイベントへの自動対応 → EventBridgeルール+SNS/Lambda/SSM Automation。
  • EBS-backedのEC2は停止→起動で別の物理ホストに移る(再起動では移らない)。インスタンスストアのデータは消える。
  • Health APIを使うにはビジネス以上のサポートプランが必要。EventBridge経由の受信はどのプランでも使える。
  • Healthイベントはリージョンごとに発生する。グローバルなイベントは us-east-1 に届く。

複数アカウントのログを集約して分析する

1. やりたいこと#

  • 複数アカウントのアプリのログとAPIの操作の記録を、ログ集約用のアカウントに集めて長期保存したい。
  • 監査のときは、SQLで横断的に検索したい。

3. 構成図#

各アカウントのCloudWatch LogsはサブスクリプションフィルターからData FirehoseでS3へ、APIの記録は組織の証跡でS3へ集めます。分析はAthenaで行い、パーティション分割や列指向の形式にすると、読み取る量が減って費用も下がります。

4. 使うサービスと役割#

  • Amazon CloudWatch:サブスクリプションフィルターでログをリアルタイムに転送する
  • Amazon Kinesis(Data Firehose):ログをS3へ配送する
  • AWS CloudTrail:組織全体のAPI操作を1つの証跡で記録する
  • Amazon S3:ログの長期保存(ライフサイクルでGlacierへ)
  • Amazon Athena:S3のログをSQLで分析する
  • AWS Organizations:組織の証跡、アカウントの管理

5. 構築の流れ#

  1. 集約アカウントにログ用のS3バケットを作り、バケットポリシーで各アカウントからの書き込みを許可する
  2. 管理アカウントでCloudTrailの組織の証跡を作成し、保存先に集約バケットを指定する
  3. Data Firehoseの配信ストリームを作り、各アカウントのロググループにサブスクリプションフィルターを設定する
  4. S3のライフサイクルルールで、古いログをGlacierなどへ移す
  5. Athenaでテーブルを定義し、SQLで検索する

6. ポイント・注意点#

  • 短期・頻繁に検索するログはCloudWatch Logs、長期・たまに検索するログはS3。
  • CloudTrailのログの改ざん検知 → ログファイルの整合性検証。
  • Athenaのコスト削減 → パーティション分割・列指向形式。
  • ログを削除させないために、S3オブジェクトロックやバケットポリシーで削除を制限する。

コンテナ(ECS・EKS)の性能を監視する

1. やりたいこと#

  • ECS・EKSのアプリを、タスク・Pod単位のCPU・メモリ・再起動回数で監視したい。
  • メモリ不足や再起動のくり返しを、早く見つけて通知したい。
  • アプリ独自のPrometheus形式のメトリクスも、ダッシュボードで見たい。

3. 構成図#

ECSはContainer Insights、EKSはCloudWatch Observabilityアドオンでタスク・Pod単位のメトリクスとログを集め、アラームとSNSで通知します。アプリ独自のメトリクスはManaged Service for Prometheusに集め、Managed Grafanaで見ます。タスクが OutOfMemoryError で止まるときは、タスク定義のメモリの上限を見直します。

4. 使うサービスと役割#

  • Amazon CloudWatch:Container Insightsによるタスク・Pod単位のメトリクスとパフォーマンスログ、アラーム
  • Amazon ECS:クラスターの設定でContainer Insightsを有効化。コンテナのログは awslogs ログドライバーでCloudWatch Logsへ
  • Amazon EKS:Amazon CloudWatch Observability アドオン(CloudWatchエージェント+Fluent Bit)でメトリクスとログを収集
  • Amazon Managed Service for Prometheus/Amazon Managed Grafana:Prometheus形式のメトリクスの保存と可視化
  • Amazon SNS:アラームの通知

5. 構築の流れ#

  1. ECS:クラスターでContainer Insights(オブザーバビリティ強化版)を有効にする。新しいクラスターで常に有効にするなら、アカウントの設定 containerInsights を有効にする
  2. ECS:タスク定義のログ設定を awslogs にし、ロググループを指定する。タスク実行ロールにログを書く権限を付ける
  3. EKS:CloudWatch Observabilityアドオンを追加し、ノードのIAMロール(またはPod Identity)に CloudWatchAgentServerPolicy を付ける
  4. メモリ使用率・実行中のタスク数・Podの再起動回数などにアラームを作り、SNSで通知する
  5. アプリのPrometheusメトリクスは、Managed Prometheusのマネージドコレクター(またはADOT)で収集し、Grafanaでダッシュボードを作る

6. ポイント・注意点#

  • ECSの標準のメトリクスはサービス単位のCPU・メモリだけ。タスク・コンテナ単位の詳細はContainer Insightsを有効にして初めて見られる。
  • EKSには標準のノード・Podのメトリクスがない → CloudWatchエージェント(Observabilityアドオン)が必要。
  • Container Insightsの詳細データはCloudWatch Logsのパフォーマンスログとして保存され、Logs Insightsで調べられる。保存量に応じて費用がかかる。
  • タスクが OutOfMemoryError で止まる → タスク定義のメモリの上限を見直す。停止の理由はECSの「停止したタスク」で確認できる。
  • 負荷に応じたタスク数の増減は、ECSサービスの自動スケーリング(ターゲット追跡)で行う。

マイクロサービスの遅延の原因をトレースで特定する

1. やりたいこと#

  • API Gateway → Lambda → DynamoDB・外部APIの処理が、ときどき遅い。
  • どの区間で時間がかかっているかを、ログを1つずつ見ずに特定したい。

3. 構成図#

API Gatewayのステージと、Lambdaのアクティブトレースを有効にすると、X-Rayがリクエストの区間ごとの時間を記録し、トレースマップで遅い区間が分かります。既定のサンプリングは毎秒1件+5%なので、すべてのリクエストは記録されません。

4. 使うサービスと役割#

  • AWS X-Ray:トレースの収集・トレースマップ・分析
  • Amazon API Gateway:ステージの設定でX-Rayトレースを有効化
  • AWS Lambda:アクティブトレースを有効化し、コードを計測(OpenTelemetry/ADOT)
  • Amazon CloudWatch:Application Signalsでのサービス単位の指標とSLO、ログとトレースの関連付け

5. 構築の流れ#

  1. API Gatewayのステージで X-Ray トレースを有効にする
  2. Lambda関数でアクティブトレースを有効にし、実行ロールに AWSXRayDaemonWriteAccess を付ける
  3. アプリをOpenTelemetry(ADOT)で計測し、DynamoDBや外部APIの呼び出しをサブセグメントとして記録する。検索したい値(顧客IDなど)は注釈に入れる
  4. EC2・ECSのアプリは、CloudWatchエージェント(またはADOTコレクター)を通してトレースを送る
  5. トレースマップで遅い・エラーの多いノードを見つけ、該当するトレースを注釈で絞り込んで調べる

6. ポイント・注意点#

  • 「複数サービスをまたぐ処理のボトルネック」「サービス間の依存関係の可視化」→ X-Ray。
  • 検索・絞り込みに使う値は注釈(annotation)、検索しない付加情報はメタデータ。
  • 既定のサンプリングは毎秒1件+5%。全件は記録されないので、費用と詳しさの兼ね合いでサンプリングルールを調整する。
  • トレースが届かない → 実行ロールの権限、トレースの有効化、エージェント(デーモン)の起動と UDP 2000番ポートを確認する。
  • X-Ray SDKからOpenTelemetry(ADOT)への移行が推奨されている。

監視・ログ・自動修復

EC2・EBSの性能不足を見つけて改善する

1. やりたいこと#

  • EC2上のDBのディスクの読み書きが遅い。原因がEBSボリュームかインスタンスかを切り分けたい。
  • サービスを止めずに性能を上げたい。
  • 性能を持て余しているリソースは小さくして、費用を下げたい。

3. 構成図#

CloudWatchのメトリクスで、ボトルネックがボリュームかインスタンスかを切り分けます。ボリューム側ならElastic Volumesでgp3のIOPSを足し、インスタンス側ならEBS帯域の大きいタイプに変えます。サイズを増やしたら、OS側でファイルシステムの拡張も必要です。

4. 使うサービスと役割#

  • Amazon CloudWatch:VolumeQueueLength・VolumeReadOps/VolumeWriteOps・インスタンスのEBS関連の指標の確認とアラーム
  • Amazon EBS:Elastic Volumesでボリュームのタイプ・IOPS・スループット・サイズをオンラインで変更
  • Amazon EC2:インスタンスタイプの変更(EBS最適化・EBS帯域の大きいタイプ)
  • AWS Compute Optimizer:EC2・EBSの過不足の推奨

5. 構築の流れ#

  1. CloudWatchで、ボリュームの読み書き回数(IOPS)・スループット・VolumeQueueLength を確認する。IOPSやスループットがボリュームの上限に張り付き、キューが溜まっていればボリューム側が原因
  2. ボリュームに余裕があるのに遅い場合は、インスタンスの EBSIOBalance%・EBSByteBalance% などで、インスタンス側のEBS帯域の上限を確認する
  3. ボリューム側:Elastic Volumesで gp2 → gp3 に変える、gp3のIOPS・スループットを追加する、さらに高い性能が必要なら io2 にする
  4. インスタンス側:EBS帯域の大きいインスタンスタイプに変更する(停止・起動が必要)
  5. Compute Optimizerの推奨で、過剰なリソースは小さくし、変更後もアラームで監視を続ける

6. ポイント・注意点#

  • I/Oが詰まっている → VolumeQueueLength。ボリュームの性能を止めずに上げる → Elastic Volumes。
  • gp3はサイズに関係なく3,000IOPS・125MiB/sが付き、IOPS・スループットを個別に追加できる。gp2はサイズに比例するので、性能のために容量を増やす必要があった。
  • 同じボリュームの再変更は6時間空ける。サイズを増やしたら、OS側でパーティションとファイルシステムを拡張する。
  • ボリュームを速くしても、インスタンスのEBS帯域の上限で頭打ちになることがある。
  • スナップショットから復元した直後のボリュームは、初回アクセスが遅い。すぐに最大性能が必要なら高速スナップショット復元(FSR)を使う。
監視・ログ・自動修復

RDSの遅いクエリと接続数の問題を解消する

1. やりたいこと#

  • RDSのCPU使用率が高い。どのSQLが負荷の原因かを特定したい。
  • Lambdaからの接続が急増すると、「接続数が多すぎる」エラーが出る。
  • 読み取りの多い処理の負荷を、書き込み用のDBから逃がしたい。

3. 構成図#

Performance Insightsとスロークエリログで重いSQLを見つけて改善し、接続の急増はRDS Proxyで、読み取りの負荷はリードレプリカやElastiCacheで吸収します。スロークエリログをCloudWatch Logsに出すには、パラメータグループでの出力の設定と、ログのエクスポートの設定の両方が必要です。

4. 使うサービスと役割#

  • Amazon RDS:Performance Insights(SQL別・待機イベント別の負荷)、拡張モニタリング(OSの詳細)、リードレプリカ、RDS Proxy
  • Amazon CloudWatch:CPUUtilization・DatabaseConnections・ReadLatency などの監視、スロークエリログの保存と検索(Logs Insights)
  • AWS Secrets Manager:RDS ProxyがDBに接続するための認証情報
  • Amazon ElastiCache:よく読まれるデータのキャッシュ

5. 構築の流れ#

  1. Performance Insightsを有効にし、DBの負荷(平均アクティブセッション数)が多いSQL文と待機イベントを確認する
  2. パラメータグループでスロークエリログ(MySQLの slow_query_log・long_query_time など)を有効にし、CloudWatch Logsに発行する
  3. 重いSQLにインデックスを追加するなど、クエリを改善する
  4. 接続数の問題には RDS Proxy を作成し、アプリの接続先をProxyのエンドポイントに変える(認証情報はSecrets Managerに保存)
  5. 読み取りが多い場合はリードレプリカを追加し、読み取り処理の接続先を分ける。それでも足りなければインスタンスクラスを上げる

6. ポイント・注意点#

  • 「どのSQLが負荷をかけているか」→ Performance Insights。OSのプロセスやメモリの詳細 → 拡張モニタリング。
  • Lambdaなどで接続数が急増する・接続が枯渇する → RDS Proxy(フェイルオーバー時間の短縮にもなる)。
  • ログをCloudWatch Logsに出すには、パラメータグループでの出力設定と、DBインスタンスのログのエクスポート設定の両方が必要。
  • リードレプリカは非同期なので、直後の読み取りに古いデータが返ることがある。高可用性はMulti-AZ、読み取りの分散はリードレプリカ。
  • パラメータの変更には、すぐ反映されるもの(動的)と、再起動が必要なもの(静的)がある。

負荷に応じて自動でスケールするWebシステム

1. やりたいこと#

  • WebアプリをEC2で動かし、1つのAZが止まってもサービスを続けたい。
  • アクセスの増減に合わせて、台数を自動で増減したい(CPU使用率をおよそ50%に保つ)。
  • アプリが応答しなくなったインスタンスは、自動で入れ替えたい。
  • 将来、URLのパス(/api など)で振り分け先を変えたい。

3. 構成図#

パブリックサブネットに置いたALBが、2つのAZのプライベートサブネットにあるEC2に分散し、Auto Scalingグループが台数を管理します。スケーリングはターゲット追跡(CPU 50%)、ヘルスチェックはELBも使う設定にすると、アプリの異常でも自動で入れ替わります。

この構成の可用性の考え方は「高可用性とスケーリング」と「SLAと可用性」で説明しています。

4. 使うサービスと役割#

  • Elastic Load Balancing(ALB):複数AZのインスタンスにトラフィックを分散し、ヘルスチェックで異常を検知する
  • Amazon EC2:アプリケーションを動かすインスタンス
  • Amazon EC2 Auto Scaling:起動テンプレートをもとにインスタンスを自動で起動・終了し、指定した台数(最小・最大・希望)を保つ
  • Amazon CloudWatch:CPU使用率やリクエスト数などのメトリクスでスケーリングを判断する

5. 構築の流れ#

  1. AMIとインスタンスタイプなどを指定した起動テンプレートを作成する
  2. 複数AZのサブネットを指定してAuto Scalingグループを作成し、最小・最大・希望の台数を決める
  3. ALBとターゲットグループを作成し、Auto Scalingグループに関連付ける
  4. ターゲット追跡スケーリング(例:平均CPU使用率50%を維持)を設定する
  5. Auto Scalingグループのヘルスチェックの種類を「ELB」にして、アプリの異常でも入れ替わるようにする

6. ポイント・注意点#

  • ELBはリージョン内の複数AZに分散する。インスタンスも複数AZに配置して、AZ障害に備える。
  • ヘルスチェックの種類がEC2のままだと、OSは動いているがアプリが落ちている状態を検知できない → ELBヘルスチェックを使う。
  • 決まった時間に負荷が増えるならスケジュールされたスケーリング、指標を一定に保つならターゲット追跡。
  • インスタンスのサイズ見直しにはCompute Optimizerの推奨を使う。

あわせて読む:リージョンとアベイラビリティーゾーン

信頼性・事業継続

キューで処理を分離し、急増や障害に強くする

1. やりたいこと#

  • 注文の受付と重い処理を同時に行っているため、アクセスが急増すると受付まで遅くなる。
  • 処理側が止まっても、注文を失わないようにしたい。
  • 何度処理しても失敗する注文は、ほかの注文の邪魔にならないよう隔離したい。

3. 構成図#

受付と処理の間にSQSのキューを置き、キューの長さ(1台あたりのバックログ)に応じて処理側の台数を増減します。何度も失敗するメッセージはDLQに隔離します。標準キューは「少なくとも1回」届ける仕組みなので、処理はべき等に作ります。

4. 使うサービスと役割#

  • Amazon SQS:メッセージを保持するキュー、可視性タイムアウト、デッドレターキュー
  • Amazon EC2 Auto Scaling:キューの長さに応じた処理側のスケーリング(ECSやLambdaでもよい)
  • Amazon CloudWatch:ApproximateNumberOfMessagesVisible・ApproximateAgeOfOldestMessage の監視
  • AWS Lambda:イベントソースマッピングでキューを処理する場合
  • Amazon SNS:1つのイベントを複数のキューに配る(ファンアウト)場合

5. 構築の流れ#

  1. SQSキューを作る。順序と重複排除が必要ならFIFOキュー、そうでなければ標準キューにする
  2. 可視性タイムアウトを処理時間より長くする(処理中に他の処理側が同じメッセージを受け取らないように)
  3. デッドレターキューを作り、最大受信回数を設定する(この回数失敗したメッセージをDLQへ移す)
  4. 処理側は、処理が終わったらメッセージを削除する。ロングポーリング(受信待ち時間を最大20秒)で空振りの受信を減らす
  5. 「処理側1台あたりのキューの長さ」を目標にしたターゲット追跡スケーリングで、処理側の台数を増減する。DLQのメッセージ数にはアラームを設定する

6. ポイント・注意点#

  • 受付と処理を切り離して急増を吸収する(疎結合)→ SQS。
  • 同じメッセージが二重に処理される → 可視性タイムアウトが処理時間より短い。標準キューは「少なくとも1回」の配信なので、処理側は同じメッセージが来ても問題ないように作る。
  • 何度も失敗する「毒メッセージ」でキューが詰まる → デッドレターキュー。原因を直したらDLQの再処理(redrive)で元のキューに戻す。
  • メッセージの保持期間は既定4日・最大14日。処理側が長く止まる場合も考えて設定する。
  • スケーリングの指標は、キューの長さそのものより「1台あたりのバックログ」が適している。
信頼性・事業継続

キャッシュでDBの読み取り負荷を下げる

1. やりたいこと#

  • セール中は同じ商品情報を何度もDBから読むため、RDSのCPUが上がって遅くなる。
  • DBを大きくせずに、よく読まれるデータをキャッシュしたい。
  • 画像などの静的なファイルは、利用者の近くから返したい。

3. 構成図#

静的なコンテンツはCloudFrontで、くり返し読まれるデータはElastiCacheで返し、DBにはキャッシュにないときだけ読みに行きます。ElastiCacheの Evictions が多いときはメモリ不足なので、ノードを大きくするかシャードを増やします。

4. 使うサービスと役割#

  • Amazon ElastiCache:インメモリのキャッシュ(Valkey・Redis OSS・Memcached)
  • Amazon CloudFront:画像・静的ファイル・キャッシュできるAPIの応答をエッジで返す
  • Amazon RDS:元のデータ(キャッシュの裏側)。読み取りの分散にはリードレプリカも使える
  • Amazon CloudWatch:キャッシュのヒット率(CacheHitRate)・メモリ・追い出し(Evictions)の監視

5. 構築の流れ#

  1. ElastiCacheをアプリと同じVPCのプライベートサブネットに作成する。止まると困るならレプリカを置いてMulti-AZ・自動フェイルオーバーを有効にする(Valkey・Redis OSS)
  2. アプリに、キャッシュを先に読み、なければDBから読んでキャッシュに入れる処理(遅延読み込み)を実装する
  3. データの古さをどこまで許すかで TTL(有効期限)を決める。更新が多いデータは、DBへの書き込み時にキャッシュも更新する(ライトスルー)
  4. CloudFrontのキャッシュポリシーで、静的ファイルとキャッシュ可能なAPIの応答をエッジに置く
  5. ヒット率・追い出しの回数を監視し、ノードのサイズやTTLを調整する

6. ポイント・注意点#

  • 「同じデータの繰り返しの読み取りでDBが重い」→ ElastiCache。静的コンテンツ・地理的に分散した利用者 → CloudFront。
  • 遅延読み込みは必要なデータだけキャッシュするが、初回は必ずミスし、データが古くなりうる。ライトスルーは常に新しいが、使われないデータもキャッシュする。
  • Evictions が多い → メモリ不足。ノードを大きくするか、シャードを増やす。
  • ElastiCacheを増やすのは読み取りの対策。書き込みが多い場合は、DBのスケールアップやDynamoDBなどの検討が必要。
  • DynamoDBの読み取りをマイクロ秒にしたいなら DAX。
信頼性・事業継続

データベースの高可用性と読み取り分散

1. やりたいこと#

  • DBのAZの障害に備えて、自動で切り替えたい。
  • レポート作成などの重い読み取りを、本番の書き込みと分けたい。
  • Lambdaからの大量の接続にも耐えたい。

3. 構成図#

障害対策はMulti-AZ、読み取りの分散はリードレプリカ、接続の急増はRDS Proxyと、目的ごとに使い分けます。さらに高い可用性が必要ならAurora(3つのAZに6つのコピー)を検討します(高可用性とスケーリング)。

4. 使うサービスと役割#

  • Amazon RDS:Multi-AZ(障害対策)、リードレプリカ(読み取り分散)、自動バックアップ
  • RDS Proxy:大量の接続を少数のDB接続に集約・再利用する(フェイルオーバー時間の短縮にも有効)
  • AWS Secrets Manager:DBの認証情報の管理
  • Amazon CloudWatch:DatabaseConnections・FreeStorageSpace・CPUUtilization の監視

5. 構築の流れ#

  1. RDSインスタンスをMulti-AZで作成する(既存のインスタンスは変更で有効化できる)
  2. 読み取り用にリードレプリカを作成し、レポート処理などの接続先をレプリカにする
  3. RDS Proxyを作成し、アプリの書き込みの接続先をProxyのエンドポイントにする
  4. 自動バックアップの保持期間を設定する(最大35日)。それ以上残すものは手動スナップショット
  5. CloudWatchで接続数・空き容量のアラームを設定する

6. ポイント・注意点#

  • Multi-AZのスタンバイは読み取りに使えない。読み取り性能を上げるのはリードレプリカ。
  • リードレプリカは非同期なので、わずかに遅延がある(最新データが必要な処理はプライマリへ)。
  • フェイルオーバーしてもエンドポイント名は変わらないため、アプリの接続先を変える必要はない。
  • 接続数の枯渇(DatabaseConnections の上昇)→ RDS Proxy。
  • さらに高い可用性や読み取り性能が必要ならAurora(3AZに6コピー、最大15レプリカ)を検討する。

信頼性・事業継続

1つのAZの障害からアプリを切り離す

1. やりたいこと#

  • ALB+Auto Scalingで、3つのAZにまたがるWebアプリを動かしている。
  • あるAZだけで、ヘルスチェックは通るのにエラーや遅延が増える(部分的な障害)。
  • そのAZを一時的に切り離し、残りのAZで処理を続けたい。

3. 構成図#

ヘルスチェックで分からない部分的な障害は、ARCのゾーンシフトで人の判断で切り離し、AWSに任せるならゾーンオートシフトを有効にします。リージョン全体の障害への備えは、マルチリージョンの構成で行います(DR戦略)。

4. 使うサービスと役割#

  • Amazon Application Recovery Controller(ARC):ゾーンシフト(手動・一時的)、ゾーンオートシフト(AWSが自動で実行)
  • Elastic Load Balancing:複数AZへの振り分けとヘルスチェック
  • Amazon EC2 Auto Scaling:複数AZへのインスタンスの配置と台数の維持
  • Amazon CloudWatch:AZ別のエラー率・レイテンシーの監視

5. 構築の流れ#

  1. アプリを3つ以上のAZに配置し、1つのAZが使えなくても残りで処理できる台数(静的安定性)を確保する
  2. CloudWatchで、ALBのメトリクスをAZ別に見て、特定のAZだけエラーや遅延が多くないかを監視する
  3. ALBとAuto ScalingグループをARCのゾーンシフトの対象として有効にする
  4. 特定のAZの問題が分かったら、そのAZへのゾーンシフトを開始する(有効期限を指定。最長3日で延長可)。問題が解消したら終了する
  5. AWS側の障害に自動で対応させたい場合はゾーンオートシフトを有効にし、定期的に行われる練習の実行で問題がないことを確認する

6. ポイント・注意点#

  • 1つのAZの障害から通信を一時的に移す → ゾーンシフト。AWSの判断で自動で → ゾーンオートシフト。
  • ゾーンシフトは一時的な措置。期限が切れるか終了すると元に戻る。
  • 切り離した後も処理できるよう、残りのAZに事前に容量の余裕を持たせておく(障害時にスケールアウトが間に合うとは限らない)。
  • ヘルスチェックで分からない部分的な障害も、ゾーンシフトなら人の判断で切り離せる。
  • リージョン全体の障害への備えは、マルチリージョン構成とRoute 53・ARCのリージョンスイッチで行う。

DynamoDBを負荷に合わせてスケールし、誤操作から復旧する

1. やりたいこと#

  • アクセスの急増時に、DynamoDBでスロットリングが出る。
  • 負荷に合わせて容量が自動で増減するようにしたい。
  • バグで大量のデータを上書きしたときに、直前の状態に戻したい。

3. 構成図#

急増にはオンデマンドモード、または自動スケーリングで容量を保ちます。特定のキーにアクセスが集中すると、全体の容量に余裕があってもスロットリングするので、キーの設計も見直します。誤った上書きにはPITRで新しいテーブルに復元し、アプリの接続先を切り替えます(スロットリングとリトライ)。

4. 使うサービスと役割#

  • Amazon DynamoDB:キャパシティモード(オンデマンド/プロビジョンド)、自動スケーリング、PITR、オンデマンドバックアップ、グローバルテーブル
  • Amazon CloudWatch:ThrottledRequests・消費キャパシティの監視
  • AWS Backup:バックアップの一元管理・別リージョン/アカウントへのコピー

5. 構築の流れ#

  1. アクセスが予測できない・急増する → オンデマンドモードにする。予測できて安定している → プロビジョンドモード+自動スケーリング(目標の使用率を設定)
  2. グローバルセカンダリインデックス(GSI)にも容量の設定が必要。GSIのスロットリングは元のテーブルへの書き込みも止める
  3. 特定のキーにアクセスが集中しないよう、パーティションキーを分散させる。アプリ側はエクスポネンシャルバックオフで再試行する(AWS SDKは自動)
  4. テーブルのポイントインタイムリカバリ(PITR)を有効にする。長期保管が必要ならAWS Backupでもバックアップを取る
  5. リージョン障害にも備えるなら、グローバルテーブルで別リージョンにレプリカを置く

6. ポイント・注意点#

  • 予測できない急増 → オンデマンドモード。自動スケーリングは反応に数分かかり、瞬間的な急増には間に合わないことがある。
  • 特定のキーにアクセスが集中する(ホットパーティション)と、全体の容量に余裕があってもスロットリングする。
  • PITRの復元先は新しいテーブル。復元後にアプリの接続先を切り替えるか、データを戻す。自動スケーリングの設定・IAMポリシー・アラームなどは引き継がれない。
  • PITRは過去35日以内(設定で1〜35日)の秒単位の時点に戻せる。
  • 読み取りの高速化・負荷の軽減 → DAX。マルチリージョンでの読み書き・リージョン障害への備え → グローバルテーブル。

信頼性・事業継続

誤操作したRDSのデータを特定の時点に戻す

1. やりたいこと#

  • 14時05分に、誤ってテーブルのデータを削除してしまった。
  • 14時04分の状態に戻して、業務を再開したい。
  • リージョンの障害にも備えて、別のリージョンにもバックアップを置きたい。

3. 構成図#

自動バックアップのPITRで、14時04分の状態の新しいDBインスタンスを作り、アプリの接続先を切り替えます。リージョンの障害への備えには、スナップショットのリージョン間コピーや、自動バックアップのリージョン間レプリケーションを使います(DR戦略)。

4. 使うサービスと役割#

  • Amazon RDS:自動バックアップ(保持期間1〜35日)、PITR、手動スナップショット、自動バックアップのリージョン間レプリケーション
  • Amazon Aurora:バックトラック(Aurora MySQL。同じクラスターを数秒〜数分で過去に巻き戻す)
  • AWS Backup:バックアップの一元管理・別アカウントへのコピー
  • Amazon Route 53:アプリの接続先をCNAMEで切り替えやすくする

5. 構築の流れ#

  1. (事前)自動バックアップの保持期間を要件に合わせて設定する(0にすると無効)。長期保管は手動スナップショットかAWS Backupで行う
  2. 誤操作が起きたら、コンソールの「特定時点への復元」で、誤操作の直前の時刻を指定して新しいDBインスタンスを作る(最新の復元可能時刻は通常、現在の約5分前)
  3. 復元したDBに、元と同じセキュリティグループ・パラメータグループ・オプショングループが付いているかを確認する
  4. アプリの接続先を新しいエンドポイントに変える。または、元のインスタンスと新しいインスタンスの名前を入れ替えてエンドポイントを引き継ぐ
  5. 問題がなければ元のインスタンスを削除する(必要なら最終スナップショットを取る)

6. ポイント・注意点#

  • 特定の時刻に戻す → PITR。復元先は新しいDBインスタンス(エンドポイントが変わる)。
  • スナップショットからの復元も同じく新しいインスタンスになる。元のインスタンスが上書きされることはない。
  • Aurora MySQLで、新しいクラスターを作らずにすばやく戻す → バックトラック(最大72時間)。
  • 自動バックアップはDBインスタンスを削除すると既定で消える。手動スナップショットは削除するまで残る。
  • リージョン障害への備え → スナップショットのリージョン間コピーや、自動バックアップのリージョン間レプリケーション。
信頼性・事業継続

S3のデータを誤削除やリージョン障害から守る

1. やりたいこと#

  • 誤って上書き・削除しても、元に戻せるようにしたい。
  • リージョンの障害に備えて、別のリージョンにもコピーを置きたい。
  • 一定期間は誰も消せないようにしたい。古いバージョンの費用も抑えたい。

3. 構成図#

バージョニングで上書き・削除を戻せるようにし、クロスリージョンレプリケーションで別リージョンにコピーします。コピー先にはObject Lockで消せない期間を設け、古いバージョンはライフサイクルルールで整理します。特別な権限があれば解除できるようにしたいときは、Object Lockのガバナンスモードを使います。

4. 使うサービスと役割#

  • Amazon S3:バージョニング、レプリケーション(CRR/SRR)、Object Lock、ライフサイクルルール、MFA Delete
  • AWS IAM:レプリケーション用のIAMロール
  • AWS KMS:暗号化されたオブジェクトのレプリケーション
  • AWS Backup:S3のバックアップ(特定時点への復元)

5. 構築の流れ#

  1. コピー元・コピー先の両方のバケットでバージョニングを有効にする(レプリケーションの前提)
  2. レプリケーションルールを作り、コピー先のバケットとIAMロールを指定する。必要ならS3 Replication Time Control(15分以内の複製を目標)を有効にする
  3. 既にあるオブジェクトもコピーするなら、S3バッチレプリケーションを実行する(ルールの作成後に追加されたものだけが自動で複製される)
  4. 改ざん・削除を防ぐ必要があるバケットは、Object Lock(コンプライアンスモード/ガバナンスモード)と保持期間を設定する
  5. ライフサイクルルールで、古いバージョン(非現行バージョン)を一定日数後に安いストレージクラスへ移す・削除する

6. ポイント・注意点#

  • 誤削除・上書きからの復旧 → バージョニング。削除は「削除マーカー」が付くだけなので、マーカーを消すと元に戻る。
  • レプリケーションには両方のバケットのバージョニングが必要。既存のオブジェクトはバッチレプリケーションで複製する。
  • 既定では削除マーカーは複製されない(ルールで有効にできる)。バージョンIDを指定した削除は複製されないので、コピー元での悪意ある削除からは守られる。
  • 誰も(rootユーザーも)消せないようにする → Object Lockのコンプライアンスモード。特別な権限があれば解除できる → ガバナンスモード。
  • バージョニングを有効にすると旧バージョンにも料金がかかる → 非現行バージョンのライフサイクルルールで整理する。

バックアップを一元管理して別リージョンに保管する

1. やりたいこと#

  • EC2・EBS・RDS・EFSのバックアップを、サービスごとではなく一元管理したい。
  • 新しく作ったリソースも、自動で対象にしたい。
  • リージョンの障害に備えて、別のリージョンにもコピーを残したい。

3. 構成図#

AWS Backupのバックアッププランで、タグの付いたリソースを毎日バックアップし、別リージョンのボールトにコピーします。Organizationsのバックアップポリシーを使うと、組織の全アカウントに同じプランを適用できます。これはDR戦略の「バックアップと復元」にあたります(DR戦略)。

4. 使うサービスと役割#

  • AWS Backup:バックアッププラン(スケジュール・保持期間・コピー先)、リソースの割り当て(タグ/ARN)、ボールト
  • AWS Organizations:組織全体にバックアップポリシーを適用する
  • AWS KMS:バックアップの暗号化

5. 構築の流れ#

  1. バックアップボールトを作成する(コピー先のリージョンにも作成)
  2. バックアッププランを作成し、スケジュール・バックアップウィンドウ・保持期間・ライフサイクルを設定する
  3. プランのコピー先に、別リージョンのボールトを指定する
  4. リソースの割り当てで、対象をタグ(例:Backup=daily)で指定する
  5. 定期的に復元をテストして、実際に戻せることを確認する

6. ポイント・注意点#

  • 複数サービスのバックアップを一元管理 → AWS Backup。
  • 対象をタグで指定すると、新しく作ったリソースも自動で対象になる。
  • リージョン障害への備え → 別リージョンへのコピー(DR戦略の「バックアップと復元」)。
  • バックアップを誰にも削除させたくない → ボールトロック。

1. やりたいこと#

4. 使うサービスと役割#

  • Amazon Route 53:フェイルオーバールーティングとヘルスチェック
  • Amazon Aurora:グローバルデータベースで別リージョンにレプリケート
  • Amazon S3:クロスリージョンレプリケーションで静的ファイルを複製
  • AWS CloudFormation:両リージョンに同じ構成を作る(StackSets)
  • Elastic Load Balancing/Amazon EC2:各リージョンのアプリ層

5. 構築の流れ#

  1. CloudFormationで、大阪にも同じ構成(縮小版)を作成する
  2. Auroraグローバルデータベースを作成し、大阪をセカンダリリージョンにする
  3. S3バケットはクロスリージョンレプリケーションを設定する(両方でバージョニングを有効化)
  4. Route 53でプライマリ(東京)とセカンダリ(大阪)のフェイルオーバーレコードを作り、プライマリにヘルスチェックを付ける
  5. 障害時の手順(DBの昇格、台数の拡張)をランブック化して訓練しておく

6. ポイント・注意点#

  • 復旧時間(RTO)とコストのバランスで、バックアップと復元/パイロットライト/ウォームスタンバイ/マルチサイトから選ぶ。

  • 切り替えを安全・確実に行いたい → Route 53 Application Recovery Controller(ルーティングコントロール・準備状況チェック)。

デプロイ・自動化

多数のEC2の設定やソフトウェアを一定に保つ

1. やりたいこと#

  • 数百台のEC2に、CloudWatchエージェントを入れて同じ設定にしておきたい。
  • 新しく起動したインスタンスにも自動で入り、設定が変えられても元に戻したい。
  • SSHでログインして1台ずつ作業するのはやめたい。

3. 構成図#

状態の維持はState Manager、その場の作業はRun Commandで行います。対象はインスタンスIDではなくタグで指定すると、台数が増えても設定を変えずに済みます。操作の記録はCloudTrail、コマンドの出力はS3やCloudWatch Logsに残ります。

4. 使うサービスと役割#

  • AWS Systems Manager:State Manager(状態の維持)、Run Command(一括実行)、Distributor(ソフトのパッケージ配布)、Inventory(導入済みソフトの一覧)、Parameter Store(エージェントの設定)
  • Amazon EC2:SSMエージェントとIAMロール(マネージドノードにする)
  • Amazon CloudWatch:エージェントの設定の配布先、コマンドの出力の保存先
  • Amazon S3:コマンドの出力の保存先

5. 構築の流れ#

  1. インスタンスをマネージドノードにする:SSMエージェント(主要なAMIには導入済み)と、AmazonSSMManagedInstanceCore を含むIAMロール。アカウント全体で自動化するならデフォルトのホスト管理設定(DHMC)を使う
  2. プライベートサブネットなら、SSM用のVPCエンドポイント(ssm・ssmmessages・ec2messages)かNATゲートウェイを用意する
  3. State Managerの関連付けを作る:ドキュメント(例:AWS-ConfigureAWSPackage でCloudWatchエージェントを導入)、対象(タグ)、スケジュールを指定する
  4. レート制御(同時実行数・エラーのしきい値)を設定し、一度に全台が影響を受けないようにする
  5. 実行結果をS3・CloudWatch Logsに保存し、Inventoryで導入状況を確認する。準拠状況はSystems Managerの「コンプライアンス」で見る

6. ポイント・注意点#

  • 決めた状態を維持し続ける(新しいインスタンスにも自動で適用)→ State Manager。その場で1回実行 → Run Command。
  • Systems Managerの一覧にインスタンスが出ない → SSMエージェント・IAMロール・SSMのエンドポイントへの経路のどれかが原因。
  • 対象はインスタンスIDではなくタグで指定すると、台数が増えても設定を変えずに済む。
  • レート制御で同時実行数とエラーのしきい値を決め、失敗が広がったら止める。
  • SSHやキーペアは不要。操作の記録はCloudTrail、コマンドの出力はS3・CloudWatch Logsに残る。

3. 構成図#

4. 使うサービスと役割#

  • AWS IAM:EC2のロールに AmazonSSMManagedInstanceCore を付ける
  • Amazon EC2:SSM Agentが動く管理対象ノード(オンプレミスはハイブリッドアクティベーションで登録)

5. 構築の流れ#

  2. パッチベースラインで、承認するパッチ(例:重要度Critical、リリース7日後に自動承認)を定義する
  3. EC2にタグを付けてパッチグループ(例:本番・開発)に分ける

  5. コンプライアンスの画面で、適用できなかったノードを確認する

6. ポイント・注意点#

  • EC2がSystems Managerに表示されない → SSM Agent・IAMロール・アウトバウンド通信(またはVPCエンドポイント)を確認。

  • 一度に全台へ適用せず、同時実行数とエラーのしきい値を設定して少しずつ進める。

5. 構築の流れ#

  1. コンポーネント(パッチ適用・エージェントの導入・設定)と、起動後の確認を行うテストのコンポーネントを用意する
  2. ベースイメージとコンポーネントでイメージレシピを作る。インフラストラクチャ設定にインスタンスプロファイル(SSMの権限を含む)・サブネット・ログの出力先を指定する
  3. ディストリビューション設定で、配布先のリージョン・共有先のアカウントと、更新する起動テンプレートを指定する
  4. パイプラインを作り、スケジュール(毎月など)を設定する
  5. 新しいAMIができたら、Auto Scalingグループのインスタンスの更新を開始し、最小正常率(例:90%)を保ちながら入れ替える

6. ポイント・注意点#

3. 構成図#

変更セットで影響を確かめ、重要なリソースはスタックポリシーで守り、ロールバックトリガーで異常時に戻します。DBにはDeletionPolicy・UpdateReplacePolicy(Snapshot・Retain)も付けておきます。テンプレートの書き方は「JSONとYAMLの読み方」を参照してください。

4. 使うサービスと役割#

  • AWS CloudFormation:変更セット、スタックポリシー、DeletionPolicy・UpdateReplacePolicy、終了保護、ロールバックトリガー
  • Amazon CloudWatch:ロールバックトリガーに使うアラーム
  • AWS IAM:CloudFormationが使うサービスロール、スタックを操作できる人の制限

5. 構築の流れ#

  1. 重要なリソース(RDS・S3など)に DeletionPolicy: Snapshot(または Retain)と UpdateReplacePolicy を設定する
  2. スタックポリシーで、本番DBなどの置き換え・削除を伴う更新を拒否する。スタックには終了保護を有効にする
  3. 更新は直接行わず、変更セットを作って、各リソースが変更・置換(Replacement)・削除のどれになるかを確認する
  4. エラー率などのCloudWatchアラームをロールバックトリガーに設定し、監視時間内にアラームが鳴ったら自動でロールバックさせる
  5. 変更セットを実行する。EC2の起動処理の完了を待つ必要があれば、CreationPolicy と cfn-signal を使う

6. ポイント・注意点#

  • 更新の影響を事前に確認 → 変更セット。DBの名前など、変更すると置換になるプロパティがある。
  • 特定のリソースの更新・置換を禁止 → スタックポリシー。スタックの削除を防ぐ → 終了保護。
  • スタックを消してもリソースを残す・スナップショットを取る → DeletionPolicy(Retain/Snapshot)。
  • ロールバックも失敗して UPDATE_ROLLBACK_FAILED になった → 原因を直して「更新のロールバックを続行」。必要なら問題のリソースをスキップする。
  • テンプレートの外でリソースを手で変更すると、更新が失敗する原因になる(ドリフト)。

ECSのサービスを止めずに更新し、失敗したら自動で戻す

1. やりたいこと#

  • ECS(Fargate)のアプリの新しいバージョンを、止めずにリリースしたい。

3. 構成図#

ローリング更新で、新しいタスクを起動してから古いタスクを止めます。起動の失敗はデプロイサーキットブレーカーで、エラーの増加はCloudWatchアラームで検知して自動で戻します。新旧を並べて一度に切り替えるならBlue/Greenデプロイを使います(デプロイ戦略)。

4. 使うサービスと役割#

  • Amazon ECS:ローリング更新(minimumHealthyPercent・maximumPercent)、デプロイサーキットブレーカー、Blue/Greenデプロイ
  • Amazon ECR:コンテナイメージの保存
  • Elastic Load Balancing:新しいタスクのヘルスチェックと通信の切り替え
  • Amazon CloudWatch:デプロイの失敗を判定するアラーム(5xxエラー率など)
  • AWS CodePipeline:ビルドからデプロイまでの自動化

  1. 新しいイメージをECRにプッシュし、そのイメージを使う新しいタスク定義のリビジョンを作る
  2. サービスのデプロイ設定で minimumHealthyPercent(例:100)と maximumPercent(例:200)を決める。100/200なら、台数を減らさずに新しいタスクを先に起動する
  3. デプロイサーキットブレーカーをロールバックありで有効にする(新しいタスクが起動・ヘルスチェックに失敗し続けると、デプロイを失敗とみなして戻す)
  4. 5xxエラー率などのCloudWatchアラームをデプロイの監視対象に指定し、アラームが鳴ったらロールバックするよう設定する
  5. アプリの起動に時間がかかる場合は、ヘルスチェックの猶予期間を設定する。一気に切り替えて素早く戻したい場合は、ECSのBlue/Greenデプロイを使う

6. ポイント・注意点#

  • 起動に失敗し続けるデプロイを自動で止めて戻す → デプロイサーキットブレーカー。リリース後のエラー増加で戻す → CloudWatchアラームによるロールバック。
  • minimumHealthyPercent を下げると、追加の容量なしで更新できるが、更新中の処理能力が下がる。
  • 新旧の環境を並べ、ALBの通信を一度に切り替える → Blue/Greenデプロイ。少しずつ移す → Canary・Linear。
  • 新しいタスクがすぐ止まる → 「停止したタスク」の停止理由、コンテナのログ、イメージの取得権限(タスク実行ロール)を確認する。

1. やりたいこと#

  • 開発環境のEC2とRDSを、平日の20時(日本時間)に停止し、平日の9時に起動したい。

3. 構成図#

Auto Scalingグループに属するEC2は、個別に停止してもヘルスチェックで入れ替えられてしまうので、グループのスケジュールされたアクションで台数を0にします。

4. 使うサービスと役割#

  • Amazon EventBridge:Scheduler(cron式・タイムゾーン指定)で決まった時刻に処理を起動
  • AWS Systems Manager:Automationランブック(AWS-StopEC2Instance・AWS-StartEC2Instance・AWS-StopRdsInstance など)をタグの対象に実行
  • Amazon EC2/Amazon RDS:停止・起動の対象
  • Amazon EC2 Auto Scaling:スケジュールされたアクションで希望容量を変更
  • AWS Cost Explorer:タグ別の費用で効果を確認

5. 構築の流れ#

  1. 対象のリソースにタグ(例:Schedule=office-hours)を付ける
  2. Automationの実行用IAMロール(EC2・RDSの停止・起動の権限)を作る
  3. EventBridge Schedulerで、平日20時(タイムゾーンを Asia/Tokyo に指定)に停止のランブックを、タグを対象に実行するスケジュールを作る。同様に9時の起動も作る
  4. Auto Scalingグループは、ランブックではなくスケジュールされたアクションで、夜間は最小・希望容量を0、朝に元の値へ戻す(グループ内のインスタンスを直接止めると、Auto Scalingが置き換えてしまう)
  5. Cost Explorerでタグ別の費用を確認し、効果を測る

6. ポイント・注意点#

  • EC2を停止しても、EBSボリュームとElastic IPの料金はかかる。インスタンスストアのデータは消える。

3. 構成図#

アカウントAがSTSでアカウントBのロールを引き受け、ロールの信頼ポリシーで許可されていれば一時的な認証情報が返ります。その認証情報で、ロールの権限ポリシーの範囲でS3を操作します。CloudTrailには AssumedRole として記録されます。

4. 使うサービスと役割#

  • AWS STS:有効期限付きの一時認証情報(アクセスキー、シークレットキー、セッショントークン)を発行する
  • AWS IAM:アカウントAのIDベースポリシー、アカウントBのロール(信頼ポリシー・権限ポリシー)を定義する
  • Amazon S3などのアクセス先リソース:必要に応じてリソース側のポリシー(バケットポリシーなど)も確認される
  • AWS CloudTrail:ロールを引き受けた操作が AssumedRole として記録される

5. 構築の流れ#

手順誰が何をするか確認・使用されるポリシー結果
①アカウントAのIAMユーザー/ロールSTSに sts:AssumeRole を呼び出す(BのロールのARNを指定)AのIDベースポリシー(Bのロールへの sts:AssumeRole が許可されているか)引き受けのリクエストがSTSに届く
②AWS STSBのロールの信頼ポリシーを確認するBのロールの信頼ポリシー(Principal にAが含まれるか、ExternalIdなどの条件を満たすか)引き受けの可否が判定される
③AWS STSAのプリンシパルに一時認証情報を返す(有効期限はデフォルト1時間)―アクセスキー、シークレットキー、セッショントークンを取得
④アカウントAのIAMユーザー/ロール一時認証情報を使ってBのリソースを操作するBのロールの権限ポリシー(必要に応じてリソース側のポリシーも)ロールの権限の範囲で操作できる。CloudTrailには AssumedRole として記録される

6. ポイント・注意点#

ポリシーひとことで答える問い
IDベースポリシー「自分が何をできるか」このユーザー/ロールは、どのリソースに何をしてよいか
権限ポリシー「ロールになった後に何ができるか」このロールを引き受けた人は、何をしてよいか
信頼ポリシー「誰がこのロールになれるか」このロールを引き受けてよいのは誰か
  • 信頼ポリシーは、ロールを引き受けてよい相手の一覧。例:アカウントAはOK、アカウントBのIAMユーザー tanaka はNG。
  • 権限ポリシーは、ロールで何ができるか。例:特定のS3バケットに読み書きできる。
  • AssumeRoleできないときは、Aの IDベースポリシーとBのロールの信頼ポリシーの両方を確認する。
  • アクセスキーを渡さずに済み、認証情報は自動で期限切れになるため安全。

「AccessDenied」の原因を調べ、最小権限に直す

1. やりたいこと#

  • アプリのロールにS3の権限を付けたのに、オブジェクトの取得で AccessDenied になる。

4. 使うサービスと役割#

  • AWS CloudTrail:拒否されたAPI呼び出し(errorCode: AccessDenied)と呼び出し元の記録

  • AWS Organizations:SCP・RCPによる制限の確認
  • AWS KMS:暗号化されたデータを読むためのキーポリシー

  1. CloudTrailのイベント履歴(またはAthena)で、拒否されたAPI・呼び出し元のロール・対象のリソースを特定する。エラーメッセージにどの種類のポリシーで拒否されたかが出ることもある
  2. ポリシーシミュレーターで、そのロールが該当の操作を許可されているかを確認する
  3. ポリシーの評価順に確認する:SCP・RCPに拒否はないか → 許可境界・セッションポリシーで制限されていないか → バケットポリシーに明示的なDenyはないか → SSE-KMSのキーポリシーで kms:Decrypt が許可されているか
  4. 原因のポリシーを直す。別のアカウントのリソースなら、IAMポリシーとリソースベースのポリシーの両方で許可する
  5. Access Analyzerで、CloudTrailの記録から実際に使った操作だけのポリシーを生成し、未使用の権限・ロールを見つけて削除する

6. ポイント・注意点#

  • IAMポリシーで許可しても、SCP・許可境界の範囲外なら拒否される(実際の権限は重なった部分だけ)。
  • KMSで暗号化されたS3のオブジェクトは、S3の権限に加えてKMSキーの権限が必要。
  • クロスアカウントのアクセスは、呼び出し元のIAMポリシーと、相手側のリソースベースのポリシー(またはロールの信頼ポリシー)の両方が必要。
  • 最小権限への絞り込み → Access Analyzerのポリシー生成・未使用のアクセスの検出、IAMの最終アクセス情報。

  4. ターゲットの自動処理で、インスタンスの終了保護を有効にし、EBSのスナップショットを取り、セキュリティグループを隔離用に付け替える。Auto Scalingグループからは切り離す

CloudFrontにAWS WAFのWeb ACLを関連付け、マネージドルールとレートベースルールで攻撃を止めます。DDoSはShield Standardで自動的に守られ、大規模な攻撃への支援が必要ならShield Advancedを使います。ブロックの記録はWAFのログに残します。

4. 使うサービスと役割#

  • AWS WAF:マネージドルール(SQLインジェクション・既知の悪い入力・IP評価リスト)、レートベースルール、ジオマッチ、ログ
  • AWS Shield:Standard(自動)によるL3/L4のDDoS対策、必要ならAdvanced
  • Amazon CloudFront:エッジでの受付とキャッシュ
  • Elastic Load Balancing:オリジンのALB
  • Amazon CloudWatch:ルールごとのブロック件数の監視

5. 構築の流れ#

  1. CloudFront用のWeb ACLを作る(CloudFront用はus-east-1で作成)
  2. AWSマネージドルール(コアルールセット・SQLデータベース・既知の悪い入力・Amazon IP評価リスト)を追加する
  3. ログインのパスに、IPごとのレートベースルールを追加する。必要に応じて国のジオマッチやBot Controlを加える
  4. まずは新しいルールを Count で動かし、正常な通信を誤ってブロックしていないかログで確かめてから Block にする
  5. ALBのセキュリティグループで、CloudFrontのマネージドプレフィックスリストからの通信だけを許可する(またはCloudFrontのVPCオリジンを使う)
  6. WAFのログを有効にし(ロググループ名は aws-waf-logs- で始める)、ブロック件数にアラームを設定する

6. ポイント・注意点#

  • アプリ層の攻撃(SQLi・XSS)→ WAF。同じIPからの大量アクセス → レートベースルール。
  • CloudFrontのWeb ACLはus-east-1で作る。ALB用はALBと同じリージョン。
  • WAFは NLB・EC2に直接付けられない。CloudFront・ALB・API Gatewayなどの前段に付ける。
  • オリジンに直接アクセスされるとWAFを迂回されるので、ALBへの経路をCloudFrontからだけに絞る。
  • 大規模なDDoSへの24時間の支援や費用の保護が必要 → Shield Advanced。複数アカウントへ同じルールを展開 → Firewall Manager。

1. やりたいこと#

  • チームが自由にVPCを作った結果、CIDRが重なり、つなげないVPCが出てきた。
  • これから作るVPCには、決めた範囲から重ならないCIDRを自動で割り当てたい。
  • 使用状況を1か所で把握したい。

3. 構成図#

委任管理者のアカウントでIPAMとプールを作り、RAMで本番のOUに共有します。各アカウントはVPCの作成時にプールを指定するだけで、重ならないCIDRが割り当てられます。プールの使用率はCloudWatchで監視し、枯渇の前に範囲を追加します。

4. 使うサービスと役割#

  • Amazon VPC IP Address Manager(IPAM):プールの階層、割り当てルール、使用状況・重複の監視
  • AWS Organizations:IPAMの委任管理者、組織全体のリソースの検出
  • AWS RAM:プールの共有
  • AWS CloudFormation:VPCのテンプレートでIPAMプールを指定(StackSetsで各アカウントへ展開)
  • Amazon CloudWatch:プールの使用率のアラーム

5. 構築の流れ#

  1. Organizationsの管理アカウントで、IPAMの委任管理者アカウントを指定する(高度なティアを使う)
  2. 委任管理者でIPAMを作り、管理するリージョンを指定する。最上位のプール(例:10.0.0.0/8)の下に、リージョン・環境ごとのプールを作る
  3. 各プールに割り当てルール(CIDRのサイズの最小・最大・既定、必須のタグ)を設定する
  4. RAMで、プールを対象のOU・アカウントに共有する
  5. 各アカウントでは、VPCの作成時(またはCloudFormationの Ipv4IpamPoolId)にプールとネットマスクを指定する。既存のVPCの重複や非準拠は、IPAMのリソースの一覧で確認する

6. ポイント・注意点#

  • 組織全体のVPCのCIDRの重複を防ぐ・一元管理する → IPAM。他のアカウントへのプールの共有 → RAM。
  • CIDRが重なったVPCどうしは、ピアリングやTransit Gatewayで正しくルーティングできない。後から直すのは大変なので、作る前に計画する。
  • プールの使用率をCloudWatchで監視し、枯渇の前にCIDRを追加する。
  • VPCのCIDRは後から追加(セカンダリCIDR)できるが、元のCIDRは変更できない。
  • プライベートのプールや他のアカウントへの割り当てには、IPAMの高度なティアが必要。

プライベートサブネットからNATなしでAWSのサービスを使う

1. やりたいこと#

  • プライベートサブネットのEC2から、S3のオブジェクトを読み書きしたい。
  • 同じEC2に、Session Managerで接続して操作したい。
  • 費用とインターネットへの経路をなくすため、NATゲートウェイは使わない。

3. 構成図#

S3へは無料のゲートウェイ型エンドポイントをルートテーブルに関連付け、Systems Managerへはインターフェイス型エンドポイントを作ってセキュリティグループで443を許可し、プライベートDNS名を有効にします。EC2には AmazonSSMManagedInstanceCore を付けたIAMロールが必要です。

2種類のエンドポイントの違いは「VPCエンドポイント」、NATゲートウェイとの費用の比較は「料金の基本」で説明しています。

4. 使うサービスと役割#

  • Amazon VPC:VPCエンドポイント(ゲートウェイ型・インターフェイス型)、エンドポイントポリシー、ルートテーブル
  • Amazon S3:バケットポリシーで、特定のVPCエンドポイント経由のアクセスだけを許可(aws:SourceVpce)
  • AWS Systems Manager/AWS Secrets Manager:インターフェイス型エンドポイントの接続先
  • AWS Cost Explorer:NATゲートウェイのデータ処理料金の削減効果の確認

5. 構築の流れ#

  1. S3のゲートウェイ型エンドポイントを作り、プライベートサブネットのルートテーブルに関連付ける
  2. SSMには ssm・ssmmessages・ec2messages、Secrets Managerには secretsmanager のインターフェイス型エンドポイントを、各AZのサブネットに作る
  3. インターフェイス型エンドポイントのセキュリティグループで、VPC内からのHTTPS(443番)を許可する。VPCの「DNS解決」「DNSホスト名」を有効にし、プライベートDNSを有効にする
  4. エンドポイントポリシーで、使ってよいバケットだけに絞る。バケット側でも aws:SourceVpce の条件で、エンドポイント経由以外を拒否する
  5. NATゲートウェイを通る通信が減ったことを、フローログやCost Explorerで確認する

6. ポイント・注意点#

  • S3・DynamoDB → ゲートウェイ型(無料、ルートテーブルで経路を追加)。その他のサービス → インターフェイス型(PrivateLink、時間とデータ量の料金)。
  • ゲートウェイ型はオンプレミスやピアリング先のVPCからは使えない。オンプレミスからS3に私的に接続するならS3のインターフェイス型エンドポイントを使う。
  • インターフェイス型で名前解決がエンドポイントに向かない → VPCのDNS設定とプライベートDNSの有効化を確認する。
  • 大量のS3の通信をNAT経由にしていると、NATゲートウェイのデータ処理料金がかさむ。
  • ゲートウェイ型エンドポイントは同じリージョンのS3にだけ使える。

3. 構成図#

4. 使うサービスと役割#

  • Amazon VPC:インターネットに出られないサブネットから、インターフェイス型エンドポイント(ssm・ssmmessages・ec2messages)でSystems Managerに接続する
  • AWS IAM:EC2のロール(AmazonSSMManagedInstanceCore)と、利用者が接続できる範囲の制御

  • AWS CloudTrail:セッションの開始・終了の記録

5. 構築の流れ#

  1. EC2のIAMロールに AmazonSSMManagedInstanceCore を付け、SSM Agentが動いていることを確認する
  2. プライベートサブネットに、ssm・ssmmessages・ec2messages のインターフェイス型VPCエンドポイントを作成する(エンドポイントのSGで443番を許可)
  3. EC2のセキュリティグループから22番ポートのインバウンドルールを削除する
  4. Session Managerの設定で、操作ログの保存先(S3・CloudWatch Logs)を指定する

6. ポイント・注意点#

  • ポートフォワーディングで、手元のPCからプライベートなRDSなどに接続することもできる。

外向きの通信を許可したドメインだけに制限する

1. やりたいこと#

  • プライベートサブネットのサーバーが、NAT経由でインターネットのどこにでもつながってしまう。
  • OSのアップデートなど、必要なドメインだけに外向きの通信を絞りたい。
  • 不正なドメインは、名前解決の段階でも止めたい。

3. 構成図#

DNS Firewallで不正なドメインの名前解決を止め、Network Firewallで許可したドメイン以外への通信を止めます。インスタンスが外部のDNSサーバーを直接使うとDNS Firewallを迂回されるので、53番の外向きの通信もファイアウォールで止めます。エンドポイントはAZごとに置きます(アウトバウンド通信)。

4. 使うサービスと役割#

  • AWS Network Firewall:ステートフルルールのドメインリスト(TLSのSNI・HTTPのHostヘッダーで判定)で許可リスト方式の制限
  • Route 53 Resolver DNS Firewall:AWS管理のドメインリストで、マルウェアなどのドメインの名前解決をブロック
  • Amazon VPC:ファイアウォール用サブネットとルートテーブル、NATゲートウェイ
  • Amazon CloudWatch:ファイアウォールのアラートログ・Resolverクエリログの保存と検索
  • Amazon GuardDuty:不審な通信の検出

5. 構築の流れ#

  1. 各AZにファイアウォール用のサブネットを作り、Network Firewallのエンドポイントを置く
  2. ルートテーブルを設定する:ワークロード → NATゲートウェイ → ファイアウォールエンドポイント → インターネットゲートウェイの順に通り、戻りの通信もファイアウォールを通るようにする
  3. ステートフルルールグループに、許可するドメイン(例:.amazonaws.com、OSのリポジトリ)の許可リストを作り、それ以外を拒否する
  4. DNS FirewallのルールグループにAWS管理のドメインリスト(マルウェア・ボットネット)をブロックとして設定し、VPCに関連付ける
  5. アラートログとResolverクエリログをCloudWatch Logsに出し、ブロックされた通信を確認しながら許可リストを調整する

6. ポイント・注意点#

  • ドメイン名で外向きの通信を絞る、IDS/IPS → Network Firewall。DNSの問い合わせの段階で止める → DNS Firewall。
  • Network Firewallは、ルートテーブルで通信をエンドポイントに通さないと検査されない。行きと戻りの経路を対称にする。
  • セキュリティグループ・ネットワークACLはIPアドレスとポートでしか制御できず、ドメイン名では絞れない。
  • DNS Firewallは、インスタンスが外部のDNSサーバーを直接使うと迂回される。53番ポートの外向き通信もファイアウォールで止める。
  • ファイアウォールのエンドポイントはAZごとに置き、そのAZのサブネットの通信は同じAZのエンドポイントを通す。

複数のVPCとオンプレミスを接続する

1. やりたいこと#

  • 複数のVPCとオンプレミスを、インターネットを経由せずにプライベートIPで相互に通信させたい。
  • VPCが今後増えても、接続の管理が複雑にならないようにしたい。

3. 構成図#

Transit Gatewayをハブにして、各VPCと、オンプレミスとのVPN・Direct Connectをつなぎます。CIDRが重なっていると正しく通信できないので、最初にアドレスを設計します(CIDR)。通信できないときは、双方のルートテーブルに相手のCIDRへの経路があるかを確認します。

4. 使うサービスと役割#

  • AWS Transit Gateway:多数のVPC・オンプレミスをハブ&スポークで接続する(インバウンド通信参照)
  • AWS Site-to-Site VPN/AWS Direct Connect:オンプレミスとの接続(VPNはインターネット上を暗号化、DXは専用線)
  • Amazon VPC:各VPCのルートテーブルに、相手のCIDR向けの経路を追加する
  • AWS Resource Access Manager:Transit Gatewayを組織内の他アカウントと共有する

5. 構築の流れ#

  1. 各VPC・オンプレミスのCIDRが重複していないことを確認する
  2. Transit Gatewayを作成し、各VPCをアタッチする(別アカウントのVPCはRAMで共有してからアタッチ)
  3. オンプレミスとSite-to-Site VPN(またはDirect Connect)で接続し、Transit Gatewayにアタッチする
  4. 各VPCのサブネットのルートテーブルに、他のVPC・オンプレミスのCIDR → Transit Gateway のルートを追加する
  5. セキュリティグループ・NACLで、必要な通信だけを許可する

6. ポイント・注意点#

  • VPCピアリングは1対1で推移的なルーティングができない。VPCが多いならTransit Gateway。
  • CIDRが重複していると接続できない。最初にアドレス設計をしておく。
  • 通信できないときは、双方のルートテーブルに相手側CIDRの経路があるかを確認する。
  • 暗号化が必要で帯域・安定性も欲しい場合は、Direct Connectの上でVPNを使う構成もある。

オンプレミスとVPCで互いの名前を解決する

1. やりたいこと#

  • Direct ConnectでオンプレミスとVPCをつないでいる。
  • VPCのEC2から、社内のDNSの corp.example.com を引きたい。
  • オンプレミスから、VPCのプライベートホストゾーンの aws.example.com を引きたい。

3. 構成図#

VPCからオンプレミスへはアウトバウンドエンドポイントと転送ルール、オンプレミスからVPCへはインバウンドエンドポイントを使います。エンドポイントは複数のAZに置いて冗長にし、転送ルールはRAMでほかのアカウントと共有できます。

4. 使うサービスと役割#

  • Amazon Route 53:Resolver(VPCのDNS)、インバウンド/アウトバウンドエンドポイント、転送ルール、プライベートホストゾーン
  • AWS Direct Connect/AWS Site-to-Site VPN:DNSの問い合わせが通る経路
  • AWS RAM:転送ルールを他のアカウントと共有
  • Amazon VPC:エンドポイントを置くサブネットとセキュリティグループ

5. 構築の流れ#

  1. 2つ以上のAZのサブネットに、アウトバウンドエンドポイントとインバウンドエンドポイントを作る。セキュリティグループでDNS(TCP/UDP 53番)を許可する
  2. アウトバウンド:corp.example.com を社内のDNSサーバーのIPアドレスに転送する転送ルールを作り、VPCに関連付ける
  3. インバウンド:社内のDNSサーバーに、aws.example.com をインバウンドエンドポイントのIPアドレスへ送る条件付き転送を設定する
  4. プライベートホストゾーン aws.example.com をVPCに関連付ける
  5. 複数のアカウントのVPCで同じルールを使うなら、RAMで転送ルールを共有し、各VPCに関連付ける

6. ポイント・注意点#

  • VPC → オンプレミスの名前解決 → アウトバウンドエンドポイント+転送ルール。
  • オンプレミス → VPC(プライベートホストゾーン)の名前解決 → インバウンドエンドポイント。
  • VPCのResolver(VPCのCIDR+2のアドレス)には、オンプレミスから直接問い合わせできない。だからインバウンドエンドポイントが必要。
  • VPCの「DNS解決」「DNSホスト名」の設定を有効にしておく。
  • エンドポイントは複数のAZに置いて冗長化する。オンプレミス側のファイアウォールでも53番ポートを許可する。

社員の端末からVPCの社内システムに安全に接続する

1. やりたいこと#

  • 自宅のPCから、VPCの社内システムとオンプレミスのファイルサーバーを使いたい。
  • ログインは社内のIDでシングルサインオンにし、部署ごとにアクセスできる宛先を分けたい。
  • インターネットの閲覧まで、すべてVPN経由にはしたくない。

3. 構成図#

Client VPNのエンドポイントで、社内のIdPによるSAML認証と、部署ごとの認可ルールを設定します。スプリットトンネルで、必要な通信だけをVPN経由にします。クライアントCIDRは接続先のネットワークと重ならないようにし(作成後は変更できない)、可用性のため2つのAZに関連付けます。

4. 使うサービスと役割#

  • AWS Client VPN:エンドポイント、SAML認証、認可ルール、ルートテーブル、スプリットトンネル、接続ログ
  • AWS Certificate Manager:エンドポイントのサーバー証明書
  • AWS IAM Identity Center:SAMLのIdP(外部のIdPでもよい)
  • AWS Transit Gateway/AWS Site-to-Site VPN:VPCからオンプレミスへの経路
  • Amazon CloudWatch:接続ログ

5. 構築の流れ#

  1. サーバー証明書をACMに用意し、IdPとSAMLで連携するためのIAMのSAMLプロバイダーを作る
  2. Client VPNエンドポイントを作る:クライアントCIDR(VPCやオンプレミスと重ならない範囲)、認証方法(SAML)、接続ログ、スプリットトンネルを設定する
  3. 2つのAZのサブネットをターゲットネットワークとして関連付け、エンドポイントにセキュリティグループを付ける
  4. 認可ルールで、IdPのグループごとにアクセスできる宛先のCIDRを決める(例:経理グループ → 経理システムのサブネット)
  5. オンプレミス宛ての経路をエンドポイントのルートテーブルに追加し、VPC側のルートテーブル・セキュリティグループでもクライアントからの通信を許可する

6. ポイント・注意点#

  • 社員の端末からのリモートアクセス → Client VPN。拠点どうしの接続 → Site-to-Site VPN。
  • VPN以外の通信までVPN経由になる → スプリットトンネルを有効にする。
  • 接続はできるのに目的のサーバーに届かない → 認可ルール、エンドポイントのルートテーブル、宛先側のセキュリティグループ・ルートの順に確認する。
  • クライアントCIDRは、接続先のネットワークと重ならないようにする(作成後は変更できない)。
  • 関連付けたサブネットの数と接続時間で料金がかかる。可用性のため2つのAZに関連付ける。

利用者の場所や割合でアクセスを振り分ける

1. やりたいこと#

  • 東京とバージニア北部の2リージョンで動かしている。利用者を応答の速いほうへ振り分けたい。
  • 片方が落ちたら、もう片方だけに送りたい。
  • 新しいバージョンの環境に、まず通信の10%だけを流したい。

3. 構成図#

レイテンシーベースルーティングとヘルスチェックで、速いほうへ振り分けつつ、異常なリージョンを自動で外します。割合で分けたいときは加重ルーティングを使います。DNSのTTLとヘルスチェックの間隔の分だけ切り替えに時間がかかるので、すぐに切り替えたい場合はGlobal Acceleratorも候補です。

4. 使うサービスと役割#

  • Amazon Route 53:ルーティングポリシー(シンプル・加重・レイテンシー・フェイルオーバー・位置情報・地理的近接性・複数値回答・IPベース)、ヘルスチェック、エイリアスレコード
  • Elastic Load Balancing:各リージョンの入り口
  • Amazon CloudWatch:ヘルスチェックの状態のアラーム(us-east-1)
  • AWS Global Accelerator:DNSのキャッシュに左右されない切り替えが必要な場合

5. 構築の流れ#

  1. 各リージョンのALBを指すエイリアスレコードを、同じ名前で2つ作り、ルーティングポリシーを「レイテンシー」にしてリージョンを指定する
  2. エイリアスレコードでは「ターゲットのヘルスを評価」を有効にする(ALBの背後のターゲットの状態を見る)。独自の確認先があればヘルスチェックを作って関連付ける
  3. 新バージョンの試験導入は、加重ルーティングで旧環境90・新環境10の重みを付けて作り、問題がなければ重みを変えていく
  4. 国ごとにコンテンツを変える・特定の国からのアクセスだけを特定のリージョンに送る必要があれば、位置情報ルーティングを使い、どこにも一致しない場合の「デフォルト」レコードも作る
  5. TTLを短めにして、切り替えが早く反映されるようにする

6. ポイント・注意点#

  • 速い方へ → レイテンシー。割合で分ける → 加重。国・地域で決める → 位置情報。正常時はプライマリ、障害時だけセカンダリ → フェイルオーバー。
  • 位置情報ルーティングは、一致しない場所からの問い合わせに応答しない。デフォルトのレコードを作っておく。
  • AWSリソース(ALB・CloudFront・S3など)を指すならエイリアスレコード(ゾーンの頂点にも作れ、問い合わせ料金がかからない)。
  • ヘルスチェックの判定から切り替えまで、DNSのTTLとヘルスチェックの間隔・しきい値の分だけ時間がかかる。
  • プライベートなリソースは、Route 53のヘルスチェック(インターネットから確認)では直接確認できない。CloudWatchアラームの状態に基づくヘルスチェックを使う。

静的サイトを独自ドメイン・HTTPSで安全に配信する

1. やりたいこと#

  • 会社のWebサイト(静的ファイル)を、独自ドメインとHTTPSで世界中に高速配信したい。
  • S3バケットは公開せず、CloudFront経由のアクセスだけを許可したい。

3. 構成図#

Route 53のエイリアスレコードで独自ドメインをCloudFrontに向け、us-east-1のACM証明書でHTTPSにします。S3はOACでCloudFrontからのアクセスだけを許可し、ビューワープロトコルポリシーでHTTPをHTTPSにリダイレクトします。

4. 使うサービスと役割#

  • Amazon S3:静的ファイルの保存先(オリジン)
  • Amazon CloudFront:エッジでキャッシュして高速配信、OACでS3へアクセス
  • AWS Certificate Manager:独自ドメインの証明書(CloudFront用はus-east-1)
  • Amazon Route 53:独自ドメインをCloudFrontに向ける(エイリアスレコード)

5. 構築の流れ#

  1. S3バケットにファイルを置き、ブロックパブリックアクセスを有効にしたままにする
  2. us-east-1のACMで独自ドメインの証明書を発行する
  3. CloudFrontのディストリビューションを作成し、オリジンにS3、OACを設定する。代替ドメイン名と証明書を指定し、Viewer Protocol PolicyでHTTPSにリダイレクトする
  4. S3のバケットポリシーで、そのディストリビューション(OAC)からの読み取りだけを許可する
  5. Route 53でドメインをCloudFrontに向けるエイリアスレコードを作成する

6. ポイント・注意点#

  • S3への直接アクセスを禁止 → OAC。
  • CloudFrontで使うACM証明書はus-east-1で発行する。
  • 利用者側をHTTPSに強制 → Viewer Protocol Policy。
  • ファイルを更新してもキャッシュが残って古い内容が表示される → キャッシュの無効化(インバリデーション)を実行するか、TTLを短くする。

ネットワーク・コンテンツ配信

EC2に接続できない原因を調査する

1. やりたいこと#

  • インターネットからEC2のWebサーバーにアクセスできない。
  • どこで通信が止まっているかを、記録と解析で特定したい。

3. 構成図#

ルートテーブル → インターネットゲートウェイ → セキュリティグループ → ネットワークACL → パブリックIPの順に確認し、VPCフローログのREJECTをLogs Insightsで検索して止まっている場所を絞り込みます。設定上の経路はReachability Analyzerで自動で解析できます。

4. 使うサービスと役割#

  • Amazon VPC:ルートテーブル、IGW、セキュリティグループ、ネットワークACL、VPCフローログ
  • Amazon CloudWatch:フローログの保存とLogs Insightsでの検索
  • Amazon EC2:ステータスチェック、パブリックIPの確認
  • AWS CloudTrail:最近SGやルートテーブルを変更した人を調べる

5. 構築の流れ(調査手順)#

  1. ルートテーブル:サブネットに 0.0.0.0/0 → IGW の経路があるか(ルートテーブル)
  2. IGW/NAT:IGWがVPCにアタッチされているか、NATゲートウェイが正常か
  3. セキュリティグループ:80/443番のインバウンドが許可されているか
  4. ネットワークACL:インバウンドに加えて、戻りのアウトバウンド(エフェメラルポート)も許可されているか
  5. パブリックIP:EC2にパブリックIPまたはElastic IPが割り当てられているか
  6. VPCフローログを有効にし、Logs Insightsで REJECT の記録を確認する

6. ポイント・注意点#

  • SGはステートフルで戻りの通信は自動で許可。NACLはステートレスで戻りの通信も許可が必要(NACLとSG)。
  • ルートテーブルは経路を決めるだけで、許可・拒否はしない。
  • フローログで、インバウンドがACCEPTなのにアウトバウンドがREJECTなら、NACLのアウトバウンド(戻り)ルールが原因であることが多い。
  • 設定上の経路を自動で解析するには、VPC Reachability Analyzerも使える。
