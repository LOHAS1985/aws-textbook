パッチ適用済みのAMIを定期的に作り、Auto Scalingに反映する

最終更新:2026-10-26

1. やりたいこと#

  • 起動のたびにパッチや監視エージェントを入れているため、起動が遅く、手順もばらつく。
  • 必要なものを入れたAMIを毎月自動で作り、ほかのリージョンにも配りたい。
  • 動いているインスタンスも、順番に新しいAMIに入れ替えたい。

2. 構成を組み立てる#

① パッチの適用・ソフトの導入・テストをしてAMIを作るものは?

  • EC2 Image BuilderレシピとコンポーネントでAMIを作り、テストし、ほかのリージョンやアカウントへの配布まで自動で行います。
  • Data Lifecycle Manager既存のインスタンスのAMIやスナップショットを定期的に取るだけで、パッチの適用やテストはしません。
  • AWS CodeDeployアプリをインスタンスに配置するもので、AMIは作りません。

② 動いているインスタンスを、新しいAMIに順に入れ替えるものは?

  • Auto Scalingのインスタンスの更新最低限の正常な割合を保ちながら、インスタンスを少しずつ新しい起動テンプレートで入れ替えます。
  • インスタンスを手動ですべて終了する一度に全台が止まり、サービスが中断します。
  • Patch Manager今のインスタンスにパッチを当てる方法で、新しいAMIへの入れ替えではありません。

③ 暗号化されたAMIを別のアカウントと共有するときに必要なことは?

  • カスタマー管理のKMSキーのポリシーで、そのアカウントに使用を許可するAWS管理キーで暗号化したAMIは共有できません(暗号化)。
  • AMIを公開する誰でも使えるようになり、安全ではありません。暗号化されたAMIは公開もできません。
  • 何もしなくてよいキーの使用を許可しないと、相手のアカウントで起動できません。

3. 構成図#

Image Builderが毎月AMIを作って配布し、起動テンプレートの新しいバージョンに反映します。Auto Scalingのインスタンスの更新で、動いているインスタンスを順に入れ替えます。最新のAMI IDをParameter Storeに保存しておくと、ほかの仕組みからも参照できます。

4. 使うサービスと役割#

  • Amazon EC2 Image Builder:イメージレシピ・コンポーネント・テスト・配布(リージョン・アカウント)
  • Amazon EC2 Auto Scaling:起動テンプレートのバージョン指定、インスタンスの更新(ローリングでの入れ替え)
  • AWS Systems Manager:ビルド用インスタンスの操作、Parameter Storeに最新のAMI IDを保存
  • Amazon Inspector:作ったAMIの脆弱性スキャン
  • Amazon SNS:パイプラインの完了・失敗の通知

5. 構築の流れ#

  1. コンポーネント(パッチ適用・エージェントの導入・設定)と、起動後の確認を行うテストのコンポーネントを用意する
  2. ベースイメージとコンポーネントでイメージレシピを作る。インフラストラクチャ設定にインスタンスプロファイル(SSMの権限を含む)・サブネット・ログの出力先を指定する
  3. ディストリビューション設定で、配布先のリージョン・共有先のアカウントと、更新する起動テンプレートを指定する
  4. パイプラインを作り、スケジュール(毎月など)を設定する
  5. 新しいAMIができたら、Auto Scalingグループのインスタンスの更新を開始し、最小正常率(例:90%)を保ちながら入れ替える

6. ポイント・注意点#

  • パッチ適用済みのAMIを定期的に自動作成 → EC2 Image Builder。
  • Auto Scalingのインスタンスを新しいAMIに入れ替える → 起動テンプレートの更新+インスタンスの更新(Instance Refresh)。
  • AMIはリージョンごとのリソース。他リージョンで使うにはコピーが必要(ディストリビューション設定で自動化できる)。
  • 暗号化されたAMIを他のアカウントと共有するときは、KMSキーのポリシーでそのアカウントに使用を許可する(AWS管理キーで暗号化したものは共有できない)。
  • 起動テンプレートのバージョンを $Latest にすると、テンプレートの更新がそのまま新しく起動するインスタンスに使われる。
