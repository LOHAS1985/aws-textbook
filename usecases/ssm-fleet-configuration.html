多数のEC2の設定やソフトウェアを一定に保つ

最終更新:2026-10-26

1. やりたいこと#

数百台のEC2すべてに、CloudWatchエージェントを入れて同じ設定にしておきたい。新しく起動したインスタンスにも自動で入り、誰かが止めたり設定を変えたりしても決めた状態に戻るようにしたい。SSHでログインして1台ずつ作業するのはやめたい。

2. 構成図#

3. 使うサービスと役割#

  • AWS Systems Manager:State Manager(状態の維持)、Run Command(一括実行)、Distributor(ソフトのパッケージ配布)、Inventory(導入済みソフトの一覧)、Parameter Store(エージェントの設定)
  • Amazon EC2:SSMエージェントとIAMロール(マネージドノードにする)
  • Amazon CloudWatch:エージェントの設定の配布先、コマンドの出力の保存先
  • Amazon S3:コマンドの出力の保存先

4. 構築の流れ#

  1. インスタンスをマネージドノードにする:SSMエージェント(主要なAMIには導入済み)と、AmazonSSMManagedInstanceCore を含むIAMロール。アカウント全体で自動化するならデフォルトのホスト管理設定(DHMC)を使う
  2. プライベートサブネットなら、SSM用のVPCエンドポイント(ssm・ssmmessages・ec2messages)かNATゲートウェイを用意する
  3. State Managerの関連付けを作る:ドキュメント(例:AWS-ConfigureAWSPackage でCloudWatchエージェントを導入)、対象(タグ)、スケジュールを指定する
  4. レート制御(同時実行数・エラーのしきい値)を設定し、一度に全台が影響を受けないようにする
  5. 実行結果をS3・CloudWatch Logsに保存し、Inventoryで導入状況を確認する。準拠状況はSystems Managerの「コンプライアンス」で見る

5. ポイント・注意点#

  • 決めた状態を維持し続ける(新しいインスタンスにも自動で適用)→ State Manager。その場で1回実行 → Run Command。
  • Systems Managerの一覧にインスタンスが出ない → SSMエージェント・IAMロール・SSMのエンドポイントへの経路のどれかが原因。
  • 対象はインスタンスIDではなくタグで指定すると、台数が増えても設定を変えずに済む。
  • レート制御で同時実行数とエラーのしきい値を決め、失敗が広がったら止める。
  • SSHやキーペアは不要。操作の記録はCloudTrail、コマンドの出力はS3・CloudWatch Logsに残る。

この構成を組み立てる演習#

  • 多数のEC2の設定を一定に保つ構成を組み立てるタグで選んだインスタンスに、決めた状態をSSHなしで適用し続ける
