誤操作したRDSのデータを特定の時点に戻す

自動バックアップのポイントインタイムリカバリ(PITR)で、誤操作の直前の状態のDBを作り直す

最終更新:2026-10-25

1. やりたいこと#

運用中のRDSで、14時05分に誤ってテーブルのデータを削除してしまった。14時04分の状態に戻して業務を再開したい。また、こうした事態に備えて、バックアップの保持期間や別リージョンへのバックアップも整えておきたい。

2. 構成図#

3. 使うサービスと役割#

  • Amazon RDS:自動バックアップ(保持期間1〜35日)、PITR、手動スナップショット、自動バックアップのリージョン間レプリケーション
  • Amazon Aurora:バックトラック(Aurora MySQL。同じクラスターを数秒〜数分で過去に巻き戻す)
  • AWS Backup:バックアップの一元管理・別アカウントへのコピー
  • Amazon Route 53:アプリの接続先をCNAMEで切り替えやすくする

4. 構築の流れ#

  1. (事前)自動バックアップの保持期間を要件に合わせて設定する(0にすると無効)。長期保管は手動スナップショットかAWS Backupで行う
  2. 誤操作が起きたら、コンソールの「特定時点への復元」で、誤操作の直前の時刻を指定して新しいDBインスタンスを作る(最新の復元可能時刻は通常、現在の約5分前)
  3. 復元したDBに、元と同じセキュリティグループ・パラメータグループ・オプショングループが付いているかを確認する
  4. アプリの接続先を新しいエンドポイントに変える。または、元のインスタンスと新しいインスタンスの名前を入れ替えてエンドポイントを引き継ぐ
  5. 問題がなければ元のインスタンスを削除する(必要なら最終スナップショットを取る)

5. ポイント・注意点#

  • 特定の時刻に戻す → PITR。復元先は新しいDBインスタンス(エンドポイントが変わる)。
  • スナップショットからの復元も同じく新しいインスタンスになる。元のインスタンスが上書きされることはない。
  • Aurora MySQLで、新しいクラスターを作らずにすばやく戻す → バックトラック(最大72時間)。
  • 自動バックアップはDBインスタンスを削除すると既定で消える。手動スナップショットは削除するまで残る。
  • リージョン障害への備え → スナップショットのリージョン間コピーや、自動バックアップのリージョン間レプリケーション。
