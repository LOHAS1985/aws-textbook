複数アカウントのログを集約して分析する

最終更新:2026-10-26

1. やりたいこと#

  • 複数アカウントのアプリのログとAPIの操作の記録を、ログ集約用のアカウントに集めて長期保存したい。
  • 監査のときは、SQLで横断的に検索したい。

2. 構成を組み立てる#

① サブスクリプションフィルターから受けたログを、S3へ配送するものは?

  • Amazon Data Firehose流れてくるデータをまとめて、S3などの保存先へ自動で配送します。サーバーの管理は不要です。
  • Amazon SQSメッセージをためるキューで、S3へ配送する機能はありません。
  • AWS DataSyncオンプレミスとAWSの間などでファイルをまとめて転送するサービスで、ログの流れを受けるものではありません。

② S3に置いたログを、そのままSQLで検索するものは?

  • Amazon AthenaS3のデータに対して直接SQLを実行します。サーバーは不要で、読み取ったデータ量に応じて課金されます。
  • Amazon RDSデータをDBに取り込む必要があり、ログの長期保存・検索には向きません。
  • CloudWatch Logs InsightsCloudWatch Logsのロググループを検索するもので、S3のログは対象外です。

③ 組織の全アカウントのAPIの記録を集めるには?

  • CloudTrailの組織の証跡を作る管理アカウントで1つ作るだけで、全アカウントの記録が指定したS3に届きます。メンバーアカウントからは削除できません。
  • 各アカウントで別々に証跡を作る動きはしますが、新しいアカウントで作り忘れるおそれがあります。
  • Config のアグリゲーターを作るリソースの設定の情報が集まるだけで、APIの記録は集まりません。

④ 集めたログを削除・改ざんされないようにするには?

  • S3オブジェクトロックとバケットポリシーで削除を制限するCloudTrailのログファイルの整合性の検証とあわせて、改ざんされていないことを示せます。
  • ライフサイクルルールでGlacierに移す費用は下がりますが、削除の防止にはなりません。
  • Athenaの結果を別のバケットに保存する元のログの保護にはなりません。

3. 構成図#

各アカウントのCloudWatch LogsはサブスクリプションフィルターからData FirehoseでS3へ、APIの記録は組織の証跡でS3へ集めます。分析はAthenaで行い、パーティション分割や列指向の形式にすると、読み取る量が減って費用も下がります。

4. 使うサービスと役割#

  • Amazon CloudWatch:サブスクリプションフィルターでログをリアルタイムに転送する
  • Amazon Kinesis(Data Firehose):ログをS3へ配送する
  • AWS CloudTrail:組織全体のAPI操作を1つの証跡で記録する
  • Amazon S3:ログの長期保存(ライフサイクルでGlacierへ)
  • Amazon Athena:S3のログをSQLで分析する
  • AWS Organizations:組織の証跡、アカウントの管理

5. 構築の流れ#

  1. 集約アカウントにログ用のS3バケットを作り、バケットポリシーで各アカウントからの書き込みを許可する
  2. 管理アカウントでCloudTrailの組織の証跡を作成し、保存先に集約バケットを指定する
  3. Data Firehoseの配信ストリームを作り、各アカウントのロググループにサブスクリプションフィルターを設定する
  4. S3のライフサイクルルールで、古いログをGlacierなどへ移す
  5. Athenaでテーブルを定義し、SQLで検索する

6. ポイント・注意点#

  • 短期・頻繁に検索するログはCloudWatch Logs、長期・たまに検索するログはS3。
  • CloudTrailのログの改ざん検知 → ログファイルの整合性検証。
  • Athenaのコスト削減 → パーティション分割・列指向形式。
  • ログを削除させないために、S3オブジェクトロックやバケットポリシーで削除を制限する。
