プライベートサブネットからNATなしでAWSのサービスを使う

ゲートウェイ型・インターフェイス型のVPCエンドポイントで、インターネットを通らずにS3やSSMなどへ接続する

最終更新:2026-10-25

1. やりたいこと#

プライベートサブネットのEC2から、S3への大量のデータの読み書きや、Systems Manager・Secrets Managerの利用をしている。今はNATゲートウェイ経由のため、データ処理料金が高く、通信がインターネット側に出るのもセキュリティ上避けたい。特定のバケット以外にはアクセスさせたくない。

2. 構成図#

3. 使うサービスと役割#

  • Amazon VPC:VPCエンドポイント(ゲートウェイ型・インターフェイス型)、エンドポイントポリシー、ルートテーブル
  • Amazon S3:バケットポリシーで、特定のVPCエンドポイント経由のアクセスだけを許可(aws:SourceVpce)
  • AWS Systems Manager/AWS Secrets Manager:インターフェイス型エンドポイントの接続先
  • AWS Cost Explorer:NATゲートウェイのデータ処理料金の削減効果の確認

4. 構築の流れ#

  1. S3のゲートウェイ型エンドポイントを作り、プライベートサブネットのルートテーブルに関連付ける
  2. SSMには ssm・ssmmessages・ec2messages、Secrets Managerには secretsmanager のインターフェイス型エンドポイントを、各AZのサブネットに作る
  3. インターフェイス型エンドポイントのセキュリティグループで、VPC内からのHTTPS(443番)を許可する。VPCの「DNS解決」「DNSホスト名」を有効にし、プライベートDNSを有効にする
  4. エンドポイントポリシーで、使ってよいバケットだけに絞る。バケット側でも aws:SourceVpce の条件で、エンドポイント経由以外を拒否する
  5. NATゲートウェイを通る通信が減ったことを、フローログやCost Explorerで確認する

5. ポイント・注意点#

  • S3・DynamoDB → ゲートウェイ型(無料、ルートテーブルで経路を追加)。その他のサービス → インターフェイス型(PrivateLink、時間とデータ量の料金)。
  • ゲートウェイ型はオンプレミスやピアリング先のVPCからは使えない。オンプレミスからS3に私的に接続するならS3のインターフェイス型エンドポイントを使う。
  • インターフェイス型で名前解決がエンドポイントに向かない → VPCのDNS設定とプライベートDNSの有効化を確認する。
  • 大量のS3の通信をNAT経由にしていると、NATゲートウェイのデータ処理料金がかさむ。
  • ゲートウェイ型エンドポイントは同じリージョンのS3にだけ使える。
