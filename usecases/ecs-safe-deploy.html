デプロイ・自動化

ECSのサービスを止めずに更新し、失敗したら自動で戻す

最終更新:2026-10-26

1. やりたいこと#

ECS(Fargate)で動くWebアプリの新しいバージョンを、サービスを止めずにリリースしたい。新しいタスクが起動に失敗し続けたり、リリース後にエラーが増えたりした場合は、人が気づく前に自動で前のバージョンに戻したい。

2. 構成図#

3. 使うサービスと役割#

  • Amazon ECS:ローリング更新(minimumHealthyPercent・maximumPercent)、デプロイサーキットブレーカー、Blue/Greenデプロイ
  • Amazon ECR:コンテナイメージの保存
  • Elastic Load Balancing:新しいタスクのヘルスチェックと通信の切り替え
  • Amazon CloudWatch:デプロイの失敗を判定するアラーム(5xxエラー率など)
  • AWS CodePipeline:ビルドからデプロイまでの自動化

4. 構築の流れ#

  1. 新しいイメージをECRにプッシュし、そのイメージを使う新しいタスク定義のリビジョンを作る
  2. サービスのデプロイ設定で minimumHealthyPercent(例:100)と maximumPercent(例:200)を決める。100/200なら、台数を減らさずに新しいタスクを先に起動する
  3. デプロイサーキットブレーカーをロールバックありで有効にする(新しいタスクが起動・ヘルスチェックに失敗し続けると、デプロイを失敗とみなして戻す)
  4. 5xxエラー率などのCloudWatchアラームをデプロイの監視対象に指定し、アラームが鳴ったらロールバックするよう設定する
  5. アプリの起動に時間がかかる場合は、ヘルスチェックの猶予期間を設定する。一気に切り替えて素早く戻したい場合は、ECSのBlue/Greenデプロイを使う

5. ポイント・注意点#

  • 起動に失敗し続けるデプロイを自動で止めて戻す → デプロイサーキットブレーカー。リリース後のエラー増加で戻す → CloudWatchアラームによるロールバック。
  • minimumHealthyPercent を下げると、追加の容量なしで更新できるが、更新中の処理能力が下がる。
  • 新旧の環境を並べ、ALBの通信を一度に切り替える → Blue/Greenデプロイ。少しずつ移す → Canary・Linear。
  • 新しいタスクがすぐ止まる → 「停止したタスク」の停止理由、コンテナのログ、イメージの取得権限(タスク実行ロール)を確認する。

この構成を組み立てる演習#

  • ECSを止めずに更新する構成を組み立てる新しいバージョンを止めずにリリースし、失敗したら自動で前のバージョンに戻す
