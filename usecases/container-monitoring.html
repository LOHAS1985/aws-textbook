コンテナ(ECS・EKS)の性能を監視する

最終更新:2026-10-26

1. やりたいこと#

  • ECS・EKSのアプリを、タスク・Pod単位のCPU・メモリ・再起動回数で監視したい。
  • メモリ不足や再起動のくり返しを、早く見つけて通知したい。
  • アプリ独自のPrometheus形式のメトリクスも、ダッシュボードで見たい。

2. 構成を組み立てる#

① Prometheus形式のメトリクスを保存するマネージドサービスは?

  • Amazon Managed Service for PrometheusPrometheusと同じ形式・クエリ(PromQL)のまま、サーバーを管理せずにメトリクスを保存できます。
  • Amazon OpenSearch Serviceログの全文検索・分析に向いたサービスで、Prometheus形式のメトリクスの保存先ではありません。
  • Amazon DynamoDBアプリのデータベースで、メトリクスの保存や集計の機能はありません。

② メトリクスをダッシュボードで見るマネージドサービスは?

  • Amazon Managed GrafanaPrometheus・CloudWatchなど複数のデータソースをまとめて、ダッシュボードで表示します。
  • Amazon QuickSight業務データの分析(BI)向けで、運用のメトリクスの監視には使いません。
  • AWS X-Rayリクエストの経路と遅延を追うトレースのサービスです。

③ ECSでタスク単位のCPU・メモリを見るために必要な設定は?

  • クラスターでContainer Insightsを有効にするECSの標準のメトリクスはサービス単位だけです。タスク・コンテナ単位はContainer Insightsで集めます。
  • EC2の詳細モニタリングを有効にするEC2インスタンスのメトリクスの間隔が1分になるだけで、タスク単位にはなりません。
  • タスク定義のメモリの上限を増やすメモリ不足の対策にはなりますが、監視の設定ではありません。

3. 構成図#

ECSはContainer Insights、EKSはCloudWatch Observabilityアドオンでタスク・Pod単位のメトリクスとログを集め、アラームとSNSで通知します。アプリ独自のメトリクスはManaged Service for Prometheusに集め、Managed Grafanaで見ます。タスクが OutOfMemoryError で止まるときは、タスク定義のメモリの上限を見直します。

4. 使うサービスと役割#

  • Amazon CloudWatch:Container Insightsによるタスク・Pod単位のメトリクスとパフォーマンスログ、アラーム
  • Amazon ECS:クラスターの設定でContainer Insightsを有効化。コンテナのログは awslogs ログドライバーでCloudWatch Logsへ
  • Amazon EKS:Amazon CloudWatch Observability アドオン(CloudWatchエージェント+Fluent Bit)でメトリクスとログを収集
  • Amazon Managed Service for Prometheus/Amazon Managed Grafana:Prometheus形式のメトリクスの保存と可視化
  • Amazon SNS:アラームの通知

5. 構築の流れ#

  1. ECS:クラスターでContainer Insights(オブザーバビリティ強化版)を有効にする。新しいクラスターで常に有効にするなら、アカウントの設定 containerInsights を有効にする
  2. ECS:タスク定義のログ設定を awslogs にし、ロググループを指定する。タスク実行ロールにログを書く権限を付ける
  3. EKS:CloudWatch Observabilityアドオンを追加し、ノードのIAMロール(またはPod Identity)に CloudWatchAgentServerPolicy を付ける
  4. メモリ使用率・実行中のタスク数・Podの再起動回数などにアラームを作り、SNSで通知する
  5. アプリのPrometheusメトリクスは、Managed Prometheusのマネージドコレクター(またはADOT)で収集し、Grafanaでダッシュボードを作る

6. ポイント・注意点#

  • ECSの標準のメトリクスはサービス単位のCPU・メモリだけ。タスク・コンテナ単位の詳細はContainer Insightsを有効にして初めて見られる。
  • EKSには標準のノード・Podのメトリクスがない → CloudWatchエージェント(Observabilityアドオン)が必要。
  • Container Insightsの詳細データはCloudWatch Logsのパフォーマンスログとして保存され、Logs Insightsで調べられる。保存量に応じて費用がかかる。
  • タスクが OutOfMemoryError で止まる → タスク定義のメモリの上限を見直す。停止の理由はECSの「停止したタスク」で確認できる。
  • 負荷に応じたタスク数の増減は、ECSサービスの自動スケーリング(ターゲット追跡)で行う。
