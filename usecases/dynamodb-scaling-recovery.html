DynamoDBを負荷に合わせてスケールし、誤操作から復旧する

キャパシティモードと自動スケーリングでスロットリングを防ぎ、PITRで任意の時点に戻せるようにする

最終更新:2026-10-25

1. やりたいこと#

DynamoDBのテーブルで、アクセスの急増時に ProvisionedThroughputExceededException(スロットリング)が出る。負荷に合わせて容量が増減するようにしたい。また、バグで大量のデータを上書きしてしまったときに、直前の状態に戻せるようにしたい。

3. 使うサービスと役割#

  • Amazon DynamoDB:キャパシティモード(オンデマンド/プロビジョンド)、自動スケーリング、PITR、オンデマンドバックアップ、グローバルテーブル
  • Amazon CloudWatch:ThrottledRequests・消費キャパシティの監視
  • AWS Backup:バックアップの一元管理・別リージョン/アカウントへのコピー

4. 構築の流れ#

  1. アクセスが予測できない・急増する → オンデマンドモードにする。予測できて安定している → プロビジョンドモード+自動スケーリング(目標の使用率を設定)
  2. グローバルセカンダリインデックス(GSI)にも容量の設定が必要。GSIのスロットリングは元のテーブルへの書き込みも止める
  3. 特定のキーにアクセスが集中しないよう、パーティションキーを分散させる。アプリ側はエクスポネンシャルバックオフで再試行する(AWS SDKは自動)
  4. テーブルのポイントインタイムリカバリ(PITR)を有効にする。長期保管が必要ならAWS Backupでもバックアップを取る
  5. リージョン障害にも備えるなら、グローバルテーブルで別リージョンにレプリカを置く

5. ポイント・注意点#

  • 予測できない急増 → オンデマンドモード。自動スケーリングは反応に数分かかり、瞬間的な急増には間に合わないことがある。
  • 特定のキーにアクセスが集中する(ホットパーティション)と、全体の容量に余裕があってもスロットリングする。
  • PITRの復元先は新しいテーブル。復元後にアプリの接続先を切り替えるか、データを戻す。自動スケーリングの設定・IAMポリシー・アラームなどは引き継がれない。
  • PITRは過去35日以内(設定で1〜35日)の秒単位の時点に戻せる。
  • 読み取りの高速化・負荷の軽減 → DAX。マルチリージョンでの読み書き・リージョン障害への備え → グローバルテーブル。
