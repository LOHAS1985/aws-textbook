RDSの遅いクエリと接続数の問題を解消する

最終更新:2026-10-26

1. やりたいこと#

  • RDSのCPU使用率が高い。どのSQLが負荷の原因かを特定したい。
  • Lambdaからの接続が急増すると、「接続数が多すぎる」エラーが出る。
  • 読み取りの多い処理の負荷を、書き込み用のDBから逃がしたい。

2. 構成を組み立てる#

① 急増する接続をまとめ、DBの接続数を抑えるものは?

  • RDS Proxy接続をプールして使い回し、DBへの接続数を抑えます。フェイルオーバーの時間も短くなります。
  • Application Load BalancerHTTPのリクエストを振り分けるもので、DBの接続を集約しません。
  • Multi-AZ配置障害に備えた待機系で、接続数の問題は解決しません。

② どのSQLがDBの負荷をかけているかを示すものは?

  • Performance InsightsSQL別・待機イベント別に負荷を表示します。
  • 拡張モニタリングOSのプロセスやメモリの詳細を見るもので、SQL別の負荷は分かりません。
  • AWS CloudTrailAWSのAPIの操作の記録で、DBの中のSQLは記録しません。

③ 読み取りの多い処理を逃がす先は?

  • リードレプリカ非同期で複製された読み取り専用のDBです。直後の読み取りに古いデータが返ることがあります。
  • Multi-AZのスタンバイ従来のMulti-AZのスタンバイは読み取りに使えません(高可用性とスケーリング)。
  • スナップショットバックアップで、アプリから読み取ることはできません。

3. 構成図#

Performance Insightsとスロークエリログで重いSQLを見つけて改善し、接続の急増はRDS Proxyで、読み取りの負荷はリードレプリカやElastiCacheで吸収します。スロークエリログをCloudWatch Logsに出すには、パラメータグループでの出力の設定と、ログのエクスポートの設定の両方が必要です。

4. 使うサービスと役割#

  • Amazon RDS:Performance Insights(SQL別・待機イベント別の負荷)、拡張モニタリング(OSの詳細)、リードレプリカ、RDS Proxy
  • Amazon CloudWatch:CPUUtilization・DatabaseConnections・ReadLatency などの監視、スロークエリログの保存と検索(Logs Insights)
  • AWS Secrets Manager:RDS ProxyがDBに接続するための認証情報
  • Amazon ElastiCache:よく読まれるデータのキャッシュ

5. 構築の流れ#

  1. Performance Insightsを有効にし、DBの負荷(平均アクティブセッション数)が多いSQL文と待機イベントを確認する
  2. パラメータグループでスロークエリログ(MySQLの slow_query_log・long_query_time など)を有効にし、CloudWatch Logsに発行する
  3. 重いSQLにインデックスを追加するなど、クエリを改善する
  4. 接続数の問題には RDS Proxy を作成し、アプリの接続先をProxyのエンドポイントに変える(認証情報はSecrets Managerに保存)
  5. 読み取りが多い場合はリードレプリカを追加し、読み取り処理の接続先を分ける。それでも足りなければインスタンスクラスを上げる

6. ポイント・注意点#

  • 「どのSQLが負荷をかけているか」→ Performance Insights。OSのプロセスやメモリの詳細 → 拡張モニタリング。
  • Lambdaなどで接続数が急増する・接続が枯渇する → RDS Proxy(フェイルオーバー時間の短縮にもなる)。
  • ログをCloudWatch Logsに出すには、パラメータグループでの出力設定と、DBインスタンスのログのエクスポート設定の両方が必要。
  • リードレプリカは非同期なので、直後の読み取りに古いデータが返ることがある。高可用性はMulti-AZ、読み取りの分散はリードレプリカ。
  • パラメータの変更には、すぐ反映されるもの(動的)と、再起動が必要なもの(静的)がある。
